# 状態と冗長構成

この記録はノードの状態をどこに置くかと、冗長構成と継続性の設計です。調査の記録は [redundancy.md](../background/redundancy.md) にあります。

## 考え方

各役割を複数台で動かし、利用者を 1 つのプロセスに縛らない作りにします。全加入者を走査する処理と、役割全体を止めるロックも入れません。これが無ければ、IMS である意味が無く、SIP の PBX で足りてしまうためです（[requirements.md](../requirements.md)）。

そのため、ノードの状態は最初から `Store` の境界の後ろに置き、ノードの外に出せるようにしてあります。設定に `store` の節が無いノードはプロセスの中の `MemoryStore` を使い、`store.kind: valkey` のノードは `internal/kvstore/<役割>store` の実装で Valkey に置きます（「保存先」）。

規模を広げる妨げになっていた所は、冗長構成の作りと合わせて取り除きました（「残っている課題」）。S-CSCF の中で全利用者の処理を 1 つのロックで順番に並べていた作りは、妨げになるため、利用者ごとのロック（`ims.UserLocks`）に直しました。S-CSCF と P-CSCF の `MemoryStore` の全件の走査も、ID ごとの索引に直しました。

冗長構成はロードマップの完了条件の 2 つと、水平に広げられる組み方を満たす、いちばん小さい作りにします。状態は共有の保存先に置き、同じ名前とアドレスで作り直したノードが、その状態から続けます。保存先で吸収できない障害（S-CSCF の組の全体が止まった、UE の P-CSCF が戻らない）には、TS 23.380 の手順を使います。

## 保存先

| 主題 | 作り |
| --- | --- |
| 方式 | 調査の候補 C（外部の保存先）にします。各役割の `Store` の実装を、`internal/kvstore` の上の実装（`internal/kvstore/<役割>store`）に替えます。候補 B（HSS に預ける）は、復旧手順を見せるために S-CSCF でだけ作ります（「復旧手順」の節）。候補 A（UE の登録し直しに任せる）は、完了条件の「再登録なしで着信できる」を満たさないので採りません。候補 D（ノードのあいだの複製）は作りません。 |
| 製品 | Valkey 9.0.8（BSD 3-Clause）です。Compose のイメージは `valkey/valkey:9.0.8-alpine` で、イメージの中の Alpine のパッケージのライセンスは確かめていません。 |
| クライアント | 標準ライブラリだけで書いた `internal/kvstore` の RESP2 のクライアントを使います。`go.mod` は変えません。go-redis v9.23.0 と同じ適合試験が通り、遅延の差は測定の揺れの中に収まりました（調査の記録の 13.3、13.4）。 |
| 永続化 | AOF を 1 秒ごとに同期し（`--appendonly yes --appendfsync everysec`）、名前付きのボリュームに置きます。保存先のプロセスを落とした試作では、応答を返した書き込みは 1 つも失われませんでした。毎回同期する設定では、`Put` が約 7 倍、登録が約 4.6 倍遅くなりました（13.4、13.5）。 |
| 既定 | 設定に `store` の節が無いノードは、今の `MemoryStore` を使います。冗長構成を使わない構成とキャプチャは変わりません。冗長構成は上書きのファイル（`deploy/redundancy/`）で組み、そこで `store.kind: valkey` にします。 |
| 保存先の冗長 | 作りません。保存先は 1 台なので、単一障害点です。止まっているあいだ、ノードは状態を読み書きできず、要求に誤りを返します。作り直して読めるようになるまでは、試作で 0.2 秒から 0.3 秒でした（13.5）。Sentinel とクラスタは拡張の候補にします。そのときは、クライアントを go-redis に替えるほうが小さく済む見込みです（13.3）。`SIMPLIFIED:` に書きます。 |
| CI | Valkey のサービスのコンテナを足し、環境変数 `KVSTORE_VALKEY_ADDR` を渡して、`internal/kvstore` と各実装の適合試験を Valkey でも流します。 |

遅延の測定（13.4、13.8。1 台の機械の中のループバック）では、保存先の操作 1 回に約 59 マイクロ秒かかりました。登録 1 回で約 1.7 ミリ秒、呼 1 回（INVITE から BYE まで）で約 3.3 ミリ秒です。SIP の T1（500 ミリ秒）と比べて小さいので、遅延は方式を決める理由になりません。機械をまたいだ往復と、負荷をかけたときは測っていません。一方、索引に直す前の `MemoryStore` は全件を走査していたので、登録した利用者が 5000 人のとき、呼 1 回の `Store` の呼び出しに約 6.2 ミリ秒かかり、利用者の数に比例して伸びました。索引に直したあとは、利用者を 100 人から 20000 人に増やしても、1 回の検索の時間は伸びません（`internal/kvstore/storetest` の `TestMemoryStoreLookupsDoNotGrow`）。

## Store の形と書き込みの決まり

| 主題 | 作り |
| --- | --- |
| 誤りを返す | 各役割の `Store` の操作は、`context.Context` を取り、`error` を返す形にします（調査の記録の 13.8）。保存先の失敗を「項目が無い」として扱うと、保存できなかった登録に 200 を返してしまうためです。状態を読み書きできなかった要求には、SIP では 500 を、Diameter では DIAMETER_UNABLE_TO_COMPLY を返します。 |
| キー | `<store.prefix><役割>:<項目の種類>:<名前>` の形です。名前の中の `:` と `%` は、`%3A` と `%25` に書き換えます（13.8）。 |
| 1 回の操作 | 1 回の操作は、1 つのキーだけを触ります。複数のキーをまとめて変える操作は作りません。保存先をクラスタにしても、この形ならそのまま動きます。 |
| 索引 | 別の ID で引く検索には、値に主の項目のキーを持つ索引の項目を使います。索引は主の項目より先に書き、主の項目より後に消します。索引から引いた主の項目がその ID を持っていなければ、見つからなかったことにします（13.8）。`MemoryStore` も ID ごとの索引で引き、全件を走査しません（`RegistrationOf`、`SubscriptionsOf`、`AssociationOfContact`）。 |
| 比べて入れ替える | 版は、書くたびに作る乱数です。項目を消して書き直したときに、同じ版が戻らないようにするためです。読んで、変えて、書く操作（`Update` の付く操作、数の更新、索引の集合）は、版が読んだときのままのときだけ書き、違えば読み直します。変える関数は 2 回以上呼ばれることがあるので、引数を変えるだけの関数にします。1 台だけが取る操作（`Take` の付く操作）は、読み出しと、版を条件にした消去で行います。 |
| 並べ替えた索引 | 保守の操作が求める一覧（HSS の加入者）と、1 台が持つ呼の一覧（IBCF の呼と、中継ノードのコンテキスト）は、`kvstore.Store` の並べ替えた索引から引きます。索引は名前を並べて持ち、`MembersAfter` が、前のページが終わった名前の次から `limit` 件を返します。1 ページの手間は、索引に 10 件あっても 100 万件あっても変わりません。サーバーでは、得点をすべて 0 にした整列集合の範囲の検索（`ZRANGE ... BYLEX`）、メモリの実装では並んだ列の 2 分探索です。時刻の索引と同じく、1 回の操作が触るのは 1 つの索引だけです。 |
| 版を見ない書き込み | 版を見ない `Put` は、利用者ごとのロックの中の書き込みと、作った台しか書かない項目（P-CSCF の対応付け、MMTel AS の呼の記録など）にだけ使います。 |
| 利用者ごとのロック | S-CSCF、HSS、IP-SM-GW が使う `ims.UserLocks` を、インタフェース `ims.UserLocker` の 1 つの実装にします。冗長構成では、保存先に置くロック（期限付きで「無いときだけ書く」、版を条件に消す）を使います。期限は 15 秒です。登録の処理は、Cx の往復（応答を 5 秒まで待つ）を 2 回含むためです。ロックは利用者ごとなので、役割全体を止めません。 |

保存先のロックには、期限が切れたあとで、遅れて動き出した古い台の書き込みを防ぐ仕組み（番号を付けた書き込み）がありません。処理の途中で 15 秒より長く止まった台は、次の台の書き込みを上書きすることがあります。`SIMPLIFIED:` に書きます。

## キーと期限

調査の記録の 13.8 の実装のキーをそのまま使います。「新規」の項目は 13.8 のあとに増えたもので、実装を足します。

| HSS | `subscriber:<IMPI>`、`settings`（保守用の API で変える設定と、その世代）、`profile-push:<プロファイルの名前の出どころ>`（設定を変えたときの push の進み） | `public:<IMPU>`、並べ替えた索引 `subscribers`（`List` が 1 ページずつ引く）、並べ替えた索引 `served:<プロファイルの名前の出どころ>`（S-CSCF がプロファイルを持っている加入者。`ListServed` が 1 ページずつ引く） | 時刻の索引 `profile-pushes`（出どころごとの push の回。借りた台が 1 ページ分の PPR を送る）と `profile-push-retries`（回を借りた台が S-CSCF の接続を持たずに送れなかった PPR。接続を持つ台が送る）。[hss-provisioning.md](hss-provisioning.md) の「設定を台のあいだで分ける」 |
| メディア中継ノード（新規） | `<台の名前>-<役割>:context:<ID>` | 並べ替えた索引 `<台の名前>-<役割>:context-ids`（その台のコンテキストの ID。作り直した台が 1 ページずつ引く） | なし |

P-CSCF の購読は利用者ごとに 1 つなので、主の項目は IMPI で引きます。NOTIFY はダイアログの Call-ID しか名乗らないため、Call-ID から IMPI を引く索引を添えます。IP-SM-GW の購読は逆に、主の項目を Call-ID で引き、公開の識別子の索引を添えます。どちらも、再登録のときに自分の購読を見つけ、NOTIFY のときにその購読を見つけられます。

中継ノードの名前に役割を付けるのは、1 つのノードが `agw` と `mrfp` の両方の役割を持てるためです。このとき中継ノードは 2 つあり、RTP のポートの範囲もそれぞれ別です。片方がもう片方のコンテキストを読むと、自分の範囲の外のポートを開こうとして、そのコンテキストを捨ててしまいます。

中継ノードのコンテキストの ID の索引は、その台のポートの範囲で数が決まるので、利用者の数では伸びません。IBCF の呼の ID の索引も、その台が同時に持つ呼の数までしか伸びません。IBCF の台は、起動したときに自分の索引を 1 ページずつ読み、記録を 1 件ずつ読んで、前のプロセスが残した呼を終わらせます。Replaces を持つ INVITE を受けたときは、ほかの台が持つ呼でも、Replaces が指すダイアログの索引からその呼の記録を 1 件だけ引きます。BYE を誰も見なかった呼の P-CSCF のダイアログと MMTel AS の呼の記録は、期限が無いので残ります。今の `MemoryStore` と同じで、`SIMPLIFIED:` に書きます。

IBCF の呼の ID と中継ノードのコンテキストの ID は、並べ替えた索引に置きます。呼の始まりと終わりは、索引に自分の ID を 1 件足すか消すだけで、一覧の全体を読み書きしません。中継ノードの `Modify` は、コンテキストの項目を書き直し、索引にはもうある ID を足し直すだけなので、索引は変わりません。一覧を 1 つの項目に入れると、呼が始まるたびと終わるたびに、その台の呼の数だけの一覧を読み、比べて入れ替える書き込みで書き戻すことになります。同時の呼が増えるほど 1 回の操作が重くなり、同じ台の呼が 1 つの項目を取り合います。100 回続けて負けた書き込みはあきらめるので、IBCF の新しい呼と中継ノードの新しいコンテキストは断られます。並べ替えた索引への追加と削除は、保存先が 1 回で行うので、取り合いになりません。

中継ノードの索引には、コンテキストを書いた時刻を持たせません。起動した台が見つけた、コンテキストの無い ID は、書いている途中の `PutContext` のものではなく、途中で止まったプロセスが残したものだからです。索引を読むのは台が起動したときだけで、そのとき同じ台のほかのプロセスは動いていない、という前提に立ちます。この前提は、同じ名前の中継ノードを 1 つしか動かさないデプロイが守ります。コードはこれを確かめません。索引を読むのはポートを開く前なので、ポートがぶつかることで気づくこともできません。同じ名前で 2 つ目のプロセスが動くと、1 つ目の書いている途中の `PutContext` の ID を消してしまい、そのコンテキストは索引から外れたまま残ります。この前提のもとで、起動した台は、コンテキストの無い ID をすぐに索引から消します。IBCF も同じで、1 つの台の名前で動くプロセスは 1 つとしています。

前の作りの項目、IBCF の `calls-of:<台の名前>` と中継ノードの `<台の名前>-<役割>:contexts` は、新しい作りでは読みません。前の作りのプロセスが残した呼とコンテキストを、新しい作りのプロセスは見つけません。IBCF はその呼を終わらせず、中継ノードはそのポートを開き直しません。その記録とコンテキストは、期限が無いので、保存先を空にするまで残ります。前の作りの IBCF の `dialog:` の項目も残るので、それを指す Replaces は、どのプロセスも終わらせない記録に結び付きます。新しい作りから前の作りに戻すときも同じです。作りを入れ替えるときは、その台に呼が無いときに入れ替えるか、保存先を空にします。前の項目を読み直す処理は、1 回の入れ替えにしか使わないのに、コードに残り続けるので作りません。

## 期限切れを 1 台だけが処理する

| 主題 | 作り |
| --- | --- |
| 対象 | 切れたときに動作が要る期限です。S-CSCF の reg-await-auth、登録、購読、未登録のプロファイル、IP-SM-GW の TR1N、P-CSCF の Timer N と reg イベントの購読の更新、SC の宛先ごとの次の試行が当たります。SC は同じ時刻の索引を宛先ごとのリースに使い、リースの長さは上の表のとおりです（[sms.md](sms.md) の「SC の役割の作り」）。消えるだけでよい期限は TTL にし、タイマーを持ちません。P-CSCF の対応付けを消すまでの猶予（`endAssociation` の `KeepUntil`）と SA の期限が、これに当たります。 |
| 仕組み | 期限の時刻を時刻の索引に入れます。各台は 1 秒ごとに `ClaimDue` で時刻の来たものを借り、借りた台だけが処理し、終わったら `Done` で外します。リースは 15 秒です。役割のプロセスの中の `time.AfterFunc` のタイマーはなくします。 |
| 1 回だけ動くこと | 借りた台は、利用者ごとのロックを取り、主の項目を読み直し、期限が変わっていないことを確かめてから、SAR や NOTIFY を送ります。ロックを取らない役割もあります。IP-SM-GW は `TakeDelivery` で、P-CSCF は購読を版ごと入れ替える書き込みで、1 台だけが先に進みます。そのあとで項目を消し、ロックを放してから `Done` を呼びます。ふだんは 1 台が 1 回だけ処理します。処理の途中で台が止まると、リースが切れたあとで、別の台が同じ処理をやり直します。SAR（TIMEOUT_DEREGISTRATION）と NOTIFY（terminated）は、2 回送っても結果が変わらないので、送ったあとで台が止まっても状態は壊れません。S-CSCF の reg-await-auth は、SAR（AUTHENTICATION_TIMEOUT）に HSS が答えないときも同じです。チャレンジを消さず、`Done` も呼ばないので、次に借りた台が SAR を送り直します。チャレンジのことを HSS に伝えるものが、ほかにないためです。送り直すのは、保存先がチャレンジを忘れるまで、つまり期限が切れてから reg-await-auth が経つまでです。試作では、2 台で 60 件を処理して、2 回処理されたものは 0 件でした。止まった台が借りていた 1 件は、約 2 秒のリースが切れたあとで、もう 1 台が処理しました（13.5）。 |
| 索引と項目の順 | 時刻の索引の要素も、ほかの索引と同じ順で書きます（「Store の形と書き込みの決まり」）。時刻の付いた要素は主の項目より先に書き、要らなくなった要素は主の項目より後に消します。途中で失敗したときに残るのは、主の項目が持たない時刻の要素です。借りた台は主の項目を読み、期限が来ていなければ何もせず、`Done` でその要素を外します。逆の順で書くと、主の項目の持つ期限を呼び出す要素が無くなり、どの台もその期限を処理しません。 |
| 時計 | 台どうしの時計のずれは、リースより十分に小さいものとします。 |
| `MemoryStore` | 同じ操作を最小ヒープで行います。1 台の構成でも、同じ処理の道を通ります。 |
| プロセスの中に残すもの | 処理の途中のトランザクション、P-CSCF が 2xx の ACK を待つタイマー（`release.go`、64×T1）、MMTel AS の CFNR の無応答のタイマー、MRFC の待ちです。どれも呼が確立する前のものか、短いあいだだけのものです。止まった台のこれらは失われます。呼び出し中の呼は失敗しますが、完了条件が求めるのは確立した呼です（調査の記録の 2 章）。 |

## ノードを止める順

ノードは SIGTERM を受けると、次の順に止まります（`cmd/ims` の `stopNode`）。

1. 役割が自分から始める仕事。S-CSCF、P-CSCF、IP-SM-GW の期限切れの掃引と、SC の配達です。互いに待つことがないので、一度に止め、すべてが終わるのを待ちます。
2. SIP のスタックと、MMTel AS の UA。
3. Diameter の接続と待ち受け。
4. 保存先のクライアント。

IBCF と MRFC の UA、HSS が送る途中の通知（S6c の alert と Sh の push）は、今も Diameter のあとで閉じます。この順の外に残っています。

逆に、SIP と Diameter を先に閉じて、掃引と SC の配達をそのあとで止めると、台を止めるたびに、保存先の状態を壊すか、仕事を取りこぼします。

| 段 | 止め方 | 理由 |
| --- | --- | --- |
| 掃引 | 新しく借りるのをやめ、借りた分は最後まで処理してから止まります。1 件を待つのは、そのリース（15 秒）が切れるまでです。 | 借りた台は、主の項目を消してから NOTIFY と SAR を送ります（「期限切れを 1 台だけが処理する」）。SIP と Diameter を閉じたあとで借りると、登録と購読は消えるのに、NOTIFY も SAR も出ません。別の台が借り直しても、もう何も見つけません。途中で打ち切っても同じで、消したあとの SAR が出なくなります。先に掃引を止めた台は何も借りないので、止めているあいだに期限が来た登録は、運用中の台が借りて、NOTIFY と SAR を送ります。P-CSCF の reg イベントの購読の更新も、版を条件に「送った」と書いてから SUBSCRIBE を送るので、掃引を止めてから SIP のスタックを閉じます。ただし、更新の SUBSCRIBE はハンドラが戻ったあとに別の goroutine から出ます。スタックを閉じる直前に出たものは届かないことがあり、その購読はあとで期限が来て消えます。 |
| SC の配達 | 試行中の配達を打ち切り、宛先を今の時刻で手放します。打ち切った試行は、試行の回数に数えません。 | TFA を待つ試行は最長で約 90 秒かかり、ノードに与える猶予（このリポジトリの Kubernetes の構成では 10 秒）より長いためです。Diameter の接続が先に閉じて TFR に答えが返らないと、SC はそれを時間が経てば直るかもしれない失敗と読み、次の再送の時刻（Compose の設定では 1 時間後）まで誰も試しません。今の時刻で手放せば、運用中の台がすぐに取ります。打ち切った TFR を IP-SM-GW がもう届けていれば、受け手は同じショートメッセージを 2 回受け取ります。保守の lock で接続を閉じたときと同じです。止めたあとで届いた OFR と ALR には、いつもどおり答え、配達は運用中の台に任せます。 |
| SIP のスタック | 応答を待っているクライアントトランザクションを、`sip.ErrStackClosed` で終わらせます。 | 要求は相手に届いていて、応答が途中にあるかもしれません。そのため、役割はこの終わりを相手の失敗と読まず、保存先の状態を変えません。S-CSCF は NOTIFY の購読を消さず、第三者 REGISTER に iFC の既定の処理を当てはめません。P-CSCF と IP-SM-GW は、最初の SUBSCRIBE の購読を消しません。P-CSCF は、REGISTER が切れても UE の IP association を消しません。残した購読は、次の NOTIFY を送る台がそのまま使うか、Timer N か期限で消えます。IP-SM-GW が届けている途中の MESSAGE は、今も 408 と同じに扱い、SC には失敗を返します。 |
| Diameter | 接続を閉じ、待ち受けを止めます。 | SIP で受けた要求の処理が、Cx や Sh を使っているかもしれないためです。SIP を先に閉じれば、そのような要求はもう増えません。 |
| 保存先 | 最後に閉じます。 | 上の段の仕事が、最後まで読み書きできるようにするためです。 |

- 止める途中の保存先の操作は、止めることでは打ち切りません。`internal/kvstore` のクライアントは、`context.Context` が終わると応答を待たずに諦めます。保存先が済ませた借り（`ClaimDue`）や手放し（`Release`）をこの台が知らないまま終わると、その項目はリースが切れるまで、どの台も扱えません。
- 猶予を過ぎて強制的に終わらせた台の仕事は、障害で止まった台のものと同じく、リースが切れたあとで別の台が引き継ぎます。掃引が 1 件を待つ時間は猶予より長いことがあるので、HSS が答えないときなどには、この道を通ります。ただし、主の項目を消したあとで終わらされたハンドラの NOTIFY と SAR は、引き継ぐ台が何も見つけないので出ません。
- SIGTERM を受けて、ドレインしてから止まる動きは作りません。調査の記録で未決としている論点で、この順はそれを決めません。

## 名前と DNS

| 主題 | 作り |
| --- | --- |
| 台の名前と組の名前 | 同じ役割の台は、台ごとの名前（`sip.host`。例 `scscf-1.<ドメイン>`）と、組の名前（例 `scscf.<ドメイン>`）を持ちます。Via の sent-by と Diameter の Origin-Host には、台の名前を使います。組の名前は、DNS の SRV が組のすべての台を返す名前で、URI にポートを付けません。ポートがあると SRV が引かれないためです（RFC 3263 4.2）。組の名前を設定で受け取るのは、今は IBCF だけです（`ibcf.sip.pool` と `ibcf.external_sip.pool`）。ほかの役割は自分の Record-Route や Service-Route に組の名前を書かないので、設定 `sip.pool` を置いていません。どの役割も読まない設定を受け付けると、組で動いているように見えてしまうためです。ほかの役割が組の名前を読むようになったら、その役割に同じ設定を足します。 |
| 組の名前を使う所 | S-CSCF の Service-Route、Record-Route、Server-Name、ODI を載せた Route。I-CSCF の設定の `scscfs[].name`。iFC の AS の URI（`sip:mmtel.<ドメイン>`、`sip:ipsmgw.<ドメイン>`）。AS から MRFC への Request-URI。IP-SM-GW の Contact（今も DNS の名前です）。 |
| 台の名前を使う所 | P-CSCF の Path と Record-Route、MMTel AS と MRFC の Contact です。どれも、その台のプロセスの中にダイアログかトランザクションがある所です。作り直した P-CSCF の台は、同じ名前とアドレスで保存先から状態を引き継ぎます。MMTel AS と MRFC の作り直した台は、前のプロセスのダイアログを続けません（下の「ダイアログの中の要求」）。Compose では固定のアドレスで、Kubernetes では StatefulSet の Pod の名前で、名前を保ちます（[k8s.md](../background/k8s.md) の 3 章と 4 章）。 |
| 自分宛ての Route | `sip.PopOwnRoute` に、台の名前と組の名前の両方を渡します。 |
| SRV | DNS のゾーンに、組ごとに `_sip._udp` と `_sip._tcp` の SRV を置き、組の台を同じ優先度と同じ重みで並べます。同じ役割のノードを複数台起動できるようにするためです。 |
| 送り直し | RFC 3263 4.3 のとおり、503、トランスポートの異常、応答が何も無いうちのタイマー B か F の時間切れのときは、SRV の次の宛先へ、Via の branch を変えた新しいトランザクションで送り直します。これはできています。プロキシ（P-CSCF、I-CSCF、S-CSCF、IBCF）も UA（MMTel AS、MRFC、IP-SM-GW、UE シミュレータ）も、`sip.Stack.SendRequest` に宛先の一覧を渡し、スタックが送り直します。一覧は `ims.Targets` が DNS から作ります。プロキシと UA で送り直す部品を分けると、何を失敗と数えるかを 2 か所で決めることになるためです。TU が持つ `ClientTransaction` は送り直しても 1 つのままで、次の宛先の応答もそこに届きます。2xx 以外の応答への ACK と CANCEL は、元の要求を受け取った宛先に送ります（RFC 3263 4）。2xx への ACK は別のトランザクションなので、送れない宛先を飛ばして次の宛先へ送ります。P-CSCF の REGISTER は、3xx と 480 でも次の I-CSCF へ移る（TS 24.229 5.2.2.1 の 7 番目の項目）ので、P-CSCF が I-CSCF を 1 つずつスタックに渡して自分で次へ進みます。 |
| 時間切れまでの時間 | 設定 `sip.transaction_timeout` で、役割ごとにタイマー B と F を短くできます。これはできています。IBCF は内側と外側で別の値を持てます。P-CSCF の保護されたポートは UE にだけ送り、次の宛先が無いので、既定のままにします。既定は標準どおり 64×T1（32 秒）です。冗長構成の上書きのファイル（`deploy/redundancy/`）を作るときに、そこで 4 秒にします。TS 24.229 5.4.3.3 の NOTE 24 も、S-CSCF が P-CSCF の応答を待つ時間をタイマー B と F より短くするよう求めています。 |
| DNS の問い合わせ | `internal/sipdns` は、1 秒で答えの無い問い合わせを送り直し、3 回まで試します。今は 2 秒で 1 回だけ問い合わせるので、30 % の損失で登録が失敗しました（調査の記録の 8 章）。送り直しの回数の根拠にする条項は確かめていません（[unverified-clauses.md](../unverified-clauses.md)）。 |
| Retry-After | 503 の Retry-After を、宛先ごとに覚えることはしません（RFC 3261 21.5.4）。ドレイン中の台は、新しい要求のたびに 503 を返し、上流はそのたびに次の台へ送り直します。この様子はキャプチャに毎回写ります。`SIMPLIFIED:` に書きました。 |

## ダイアログの中の要求

| 役割 | ダイアログの中の要求を処理する台 | 要る状態 |
| --- | --- | --- |
| I-CSCF | Record-Route に入らない | なし |
| S-CSCF | 組のどの台でもよい。状態を持たないプロキシとして Route に従う | ODI（保存先） |
| P-CSCF | Record-Route の台の名前の台。作り直した台は保存先から続ける | 対応付け、ダイアログ、SA、reg イベントの購読（保存先） |
| IP-SM-GW | 組のどの台でもよい（今と同じ） | 配達、購読（保存先） |
| SC のスタブ | IP-SM-GW と同じプロセス | 状態報告の要求（保存先） |
| MMTel AS の 2 者の呼 | Contact の台の名前の台。作り直した台は続けず、前のプロセスの呼のダイアログの中の要求に 481 を返す | 呼の記録（保存先）。どの台も、Replaces が指すダイアログから呼のもう一方の脚を探すのに使う |
| MMTel AS の会議のフォーカス、MRFC | Contact の台の名前の台。作り直した台は続けない。強制的に止められた MRFC の台は、MRFP のターミネーションを解放しない | 会議の記録（保存先） |

- P-CSCF の reg イベントの購読は、IP-SM-GW と同じ形で保存先に置きます（調査の記録の 6 章の案 1）。更新の時刻は TS 24.229 5.2.3 のままにし、その時刻と Timer N を購読と一緒に保存先に置きます。時刻の来たものを借りた台が更新を送ります（「期限切れを 1 台だけが処理する」）。UE の再登録の 200 のたびに更新する案は採りません。5.2.3 の時刻を変えずに済み、どの台でも更新できるためです。NOTIFY は、作り直した台が保存先から引いて処理します。`internal/sip` を変えずに作れます（IP-SM-GW が使う `sip.NewSubscriberDialog`）。
- MMTel AS は、ダイアログの中の要求を、最初に INVITE を受けた台に戻します。調査が勧めた案です。どの台でもダイアログの中の要求を処理する案は採りません。B2BUA は片方の脚の re-INVITE への 200 を、もう片方の脚のトランザクションへの 200 にして返します。2 つのトランザクションは同じプロセスの中に要るので、どの台でも処理する形にしても、要求ごとにその台へ縛られます。そのうえ、両方の脚の CSeq を、要求のたびに比べて入れ替える操作で更新することになります。
- そのため、MMTel AS の呼の状態は、INVITE を受けた台のプロセスの中にあります。保存先の呼の記録（`CallRecord` の 2 つの `sip.Dialog`）は、2xx のときと、ダイアログの中の要求のたびに書きます。読むのは、Replaces が指すダイアログから呼のもう一方の脚を探すときだけです（`internal/mmtel` の `otherSide`）。IP-SM-GW はどの台でも続きを処理します。
- 同じ名前で作り直した台は、前のプロセスの呼を組み立て直しません。`sip.UAConfig.OnUnknownDialog` は、UA が知らないダイアログの要求に 481 を返す前に、その要求を役割に渡す口です。この口を設定している役割はありません。そのため、作り直した台は、前のプロセスの呼のダイアログの中の要求に 481 を返します（RFC 3261 12.2.2）。481 を受けた側は、そのダイアログを終えます（12.2.1.2）。呼の記録は、期限の無いまま保存先に残ります。`internal/mmtel` の `SIMPLIFIED:` に書きました。組み立て直すことは、ロードマップの冗長構成に残しています。
- 会議のフォーカスも、作り直した台は続けません。戻らない台（作り直さずに台を減らした場合）を通っていた呼も失われます。
- MRFC の台が強制的に止められるか、ダイアログがターミネーションを取り除く前にプロセスが終わると、そのターミネーションは、ポートを開いたまま MRFP に残ります。ターミネーションを取り除くのは、それを加えた goroutine だけで、ダイアログが終わるときと、作ったばかりの会議のコンテキストを手放すときに取り除きます（`internal/mrfc` の `leg.release`）。止まるよう指示されたノードは UA を閉じ、BYE を送らずにダイアログを終えますが、そのあとの goroutine の後始末を待ちません。同じ名前で起動し直した台も、起動し直したことを ServiceChange で知らせません（TS 23.333 6.1.5.1、TS 29.333 5.17.3.5）。会議のコンテキストは空にならず、混合のクロックも動き続けます。保存先の会議の項目も残ります。`SIMPLIFIED:` に書きました。後始末は、ロードマップの冗長構成に残しています。

## メディア

| 主題 | 作り |
| --- | --- |
| 選び方 | P-CSCF の設定を `pcscf.media_relays`（URL の一覧）にし、前の `media_relay` をなくしました。P-CSCF は Call-ID の hash で呼ごとに中継ノードを選び、`Add` が失敗するか 503 が返れば、一覧の次の中継ノードを試します（`internal/pcscf` の `addContext`）。MRFC も同じで、Call-ID か会議の ID の hash で MRFP を選び、`Add` が失敗すれば次の MRFP を試します（`internal/mrfc` の `candidates`）。ただし、すでにコンテキストのある会議の参加者は、混合を持つ MRFP に送ります。ダイアログの `RelayContext` の `Relay` に中継ノードの URL を入れ、`Modify` と `Subtract` はその中継ノードに送ります。これはできています。 |
| コンテキストの ID | 中継ノードは起動のたびに変わる乱数から ID を数えます（`internal/agw` の `NewRelay`）。作り直す前の ID が、あとの呼のコンテキストに当たらないようにするためです。これはできています。中継ノードどうしでは ID が重なることもありますが、ダイアログが中継ノードの URL も持つので、P-CSCF は取り違えません。 |
| 同じアドレスで作り直した中継ノード | 中継ノードは、コンテキストとターミネーション（ID、自分のポート、相手のアドレス、モード）を保存先に書きます。起動したときに自分のコンテキストを読み直し、同じポートを開き直します。RTP は作り直すあいだだけ途切れ、そのあとは同じポートで戻ります。SIP の信号は変わりません。調査の記録の 5 章の案 2 です。 |
| 戻らない中継ノード | その中継ノードを通る呼は、音声を失ったままになります。P-CSCF は何もせず、UE が切るまで呼は続きます。新しい呼には、ほかの中継ノードが選ばれます。P-CSCF は使えない中継ノードを覚えないので、hash でその中継ノードに当たった呼は、そこへの `Add` が失敗してから次へ進みます。TS 23.334 V19.0.0 の 6.1.2 は、使えない IMS-AGW を戻るまで使わないよう IMS-ALG に求めています。この点も含めて `SIMPLIFIED:` に書きました。 |
| 採らなかった案 | 別の中継ノードへ移し、両側に re-INVITE か UPDATE を送る案（調査の案 3）は採りません。P-CSCF はプロキシなので、自分で re-INVITE を出すと B2BUA の振る舞いになり、両側のダイアログの CSeq を持つ必要があるためです。中継ノードが止まったら呼を切る案も採りません。中継ノードごとに、そこを通る呼の一覧を持つ必要があり、作り直したときに音声が戻る様子も見せられないためです。 |
| MRFP | 中継ノードと同じ実装なので、ターミネーションは同じように開き直します。再生中の音声ガイダンスと CAT（シグナル）は戻しません。`SIMPLIFIED:` に書きます。MRFP の選び方は、今の MRFC の一覧と hash のままです。 |
| TrGW | 同じ実装です。TrGW のコンテキストは IBCF の呼の記録に入れ、台ごとに保存先に置きます（`internal/kvstore/ibcfstore`）。同じ名前で起動し直した IBCF は、記録を読み、呼ごとにコンテキストを解放して、両側に BYE を送ります。記録を読めなければ、IBCF は起動しません。 |

H.248 で制御すると、中継ノードの作り直しは ServiceChange で、コンテキストの確認は Audit で見られます（[media-control.md](media-control.md)）。

## HSS と Diameter

| 主題 | 作り |
| --- | --- |
| HSS の台 | HSS を複数台にし、`hss.Store` を保存先に置きます（`internal/kvstore/hssstore`）。どの台も全加入者を扱えるサーバーファームで、CSCF と AS からは 1 つの HSS に見えます（TS 29.228 6.4）。加入者は、保存先のキーで分かれます。 |
| SLF と DRA | 作りません。SLF（Dx）は拡張の候補にします。SLF は、加入者を別々の HSS に分けて置くときに要るもので、サーバーファームでは要りません（TS 29.228 6.4）。「Diameter の経路で振り分けられること」は、下の接続の切り替えで満たします。Dx が Cx と同じアプリケーション ID を使うかは、確かめていません。 |
| Origin-Host | HSS と S-CSCF の各台は、台ごとの Origin-Host（`hss-1.<ドメイン>` など）を名乗ります。同じ Origin-Host の 2 本目の接続は、今の `internal/diameter` が断るためです（[k8s.md](../background/k8s.md) の 4 章）。 |
| Destination-Host | この行は、仕様を読み直して取り消しました。TS 29.229 5.5 は、I-CSCF と S-CSCF が利用者の HSS の名前を知っているなら Destination-Host を入れることを求め、S-CSCF はその名前を覚えると書いています。TS 29.228 の Table 6.1.2.1（SAR）と Table 6.3.1（MAR）も、すでにある登録への要求では、MAA の Origin-Host から得た HSS の名前を入れると書いています。そこで、S-CSCF は今までどおり `HSSHost` を覚え、SAR に入れます。入らないのは、最初の登録の MAR、I-CSCF の UAR と LIR、AS の Sh の要求、未登録の利用者への SAR です。 |
| Destination-Host と組の切り替え | Destination-Host の入った要求は宛先が決まっているので、`PeerGroup` はその名前の台にだけ送り、ほかの台には送り直しません（RFC 6733 5.5.4）。台ごとの Origin-Host を名乗る組では、始まった登録はその台に結び付き、その台が止まると、その登録の SAR は失敗します。利用者は登録し直し、次の MAR には Destination-Host が入らないので、別の台が答えます。Destination-Host の入らない要求は、組のどの台でも答えられます。商用網が、組の台に 1 つの Diameter の名前を名乗らせる（前に負荷分散を置く）か、DRA を置くかで、この結び付きを解くのは、この構成では作りません。`SIMPLIFIED:` に書きます。 |
| 接続の切り替え | `internal/diameter` に、複数の接続をまとめる `PeerGroup` を足します。開いている接続のうち設定で先にあるものへ送ります。応答が無い、接続が閉じた、DIAMETER_TOO_BUSY が返った、のどれかなら、次の開いている接続へ送り直します（RFC 6733 5.5.4、7.1.3）。送り直す要求は、T ビットを立てた写しにします。写しにするのは、ビットと新しい Hop-by-Hop Identifier が、前の台がまだ書いている最中の要求や、最初の要求のキャプチャに届かないようにするためです。End-to-End Identifier は変えません。受け取った台は、それと Origin-Host で重複と分かるためです（5.5.4）。接続が開いていなくて要求が一度も出ていないときは、次の接続への要求は送り直しではないので、T ビットを立てません。DIAMETER_UNABLE_TO_DELIVER などそのほかの応答は、そのまま呼び出し元に返します。送り直しても応答が無いときに返すのは、最後に試した接続の答えか誤りで、途中の試みはログに残します。接続の監視（DWR と DWA）は、今の接続ごとの監視を使います（RFC 3539）。1 回の要求にかける時間は、試す台の数によらず応答のタイマー（既定で 5 秒）までにします。登録は利用者ごとのロックの中で Cx の往復を 2 回含むので、台が増えても、ロックの期限（`ims.UserLockLease`、15 秒）に収まったままにするためです。各回には、残りの時間を残りの台数で割った分を与えます。開いているのに答えない台が、次の台の分まで使い切らないようにするためです。 |
| HSS から送る要求 | RTR は、今と同じく、最後に SAR を送った S-CSCF の台の Origin-Host に送ります。その台が無ければ失敗をログに書き、組のほかの台には送り直しません。RTR は保守の操作で加入者を消すときにだけ送るので、`SIMPLIFIED:` に書きます。 |
| 起動 | HSS の各台は、設定の加入者を `Add` で保存先に入れ、すでにあれば（`ErrIdentityTaken`）そのままにします（13.8）。 |
| 加入者の一覧 | `hss.Store.List` を、続きの位置と件数を受け取り、次の位置を返す形にします。保存先に置く実装は、秘密の識別子の並べ替えた索引を 1 ページずつ引きます（「並べ替えた索引」）。保守用の `GET /subscriptions` は、`after` と `limit` を受け付けるように広げます。引数の無い呼び方は、今と同じ答えを返します。次のページは、本文ではなく `Link` ヘッダの `rel="next"` で返します（RFC 8288 3）。本文の形が変わらないので、これを読むラボを直さずに済みます。 |
| EPC と PCRF | スタブなので 1 台のままにし、保存先にも載せません。P-CSCF の各台は、自分の Origin-Host で PCRF につなぎます。PCRF からの RAR と ASR は、その Origin-Host の P-CSCF に届き、作り直した P-CSCF は保存先のダイアログから続けます。 |

## ドレイン

ドレインは、各ノードの保守用の API（`internal/maintenance`）の `PUT /maintenance/v1/functions/{role}/administrative-state` で始めます。各ノードの設定に `maintenance.listen` を足します。`SHUTTINGDOWN` がドレインで、役割の `Users` が 0 になると `LOCKED` に移ります。調査の記録の 9 章の案（`admin_listen` と `POST /drain`）は、このパッケージができる前のものなので採りません。

| --- | --- | --- | --- |
| P-CSCF | REGISTER（最初の登録も再登録も）に 503 と Retry-After を返す。Retry-After は UE のタイマー F（64*T1。UE の T1 が 2 秒なら 128 秒）より長い 300 秒にする。そうすると UE は P-CSCF を使えないものとして扱い、別の P-CSCF で最初の登録を行う（TS 24.229 5.1.1.2.1） | 登録済みの UE の発信と着信、ダイアログの中の要求、登録の解除 | この台が作った対応付け。要求を通すかどうかを決めるためにメモリに持つ写しの件数で、保存先が忘れるまで数える |
| I-CSCF | すべての要求に 503 と Retry-After を返す。Retry-After は 30 秒にする。P-CSCF は REGISTER を SRV の次の I-CSCF へ送り、残っていなければ UE に 504 を返す（TS 24.229 5.2.2.1 の 7 番目の項目）。発信側の S-CSCF と IBCF も、最初の要求を SRV の次の I-CSCF へ送り（RFC 3263 4.3）、残っていなければ 500 を返す（RFC 3261 16.7 の手順 6） | なし。I-CSCF は要求と要求のあいだに何も持たず、Record-Route にも入らないので、続けるものがない | 処理中のトランザクション |

- 503 を受けて次の宛先が残っていないとき、プロキシ（P-CSCF、I-CSCF、S-CSCF）は 503 を上流へ返さず、自分で 500 を返します（RFC 3261 16.7 の手順 6、`internal/ims` の `Finish`）。503 は、送った台が今は要求を受けないことを示します。そのまま返すと、ほかの要求は受けているプロキシも要求を受けないと伝えることになります。UE は 503 を自分の P-CSCF のことと読み、Retry-After が無いかタイマー F より長ければ、その P-CSCF を使えないものとして扱います（TS 24.229 5.1.1.2.1、5.1.2A.1.6）。Retry-After は 503 を送った台についての値なので、500 には付けません。REGISTER を転送する P-CSCF だけは別で、I-CSCF から 503 が返ると次の I-CSCF へ移り、残っていなければ 504 を返します（TS 24.229 5.2.2.1 の 7、RFC 3263 4.3）。
- 受けた 503 の扱いを、役割ごとに TS 24.229 V20.1.0 で確かめました。P-CSCF は、UE の INVITE に要る資源を網が認めないとき、UE からの要求をこれ以上受けられないなら 503 を、受けられるなら 500 を返します（5.2.7.2）。I-CSCF の手順（5.3.1.3、5.3.2.2）には、S-CSCF から 503 を受けたときの扱いがありません。S-CSCF の手順の 5.4.3.2 は、AS が失敗して既定の処理が SESSION_TERMINATED のとき、受けた応答を転送するか、最初の INVITE なら 408 か 5xx を返すと書いています。503 を除くとは書いていないので、転送は RFC 3261 16.7 に従うと読み、503 は 500 にします。
- UE は P-CSCF のアドレスに結びついているので、P-CSCF のドレインは、その台の UE がそれぞれの再登録で動くまで終わりません。それまでは、登録済みの UE の新しい呼がドレイン中の P-CSCF を通ります。EPC のスタブから PCO で新しい一覧を送り、早めに動かす方法（TS 23.380 5.1.2）は、拡張の候補にします。
- 組の S-CSCF をすべてドレインして、利用者を別の組に移すことはしません。
- ドレインの状態はプロセスの中にあり、作り直した台は `UNLOCKED` で起動します（`internal/maintenance` の決まり）。

### HSS のドレインで何を返すか

ドレイン中の HSS は、Diameter の相手に Disconnect-Peer-Request（DPR）を送り、Disconnect-Cause に REBOOTING を入れて接続を閉じます（RFC 6733 5.4、5.4.3）。閉じるまでに受けた要求は最後まで扱います。接続が閉じれば、相手の `Peer` はその後の要求をその場で断り、`PeerGroup` はその台を飛ばして次の台へ送るので、組の側は今の作りのままで済みます。これは `internal/hss/maintenance.go` と `internal/diameter` の `Server.DisconnectPeers` で作りました。

初めの案は、ドレイン中の HSS が新しい要求すべてに DIAMETER_TOO_BUSY（3004）を返すものでしたが、これは採りません。RFC 6733 7.1.3 は 2 つのことを言っています。この答えを受け取ったノードは、別の相手に送り直すのがよい（SHOULD）。そして、この答えは特定のサーバーを指した要求に、そのサーバーがそれに応えられないときにだけ使わなければならない（MUST）。「特定のサーバーを指した要求」とは、6.1 が Destination-Host と Destination-Realm の両方を入れると決めている要求のことです。Destination-Host を入れない要求は、レルムの中のどのサーバーが扱ってもよい要求です。

この実装で Destination-Host を入れるのは、SAR のうち UNREGISTERED_USER 以外のすべてです。S-CSCF は MAA を返した台の Origin-Host を覚えていて、登録、再登録、利用者からの登録の解除、保守の操作による登録の解除、期限切れの登録の解除、認証の失敗、認証の期限切れの SAR を、どれもその台に送ります（`internal/scscf/scscf.go` の `serverAssignment`）。入れないのは、UAR、LIR、MAR、UNREGISTERED_USER の SAR、Sh の要求です。どの台が扱ってもよい要求がこれだけ残るので、新しい要求すべてに TOO_BUSY を返す作りは 7.1.3 の MUST に反します。

`PeerGroup` の側は本文のとおりに動くことを確かめました。TOO_BUSY の答えを受けると、組の次の相手に同じ要求を送り直します。Destination-Host の入った要求は、その 1 台にしか送れないので、TOO_BUSY はそのまま呼び出し元に返ります。

DPR を選んだのは、要求の種類で分かれないからです。Destination-Host の入った要求にだけ TOO_BUSY を返す作りも 7.1.3 には合いますが、それだと、`LOCKED` にしたあとも Destination-Host の無い要求、つまり新しい登録と着信の問い合わせが届き、台はそれに答え続けます。DPR で接続を閉じれば、`LOCKED` の台にはどの要求も届きません。`SHUTTINGDOWN` のあいだはどちらの作りでも新しい要求を扱います。ほかの役割のドレインと同じで、そこを区切るのは期限か lock です。Disconnect-Cause（5.4.3）は REBOOTING（0）、BUSY（1）、DO_NOT_WANT_TO_TALK_TO_YOU（2）の 3 つです。受け取った側は、REBOOTING なら接続し直してもよく（MAY）、あとの 2 つなら接続し直さないほうがよい（SHOULD NOT）とされています。ドレインした台は作業のあとに網へ戻るので、REBOOTING を選びます。

DPR を送ったあと、相手は REBOOTING を受けて Tc ごとに接続し直しに来ます。そこで、`UNLOCKED` でないあいだはノードが待ち受けを閉じ、相手は TCP の段階で断られるようにしました。

これは RFC 6733 2.1 から外れる選択です。2.1 は、ノードがいつでもポート 3868 で接続を受けられることを求めています（MUST）。運用から外しているあいだだけ、そこから外れると決めました。根拠は 5.4.3 の REBOOTING です。この理由はノードがこれから再起動することを表し、受け取った側は接続し直してもよい（MAY）とされています。再起動中のノードは待ち受けを持たないので、接続を断られて 2.1 の Tc ごとに試し直すことは、相手が元から見込んでいる動きです。

ほかの 2 つの案はこれより劣ります。CER を CEA で断る案には、運用から外れていることを表す Result-Code がありません。5.3 が挙げるのは DIAMETER_NO_COMMON_APPLICATION、DIAMETER_NO_COMMON_SECURITY、DIAMETER_UNKNOWN_PEER の 3 つで、どれもこの台には当てはまりません。CEA に TOO_BUSY を入れる案も、CER は Destination-Host を持たないので、上と同じ理由で 7.1.3 の MUST に反します。接続を受け入れてからまた DPR を送る案では、CER、CEA、DPR、DPA のやり取りを、運用から外しているあいだ Tc ごとに繰り返します。

`Users` は処理中の Cx と Sh の要求の数です。`SHUTTINGDOWN` のあいだに応答を返し終えてから `LOCKED` に移り、そこで DPR を送ります。要求の数を減らすのは、応答を送り出したあとの `diameter.Node.AfterAnswer` の中で行います。応答を outbox に渡す前に減らすと、DPR が先に出て、その応答が送られないまま接続が閉じるためです。

`SHUTTINGDOWN` のあいだ、相手との接続は開いたままで、相手は要求を送り続けます。そのため、要求の数が 0 になるのは要求の流れが途切れたときで、登録が続けて来ているあいだは 0 にならないこともあります。そこを区切るのが `ShutDown` の `timeout_seconds` で、ほかの役割のドレインと同じ形です。期限が切れたときと、運用者が lock をかけたときは、処理中の要求を残したまま接続を閉じます。そのとき、送り出す途中だった応答は捨てられ、送り手には応答が届きません。受けた要求すべてに応答を返してから DPR を送るのは、最後の要求の応答で `LOCKED` になった shut down だけです。DPA を待つのは Answer タイマー（5 秒）までで、期限が切れればそのまま閉じます。

`operational_state` は、lock を解いたのにアドレスを取り直せなかったときだけ `DISABLED` にします。管理状態で待ち受けを閉じているあいだは `ENABLED` のままです。X.731 が管理状態と運用状態を別のものとして扱うためです。取り直しを自分で繰り返す仕組みは作りません。保守用の API が役割に伝えるのは状態が変わったときだけで、すでに `UNLOCKED` の台にもう一度 lock を解いても何も起きません。運用者が lock をかけて、もう一度解きます。

加入者の API（`provisioning_listen`）はドレインの対象にしません。3GPP のインタフェースではなく、このプロジェクト独自のものなので、Cx と Sh を止めることとは別の話です。

### MMTel AS のドレインで何を返すか

ドレイン中の MMTel AS は、新しいセッションを始める要求に 503 と Retry-After（30 秒）を返し、始まっているものを続けます。`internal/mmtel/maintenance.go` で作りました。続けなければならないのは、呼の扱いが INVITE を受けた台の中にあるからです。両方のレグの Contact がその台を指し、会議の URI は DNS がフォーカスの台へ導くので、ほかの台は続きを扱えません。

扱うのは次のものです。

- ダイアログの中の要求。受け持っている呼とその転送、保留、フォーカスになっている会議が、ドレインが無かったときと同じように終わります。購読の更新と終了（RFC 6665 4.1.2.3）もここに入ります。
- この台が持っている会議の URI を宛先にした要求。ダイヤルインして入る利用者と、抜けたあとに戻る利用者の INVITE（TS 24.147 5.3.2.4.1）、同じ URI を宛先にして、その利用者の発信側のサービスのために届く INVITE、そして、その会議への購読を始める SUBSCRIBE です。どれも新しいものではありません。その会議はこの台だけで動いていて、URI も対話もほかの台にはないので、断れば、続いている会議からその参加者を締め出すことになります。REFER で招かれた参加者も、会議の状態を購読できなくなります。
- AS が転送した呼の INVITE。S-CSCF は、転送した利用者の発信側のサービスのために、P-Served-User に `orig-cdiv` を付けて AS に渡し直します（TS 24.229 5.4.3.3 の step 3）。ダイアログの外の INVITE ですが、shut down の前に始まった呼の続きです。Compose の ORIGINATING_CDIV の iFC は SESSION_TERMINATED なので、断ると続いている呼が終わります。
- ダイアログの外の OPTIONS。UA が自分で 200 を返します（RFC 3261 11.2）。ノードに何ができるかを尋ねる要求で、ノードは生きています。
- 答え始めている Ut の要求。

503 を返すのは次のものです。

- ダイアログの外の INVITE のうち、呼を 1 つ始めるもの。利用者の iFC がこの AS に送るものです。
- 会議のファクトリ URI 宛ての INVITE。この台に会議を作る要求です（TS 24.147 5.3.2.3.1）。
- この台が持っていない会議の URI 宛ての INVITE と、購読を始める SUBSCRIBE。その会議は終わって URI を手放しているので（5.3.2.7）、この台にとってはほかのセッションと同じく新しいものです。
- Ut の新しい要求。理由はこの節の最後に書きます。

ダイアログの外の MESSAGE、REFER、PUBLISH はここまで届きません。AS はダイアログの外でこれらを受けないので、UA が 405 を返します。

S-CSCF は iFC でこの AS に送るので、503 は S-CSCF に返ります。S-CSCF はこれを AS の失敗として読み、サーバー名について DNS が返した次の台へ送り（RFC 3263 4.3。送り直しは `sip.Stack` でできています）、残っていなければ iFC の既定の処理に従います（TS 24.229 5.4.3.2、5.4.3.3）。SESSION_CONTINUED は優先度の低い iFC から照らし合わせを続け、SESSION_TERMINATED は呼を終わらせます。`deploy/compose/hss.yaml` は発信側と ORIGINATING_CDIV の iFC に SESSION_TERMINATED、着信側に SESSION_CONTINUED を書いているので、ドレイン中の AS に当たった発信は 500 で終わります。

TS 24.229 5.4.3.2 の NOTE 25A が、この動きをそのまま書いています。応答が無いか 503 が返った AS について、S-CSCF は利用者の新しいセッションを別の AS に任せ、前の AS は受け持っているセッションを続ける、というものです。5.4.3.6.2 の NOTE 1 も同じ文です。ドレインはこの NOTE の状況を運用者の操作で作ります。

購読を始める SUBSCRIBE と、購読のダイアログの中の SUBSCRIBE は、To の tag で見分けます。後者は購読の更新と終了（RFC 6665 4.1.2.3）なので、ドレイン中も扱います。

`Users` は、この台が受けたダイアログの外の INVITE のうち、まだ終わっていないものの数で、INVITE 1 つが 1 人です。iFC で来た呼は 1 人で、中継する 2 つのレグを合わせて数えます。会議はそれを作った利用者の呼として 1 人で、会議があるあいだ続きます。会議は作った利用者が抜けたときに終わるためです（TS 24.147 5.3.2.7 の 3 番目の項目）。ダイヤルインした利用者はそれぞれもう 1 人で、その利用者が会議にいるあいだ続きます。ドレイン中に入った利用者も同じように数えるので、shut down はその利用者が抜けるまで待ちます。フォーカスが招いた参加者は数えません。招く INVITE が出ていくのは、頼んだ参加者のダイアログの中の REFER からです。答えている途中の Ut の要求も、1 つを 1 人として数えます。

Ut（XCAP）もドレインの対象です。`UNLOCKED` でないあいだ、AS は新しい XCAP の要求に 503 と Retry-After（30 秒）を返し、答え始めている要求は答えます。答えている途中の要求は `Users` に入るので、shut down はそれを待ちます。XCAP の要求は HSS の文書を読み書きしてすぐ終わるので、待つのはそのあいだだけです。

理由は 3 つあります。X.731 の `LOCKED` はどの利用者にも応じない状態なので、`LOCKED` にした台は運用者がそのまま止められます。Ut は 3GPP が決めた、利用者に向いたインタフェースです（TS 24.623）。加入者の API（`provisioning_listen`）のような、このプロジェクト独自のものとは違います。そして、文書は HSS にあってどの台も読み書きするので、断られた利用者はほかの台から同じ文書に届き、失われるものがありません。

503 と Retry-After は HTTP のものです。TS 24.623 V19.0.0 には、XCAP のクライアントが 503 を受けたときの手順も、運用から外れた XCAP サーバーの扱いもありません。クライアントの手順にあるのは、403 を受けたらしばらく XCAP をやり直さない（5.3.1.2.2）、409 を受けたら同じ内容では送り直さない（5.3.1.2.3）、応答が来なければほかの IP アドレスで送り直してよい（5.3.1.2.4）の 3 つです。そこで RFC 9110 に従います。503 は、計画した保守のためにサーバーが今その要求を扱えないことを表し、Retry-After は、クライアントがどれだけ待つべきかを表します（RFC 9110 15.6.4、10.2.3）。

### MRFC のドレインで何を返すか

ドレイン中の MRFC はダイアログの外の INVITE に 503 と Retry-After（30 秒）を返し、持っているダイアログを続けます。`internal/mrfc/maintenance.go` で作りました。MRFC は受けた INVITE ごとの終端の UA で、そのダイアログはその台の中にあります。Contact はその台を指し、MRFP の termination、タイマー、音声ガイダンスの終わりを知らせる Notify を待つ処理も、その台のプロセスにあります。

扱うのは次のものです。

- ダイアログの中の要求。音声ガイダンスは最後まで流れ、会議の参加者は混合に残ります。保留と、混合から離れて戻るための re-INVITE（TS 24.229 5.8.4.1.1.1）、流すのを止める BYE（5.8.3.1.1）、MRFP が終わりを知らせたときに MRFC 自身が送る BYE（5.8.3.2.1）です。
- ダイアログの外の OPTIONS。UA が自分で 200 を返します（RFC 3261 11.2）。ノードに何ができるかを尋ねる要求で、ノードは生きています。

503 を返すのは、ダイアログの外の INVITE です。RFC 4240 3 の音声ガイダンスと、RFC 4240 5 の会議の参加者で、この台がその会議の参加者をすでに持っていても断ります。

ここが MMTel AS と違う所です。AS の会議はフォーカスがその台にあるので、ダイヤルインを断ると、続いている会議から参加者を締め出します。MRFC の会議がどの台にも結び付かないのは、台が 1 つの Store を共有しているあいだです。混合を持つ MRFP とコンテキストはそこにあり、どの台もすべての MRFP を知っているので、ほかの台が受けた参加者は同じ混合に入ります（`internal/mrfc/mrfc.go`）。断っても失われるものがないので、AS のダイヤルインに当たるものも断ります。

台ごとに自分のプロセスの中に Store を持つ構成（`mrfc.MemoryStore`）では、これが成り立ちません。断られた参加者を受けた台は、その会議のメディアを Store から見つけられず、MRFP に別のコンテキストを作らせるので、混合が 2 つに分かれます（`internal/mrfc/conference.go` の `attach`）。MRFC を複数台で動かす構成は、そのためにプロセスの外の Store を使います（`deploy/redundancy/mrfc.yaml`）。1 台だけで動かす Compose のプロジェクトには、断られた参加者を受ける台がそもそもありません。MRFC を運用から外しているあいだに、混合から離れた参加者が戻ろうとすると、そのまま断られます。

TS 24.229 5.8.1 は、MRFC が持っているダイアログの GRUU を宛先にして、そのダイアログの外から届いた要求を扱うと決めています。たとえば、そのダイアログを置き換える Replaces を載せた INVITE です。これは始まっているものの続きなので、ドレイン中の MRFC も扱わなければなりません。この MRFC の Contact は台の SIP URI で、GRUU は使いません。この網で MRFC にダイアログの外から要求を送るものもないので（`internal/mrfc/mrfc.go` の `Listen` の簡略化）、扱うべき要求がありません。

この MRFC は SUBSCRIBE を受けません。会議のイベントパッケージはフォーカスである AS にあるので（TS 24.147 4）、UA が 405 を返し、Allow にも SUBSCRIBE を入れません。ドレインの対象はダイアログの外の INVITE だけです。

AS は設定に書いた名前で MRFC に届くので、503 は AS に返ります。AS の stack は、その名前について DNS が返した次の台へ INVITE を送り、台が残っているあいだは 503 を AS 自身に渡しません（RFC 3263 4.3、`internal/sip/nexttarget.go`）。台が残っていなければ AS が 503 を受け取り、MRF なしで続けます。音声ガイダンス（`internal/mmtel/announcement.go`）と CAT（`cat.go`）は流さずに呼を続け、会議は参加者を断ります（`conference.go`）。混合する MRFP がなければ会議のメディアがないためです。AS が断りに使うのは MRFC が返した応答コード、つまり 503 ですが、参加者に届くのは 500 です。途中のプロキシは 503 をそのまま渡さず、自分の 500 を返します（RFC 3261 16.7 の手順 6、`ims.Finish`）。

`Users` は、この台が持っているダイアログの数です。ダイアログの外の INVITE 1 つが 1 つで、音声ガイダンスは流し終わるか AS が終わらせるまで、会議の参加者はその参加者が混合にいるあいだ数えます。Request-URI が指すサービスや SDP を見て断る INVITE も、答えるあいだは数に入ったままです。Request-URI そのものを読めない INVITE は、数に入る前に 400 で返します（`internal/mrfc/maintenance.go` の `onCall`）。shut down はこれらすべてを待つので、ノードの状態を見れば、流している音声ガイダンスも、この台を通って混合にいる参加者も残っていないと分かります。混合そのものは MRFP にあり、このノードより長く残ります。

MRFC は ENABLED のままです。MRFP との結び付きを持たないためです。Mp の操作は 1 つずつが媒体ノードの制御 API への要求で（`internal/agw`）、答えない MRFP はその INVITE の断りに現れます。H.248 で制御すると関係が続くので、そのときは operational state に出せます。設定の `mrfp` は今は http:// の URL だけです。

### IP-SM-GW のドレインで何を返すか

ドレイン中の IP-SM-GW は始まっていない仕事に 503 と Retry-After（30 秒）を返し、手元にある仕事を終わらせます。`internal/ipsmgw/maintenance.go` で作りました。

IP-SM-GW が 1 つの SIP トランザクションより長く持つものは、すべて Store にあります（`internal/ipsmgw/store.go`）。配達の報告を待っている配達とその TR1N、reg event の購読です。どれも台に結び付いていません。配達の報告は DNS が導いた IP-SM-GW に届き、NOTIFY も同じです。SUBSCRIBE の Contact は IP-SM-GW の DNS 上の名前で、1 台を指さないためです（`regevent.go`）。MMTel AS が INVITE を受けた台に呼を結び付けるのとは違い、ここでは台が持つのは、その時点で手元にある要求だけです。

`UNLOCKED` でないあいだ続けるものは次のとおりです。

- 配達の報告を運ぶ MESSAGE。In-Reply-To がほかの MESSAGE と見分けます（TS 24.341 5.3.2.4 の項目 d）。この網がすでに UE へ送った RP-DATA に対する RP-ACK か RP-ERROR で、始まっている配達の終わりです。503 を返すと配達は待ち続け、TR1N が切れたあとで SC は system failure を聞きます。UE は受け取っていたのに、です。
- reg event の購読の NOTIFY。この網が送った SUBSCRIBE のダイアログの中にあり、その SUBSCRIBE の続きです。最初の NOTIFY がダイアログを完成させ、どの NOTIFY も、利用者が短いメッセージを受け取る contact を持っているかを伝えます（TS 24.341 5.3.3.2）。503 を返すと、その内容は次の NOTIFY まで失われ、HSS には合わなくなった SMSRegistrationInfo が残ります。
- SC から渡された配達（`Deliver`）。このノードの SC は始めた台にだけ頼みます。UE から受けた短いメッセージの SMS-DELIVER、自分が終わらせた配達の SMS-STATUS-REPORT、MESSAGE で受けたほかの IMS 網からの短いメッセージの 3 つです。
- 自分の sweep が claim した TR1N の期限（`reportTimedOut`）。SC はすべての配達の結果を聞きます。報告が来なかった配達は、どこかの sweep が終わらせるまで結果を持ちません。claim はすでにこの台のものです。

503 と Retry-After を返すものは次のとおりです。

- 第三者 REGISTER。登録、再登録、登録解除のどれもです（TS 24.341 5.3.3.2）。登録と再登録は、この台に、利用者の登録状態への購読を始めさせるか、購読を更新させます。その購読は Store にあり、どの台からも見えます。登録解除を断っても失うものはありません。`register` は 200 を返すだけで、ほかに何もしないためです。購読は、S-CSCF が Subscription-State を terminated にした NOTIFY で終わらせます（TS 24.229 5.4.2.1.2）。この NOTIFY はダイアログの中にあるので、ドレイン中のこの台も受け取ります。`receiveRegEvent` が購読を消し、利用者が短いメッセージを受け取らなくなったことを HSS に伝えます（`regevent.go`）。
- UE が送った短いメッセージの MESSAGE と、UE にメモリが戻ったことを知らせる MESSAGE（TS 24.341 5.3.3.4.1）。どちらも短いメッセージの転送を始めます。
- ほかの IMS 網の IP-SM-GW が、この網の利用者へ送る短いメッセージの MESSAGE（TS 23.204 6.4a の手順 2）。向こうの網では始まっていますが、この台の手元には何も来ていないので、別の台がまるごと引き取れます。

IP-SM-GW が受けないメソッドは、administrative state に関わらず 405 を返します（`ipsmgw.go` の `OnRequest`）。運用から外しても、そのメソッドを扱えるようになるわけではなく、次の台も同じ答えを返すためです。OPTIONS もここに入ります。この IP-SM-GW は REGISTER、MESSAGE、NOTIFY だけを受け、UA に OPTIONS を答えさせていません。

`UNLOCKED` でないあいだに届いた SGd の TFR は、DIAMETER_TOO_BUSY で断ります（`sgd.go`）。断る前に受けた TFR は、上のとおり TFA を返すまで扱います。TFR は Destination-Host でこの台を名指しした要求なので、この答えを特定のサーバーを指した要求にだけ使わせる RFC 6733 7.1.3 の MUST に合います。SC は、同じ realm の IP-SM-GW のうち SGd でつながっているほかの台へ、同じ TFR を送ります。SC がこの台への接続を持たないときも同じです（[sms.md](sms.md) の「名指しした台が使えないとき」）。

S-CSCF は利用者の iFC で IP-SM-GW に要求を届けるので、503 は S-CSCF に返ります。S-CSCF は、サーバー名について DNS が返した次の台へ送り（RFC 3263 4.3）、残っていなければ iFC の既定の処理に従います。第三者 REGISTER は TS 24.229 5.4.1.7、ほかは 5.4.3.2 と 5.4.3.3 です。`deploy/compose/hss.yaml` の IP-SM-GW の iFC は、利用者が送る MESSAGE だけが SESSION_TERMINATED で、ほかは SESSION_CONTINUED です。そのため、次のようになります。

- どの台も答えなかった第三者 REGISTER は、登録をそのまま残します（5.4.1.7）。登録と再登録では、利用者は登録され、どの IP-SM-GW も reg event の購読を持たないので、HSS はその利用者が短いメッセージを受け取ることを知りません。次の再登録の第三者 REGISTER が購読します。登録解除では、やり残しはありません。購読を終わらせるのは NOTIFY だからです。
- 発信側の MESSAGE は、そこで終わります。S-CSCF は優先度の低い iFC へ進まず、IP-SM-GW の応答を UE へ返します（TS 24.229 5.4.3.2）。プロキシは 503 を転送しないので（RFC 3261 16.7 の step 6）、UE が短いメッセージについて見るのは 500 です。Retry-After は IP-SM-GW と S-CSCF のあいだで止まります。この iFC を SESSION_TERMINATED にしたのは、利用者が送る短いメッセージを扱えるノードが IP-SM-GW のほかに無いためです。SESSION_CONTINUED だと、S-CSCF は Request-URI、つまり UE が宛てた SC の PSI へ進みます（TS 24.341 5.3.1.2 の項目 a）。SC は IP-SM-GW のノードの中にあり、DNS 上の名前を持つノードではないので（`internal/ipsmgw/servicecentre.go`）、S-CSCF は ENUM で番号を変換できず、404 を返します（TS 24.229 5.4.3.2 の手順 10）。404 は宛先が存在しないことを示す応答で（RFC 3261 21.4.5）、SC はあるのに使えない、という状況とは意味が違います。DefaultHandling をどちらにするかは標準が決めていない、運用者の選択です。TS 24.341 5.3.1.2 は、SM-over-IP sender がこの MESSAGE の失敗の応答をどう扱うかを決めていません。別の MESSAGE で来る submit report を受け取ることだけを決めています。
- 着信側の MESSAGE、つまりほかの IMS 網からの短いメッセージは、受け手の登録済みの contact へ進みます（5.4.3.3、そのあと 5.4.3.2 の手順 10 以降）。UE はこの網の IP-SM-GW を経ずに、向こうの網の RP-DATA を受け取ります。

`Users` は、この台が手元に持っていて、まだ終わっていない仕事です。

- 答えている途中の要求 1 つずつ。数え始めるのは、受けないと決めた要求を断ったあとです（`take`）。第三者 REGISTER は 200 を書いて Store を読み終えるまで（この網の短いメッセージが届かなかった利用者の再登録では、利用者が戻ったことを HSS に伝え終わるまで。`regevent.go` の `tellReachable`）、MESSAGE はそれに答える submit report か配達の報告の処理が終わるまで、NOTIFY はその内容を HSS に伝え終わるまで数えます。415、403、400、481、488、489、500 で断る要求も、答えるあいだは 1 人です。受けないメソッドは数える前に 405 で返します。
- 自分の SUBSCRIBE と、その更新。最終応答が返るまで数えます（`regevent.go`）。SUBSCRIBE を出したまま止まった台が、ダイアログの無い購読を残さないためです。
- 利用者が送った MESSAGE のあとの仕事。この台が届けられなかった利用者が戻ったことを、HSS に伝え終わるまでです（`regevent.go` の `reachableAgain`）。
- SC から渡された配達。RP-DATA を運ぶ MESSAGE に最終応答が返るまでです（`Deliver`）。
- 受けた TFR。TFA を返すまでです（`sgd.go`）。TFA は UE の配達の報告を SC に運ぶので、この 1 つは配達の報告を待ちます。途中で止まった台は、始めた配達の結果を誰にも伝えず、SC は自分のタイマーが切れるまで答えを待つことになります。
- 自分の sweep が claim した TR1N の期限。配達を終わらせて SC に伝えるまでです（`reportTimedOut`）。

配達の報告を待っている時間は、TFR に答えるものを除いて数えません。配達とその TR1N は Store にあるので、報告は届いた台が扱い、TR1N が切れればどの台の sweep でも配達を終わらせられます。この台を止めても何も失われません。報告を待って shut down を止めると、このノードを必要としなくなった仕事のために TR1N の 64 秒を待つことになります。

数えるもののうち TFR を除くものは、SIP のトランザクション数回で終わります。手元に TFR が無ければ、shut down はすぐに `LOCKED` に移ります。TFR はその配達が終わるまで、つまり TR1N と、それを終わらせる sweep の 1 回分まで続きます。ほかに移れないのは、新しい仕事が続けて来るときです。sweep はほかの台が送った配達の期限も claim し続け、claim 1 つが終わるまで 1 人として数えます。ドレイン中の S-CSCF が自分の期限の処理を続けるのと同じです。そこを区切るのが shut down の `timeout_seconds` で、HSS と同じ形です。

operational state は Sh の相手に従います。IP-SM-GW は利用者の登録状態を聞いても SMSRegistrationInfo を書けなければ使えず（TS 24.341 5.3.3.2）、隣の SC も短いメッセージの宛先の番号を持つ利用者を HSS に聞けません。どちらも HSS が要るので、Sh の相手がいなければ DISABLED にします。IP-SM-GW と同じプロセスで動く SC のスタブは、operational state に入れません。`ServiceCentre` の境界の向こうにあり、状態を報告できる結び付きが無いためです。SGd でノードとしての SC（`sc` の役割）につなぐ IP-SM-GW も、operational state は Sh の相手だけで決めます。SC が届かないあいだも登録は続けられ、発信のショートメッセージには RP-Cause 41 を返して UE に送り直しを促せるためです。SC そのものの状態は、SC のノードが自分の保守用の API で報告します（次の節）。

### SC のドレインで何を返すか

ドレイン中の SC は、HSS と同じく Diameter の待ち受けで運用から外れます。shut down で新しい接続を受けなくなり、`LOCKED` で serving node が開いた接続に DPR を送って閉じます。`internal/smsc/maintenance.go` と `cmd/ims/sc.go` の `scFunction` で作りました。待ち受けを閉じて DPR を送る手順は、HSS と共通の `diameter.ListenerDrain` にまとめました。

SC が 1 つの要求より長く持つものは、すべて保存先にあります（`internal/smsc/store.go`）。預かったショートメッセージと、宛先ごとに次に試す時刻です。どの台も受け取れ、どの台も配達できます。台に結び付くのは、配達を試しているあいだの宛先のリースだけです。そのため、運用から外した台が終えるのは、始めた試行だけです。

応答で断る作りは採りません。理由は次のとおりです。

- OFR は Destination-Host を持ちません。SC のアドレスから SMS-IWMSC の名前を引けない serving node は realm だけを入れる、と TS 29.338 V19.3.0 6.3.1.1 が決めていて、この IP-SM-GW はそうしています。RFC 6733 7.1.3 は DIAMETER_TOO_BUSY を特定のサーバーを指した要求にしか使わせないので、IP-SM-GW の TFR のようには断れません。HSS で TOO_BUSY を採らなかったのと同じ理由です。
- TS 29.338 V19.3.0 6.2.1.1 の Table 6.2.1.1/2 が OFA に定める失敗の原因（unknown Service Centre address、Service Centre congestion、invalid Short Message Entity address、user not Service Centre user）は、どれもそのショートメッセージを断るものです。Service Centre congestion を返すと、UE には RP-Cause 42 の RP-ERROR が届きます。`PeerGroup` が別の台へ送り直すのは TOO_BUSY と答えが無いときだけなので、ほかの台へは移りません。設定の順で最初の台をドレインすると、その台が接続を持っているあいだ、UE が送るショートメッセージはすべて失敗します。これはドレインになりません。
- DIAMETER_UNABLE_TO_DELIVER（3002）は、レルムの中に要求を扱えるホストが無いために要求を届けられなかったノードが返すものです（RFC 6733 7.1.3）。SC は要求の宛先そのものなので、自分について返すのは実際の網に無い動きです。

続けるものは次のとおりです。

- 持っている接続で届く OFR。`SHUTTINGDOWN` のあいだは接続が残るので、OFR が届きます。いつもどおり受け取って保存先に預け、OFA を返します。配達は始めず、運用中の台に任せます（`deliverSoon`）。HSS が `SHUTTINGDOWN` のあいだも新しい要求を扱うのと同じで、断る手段が無いためです。
- HSS の ALR。保存先の `Alert` でその利用者の宛先を今すぐ試す状態にし、成功を返します。配達は運用中の台の `ProcessDue` が拾います。ALR は、以前の配達が始めた待ちの終わりです（TS 23.040 3.2.7）。断ると HSS は MWD に SC のアドレスを残し（再送するかどうかは運用者の選択です。TS 29.338 V19.3.0 5.2.2.2）、配達は利用者が次に戻るときか、再送の時刻（Compose では 1 時間）まで遅れます。
- リースを持っている宛先の、今の試行。試行を終えてリースを放したあとは、同じ宛先の次のショートメッセージを取りにいきません（`serve`）。`ProcessDue` も宛先を claim しません。再送、有効期間の終わり、ALR で試す状態になった宛先は、保存先で運用中の台を待ちます。

`Users` が数えるものは次のとおりです。

- 答えている途中の OFR と ALR。答えを送り出してから減らします（`diameter.Node.AfterAnswer`）。最後の答えより先に DPR が出ないようにするためで、HSS と同じです。
- リースを持っている宛先。claim の前に数え、リースを放したあとで減らします。claim のあとで数えると、そのあいだに shut down が数えたとき、リースを見落とすためです。

保存先は走査しません。預かっているショートメッセージも数えません。どの台でも配達できるためです。1 回の試行は IP-SM-GW の TFA を待つので、最長で `scAnswerTimeout`（約 90 秒）かかります。shut down がそれより長く待たないよう区切るのは `timeout_seconds` で、ほかの役割と同じです。

lock と期限切れは、試行を待ちません。接続が閉じると、TFA を待っている TFR には答えが返らず、SC はこれを時間が経てば直るかもしれない system failure と読み、ショートメッセージを次の再送まで預かります。IP-SM-GW がもう配達していれば、受け手は同じショートメッセージを 2 回受け取ります。HSS の lock が処理中の要求を待たないのと同じです。

HSS との接続は閉じません。SC が自分で開いた接続で、HSS は ALR をこの接続で送るためです（`hss.SetPeers`）。止まった台は HSS への接続も持たないので、HSS は設定の `hosts` が同じ SC のアドレスに挙げる次の台へ ALR を送ります（[sms.md](sms.md) の「名指しした台が使えないとき」）。

operational state は、S6c の相手（HSS の `PeerGroup`）が使えるあいだ ENABLED です。HSS が無いと、宛先を確かめることも、宛先を受け持つノードを調べることもできないためです。加えて、運用中なのにノードが待ち受けていないときも DISABLED にします。待ち受けをやり直すバインドに失敗したときと、同じノードのほかの役割が待ち受けを閉じているときです。

1 つのノードが HSS と SC の両方を持つときは、Diameter の待ち受けも 1 つです。どちらかを外すと待ち受けが閉じ、両方が戻ったときに開きます（`diameter.Server.SetAccepting` が、閉じている役割を数えます）。lock の DPR も、ノードのすべての接続に送ります。片方だけを外したい運用者は、2 つを別のノードにします。Compose、Kubernetes、冗長構成では、どちらも別のノードです。

Compose の SC は 1 台なので、運用から外れているあいだに預かったものは、戻すまで待ちます。

### メディア中継ノードと MRFP のドレインで何を返すか

ドレイン中の媒体ノードは新しいコンテキストを作る `Add` に 503 を返し、持っているコンテキストを続けます。`internal/agw/maintenance.go` で作りました。中継ノードと MRFP は同じ実装なので、ドレインも同じで、役割の名前（`agw` と `mrfp`）だけが違います。どちらも設定の役割ごとに `maintenance.Function` を持つので、両方の役割を持つノードでは、運用する人が片方だけを外せます。

コンテキストがあるのは、そのポートを開いたノードの中だけです。呼の UDP ソケットはこの中継ノードにあり、制御する側が持っているのはこの中継ノードが渡したコンテキストの ID で、呼の RTP はこのプロセスだけを行き来します。だから、運用から外した台は持っているコンテキストを続けます。これは TS 23.334 V19.0.0 6.1.2（IMS-AGW）と TS 23.333 V19.0.0 6.1.2（MRFP）が言う graceful の方法です。どちらの条項も、保守のために閉じたことを媒体ノードが制御する側に伝え、graceful ならその呼が切れるにつれて接続を解放する、と書いています。

扱うのは次のものです。

- 持っているコンテキストへの操作すべて。相手のアドレスやモードを変える `Modify`、音声ガイダンスを始める `Modify`、ターミネーションかコンテキストを解放する `Subtract` です。`Subtract` を断ると、ドレインが終わらなくなります。
- 持っているコンテキストへのターミネーションの `Add`（`AddTermination`）。この台に混合がある会議に参加者が入るときのものです。混合はこの台にしか無いので、断ると続いている会議から参加者を締め出します。コンテキストは増えないので、`Users` は shut down のあいだ減るだけです。
- 制御する側に送る Notify と、コンテキストと音声ガイダンスを読む Audit。ノードが持っているものを伝えるだけで、何も始めません。

503 を返すのは、新しいコンテキストを作る `Add` だけです。これが新しく始まる唯一の操作で、TS 29.334 5.17.2.2 と TS 29.333 5.17.2.2 の手順に当たります。HTTP の制御 API では、誤りの符号が `out_of_service` の 503 です。H.248 では Add のコマンドに誤り 502（Not ready）を返します。TS 29.334 5.7.10 の Table 5.7.10.2 が、IMS-AGW が送る符号として挙げているものです。

503 に Retry-After は付けません。P-CSCF も MRFC も使えない媒体ノードを覚えないので（`internal/pcscf` の `addContext` と `internal/mrfc` の `candidates` の `SIMPLIFIED:`）、読むものがいません。断られた側は一覧の次の台を試し、1 台も残らなければ上流に答えます。Compose のプロジェクトは中継ノードも MRFP も 1 台なので、新しい呼はそこで終わります。P-CSCF は INVITE に 500 を返し（`internal/pcscf` の `session.go`）、MRFC が AS に返した 503 を受けた AS は、MRF なしで呼を続けます。

`Users` はこの台が持っているコンテキストの数です。P-CSCF を通る呼の片側ごとに 1 つ、音声ガイダンス 1 つにつき 1 つ、会議 1 つにつき 1 つで、会議はターミネーションの数によらず 1 つです。前のプロセスが保存先に残し、起動したときに開き直したコンテキストも入ります（`internal/agw` の `restore`）。数えるのは `Relay` が持つ一覧の長さで、保存先を走査しません。保存先には同じ名前のほかのプロセスのコンテキストも入っているためです。shut down はこれらすべてを待つので、ノードの状態を見れば、このノードを止めてもメディアを切らないと分かります。呼の状態そのものは制御する側にあり、このノードより長く残ります。

媒体ノードは ENABLED のままです。自分のソケットで答え、状態を報告できるような結び付きを持たないためです。H.248 で制御するときは、隣の `mediactl.Gateway` がコントローラとの結び付きを持ちますが、`Relay` はそれを知りません。

運用から外したことを、この媒体ノードは制御する側に伝えません。実物の IMS-AGW と MRFP は ROOT に GRACEFUL の ServiceChange を送って知らせ（TS 29.334 5.17.3.2、TS 23.333 8.30）、受けた側は戻るまでその台に新しい接続を作りません（TS 23.334 6.1.2、TS 23.333 6.1.2）。ここでは、制御する側が次の `Add` を断られて気づきます。`internal/h248/mediactl` の `Controller` は、ゲートウェイから来た GRACEFUL の ServiceChange を受けて、その台に新しいコンテキストを作らなくなりますが、`Gateway` はそれを送りません。`SIMPLIFIED:` と手順書の表に書きました。

## 作らないもの

上の節で `SIMPLIFIED:` に書くとしたもののほかに、次のものを作りません。保存先の冗長、SLF、TS 23.380 の 5.1.2、5.4、5.5 は、ロードマップの「拡張の候補」に載せます。

- 保存先の冗長（Sentinel、クラスタ）。
- SLF（Dx）、DRA。
- TS 23.380 の 5.1.2、5.4、5.5（P-CSCF の網からの復旧）。
- EPC と PCRF のスタブの冗長。
- トランザクションの状態を外に出すこと。
- 戻らない中継ノードを通る呼の音声を戻すこと。

## 調査と違うところ

- HSS は調査の推奨（サーバーファームと SLF の両方）のうち、サーバーファームだけを作ります。
- P-CSCF の網からの復旧は、調査が推奨した PCRF を使う方法も作りません。
- ドレインを始める操作には、調査の案（9 章）の代わりに、あとからできた `internal/maintenance` を使います。
- `Store` の形を変えることは、調査の 13.8 の案をそのまま採りました。

## 残っている課題

各役割を複数台で動かす作りを妨げていた 3 つの所は、上の節の作りで取り除きました。

| 妨げになっていた所 | 今の作り |
| --- | --- |
| HSS の振り分け | HSS は、状態を共有するサーバーファームです（`internal/kvstore/hssstore`）。I-CSCF、S-CSCF、MMTel AS、IP-SM-GW は、HSS の台を `diameter.PeerGroup` の 1 つの組として持ちます（「HSS と Diameter」）。 |
| HSS の加入者の一覧 | 保守用の `GET /subscriptions` は、`after` と `limit` で 1 ページずつ返し、次のページを `Link` ヘッダの `rel="next"` で示します。1 ページは 1000 件までです（`internal/hss/provisioning.go` の `listLimit`）。保存先に置く実装は並べ替えた索引を、`MemoryStore` は並んだ列を引き、全件を並べ替えません。 |
| `Store` の操作 | 読んで、変えて、書く操作は、版を比べて入れ替える書き込み（`kvstore.Store` の `CompareAndSwap`）で行います。S-CSCF、HSS、IP-SM-GW の利用者ごとのロックは、冗長構成では保存先に置きます（`internal/kvstore/kvlock`、「Store の形と書き込みの決まり」）。 |

残っているのは、上の節で `SIMPLIFIED:` に書いたものと、「作らないもの」です。作り直した MMTel AS の台が前のプロセスの呼を組み立て直すことと、強制的に止められた MRFC の台のターミネーションを MRFP から解放することは、ロードマップの冗長構成の「作っていないもの」にあります。
