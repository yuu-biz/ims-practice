# 実装の言語と、自作するもの

この記録はどの言語で書くか、どの層を自作し、どこに既存のライブラリを使うかの設計です。

## 選んだこと

- 呼処理のノード（CSCF、HSS スタブ、アクセス網のスタブ、UE シミュレータ、ラボのサーバー）は Go で書きます。
- メディア中継ノード（IMS-AGW の役割）も Go で書き、CSCF と同じ `ims` コマンドの役割の 1 つにします。
- SIP のメッセージの解析と組み立て、トランザクション層、ダイアログ層は自作します。
- Diameter のメッセージと AVP の符号化、TCP の接続、辞書には go-diameter（BSD-3-Clause 相当）を使います。Cx の辞書は同梱されていないので、自分で XML を書きます。
- Diameter の CER/CEA と DWR/DWA、接続の状態機械は自分で書きます。
- 学習の対象でない部分（文字列処理、ネットワーク入出力、暗号処理など）や、自作すると工数に見合わない部分には、既存のライブラリを使います。フルスクラッチは必須ではありません。
- 勉強会のスライドは自前の生成の道具で、HTML と、文字を編集できる pptx を作ります。発表者ノートは付けません（[slides/README.ja.md](../../slides/README.ja.md)）。

## SIP と Diameter のどこを自作するか

SIP の解析、トランザクション層、ダイアログ層を自作するのは、IMS の手順が SIP のどの層の動きなのかを読めるようにするためです。試作では、解析と組み立てが約 160 行で書け、IMS の最初の REGISTER（空の `nonce` を含む Authorization）を往復できました。

Go の SIP ライブラリ sipgo（BSD-2-Clause）は、メッセージの型と同じパッケージにトランザクション層と転送層を含みます。自作のトランザクション層の土台にすると、競合する実装を抱えることになるので使いません。自作のパーサーと結果を突き合わせる試験の相手としてだけ使います。

go-diameter は試作で独自の辞書を読み込むだけで MAR と MAA を送受信でき、Wireshark で正しくデコードできました。

go-diameter の `sm` パッケージは使いません。使うと、CER/CEA、DWR/DWA、接続の状態機械の手順が学習者から見えなくなるためです。`sm` の CEA は辞書にあるすべてのアプリケーションを通知するので、キャプチャを見た学習者が、HSS は Gx や Rx に対応していると誤解する問題もあります。

## 呼処理のノードを Go にした理由

同じ処理（SIP の解析と 401 の生成、Diameter の CER/CEA と DWR/DWA、Cx の MAR）を Go と Rust で試作して比べました。

| 観点 | Go | Rust |
| --- | --- | --- |
| SIP の手書きのパーサー | 約 160 行。サンプルを往復できた。 | 約 190 行。サンプルを往復できた。 |
| Diameter のライブラリ | go-diameter v4.6.0。独自の XML 辞書で Cx を追加できた。 | diameter 0.7.1。アプリケーションとコマンドが閉じた enum で、Cx にはフォークが必要。サーバーから要求を送れない。 |
| 辞書に無い AVP | 扱える | メッセージ全体のデコードに失敗する |
| イメージの大きさ | 3.6 MB（圧縮後） | 31.9 MB（圧縮後） |
| 学習者が読むときの負担 | 非同期と所有権の概念が無い。要求と応答の区別は型ではなく約束で守る。 | enum と match で状態を表せる。非同期（tokio）とトレイト境界の理解が必要。 |

決め手は Diameter です。Cx と Sh は IMS の中心なので、ライブラリをフォークして保守し続ける負担は避けます。性能は要件の性能の目安の規模（[requirements.md](../requirements.md)）では差になりません。

試作のコードは捨てるもので、比べた結果をこの表に記録したあとで削除しました。

## メディア中継ノードも Go にした理由

メディアの制御はノードのあいだの API で分けてあるので（[media-control.md](media-control.md)）、ノードごとに言語を選べます。メディア中継ノードについても、同じ機能（2 つの UDP ポートの確保、双方向の中継、最初のパケットの送信元へのラッチング、HTTP の制御 API）を両方の言語で試作して比べました。負荷は要件の性能の目安の規模で、10 セッション、各方向 50 パケット/秒、172 バイト、30 秒を 3 回流しました。

| 観点 | Go | Rust |
| --- | --- | --- |
| 行数（空行とコメントを除く） | 115 | 111 |
| 外部の依存 | なし（標準ライブラリ） | tiny_http と 4 つのクレート |
| イメージの大きさ（圧縮後） | 6.70 MB | 4.25 MB |
| 1 回のビルドが残すビルドキャッシュ | 497 MB | 1.41 GB |
| 失ったパケット | 3 回とも 0 / 30000 | 3 回とも 0 / 30000 |
| 中継の遅延の中央値 | 約 370 µs | 約 125 µs |
| 遅延の 99 パーセンタイル | 0.8〜2.6 ms | 0.5〜2.0 ms |
| CPU とメモリ | 1 コアの約 9%、5〜9 MiB | 約 3.5%、0.5〜2.4 MiB |
| 読むときに必要な概念 | goroutine と mutex | 所有権、Arc、Mutex、AtomicBool。ブロック中のソケットを別スレッドから閉じられないための工夫 |

Rust のほうが軽く速いのですが、どちらもパケットを落とさず、遅延の中央値は 20 ms のパケット間隔の 2% 未満でした。この規模では性能は決め手になりません。

決め手は次の 2 つです。

- ツールチェーンが 1 つで済みます。Rust を加えると、CI、整形と静的検査、手順書、後始末がすべて 2 言語分になります。
- 学習者が読むときの負担が小さく、同じ `ims` コマンドの役割にできます。1 つのイメージが設定で役割を切り替え、C-Plane と U-Plane を同じコンテナにまとめる構成も、分ける構成も、設定だけで選べます。

試作のコードは捨てるもので、結果をこの表に記録したあとで削除しました。
