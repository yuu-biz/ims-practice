# 実装の言語と、自作するもの

この記録はどの言語で書くか、どの層を自作し、どこに既存のライブラリを使うかの設計です。自作する SIP の層について、TCP の送信をどこで待つかと、re-INVITE への信頼できる暫定応答をどう扱うかもここに書きます。

## 選んだこと

- 呼処理のノード（CSCF、HSS スタブ、アクセス網のスタブ、UE シミュレータ、ラボのサーバー）は Go で書きます。
- メディア中継ノード（IMS-AGW の役割）も Go で書き、CSCF と同じ `ims` コマンドの役割の 1 つにします。
- SIP のメッセージの解析と組み立て、トランザクション層、ダイアログ層は自作します。
- SIP のスタックのループは、TCP の接続と書き込みを待ちません。転送層が相手ごとの待ち行列を持ち、別の goroutine で書き込みます。
- SIP のスタックは re-INVITE を送る側でも、信頼できる暫定応答に PRACK を返します。
- Diameter のメッセージと AVP の符号化、TCP の接続、辞書には go-diameter（BSD-3-Clause 相当）を使います。Cx の辞書は同梱されていないので、自分で XML を書きます。
- Diameter の CER/CEA と DWR/DWA、接続の状態機械は自分で書きます。
- 学習の対象でない部分（文字列処理、ネットワーク入出力、暗号処理など）や、自作すると工数に見合わない部分には、既存のライブラリを使います。フルスクラッチは必須ではありません。
- 勉強会のスライドは自前の生成の道具で、HTML と、文字を編集できる pptx を作ります。発表者ノートは付けません（[slides/README.ja.md](../../slides/README.ja.md)）。

## SIP と Diameter のどこを自作するか

SIP の解析、トランザクション層、ダイアログ層を自作するのは、IMS の手順が SIP のどの層の動きなのかを読めるようにするためです。試作では、解析と組み立てが約 160 行で書け、IMS の最初の REGISTER（空の `nonce` を含む Authorization）を往復できました。

Go の SIP ライブラリ sipgo（BSD-2-Clause）は、メッセージの型と同じパッケージにトランザクション層と転送層を含みます。自作のトランザクション層の土台にすると、競合する実装を抱えることになるので使いません。自作のパーサーと結果を突き合わせる試験の相手としてだけ使います。

go-diameter は試作で独自の辞書を読み込むだけで MAR と MAA を送受信でき、Wireshark で正しくデコードできました。

go-diameter の `sm` パッケージは使いません。使うと、CER/CEA、DWR/DWA、接続の状態機械の手順が学習者から見えなくなるためです。`sm` の CEA は辞書にあるすべてのアプリケーションを通知するので、キャプチャを見た学習者が、HSS は Gx や Rx に対応していると誤解する問題もあります。

## SIP の TCP の送信をループで待たない

SIP のスタック（`internal/sip` の `Stack`）は、1 つの goroutine ですべてのトランザクションを扱います。ここではこの goroutine をループと呼びます。受信したメッセージをトランザクションに対応付け、状態機械を進め、タイマーを動かすのは、ループだけです。

TCP の接続を開くことと書き込むことは、ループの外で行います。相手のホストが落ちていると、接続を開こうとしてから失敗するまでに `tcpConnectTimeout`（2 秒）かかります。相手が読まなくなったときの書き込みも、同じだけかかります。これをループで待つと、そのあいだ、その役割の受信、再送、タイマー、ほかの利用者への送信がすべて止まります。待つ送信が N 個あれば、N×2 秒止まります。役割全体を止める処理があると、規模を広げられません。

次のように決めました。

- 転送層（`TransportLayer`）は、相手（アドレスとポート）ごとに、送るメッセージの待ち行列を持ちます。ループは待ち行列にメッセージを入れるだけで、接続も書き込みも待ちません。UDP の送信は相手を待たないので、これまでどおりループから送ります。
- 待ち行列ごとに、書き込む goroutine を 1 つ動かします。この goroutine は、接続が無ければ開き、メッセージを入った順に書きます。1 つの相手に書く goroutine は 1 つだけなので、1 つの相手へのメッセージは、ループが渡した順に届きます。ただし、Via の示すアドレスへ送り直す応答（後で述べます）は、そのアドレスの待ち行列の最後に並び直すので、もとの待ち行列の順からは外れます。
- この goroutine は、待ち行列が空になると終わります。送るものの無い相手の goroutine は残りません。接続ごとではなく相手ごとにしたのは、待つのが接続を開くところで、そのときにはまだ接続が無いためです。
- 待ち行列の表を守るロックは、表を読み書きするあいだだけ取ります。接続を開くあいだと書き込むあいだは取りません。1 つの相手を待っていても、ほかの相手への送信は止まりません。
- 1 つの相手の待ち行列に入るのは、書き込み中のものとは別に 512 個までです。相手が読まなくなると、書き込み 1 回に 2 秒かかり、そのあいだもメッセージが入り続けるためです。512 は、1 つの送信元から受け入れの判定を待つ要求の上限（`maxAdmitQueue`）と同じです。網のノードは多くの利用者のメッセージを 1 つの相手に送るので、まとめて届く分を収められる大きさにしました。
- 待ち行列が一杯なら、メッセージを入れず、その場で送信の失敗を返します。ループはこれを、ほかの送信の失敗と同じく、トランザクションの転送層の失敗（RFC 3261 17.1.4、17.2.4）として扱います。
- 待ち行列に入れたあとで接続や書き込みに失敗したときは、書き込む goroutine がその失敗をイベントとしてループに返します。ループは、そのトランザクションがまだ動いていれば、転送層の失敗として状態機械に渡します。クライアントトランザクションは終わって TU に失敗を伝え（17.1.4）、要求は RFC 3263 4.3 に従って、新しいブランチで次の宛先に送り直されます（`nexttarget.go`）。トランザクションが先に終わっていたら、ログに残すだけです。TCP で動く非 INVITE のサーバートランザクションは、最終応答を転送層に渡すとすぐに終わるので、応答を送れなかったときはたいていこちらになります。
- 待ち行列で待つあいだにクライアントトランザクションが終わった要求は、送らずに捨て、そのための接続も開きません。応答が来ていないので、タイマー B か F が切れて、要求はもう次の宛先に送り直されているかもしれないためです。送ると、最初の宛先が、次の宛先より遅れて同じ要求を受け取ります。300〜699 の応答への ACK は、TCP ではトランザクションが ACK と同時に終わるので、捨てずに送ります。
- 接続を開けなかったときは、その相手の待ち行列にあるメッセージを、すべて同じ失敗で終わらせます。どれも同じ接続を待っているので、1 つずつ接続を試すと、溜まった数だけ 2 秒ずつ待つことになるためです。
- 応答は、要求の来た接続が開いていればその接続で返し、閉じていれば Via の示すアドレスへ新しい接続で送ります（RFC 3261 18.2.2）。接続が開いているかは、ループが応答を渡したときに確かめ、書き込む番が来たときにもう一度確かめます。待ち行列で待つあいだに接続が閉じても、応答は Via の示すアドレスへ届きます。その接続への書き込みに失敗したときも、応答は同じアドレスへ送り直します。
- 書き込みに失敗した接続は、その場で接続の表から外します。表に残すと、続くメッセージがその接続に書いてすぐ失敗し、新しい接続を開かないためです。ログと観測（ラボの HEP のキャプチャ）には、書き込みに成功したメッセージだけを、送ったものとして残します。UDP も同じです。実際には送られなかったメッセージを、送ったように見せないためです。記録には、書き込みを始めた時刻を付けます（`sip.Capture` の `Time`、ログの `wire_time`）。書き込みが終わってから記録するので、そのあいだに届いた応答のほうが先に記録されることがあります。順番を表すのは記録の順ではなくこの時刻で、HEP の時刻もこれにします。
- 要求を送る前に、呼び出し元の goroutine で接続を開いておく作り（`Stack.prepare`）は残します。接続を拒む宛先を、トランザクションを始める前に飛ばして次の宛先へ進むため（RFC 3263 4.3）と、1300 バイトを超える要求を TCP と UDP のどちらで送るかを、Via に書く前に決めるため（RFC 3261 18.1.1）です。ループを待たせないための作りではありません。開いた接続が、要求を書くまでに閉じたときは、書き込む goroutine が開き直します。
- `prepare` の接続と、公開の同期の送信（`TransportLayer.SendRequest` と `SendResponse`）は、これまでどおり呼び出し元の goroutine で待ちます。同期の送信を使うのは、2xx への ACK とステートレスに転送する CANCEL（`Stack.SendACK` と `SendCANCEL`）です。待つのは TU の goroutine で、ループではありません。
- 1300 バイトを超える要求を UDP で送るのは、`prepare` で TCP の接続を開けなかったときだけです（RFC 3261 18.1.1）。待ち行列に入れたあとで接続や書き込みに失敗した要求は、UDP で送り直さず、転送層の失敗として次の宛先へ進みます。Via にはもう TCP と書いてあり、送り直すには新しいブランチの要求が要るためです。
- 転送層を閉じるときは、すでに開いている接続を待つメッセージを書いてから、接続を閉じます。ループが閉じる前に渡したメッセージは、ループが自分で書いていたときと同じく相手に届きます。ただし、書き込みを待つのは、すべての相手を合わせて、閉じ始めてから書き込みの期限 1 回分の 2 秒までです。その時刻までに終わらない書き込みは失敗し、その接続は表から外れるので、残りのメッセージは新しい接続が要り、失敗で終わります。少しずつしか読まない相手がいても、待ち行列の 512 個を 2 秒ずつ待つことはありません。開いている途中の接続は取りやめるので、新しい接続の要るメッセージも失敗で終わります。

## re-INVITE の信頼できる暫定応答

SIP のスタックは re-INVITE でも、最初の INVITE と同じく RFC 3262 に従います。re-INVITE を送る側（UAC）は次のように動きます。

- 信頼できる暫定応答（`Require: 100rel` と `RSeq` のある 101〜199 の応答）に、ダイアログの中で PRACK を返します（RFC 3262 4）。再送は捨て、RSeq が 1 つ飛んだものは扱いません。
- RSeq は INVITE のトランザクションごとに数えます（RFC 3262 3）。次の re-INVITE の最初の RSeq は前の re-INVITE の最後の RSeq より小さいことがあるので、`CallDialog` は RSeq を INVITE の CSeq の番号ごとに持ちます。
- SDP のある最初の信頼できる暫定応答が、re-INVITE のオファーへのアンサーです。オファーの無い re-INVITE では、それがオファーで、アンサーは PRACK で返します（RFC 3262 5）。そのあとの 2xx の SDP は数えません（RFC 3261 13.2.1）。信頼できない暫定応答の SDP は、アンサーとして扱いません。
- 信頼できる暫定応答に Contact があれば、それをダイアログの相手の宛先にします（RFC 6141 4.7）。信頼できない暫定応答では宛先を変えません。
- PRACK への応答が 481 か 408 だったとき、または応答が無かったときは、確立したダイアログを、ほかの要求のときと同じく BYE で終えます（RFC 3261 12.2.1.2）。

### 選んだ理由

ダイアログの中の要求はどれも Supported に 100rel を挙げます。プリコンディションを使った UE は re-INVITE の Supported にも 100rel を入れます（TS 24.229 5.1.4A.1 c)）。SDP にプリコンディションを入れる UA は、Supported に 100rel を入れなければなりません（RFC 3312 11）。そして Supported に 100rel を挙げた UAC は、信頼できる暫定応答に PRACK を返さなければなりません（RFC 3262 4）。

| 形 | 採らなかった理由、採った理由 |
| --- | --- |
| re-INVITE の Supported から 100rel を外す | キャプチャに出る re-INVITE が、実際の UE のものと違う形になります。手順を省くのではなく、違う動きに変えることになるので採りません。 |
| PRACK を返さないことを `SIMPLIFIED:` に書く | RFC 3262 4 の MUST は省けないので採りません。PRACK が無いと、UAS は暫定応答を送り直し続け、SDP のある暫定応答のあとは 2xx を返せません（RFC 3262 3）。 |
| スタックで RFC 3262 に従う（採った形） | 最初の INVITE の UAC と同じ手順を、同じ関数（`reliableInOrder`、`newPRACK`、`autoPRACK`）で踏みます。 |

信頼できる暫定応答を送るかどうかは、UAS が選べます（RFC 3262 3）。re-INVITE にすぐ 200 で答える UE と MRFC は手順を省いていないので、`SIMPLIFIED:` の注記は要りません。

### 利用者に渡す口

`ReInvite` は暫定応答を利用者に見せず、最終応答だけを返します。暫定応答を受け取る利用者は、`ReInviteWith` に `ReInvitation` を渡します。

- `OnProvisional` は、スタックが受け取った暫定応答を、届いた順に 1 つずつ受け取ります。再送と、順番の外れたものは渡しません。UE は保留の re-INVITE で、ここからアンサーを読みます。
- `ManualPRACK` は、信頼できる暫定応答への PRACK を利用者に任せます。利用者は `CallDialog.PRACK` で、本文を付けて送ります。オファーのある暫定応答への PRACK は、`ManualPRACK` が無くても利用者が送ります。アンサーを持つのは利用者だけだからです。

B2BUA が re-INVITE の暫定応答を中継するときは、この 2 つを使います。`OnProvisional` で受けた暫定応答をもう一方のレグに渡し、そのレグから届いた PRACK の本文で `CallDialog.PRACK` を呼びます。もう一方のレグに信頼できる暫定応答を送るには、re-INVITE を受けた側（UAS）が暫定応答を返す口が、`InDialogRequest` に要ります。

## 呼処理のノードを Go にした理由

同じ処理（SIP の解析と 401 の生成、Diameter の CER/CEA と DWR/DWA、Cx の MAR）を Go と Rust で試作して比べました。

| 観点 | Go | Rust |
| --- | --- | --- |
| SIP の手書きのパーサー | 約 160 行。サンプルを往復できた。 | 約 190 行。サンプルを往復できた。 |
| Diameter のライブラリ | go-diameter v4.6.0。独自の XML 辞書で Cx を追加できた。 | diameter 0.7.1。アプリケーションとコマンドが閉じた enum で、Cx にはフォークが必要。サーバーから要求を送れない。 |
| 辞書に無い AVP | 扱える | メッセージ全体のデコードに失敗する |
| イメージの大きさ | 3.6 MB（圧縮後） | 31.9 MB（圧縮後） |
| 学習者が読むときの負担 | 非同期と所有権の概念が無い。要求と応答の区別は型ではなく約束で守る。 | enum と match で状態を表せる。非同期（tokio）とトレイト境界の理解が必要。 |

決め手は Diameter です。Cx と Sh は IMS の中心なので、ライブラリをフォークして保守し続ける負担は避けます。性能は要件の性能の目安の規模（[requirements.md](../requirements.md)）では差になりません。

試作のコードは捨てるもので、比べた結果をこの表に記録したあとで削除しました。

## メディア中継ノードも Go にした理由

メディアの制御はノードのあいだの API で分けてあるので（[media-control.md](media-control.md)）、ノードごとに言語を選べます。メディア中継ノードについても、同じ機能（2 つの UDP ポートの確保、双方向の中継、最初のパケットの送信元へのラッチング、HTTP の制御 API）を両方の言語で試作して比べました。負荷は要件の性能の目安の規模で、10 セッション、各方向 50 パケット/秒、172 バイト、30 秒を 3 回流しました。

| 観点 | Go | Rust |
| --- | --- | --- |
| 行数（空行とコメントを除く） | 115 | 111 |
| 外部の依存 | なし（標準ライブラリ） | tiny_http と 4 つのクレート |
| イメージの大きさ（圧縮後） | 6.70 MB | 4.25 MB |
| 1 回のビルドが残すビルドキャッシュ | 497 MB | 1.41 GB |
| 失ったパケット | 3 回とも 0 / 30000 | 3 回とも 0 / 30000 |
| 中継の遅延の中央値 | 約 370 µs | 約 125 µs |
| 遅延の 99 パーセンタイル | 0.8〜2.6 ms | 0.5〜2.0 ms |
| CPU とメモリ | 1 コアの約 9%、5〜9 MiB | 約 3.5%、0.5〜2.4 MiB |
| 読むときに必要な概念 | goroutine と mutex | 所有権、Arc、Mutex、AtomicBool。ブロック中のソケットを別スレッドから閉じられないための工夫 |

Rust のほうが軽く速いのですが、どちらもパケットを落とさず、遅延の中央値は 20 ms のパケット間隔の 2% 未満でした。この規模では性能は決め手になりません。

決め手は次の 2 つです。

- ツールチェーンが 1 つで済みます。Rust を加えると、CI、整形と静的検査、手順書、後始末がすべて 2 言語分になります。
- 学習者が読むときの負担が小さく、同じ `ims` コマンドの役割にできます。1 つのイメージが設定で役割を切り替え、C-Plane と U-Plane を同じコンテナにまとめる構成も、分ける構成も、設定だけで選べます。

試作のコードは捨てるもので、結果をこの表に記録したあとで削除しました。
