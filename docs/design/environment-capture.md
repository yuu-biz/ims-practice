# 動かす環境とキャプチャ

この記録はホストとコンテナのあいだの通信と、信号のキャプチャの取り方の設計です。

## 選んだこと

- ホストとコンテナのあいだの通信は、NAT を通る前提で作ります。SIP は RFC 3581 の `rport` に対応し、応答を実際の送信元へ返します。メディア中継ノードは最初に届いた RTP の送信元へ返送します（RFC 4961 の対称 RTP を前提にしたラッチング）。
- キャプチャはブリッジ全体を 1 つのコンテナで取ります。

## NAT を前提にする理由

Windows の Docker Desktop で試作して確かめました。

- ホストから、公開したポート（`ports: "40000:40000/udp"`）へ UDP を送ると、コンテナに届きます。コンテナから見た送信元は、ブリッジのゲートウェイ（試作では `172.30.0.1`）で、ポート番号も変わります。
- コンテナから `host.docker.internal` へ UDP を送ると、ホストに届きます。ホストから見た送信元は `127.0.0.1` で、ポート番号も変わります。

つまり、ホスト上のソフトフォンが SDP に書くアドレスとポートは、コンテナから見た実際の送信元と一致しません。そのため、上の 2 つに対応します。

実網の P-CSCF と IMS-AGW も、NAT 越しの端末のために同じ処理をします。この処理は学習の題材としても扱います。

## キャプチャの取り方

Docker Compose のネットワークに、`com.docker.network.bridge.name` でブリッジ名（たとえば `ims0`）を付けます。`network_mode: host` で動かす tcpdump のコンテナが、このブリッジのすべての通信を 1 つの pcap に書きます。試作では、コンテナ間の通信も、ホストとの間の通信も記録できました。

ホストの Wireshark で見る方法は 2 つあります。

- pcap ファイルをホストのフォルダに書き出して開く。
- `docker compose exec -T <キャプチャのコンテナ> tcpdump -i ims0 -U -w -` の出力を、ホストの Wireshark（`-k -i -`）に渡してライブで見る。Git Bash からホストの `tshark.exe` に渡せることを確かめました。

`network_mode: host` を使うのはキャプチャのコンテナだけです。IMS のノードには使いません。IMS のノードはホスト固有のネットワーク設定に依存しないようにするためです（[requirements.md](../requirements.md)）。Kubernetes では別の方法が要ります（`deploy/k8s/capture/`）。
