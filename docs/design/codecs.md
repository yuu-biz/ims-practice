# コーデック

この記録は音声コーデックの選び方と、AMR と AMR-WB の扱いの設計です。

## 選んだこと

- UE と網の音声コーデックは GSMA IR.92（VoLTE）と NG.114（VoNR）の必須の要件に従います。
- 音声通話は G.711 μ-law（PCMU、ペイロードタイプ 0）から始めました。
- AMR と AMR-WB に対応し、RFC 4867 のペイロード形式（bandwidth-efficient と octet-aligned）を扱います。AMR と AMR-WB は符号化済みのフレームを使います。製品は cgo を使いません。
- G.711 は残します。
- 通話の音声は、学習者が自分の機械に入れた再生ソフトで聞きます。UE は受け取ったものをその再生ソフトに渡すだけで、製品にも、このリポジトリが配るものにも、復号器は入れません。
- UE の offer のコーデックは AMR-WB、AMR、PCMU、telephone-event の順にします。
- EVS は EVS のコーデックを用意したときに offer に加えます。それまでは、NR のアクセスで使う offer（`sdp.VoNRCodecs`）も VoLTE の offer と同じにし、EVS を入れません。

## IR.92 と NG.114 に従う理由と、その中身

IR.92 は G.711 に触れておらず、端末には AMR と AMR-WB を求めています。NG.114 はこれに加えて EVS を求めています（[profiles.md](../background/profiles.md)）。

G.711 を残すのは、国内の網間接続の標準（JJ-90.30）が、移動網どうし以外の接続で G.711 を求めているためです。G.711 は Wireshark の RTP Player でそのまま再生できます。

今の選択は G.711 から始めて、IR.92 の必須の AMR と AMR-WB を加えた形です。EVS の扱いが決まったら、この選択に EVS が加わります（[requirements.md](../requirements.md) の未決事項）。

## AMR と AMR-WB は符号化済みのフレームで運ぶ

RFC 4867 5 章の格納形式で、符号化済みのフレームを用意します。UE は Go だけで書いたパケット化と復元で、フレームを RTP に載せます（bandwidth-efficient と octet-aligned、CMR、ToC）。製品は CGO_ENABLED=0 のままで、中継ノードは AMR と AMR-WB の符号化も復号もしません。

フレームを作る道具は cgo で opencore-amr と vo-amrwbenc（Apache-2.0）を使います。この道具はビルドタグで製品のビルドから外します。送ったフレームと受けたフレームをビットで比べられます。

CMR に応じたモードの切り替えを省くときは、`SIMPLIFIED:` に書きます。

採らなかった案は opencore-amr と vo-amrwbenc を cgo で製品に組み込む形です。この 2 つのライブラリは、フレームを作る道具だけが使います。

製品が AMR を復号しないので、MRFP は AMR の音声を混ぜられません。MRFP の扱いは [mmtel-mrf.md](mmtel-mrf.md) にあります。

- opencore-amr と vo-amrwbenc のライセンスは Apache-2.0 です。Apache-2.0 の特許の許諾は、提供者が持つ請求項のうち、その提供物が必ず侵害するものだけを対象にします（[Apache License 2.0 の 3 条](https://www.apache.org/licenses/LICENSE-2.0.txt)）。ほかの権利者の標準必須特許は入りません。

- ETSI の [IPR のデータベース](https://ipr.etsi.org/)で、AMR と AMR-WB の仕様（TS 26.071、26.073、26.090 から 26.094、26.104、26.171、26.173、26.190 から 26.194、26.204）に宣言された特許を探しました。これらの仕様を挙げた開示は 580 件ありました。宣言した会社は、Qualcomm、Nokia、Ericsson、NEC、VoiceAge、Orange、Samsung、InterDigital などです。ETSI は、宣言された権利が本当に必須かどうかを保証しないと書いています。そのため、宣言にはコーデックと関わりの薄い題名の特許（ビームフォーミングなど）も含まれています。

  - AMR-NB の音声の符号化の本体（TS 26.090）に宣言されたものに、存続の表示はありませんでした。いちばん遅い満了は 2020 年でした。

読み取れなかったこと。

- AMR-NB の特許の満了。VoiceAge の標準ごとの表に AMR-NB の列は無い一方で、ライセンスの一覧には AMR-NB のプログラムが載っています。どちらのページにも、プログラムを終えたとも続けているとも書いていません。
- 復号を符号化と別に扱うかどうか。権利者の公開資料に、復号だけの実装を別に扱うという記述は見つかりませんでした。二次資料には、パーソナルコンピュータ向けの製品（メディアプレーヤーなど）の復号器は無償だという記述があります。一次資料で確かめられなかったので、根拠には使いません。

## 通話の音声は、学習者の再生ソフトがその場で復号する

信号と RTP は AMR と AMR-WB のままにします。音声を音にするのは、学習者が自分の機械に入れた再生ソフトです。守ることを先に書きます。

- FFmpeg も、ほかの AMR の復号器も、同梱しません。配布物に入れず、ビルドでも実行でも取得しません。
- 復号は学習者の機械でだけ行います。サーバー、コンテナ、ブラウザの中では復号しません。
- `-play` は、学習者が自分で入れた `ffplay` を探し、別のプロセスとして動かすだけです（`os/exec`、シェルは通しません）。`-player` で渡せるのは `ffplay` か、ffplay と同じ指定を受け取れるプログラムです。通話を始める前に探すので、無いパスを渡したことはその場で分かります。見つからなければ再生をあきらめ、入手先を 1 度伝えて、通話はそのまま続けます。
- 通話は再生ソフトを待ちません。`-play` は 1 秒ぶん（50 パケット）の待ち行列を持ち、再生ソフトがそこから取らなくなったら、入らなくなったパケットを捨てて 1 度伝えます。RTP の受信も、通話の終わりも、再生ソフトの書き込みでは止まりません。通話の終わりに待つのは再生ソフトが終わるまでで、それも 10 秒までです。
- `-received-out -` で標準出力に流すときは、SIGPIPE を無視します。パイプの先の再生ソフトを閉じても、書き込みが EPIPE で失敗するだけで、UE は通話を最後まで続けます。標準出力と再生ソフトの両方に流しているときは、片方が終わってももう片方は鳴り続けます。

UE が音声を渡す先は 3 つです。`-play` は、通話のコーデックに合った指定で `ffplay` を起動し、受け取ったものをパケットごとに書き込みます。`-received-out -` は、同じものを標準出力に流すので、コンテナの中の UE の音声をパイプで手元の再生ソフトに渡せます。`-` の代わりにパスを渡したときは、これまでどおり通話の終わりにファイルを書きます。手順書にはこの 3 つを書きました（[volte.md](../guide/en/volte.md)、[volte.md](../guide/ja/volte.md)）。

`-play` はコンテナの中では役に立ちません。音を出す装置が無いので、`ffplay` は自分のエラーを書いて終わります。そのエラーはそのまま学習者に見えます。UE は再生ソフトの終了に気づいた時点で、残りは鳴らさないと 1 度伝え、通話は続けます。`ue serve` に `-play` を付けないのも同じ理由です。この UE はコンテナの中で動きます。

ストリームは、まだ聞ける分だけを運びます。場所がパイプに流れたあとで届いたフレームは、ストリームには入りません。通話の終わりに書くファイルには、その場所に入ります（`amr.Recorder` は 1 つの場所について良いほうのフレームを残します）。

受け取れなかったフレームは、どちらでも NO_DATA として格納し、録音の時間の進みを保ちます（RFC 4867 5.3）。FFmpeg 6.1.1 では、AMR-WB の復号器は NO_DATA を無音にし、1 秒のファイルは 1 秒のまま復号できました。AMR（狭帯域）の復号器は NO_DATA のフレームごとに invalid data を出して読み飛ばすので、50 フレームのうち 10 を NO_DATA にしたファイルは 0.8 秒になりました。AMR-WB の SPEECH_LOST（フレーム種別 14）は invalid mode になります。この実装は受け取れなかったフレームに NO_DATA を使い、VoLTE の通話は AMR-WB で成立するので、手順書の手順はこの 2 つに当たりません。

1 つの通話には標準出力が 1 つなので、標準出力に流せるのは `-received-out` だけです。`-sent-out` と `-wav-out` はファイルに書きます。標準出力に音声を流すあいだ、UE の JSON のログは標準エラー出力に移ります。パイプに音声以外のものを混ぜないためです。ログを標準出力から読んでいるスクリプトがあるので、ほかの実行では標準出力のままにします。

採らなかった案。

- cgo で製品に復号器を入れ、AMR の通話でも `-wav-out` を書く。製品の CGO_ENABLED=0 を崩し、このリポジトリが配るものに復号器を入れることになります。
- フレームを作る道具と同じビルドタグで、復号して WAV にする道具を足す。学習者に Go と C のライブラリの用意を求めることになり、手元の再生ソフトを使うより手間が増えます。音声を聞くためだけに、製品の外の道具を増やすことにもなります。
- 通話全体を、特許の扱いがはっきりしているコーデックで成立させる。IR.92 は端末に AMR と AMR-WB を求めているので、VoLTE の通話のコーデックを変えると、実際の網の動きから離れます。SDP が選んだものと違うコーデックを RTP で運ぶのも同じです。聞くことだけが目的なら、PCMU の通話で聞けます。

## ライセンスと特許を分けて考える

ソフトウェアのライセンスと特許は別のものです。Apache-2.0 の特許の許諾は、提供者が持つ請求項のうち、その提供物が必ず侵害するものだけを対象にします（[Apache License 2.0 の 3 条](https://www.apache.org/licenses/LICENSE-2.0.txt)）。LGPL も同じように、著作権と、そのコードを書いた人の特許の話です。どちらも、ほかの権利者が持つ標準必須特許には触れません。

特許は、その手順そのものを対象にします。VoiceAge は、標準を実装する製品を作る会社、売る会社、配る会社に対してポートフォリオをライセンスすると書いています（[IPR の概要](https://voiceage.com/Overview.html)）。コードをだれが独立に書いたかは、この書き方に入っていません。FFmpeg が自分で書いた復号器についても、はっきりしているのはソフトウェアのライセンスが LGPL-2.1 以降だということだけです。生きている特許があるかどうかは、上の節のとおり、公開されている資料では確かめきれません。

FFmpeg 自身も、特許については分からないと書いています。Patent Mini-FAQ には、自分たちは弁護士ではないので答える立場にないこと、FFmpeg を書くために特許を読んだことはないこと、私的な利用者が自分のために使う分には心配する理由はほとんど無いこと、金銭を得ようとすると権利者が出てくること（MPEG に関わる技術については MPEG LA の取り立てが熱心であること）が書いてあります（[legal.html](https://ffmpeg.org/legal.html)）。AMR と AMR-WB の復号は FFmpeg が自前で持っているので、OpenCORE のライブラリを足す必要はありません。FFmpeg の復号器の文書には、AMR-NB と AMR-WB のどちらについても、native な復号器があるからこのライブラリ無しで復号できると書いてあります（[ffmpeg-codecs.html](https://ffmpeg.org/ffmpeg-codecs.html)）。

そこでこのリポジトリは、復号器を配りません。配るのは、符号化済みのフレームと、そのフレームを RTP と格納形式で運ぶコードだけです。復号は、学習者が自分で選んで入れたソフトが、自分の機械で行います。

気をつけること。

- AMR に関わる特許がすべて満了したことは、公開されている資料では確かめられていません。
- 非営利のオープンソースだからといって、特許の対象から外れるわけではありません。
- FFmpeg を同梱しないことは、このリポジトリが配るものから復号器を外すだけです。だれも侵害しないことを保証するものではありません。
- FFmpeg のライセンス（LGPL と GPL）と、コーデックの特許は別の問題です。片方が片方の答えになりません。
- FFmpeg を同梱する、復号器を組み込む、商用で提供する、のどれかをするときは、この判断をやり直します。

## EVS を送れるまで、EVS を offer しない

UE は EVS の符号器を持たないので、送れるのは AMR-WB と AMR のフレームです。EVS のペイロードタイプを offer すると、EVS Primary のビットレートと帯域を示すことになります。EVS を offer する端末は、ビットレートの全範囲を扱える必要があります（TS 26.114 6.2.2.2 の Table 6.2a）。端末は最初の offer に `evs-mode-switch` を書けないので（同じ表）、AMR-WB IO だけで送ることも offer では示せません。AMR-WB IO しか送れない UE には、事実に合う EVS の offer を作れません。

送れないレートと帯域を書いた SDP は、UE の能力を偽ります。仕様に合う端末はそういう offer をしません。このプロジェクトは実際の網で起きない動きを選ばないので（[AGENTS.md](../../AGENTS.md)）、NR のアクセスで使う offer にも EVS を入れず、AMR-WB と AMR で通話します。EVS を含む offer を受けたときは、UE は持っていない EVS を断り、AMR-WB を選びます。answer の m= 行には offer にあるコーデックのうち、answer の側が送りも受けもできるものを書きます（RFC 3264 6.1）。端末は RFC 4867 と TS 26.445 のペイロード形式のオプションをすべて使えなくてもかまいませんが、どれも正しく受け入れるか断れる必要があります（TS 26.114 6.2.2.3 の最初の段落）。EVS を断って AMR-WB と AMR が残れば、AMR-WB を選びます（同じ節の Table 6.3）。

TS 26.114 5.2.1.1 は端末に超広帯域の音声を求め、超広帯域には EVS が要ります。NG.114 は VoNR の UE に EVS を求めています。この 2 つを満たさないことは、`internal/sdp` の `VoNRCodecs` に `SIMPLIFIED:` で書きました。

採らなかった案は、SDP では EVS を offer し、中身は AMR-WB のフレームを EVS AMR-WB IO として運ぶ形です（[5gc.md](../background/5gc.md) の 7 章の案 B）。上のとおり、SDP が UE の能力を偽ることになります。

## UE の offer の順

AMR-WB、AMR、PCMU、telephone-event の順にします。NR のアクセスで使う offer も同じ順です。PCMU を残すのは、PCMU だけのソフトフォンと話すためと、国内の網間接続（JJ-90.30）が G.711 を求めるためです。その分、b=AS と、PCRF に求める帯域は PCMU に合わせて大きくなります。
