# HSS のプロビジョニング API

この記録は、HSS が持つ加入者のプロビジョニングの API を決めます。1 件ずつの操作、ページに分けた一覧、一括の登録、書き出しと読み戻し、試験用の利用者の印、サービスのプロファイルの選び方、収容の方針が対象です。OAM がこの API を使います。OAM 自体の作りは [lab-oam.md](lab-oam.md)、状態の置き場所とページに分けた一覧の仕組みは [state-redundancy.md](state-redundancy.md)、調査は [oam.md](../background/oam.md) の 7 章から 9 章にあります。

この API を標準の形に寄せるかどうかは [provisioning-northbound.md](provisioning-northbound.md) が決めています。標準の加入者の管理（SuM）には OSS に面する Itf-N がありますが、その情報モデルに長期の鍵、OPc、SIP Digest のパスワードを入れる項目が無いので、この独自の API のままにしています。その記録は、ここで足す `test_user`、`service_profile`、`repository_data` にも当たる項目が無いことまで確かめているので、この記録の中身は標準の調査によって変わりません。

## 選んだこと

- API は HSS の側で 1 つに決めます。OAM は HSS が持つ口に合わせ、HSS が持たない口を当てにしません。取りかかる前の OAM は、`PUT` と `PATCH`、書き出し、`test_user` と `service_profile` の項目、`hss.service_profiles` と `hss.admission` の設定を当てにしていて、それらを持つのは OAM の試験の中の偽の HSS だけでした。
- 1 件の操作は HSS の HTTP の API に置きます。`GET`（一覧と 1 件）、`POST`（追加）、`PUT`（作成か置き換え）、`PATCH`（印とプロファイルの名前だけ）、`DELETE` です。
- 一括の登録は OAM が受け持ちます。HSS に一括の口は足しません。OAM が 1 行を 1 回の `PUT` にして送ります。
- 書き出しは `GET /subscriptions/export` です。1 行に 1 件の JSON で、資格情報、SQN_HE、Sh の Repository Data を含みます。
- ページの分け方は API の全体で 1 つにします。`after` と `limit` で位置と件数を受け取り、続きがあるときだけ `Link` ヘッダの `rel="next"` で返します。一覧も書き出しも同じ決まりです。
- 試験用の利用者の印（`test_user`）とサービスのプロファイルの名前（`service_profile`）を、加入者のデータの項目にします。判定はその加入者のデータを引いたときに行うので、索引も全件の走査も増えません。
- サービスのプロファイルは、設定 `hss.service_profiles` で名前を付けて定義します。SAA の User-Data には、選んだプロファイルの iFC を入れます。プロファイルの名前は Cx に出ません。
- 収容の方針（`hss.admission`）は HSS の設定の項目にし、保守用の API で動かしたまま変えられる項目にします。断るのは UAR で、UAA に DIAMETER_AUTHORIZATION_REJECTED を入れます。
- 動かしたまま変えられる 3 つの設定は、加入者と同じ保存先に、それを決めた変更の世代と一緒に置きます。HSS の各台はその値で答え、作り直した台も、最初の要求に答える前に保存先から読みます。設定を変えたときの push も保存先に置き、ページごとに 1 台が受け持ちます（下の「設定を台のあいだで分ける」）。

## API

本文と答えは JSON です。誤りは `http.Error` の文のままで、OAM がそれを読んで理由にします。加入者を読み書きできなかった要求には 500 を返します（[state-redundancy.md](state-redundancy.md) の「Store の形と書き込みの決まり」）。経路にない方法には、`http.ServeMux` が `Allow` を付けた 405 を返します。経路、本文、答えの形は `internal/hss/openapi.yaml` に OpenAPI 3.1 で書き、試験でハンドラーと突き合わせます（[openapi.md](openapi.md)）。下の表はその要約です。

| メソッドと経路 | 本文 | 答え | 状態コード |
| --- | --- | --- | --- |
| `GET /subscriptions?after={IMPI}&limit={n}` | なし | 加入の配列（資格情報を含まない）。続きがあれば `Link` | 200、400（`limit` の形）、500 |
| `GET /subscriptions/{IMPI}` | なし | 加入 1 件 | 200、404、500 |
| `POST /subscriptions` | 加入の要求 | 加入 1 件と `Location` | 201、400、409（識別子が別の加入のもの）、500 |
| `PUT /subscriptions/{IMPI}`（`?dry_run=true` を付けられる） | 加入の要求に `repository_data`、`test_user`、`service_profile` を足したもの | `{"result": "created" \| "updated" \| "unchanged", "subscription": {…}}` | 201（作ったとき）、200（置き換え、変化なし、`dry_run`）、400、404（置き換えのあいだに加入が消えた）、409、500 |
| `PATCH /subscriptions/{IMPI}` | `{"test_user": true, "service_profile": "trial"}`。どちらも省ける | 加入 1 件 | 200、400、404、500 |
| `DELETE /subscriptions/{IMPI}` | なし | なし | 204、404、500 |
| `GET /subscriptions/export?after={IMPI}&limit={n}` | なし | 1 行に 1 件の JSON（`application/x-ndjson`）。資格情報、SQN_HE、Repository Data を含む。続きがあれば `Link` | 200、400、500 |
| `PUT /subscriptions/{IMPI}/customized-alerting-tone` | CAT | CAT | 200、400、404、500 |

- `PUT` は置き換えです。項目ごとの更新ではありません。本文に書かれていない加入者のデータは消えます。`repository_data`、`mmtel_services`、`ut_password` を 3 つとも省いた `PUT` は、`POST` と同じく、設定の既定の MMTelServices だけを入れます。利用者が Ut で変えた付加サービスの設定は、そのような `PUT` で設定の既定に戻ります。書庫を戻す操作を「書いてあるとおりにする」にするためです。`repository_data` に空の配列を書くのは、項目を省くこととは違い、Repository Data を 1 つも持たない加入を求めることです。
- `repository_data` と、`mmtel_services`、`ut_password`、`customized_alerting_tone` のどれかを一緒に書いた要求は、400 で断ります。同じものを 2 通りに書いた要求なので、片方を黙って捨てません。
- `repository_data` は、`POST` と `PUT` が共有する要求の型の項目です。検査と変換を 1 つの関数で共有するので、`POST` でも書けます。
- Repository Data を消してから、同じ Service-Indication をあとでまた足すと、その順序番号は新しいデータの値から始まり直します。順序番号はその項目が受けた更新の回数で、項目と一緒に消えるものなので、消した項目の番号を覚えておく仕組みは作りません。Sh で読んでいる AS は、読み直した番号から更新します。この振る舞いに条項は付けません。順序番号の扱いを定める条項の本文を、この作業の環境では確かめられなかったためです。
- OAM が HSS に送る本文の `repository_data` には `omitempty` が付いているので、Go の値からは空の配列を送れません。長さ 0 の配列は項目ごと消え、HSS は「書かなかった」ものとして設定の既定の MMTelServices を入れます。一括の登録のファイルに空の配列を書いても、OAM を通ると同じことが起きます。Repository Data を 1 つも持たない加入を書き戻せるようにするので、書き出しと読み戻しを作るときに、`internal/oam` の `hssSubscriptionRequest` と `SubscriptionRecord` のこの項目から `omitempty` を外します。
- `PUT` が残すのは、動いているあいだの状態です。登録の状態、S-CSCF の名前とその Diameter の識別子、認証の途中の印、IP-SM-GW の番号とその Diameter の識別子、届けられずに待っている短いメッセージの記録（MWD、UNRI、MCEF）、SQN_HE は、置き換えても変わりません。`aka.sqn` を読むのは、新しい加入者を作るときだけです。短いメッセージの記録は、この記録を書いたあとに S6c の作業が足した項目で、同じく動いているあいだの状態なので残します。
- `unchanged` は、置き換えても加入者のデータが変わらないことです。資格情報と Repository Data も比べます。比べないのは、上の行で残すものです。OAM は資格情報を読み戻せないので、同じかどうかを言えるのは HSS だけです。
- `PATCH` があるのは、資格情報を知らずに印とプロファイルの名前だけを変えるためです。HSS は資格情報を返しません（TS 29.228 Table 6.3.5、Table 6.3.7）。`PUT` で印だけを変えるには、持っていない資格情報を書く必要があります。
- `dry_run` を付けた `PUT` は、何も変えずに同じ答えを返します。作る加入の状態コードだけは、作っていないので 201 ではなく 200 です。公開の識別子が別の加入のものかどうかは、自分で確かめて 409 を返します。本物の要求はこれを `Store` の書き込みから受け取りますが、何も書かない要求は、同じ問いを識別子ごとの索引に投げて答えを得ます。`DELETE` の試しは、OAM が `GET` で加入の有無を見るので、HSS は何もしません。

### `PUT` が `Store` に書く順

1 件の操作は、どれもその加入者のロックの中で、その加入者のデータだけを書きます。`PUT` は、今の `Store` の操作では足りないので、`Store` に `Replace` を足します。`Put` は版を見ない書き込みで、呼ぶ側がロックを持つことを求め、保存されている AKA をそのまま残すので（`internal/hss/store.go` と `internal/kvstore/hssstore`）、資格情報と公開の識別子を書き換えられません。

- `PUT` は、その加入者のロックを取り、加入者を読み直し、置き換えるかどうかを決めてから `Replace` を呼び、ロックを放します。識別子が別の加入のものなら、加入を元に戻して 409 を返します。Repository Data は `Replace` のあと、同じロックの中で書きます。途中で保存先が落ちると、加入者のデータだけが変わって Repository Data が変わっていない状態になりますが、同じ `PUT` を送り直せば続きが終わります。
- `Replace` は、主の項目を先に書き、そのあとで公開の識別子の索引を書きます。`Add` と `Delete`（索引が先）とは逆の順です。どの識別子をどの加入のものとするかを決めるのは主の項目で、索引の項目は、そこが指す加入者がその識別子を持っていなければ、次の要求が取り上げてよいものだからです（`internal/kvstore/hssstore` の `claimPublic`）。索引を先に書くと、同じ識別子を足す 2 つの `PUT` が、互いに相手の主の項目をまだ書かれていないうちに読み、どちらも「その加入は持っていない」と見て索引を取り上げ、2 つの加入が同じ識別子を持ってしまいます。`Add` にこの問題が無いのは、最初に書く仮の記録が識別子を並べているからです。代わりに、索引を取っているあいだは主の項目がその識別子を持つので、その短いあいだに同じ識別子を足そうとした別の `PUT` は、あとで手放される識別子についても「取られている」と返されます。要らなくなった索引の項目は、主の項目より後に消します（[state-redundancy.md](state-redundancy.md) の「索引」）。索引を取れなかったときは、主の項目を読み直した上で元の加入に戻し、この `PUT` が取った索引の項目を消します。
- `Replace` は、その加入者のデータをまるごと書きますが、SQN_HE だけは保存されている値を残します。`Put` が保存されている AKA を残すのと同じ理由です。SQN_HE を動かすのは `CompareAndSwapSQN` だけ、という決まりを `Store` の全体で保てます。
- 置き換えの前に今の Repository Data を読む必要があるので、`Store` に `AllRepositoryData` も足します。本文に無い Service-Indication を消すには、消す値の順序番号が要るためです。加入者の記録は Repository Data を一緒に持っているので、1 件分をまるごと読む手間は、1 つの Service-Indication を読む手間と同じです。書き出しの `GET` も、同じ操作で 1 件分を読みます。
- Repository Data は、`CompareAndSwapRepositoryData` で Service-Indication ごとに書きます。`Replace` には入れません。Sh の PUR はロックを取ってから比べて入れ替え、CAT の `PUT` はロックを取らずに比べて入れ替えるので（`internal/hss/provisioning.go` の `setCustomizedAlertingTone`）、版を見ずに書くと、どちらの更新も黙って消えます。書く値には、Sh の更新と同じく次の順序番号を与えます（TS 29.328 6.1.2.1）。入れ替えが負けたら、CAT の `PUT` と同じく読み直してやり直します。
- 加入者のロックを保存先に置く構成では、ロックの期限は 15 秒で、期限のあとに動き出した古い台の書き込みを止める仕組みがありません（[state-redundancy.md](state-redundancy.md)）。処理の途中で 15 秒より長く止まった台の `PUT` は、次の台の書き込みを上書きすることがあります。この制約は、その節が `SIMPLIFIED:` に書くとしたもので、`PUT` にもそのまま当てはまります。

## ページの分け方

- `after` は前のページが終わった IMPI、`limit` は返す件数です。`limit` を省くと 1000 件で、それより大きい値も 1000 件になります。`after` の加入者が消えていても、その次から返します。
- 続きのページがあるときだけ、`Link` ヘッダに次のページの問い合わせを入れます（RFC 8288 3）。最後のページの見分け方は、このヘッダの有無だけです。ちょうど `limit` 件のページには必ずヘッダが付くので、次のページが空になることがあります。
- 1 ページを読む手間は、加入者が 100 人でも 100 万人でも変わりません。保存先に置く実装は IMPI の並べ替えた索引を範囲で引き、`MemoryStore` は並んだ列を 2 分探索します（[state-redundancy.md](state-redundancy.md) の「並べ替えた索引」）。
- 書き出しも同じ `after`、`limit`、`Link` を使います。違うのは本文の形だけです。OAM は 1 行ずつ読んで書庫に書くので、ページの全体をメモリに持ちません。

## 一括の登録と書き出し

一括の登録は OAM の `POST /oam/v1/provisioning` です。HSS は 1 件ずつの `PUT` を受けます。

| 主題 | 作り |
| --- | --- |
| 形式 | 1 行に 1 件の JSON（JSON Lines）。項目は `PUT` の本文と同じです。`"delete": true` の行は削除で、ほかの項目を持ちません。削除は OAM が `DELETE` に直すので、この項目は HSS に送りません。 |
| 大きさの上限 | 1 行は 64 KiB です。HSS が受ける本文の上限と同じにします。行の数に上限は設けません。OAM は 1 行ずつ読み、同時に送るのは既定で 8 件までなので、使うメモリは行の数によりません。 |
| 不可分の単位 | 加入者 1 件です。1 回の `PUT` が、その加入者のロックの中で、その加入者のデータだけを書きます。複数の加入者にまたがる不可分な書き込みは作りません。保存先の 1 回の操作が 1 つのキーだけを触る決まり（[state-redundancy.md](state-redundancy.md)）に合わせるためです。 |
| 途中の誤り | 止めません。行ごとに結果（`created`、`updated`、`unchanged`、`deleted`、`rejected`、`failed`）と理由を返し、最後に集計を返します。`rejected` は送り直しても同じで、`failed` は送り直せば通るかもしれないものです。同じファイルを送り直すとすべて `unchanged` になるので、`failed` の行だけを直して送り直せます。 |
| 行の順 | 結果は行の順に返します。HSS に届く順は決まっていません。1 つのファイルは、1 つの加入を 1 回だけ書きます。 |
| 書き出しの中身 | `PUT` の本文と同じ項目に、`password`、`aka`（`k`、`opc`、`amf`、`sqn`）、`repository_data`、`test_user`、`service_profile` を含めます。Ut の資格情報は、HSS が H(A1) しか持たないので、`ut_password` ではなく `repository_data` の中の Ut-Credential として出ます。CAT も Repository Data なので一緒に出ます。 |
| 書き出しに入れないもの | 登録の状態と S-CSCF の名前です。戻すと S-CSCF が持つ登録と食い違います。戻した加入者は Not Registered で、利用者が登録し直します。 |
| 一貫性 | 書き出しのあいだ、全体のロックは取りません。1 件ごとには整合していて、全体には書き出しのあいだの変更が混じります。手順書に書きます。 |
| 書き出しの宛先 | 書き出しは、K、OPc、SIP Digest のパスワード、SQN_HE を、8081 番に届く相手なら誰にでも返します。プロビジョニングの待ち受けは内部の網だけに置き、ホストにもインターネットにも公開しません。Compose の `hss` のサービスはポートを 1 つも公開せず、同じ網の中の 172.28.0.10:8081 で届きます。公開しているのは、P-CSCF の 5060 番、中継ノードの RTP、学習用の画面の 8080 番で、どれも 127.0.0.1 に結び付けています。Kubernetes の `hss` の Service は `clusterIP: None` で、クラスタの中だけです。LoadBalancer の Service は P-CSCF の SIP と RTP のものだけです。手順書に書きます。 |
| SQN_HE | 書き出した値をそのまま戻します。古い SQN_HE で動き出すのは、消えた加入者を書庫から作り直したときだけです。加入者が残っていれば、`PUT` は持っている SQN_HE を残すためです。 |
| 古い SQN_HE | HSS が古い SQN_HE からベクタを作ると、UE が AUTS を返し、HSS が同期を取り直します（TS 33.102 6.3.5）。この様子はキャプチャで見られます。ただし、UE が配列の仕組みを使うときは、受け取った SQN は、その IND の要素に入っている番号より新しければ受け入れられます（TS 33.102 C.2.2）。全体でいちばん新しい番号より古くても受け入れられるので、作り直した加入者が必ず再同期を見せるとはかぎりません。この UE シミュレータも配列を持っています（`internal/aka/usim.go`）。 |

## 試験用の利用者の印と収容の方針

| 主題 | 作り |
| --- | --- |
| 印 | 加入者のデータの `test_user` です。設定のファイル、`POST`、`PUT`、`PATCH` で付けられます。`hss.Subscription` の項目なので、保存先に置く実装では加入者の記録が 1 項目増えるだけで、キーも索引も増えません。 |
| 方針の置き場所 | HSS の設定の `hss.admission`（`all` か `test_users`）です。保守用の API で動かしたまま変えられる項目にします（`maintenance.NewSetting`）。OAM が役割のすべての台に同じ世代で配り、変更を履歴に残し、前の値に戻せます。設定の変更を記録して前の設定に戻せることが要件にあるためです（[requirements.md](../requirements.md) の「運用と保守（OAM）」）。値と世代は、HSS の台が共有する保存先に置きます（下の「設定を台のあいだで分ける」）。 |
| 断る場所 | UAR です。方針が `test_users` で、加入者の `test_user` が false なら、UAA の Result-Code を DIAMETER_AUTHORIZATION_REJECTED にします。TS 29.228 6.1.1.1 の step 5 が、登録を認可されていない利用者にこの結果を求めています。この値は基本のプロトコルの Result-Code で、TS 29.229 6.2 にはありません（RFC 6733 7.1.5、`internal/cx/cx.go` と同じ）。I-CSCF は、否定の UAA に 403 を返します（TS 24.229 5.3.1.3。できています）。 |
| 断る範囲 | 登録と、登録の更新と、未登録の状態のサービスのための割り当てです。手順ごとの扱いは下の「収容を制限するあいだの振る舞い」にあります。 |
| 今のコード | `internal/hss/hss.go` の `userAuthorization` にある `SIMPLIFIED:`（6.1.1.1 の step 5。この HSS はすべての利用者の登録を通す）を、この検査に置き換えます。 |

### 収容を制限するあいだの振る舞い

方針を `test_users` にしたときと、`test_users` のあいだに加入者の `test_user` を外したときは、同じ扱いです。そのときに有効な登録はそのままにし、そのあとに届く要求から断ります。RTR は送りません。利用者は、登録の期限が切れたときに落ちます。期限は S-CSCF が持っているので、HSS が断っても、期限までの登録はそのまま動きます。

| 手順 | 収容の対象外の利用者への扱い | 理由 |
| --- | --- | --- |
| UAR（REGISTRATION か、User-Authorization-Type が無いもの） | 断る。Result-Code は DIAMETER_AUTHORIZATION_REJECTED | 6.1.1.1 の step 5 が、登録を認可されていない利用者にこの結果を求めています。最初の登録も登録の更新も、同じこの枝を通るので、同じ検査で断ります。 |
| UAR（REGISTRATION_AND_CAPABILITIES） | 断る。同じ結果 | step 5 の同じ枝です。I-CSCF が S-CSCF を選ぶ前に断ります。 |
| UAR（DE_REGISTRATION） | 通す | step 5 はこの枝で登録の認可を確かめません。断ると、利用者が登録を終えられず、S-CSCF と P-CSCF に登録が残ります。 |
| LIR | 通す | 6.1.4.1 の step 3 が、登録している識別子に S-CSCF の名前を返します。期限までの登録への着信が、収容の方針で切れないようにします。 |
| SAR（REGISTRATION、RE_REGISTRATION） | 届かない | その前の UAR を断るので、S-CSCF がこの SAR を送りません。 |
| SAR（UNREGISTERED_USER） | 断る。Result-Code は DIAMETER_AUTHORIZATION_REJECTED | 有効な登録を持たない利用者に、S-CSCF を新しく割り当てません。 |
| SAR（UNREGISTERED_USER 以外の型） | 通す | 6.1.2.1 の step 5 のほかの枝は、登録を終えるか、すでにある割り当てを確かめるものです。断ると、HSS に登録と認証の途中の印が残ります。 |

通す型は、登録を終える TIMEOUT_DEREGISTRATION、USER_DEREGISTRATION、ADMINISTRATIVE_DEREGISTRATION、DEREGISTRATION_TOO_MUCH_DATA と、S-CSCF の名前を残したまま登録を終える TIMEOUT_DEREGISTRATION_STORE_SERVER_NAME と USER_DEREGISTRATION_STORE_SERVER_NAME、失敗した登録の後始末をする AUTHENTICATION_FAILURE と AUTHENTICATION_TIMEOUT、そして NO_ASSIGNMENT です。REGISTRATION と RE_REGISTRATION を入れて、6.1.2.1 の step 5 の枝はこれで全部です。NO_ASSIGNMENT は、要求元の S-CSCF がすでにその利用者に割り当てられているときだけプロファイルを渡し、ほかの S-CSCF には DIAMETER_UNABLE_TO_COMPLY を返す枝なので、新しい割り当てにはなりません。「通す」は、収容の方針がその答えを変えないという意味です。このうち `*_STORE_SERVER_NAME` の 2 つと DEREGISTRATION_TOO_MUCH_DATA は、方針とは関わりなく、今の HSS が `SIMPLIFIED:` のとおり DIAMETER_UNABLE_TO_COMPLY を返す型で、方針を `test_users` にしても答えは同じです。

有効な登録を持たない利用者への着信は、LIR では止まらず、そのあとの SAR で止まります。6.1.4.1 の step 3 は、未登録の状態の着信サービスを持つ識別子に DIAMETER_UNREGISTERED_SERVICE と S-CSCF の能力を返すので、I-CSCF は S-CSCF を選び、その S-CSCF が UNREGISTERED_USER の SAR を送ります。

UNREGISTERED_USER を断るかどうかは、HSS が持つ登録の状態で決めます。状態が Registered でなければ断り、S-CSCF の名前を持っているかどうかは見ません。`*_STORE_SERVER_NAME` の登録解除のあとのように、状態が Unregistered で S-CSCF の名前が残っている利用者も、有効な登録を持たないので断ります。

この検査は、手順に無いものです。6.1.2.1 の step 5 は、この枝で認可を確かめません。それでも断るのは、登録だけを断っても、収容の対象外の利用者に未登録の状態のサービスが残るからです。DIAMETER_AUTHORIZATION_REJECTED は基本のプロトコルの Result-Code なので、この答えにも入れられます（RFC 6733 7.1.5）。`internal/hss/hss.go` の `serverAssignment` のコメントに、手順に足した検査であることと、この条項を書きます。

作り直した HSS の台は、保存先にある方針で答えます。設定のファイルの方針を使うのは、空の保存先で最初に起動した台だけです（下の「設定を台のあいだで分ける」）。

### プロファイルの push

TS 29.228 6.6.1 は、登録中か未登録の状態の識別子のプロファイルが変わったら、HSS が完全なユーザープロファイルをただちに S-CSCF に push することを求めています（should）。手順は 6.2.2 の Push-Profile-Request と Push-Profile-Answer です。

- 送る中身は、暗黙の登録の集合の公開の識別子と、そのサービスプロファイルです。変わっていない識別子のプロファイルも入れます（6.5.2.1）。User-Data は、プロファイルが変わったときに入れる条件付きの項目です（Table 6.2.2.1）。
- S-CSCF は、要求に入っている公開の識別子について、持っている情報を受け取ったもので上書きします（6.2.2.1）。
- 送り先は、その加入者に割り当てている S-CSCF です。加入者 1 人の変更が、1 回の PPR になります。
- 登録を持たない加入者のプロファイルを変えても、PPR は送りません。6.6.1 が push を求めるのは、登録中か未登録の状態の識別子だけです。

## 設定を台のあいだで分ける

HSS は、保存先を共有するサーバーファームとして、複数の台で動きます（[state-redundancy.md](state-redundancy.md)）。動かしたまま変えられる 3 つの設定も、台のあいだで食い違わないようにします。初めの作りでは、設定の値と世代が各台のプロセスの中にありました。そのため、台が複数あると問題が 3 つありました。OAM は変更を役割のすべての台に配り、各台がそれぞれ PPR を送るので、N 台なら加入者 1 人に N 通届きました。push の途中で台が止まったときの回復は「同じ値を送り直す」としていましたが、HSS は前と後の値が違うときだけ push するので、送り直しても何も起きませんでした。作り直した台は設定のファイルの値で起動し、運用者が同じ項目をもう一度変えるまで、その台だけが前の方針で答えました。

| 主題 | 作り |
| --- | --- |
| 置き場所 | 保存先の 1 つの項目に、3 つの設定と、それを決めた変更の世代を置きます（`hss.StoredSettings`。`internal/kvstore/hssstore` の鍵は、保存先の接頭辞のあとの `hss:settings:`）。空の保存先で最初に起動した台が、自分の設定のファイルの値を世代 0 で書きます。そのあとは、保守用の API の変更だけが書き換えます。保存先に加入者があるときは、ファイルの加入者を書き足さず、保存先のものを残すのと同じ扱いです（`cmd/ims` の `hssStore`）。 |
| 読み方 | 各台は、起動したとき、最初の要求に答える前に保存先から読みます。そのあとは 1 秒ごとに読み直し、より新しい世代を取り込みます。要求はプロセスの中の写しを読み、要求ごとには保存先を読みません。全台の全要求が 1 つの項目を読むと、台を増やしてもその項目への読み出しが減らないためです。ほかの台で変えた設定は、1 秒以内に取り込みます。起動してから一度も保存先を読めていない台は設定のファイルの値で、読めたことのある台は最後に読んだ値で答えます。保存先を読めないあいだは加入者も読めないので、要求はどれも DIAMETER_UNABLE_TO_COMPLY で終わります。取り込むのは項目ごとです。保存先の項目が、この台の設定のファイルに無いサービスプロファイルの名前や、この台の知らない方針のときは、その項目だけ最後に使えた値のままにし、保存先の世代ごとに 1 回エラーをログに書きます。ほかの項目と世代は取り込むので、方針のように使える項目で台のあいだが食い違うことはありません。無い名前を取り込むと、その名前の加入に iFC の無いプロファイルを渡すことになるためです。自分が受けた変更を書いたときも、書いた結果を同じ決まりで取り込みます。台は同じ設定のファイルで動かす前提です。 |
| 書き方 | 保守用の API の変更は、要求が名指しした設定だけを、保存先から読んだ値に当てはめ、その世代で、保存先の項目を compare and swap で書きます。名指ししていない設定は保存先の値のままです。ほかの台の変更をまだ取り込んでいない台が、自分の写しのまま全部を書くと、その変更を戻してしまうためです。同じ変更（同じ世代と同じ値）が保存先にもうあれば、書かずに取り込みます。OAM は同じ変更を役割のすべての台に配るので、2 台目からはこちらになります。より新しい世代か、同じ世代でほかの値が保存先にあれば、追い越された変更として 409 で断ります。保存先に書けなければ 500 で断ります。どちらのときも、要求のどの設定も変わりません（`maintenance.SettingsGroup` の `Commit`）。変更の記録の前の値は、その変更が保存先で置き換えた値です（`maintenance.SettingsGroup` の `Previous`）。台の写しの値ではありません。写しが古いと、置き換えたものと違う値が記録に残り、戻しがその値に戻してしまうためです。同じ変更が保存先にもうあったときは、この台は何も置き換えていないので、記録に変更は残りません。その変更は、書いた台の記録に残ります。 |
| 世代 | 保守用の API が見せる世代は、その台が取り込んだ設定の世代です（`maintenance.SettingsGroup` の `Generation`）。取り込みが済めば、OAM の画面の世代は台のあいだでそろいます。OAM の変更が届く前に、ほかの台の変更を保存先から取り込んだ台は、自分と同じ世代の要求を受けます。要求の値がすべて今の値なら、変更の無い記録で答えます（`maintenance.Node.ChangeConfiguration`）。OAM の戻しも同じです。ほかの台の戻しを取り込み、前の値をもう持っている台は、戻し済みとして扱います（`internal/oam` の `Rollback`）。 |
| push の担当 | 名前を設定から取る 2 つの出どころ（試験用の利用者と、ほかの加入）ごとに、push の項目を保存先に置きます（`hss.ProfilePush`。鍵は `profile-push:<出どころ>`）。項目は、その回が送るプロファイルの名前、その名前の世代（下の「変更から push まで」）、回の番号、最後に PPR を送った加入者、回が終わったかどうか、最後に書いた時刻、最後に借りた時刻を持ちます。回のあいだは時刻の索引 `profile-pushes` に出どころの要素を置き、時刻の来た要素を借りた 1 台が、1 ページ分（100 人）の PPR を送ります。借りた台は、まず借りた時刻を項目に書き、それから 1 通送るたびに、項目の続きの位置を compare and swap で進めます。加入者ごとの push のロックを取ったあとで項目を読み直し、借りたときの位置からほかの台が進めていたり、新しい回が始まっていたりしたら、その PPR は送りません。ロックを待つあいだに追い越された PPR が、あとから古いプロファイルを運んだり、同じ加入者に 2 通目を送ったりしないためです。ページを送り終えたら、続きがあれば要素の時刻をすぐに置き直し、回が終わったら要素を索引から外します。ページを送った台が次のページも借りることは多いのですが、どの台が借りてもよく、1 台が回の最後まで受け持つことには頼りません。リースは 30 秒です。加入者 1 人の push にかかる最長（ロックの待ちの 8 秒、保存先の読み書き、PPA の待ちの 5 秒）より長いので、借りるたびに少なくとも 1 人は進みます。shut down か lock をした台は、ほかの新しい仕事と同じく借りません。lock した台は Diameter の接続を閉じているので、借りれば、そのページの PPR がすべて失敗します。 |
| 変更から push まで | 保存先の設定は、2 つの名前ごとに、その名前を別の値にした最後の変更の世代（名前の世代）を持ちます。保存先の設定を書き換えた台が、名前の変わった出どころの回を、その名前の世代と一緒に push の項目に書き、それから要素をすぐに時刻の来た状態にします。同じ変更を受けたほかの台は、保存先にもう変更があるので何もしません。回は、前の回が終わっていて、名前の世代が前の回の世代より新しいときに始めます。名前が前の回の名前に戻っていても始めます。そのあいだに、SAA でほかの名前のプロファイルを渡した台があるかもしれないためです。同じ値を送り直しても、収容の方針だけを変えても、名前の世代は変わらないので、push しません。push の項目がまだ無い出どころも、名前の世代が 0 のあいだ、つまり名前が設定のファイルの値のままのあいだは、回を始めずに終わった項目を書きます。S-CSCF はその名前のプロファイルを SAA で受け取っているためです。ほかの設定の変更で保存先の世代が進んでいても同じです。回を始めるかどうかは保存先の名前で決め、台が取り込めなかった名前でも回は始めます。回の項目の書き込みがほかの台と重なって負けたときは、読み直してもう一度決めます。項目を書いてから要素の時刻を置くので、そのあいだに要素を借りた台も回を見つけて送ります。回が見つからず要素を外した台のあとでも、回を書いた台の時刻の置き直しで、要素は索引に戻ります。 |
| 台が止まったとき | 止まった台のリースは期限で切れ、要素はまた時刻の来た状態になります。次に借りた台が、項目に記録された最後の PPR の続きから送ります。PPA を受けてから記録するまでに台が止まると、その 1 人には PPR が 2 通届きます。S-CSCF は持っているプロファイルを受け取ったもので上書きするだけなので、害はありません（TS 29.228 6.2.2.1）。設定を書いたあと、回を書く前に台が止まったときは、各台が 1 秒ごとに保存先の設定と push の項目を比べるので、次の台が回を始めます。回を書いたあと、要素の時刻を置く前に止まったときは、回を借りた台がいないまま項目が古くなります。借りた台は、借りたときに項目へ時刻を書き、そのあとも 1 リースのうちに少なくとも 1 回は項目を書くので、借りた時刻からも最後に書いた時刻からもリースの 2 倍たった回には借りた台がいません。各台はそれを見つけたら要素の時刻を置き直します。借りた時刻を見るので、長く借りられずにいた回を借りた台が最初の PPR を送っているあいだに、ほかの台が取り直すことはありません。時刻は書いた台の時計なので、役割の台の時計の差はリースより十分に小さい前提です。同じ値を送り直す操作は、回復の手段として要りません。 |
| S-CSCF の接続を持たない台 | HSS が S-CSCF に送れるのは、その S-CSCF が開いた接続だけです。HSS の台を 1 つだけ指定した S-CSCF は、その台にしかつなぎません。回を借りた台がその接続を持たず、PPR が送れなかった（`diameter.ErrPeerUnavailable`）ときは、送ったことにはせず、その加入者を別の時刻の索引 `profile-push-retries` に置いて、回はほかの加入者へ進めます。どの台もそれを借り、接続を持つ台が送ります。送れなかった台は、その要素を 1 秒後に置き直してほかの台に任せます。台が順番に試すだけで、空回りはしません。置き直すのは 2 分までです。作り直した台や運用に戻した台には、S-CSCF が Tc（RFC 6733 2.1 の推奨は 30 秒）ごとにつなぎ直すので、その数回分です。それまでに送れなければ、その S-CSCF には次の登録でプロファイルが届きます。そのあいだに同じ出どころの新しい回が始まれば、新しい回が全員に送るので、古い回の要素は送らずに外します。ロックを待つあいだに新しい回が始まったときも送りません。要素の名前は、出どころ、回の番号、加入者だけです。借りた台が止まり、次に借りた台が同じ PPR を送り直して同じく送れなかったときも、要素は 1 つのままです。2 分は、要素を置いた時刻ではなく、回が最後に進んだ時刻から数えます。最後に借りた時刻と最後に書いた時刻のうち遅いほうで、終わった回なら終わった時刻です。回は PPR を置いたあとで進むので、置いてから 2 分より短くなることはありません。長く借りられずにいた回を借りた台が、最初に置いた PPR も同じです。置いた時刻を要素の名前に入れると、置き直した 2 つの要素が別のものになり、同じ PPR が 2 回送られます。置いた時刻を要素とは別に持つと、項目が 1 つ増え、要素を外すたびにそれも消すことになります。置いた台が、回を進める前に止まったときだけは、PPR 1 通にかかる時間の分だけ 2 分より短くなりますが、次の台が回を借りれば、そこから数え直します。この台の設定のファイルに無い名前の回も、同じくほかの台に任せます。回を借りた台のどれもがその名前を持たないまま、回が 2 分進まなかったときは、その回をあきらめて終わったことにし、エラーをログに書きます。その名前を持つ唯一の台が止まったときなどです。そうしないと、同じ出どころのあとの回が始まらず、設定を直してもその push が出ません。進んだかどうかは、項目の最後に書いた時刻と最後に借りた時刻のうち遅いほうで見ます。この 2 つを動かすのは、名前を持つ台だけです。回を始めた時刻で見ると、ページの多い回や、遅い S-CSCF に向けた回のように、2 分より長く進み続けている回を、名前を持たない台が途中で借りたときにあきらめてしまいます。 |
| 続けて 2 回変えたとき | 同じ出どころの回は 1 つずつ順に進みます。回の途中で名前を変えても、その変更は回を始めません。今の回が終わるときに、保存先の名前の世代が回の世代より新しければ、そこで次の回を始めます。そのため、変更はどれも push され、2 つの回が同じ加入者に同時に送ることもありません。各回の PPR は、その回の名前のプロファイルを運びます。A から B に変え、B の回の途中で A に戻したときは、B の回が終わってから A の回が始まり、S-CSCF には A が残ります。A の回の途中で B に変え、その回が終わる前に A に戻したときも、名前の世代が回の世代より新しいので、A の回をもう一度始めます。B に変えた台が回を始める前に止まり、そのあとで A に戻したときも同じです。 |
| 費用 | 各台が 1 秒ごとに読むのは、設定の項目 1 つ、push の項目 2 つ、2 つの時刻の索引への問い合わせ 1 回ずつです。どれも加入者の数に関わりません。push で読む数は、前と同じく、変わった設定で選ばれる登録の数です。役割全体を止めるロックはありません。 |
| プロセスの中の保存先 | Compose の既定の構成のように、保存先がプロセスの中にあるときも同じ作りです。設定も push も、加入者と同じくプロセスと一緒に消え、作り直したコンテナは設定のファイルの値で起動します。 |

作り直した台を今の設定に合わせる方法は、次の 2 つを比べました。

| 案 | 決め手 |
| --- | --- |
| OAM が、世代の古い台を見つけて今の設定を送り直す（TS 32.600 4.2.1.3 の監査） | 採りません。作り直した台は、OAM が見つけて送り直すまで、設定のファイルの値で答えます。OAM が動いていて、台ごとのアドレスに届くことに頼ります。Kubernetes のインベントリは役割の Service の名前を指すので、OAM は Pod を 1 つずつ選べません。役割の台がすべて作り直されたとき、今の設定を知っているのは OAM の履歴だけで、そこには OAM を通らなかった変更がありません。PPR の重なりも別に直すことになり、そのとき push を受け持つ台がまだ変更を受けていなければ、前のプロファイルを送ります。 |
| 設定を保存先に置き、各台が読む | 採ります。作り直した台は最初の要求から今の設定で答え、OAM にも台ごとのアドレスにも頼りません。push を受け持つ台は、保存先の設定で PPR を作れます。代わりに、各台が 1 秒ごとに 1 つの項目を読み、保守用の API が保存先の世代を見せる作りが要ります。 |

ほかに、要求のたびに保存先の設定を読む案、同じ値の送り直しで push をやり直す案、1 台が回の最初から最後まで push を受け持つ案も、採りませんでした。1 つ目は、取り込みの遅れが無くなる代わりに、すべての要求が同じ 1 つの項目を読みます。2 つ目は、止まった台の分をほかの台が続きから送るので、回復の手段として要りません。OAM が変更をすべての台に配るので、送り直すたびに全員へ PPR を送り直すことにもなります。3 つ目は、その台が止まると残りが送られず、引き継ぐには結局ページごとの記録が要ります。

## OAM の変更

OAM の API（`/oam/v1/…`）と画面（`web/oam`）は変わりません。変わるのは、HSS を呼ぶ側だけです。

- `internal/oam/hssclient.go` と `records.go` のコメントから、「`internal/hss` に無い」という断りを外します。
- `hssError` が 404 と 405 を「この操作が無い」と読む分岐を外します。404 は「その加入が無い」だけになります。
- 書き出しのページの終わりは、`Link` ヘッダの有無だけで判断します。ちょうど `limit` 件のページには必ず `Link` が付くので、最後に 0 件のページを読むことがあります。OAM は、それを誤りにせず、書き出しの終わりとして扱います。件数で判断する道は残しません。HSS が `Link` を返すようになったうえ、読んでいるあいだに消えた加入をそのページから外すので、行の数が `limit` に満たないページも続きを持つためです。
- `internal/oam/fakehss_test.go` の `basic`（`PUT`、`PATCH`、書き出しを持たない HSS）と、それに対して 502 を確かめる試験を外します。HSS が持つ操作なので、持たない HSS は試験の相手になりません。
- 学習用の画面（`web/lab`）と手順書は、新しい項目と経路を書きます。手順書は英語と日本語の両方を同じコミットで直します。

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| HSS に `POST /subscriptions/batch` を足す（調査の 7 章の案） | 1 行ずつ読み、順に結果を返し、同時に送る件数を抑える仕組みは、OAM にすでにあります。HSS にもう 1 組作ると、結果の語彙と大きさの上限が 2 か所になります。1 件の `PUT` はその加入者のロックだけを取るので、一括でも役割全体を止めるロックは要りません。 |
| 一覧に資格情報を出す問い合わせ（`GET /subscriptions?credentials=true`） | 間違って付けると、学習用の画面に資格情報が出ます。本文の形も違います（JSON の配列と、1 行に 1 件）。経路を分ければ、どちらを呼んでいるかが入り口で分かります。 |
| `POST` をやめて `PUT` だけにする | `POST` は識別子が取られていれば 409 で断る「追加」、`PUT` は送り直せる「置き換え」で、使う場面が違います。学習用の画面と手順書は追加を見せます。検査と変換は 1 つの関数で共有するので、写しにはなりません。 |
| `PUT` を項目ごとの更新にする | 書庫を戻す操作が「書いてあるとおりにする」になりません。印とプロファイルの名前だけを変えるには `PATCH` があります。 |
| `hss.admission` を、世代を持たない値として保存先に置き、保守用の API とは別の道で変える | 設定の出どころが 2 つになり、同じ項目を変える道が 2 つできます。世代が無いので、OAM の履歴と戻しが効きません。今の作りは、値を世代と一緒に保存先に置き、変える道を保守用の API の 1 つに保ちます。設定のファイルが値を決めるのは、空の保存先で最初に起動した台だけです（上の「設定を台のあいだで分ける」）。 |
| 作り直した台に、OAM が今の設定を送り直す | 上の「設定を台のあいだで分ける」で、保存先に置く案と比べました。 |
| 識別子の範囲（IMSI の先頭の桁など）で試験用の利用者を決める | 1 人ずつ足したり外したりできません（調査の 9 章）。 |
| 各ノードの設定に試験用の利用者の一覧を書く | ノードの数だけ写しができ、利用者の数に比例して設定が増えます（調査の 9 章）。 |
| 戻す SQN_HE に幅を足す（調査の 8 章の案） | 足す幅の根拠がありません。AUTS による同期は実装してあるので、古い SQN_HE は UE の再同期で直り、その様子は手順書の題材になります。 |

## 作らないもの

- 1 つの加入に複数のサービスプロファイルを持たせること。公開の識別子ごとのプロファイルと、複数の暗黙の登録の集合は、`internal/hss/store.go` の `SIMPLIFIED:` のままです。
- プロファイルの中身（iFC）を動かしたまま変えること。設定のファイルの項目にします。変えられるのは、どのプロファイルを使うかだけです。
- プロビジョニングの API の認証と認可。保守用の API と OAM の API と同じく、平文の HTTP で動かし、内部の網からだけ届くことに頼ります（`internal/oam` のパッケージのコメントの `SIMPLIFIED:`）。
- 書き出した内容の暗号化。試験用の値だけを使う決まりがあるためです（調査の 8 章）。
- 加入者を複数の HSS に分けて置くこと（SLF）。HSS は状態を共有するサーバーファームです（[state-redundancy.md](state-redundancy.md)）。

## 作る順番

1 つの PR は、1 つの確かめ方で終わる大きさにします。

1. この設計の記録。
2. 名前の付いたサービスのプロファイル。`hss.service_profiles` と `hss.default_service_profile` を足し、SAA が選んだプロファイルの iFC を返すようにします。`hss.test_user_service_profile` は、それを読む `test_user` の印と同じ作業で足します。読む側の無い設定を、先に入れないためです。設定の読み取り（`internal/config/ifc.go`、`roles.go`）、その試験（`internal/config/ifc_test.go`）、4 つの設定ファイル（`deploy/compose`、`deploy/k8s`、`deploy/redundancy`、`deploy/interconnect/b`）、この鍵を載せている手順書（`docs/guide/en/sms.md` と `docs/guide/ja/sms.md`）を、1 つのコミットで直します。分けると、どこかの段階で設定が読めなくなるためです。確かめ方は `internal/hss` と `internal/config` の試験と、登録と通話の e2e で信号が変わらないことです。
3. 加入者のデータの `test_user` と `service_profile`。設定のファイル、`POST`、`GET` の答え、`Store` の形に足し、`hss.test_user_service_profile` と合わせて、プロファイルの選び方を決めます。確かめ方は `internal/hss` と `internal/kvstore/hssstore` の試験です。
4. `PUT /subscriptions/{IMPI}`（`dry_run` と `repository_data` を含む）。`Store` に `Replace` を足し、`MemoryStore` と `internal/kvstore/hssstore` の両方に実装します。確かめ方は、作成、置き換え、`unchanged`、409、SQN_HE と登録の状態が残ること、Sh の更新と同時に走らせても取り違えないことの試験です。
5. `PATCH /subscriptions/{IMPI}`。確かめ方は、資格情報が変わらないことの試験です。
6. プロファイルの push。`internal/cx` に PPR と PPA を足し、HSS が送り、S-CSCF が受け取ったプロファイルで持っているものを上書きします（上の「プロファイルの push」）。プロファイルを変えられるようになってからにします。確かめ方は、登録中の加入者のプロファイルを変えると PPR が出て、次の呼が新しい iFC で動くことの試験です。
7. `GET /subscriptions/export`。確かめ方は、書き出した内容を `PUT` で戻すと `unchanged` になることの試験です。
8. `hss.admission` と、UAR と SAR の検査（上の「収容を制限するあいだの振る舞い」）。設定のファイルの項目として入れ、UAR の `SIMPLIFIED:` を置き換えます。確かめ方は `internal/hss` の試験と、試験用でない利用者の REGISTER が 403 になる e2e です。この e2e は Compose と pcap を使うので、手元では流さず、PR の CI の結果で確かめます。
9. `hss.admission` と 2 つのプロファイルの名前を、保守用の API で変えられる項目にします。HSS の役割が `internal/maintenance` をつなぎ、設定の変更を受けられるようになってからにします。その前では、変えられる項目を載せる先がありません。保守用の API が返す設定に、プロファイルごとの機能の一覧を載せるのもここです。各 iFC の `feature` を重複なく集めたものを返し、OAM がそれを読みます。確かめ方は、OAM から方針を変え、履歴から戻せることです。2 つのプロファイルの名前を変えたときの PPR と、そのための実効プロファイルごとの登録の索引（上の「設定を変えたときの反映」）も、この段階で作ります。この段階は 2 つの PR に分けます。先の PR で 3 つの設定を変えられるようにし、PPR を送らないことを `SIMPLIFIED:` に書きます。あとの PR で索引と PPR を足し、その `SIMPLIFIED:` を外します。
10. OAM を HSS の API に合わせます（上の「OAM の変更」）。偽の HSS の `basic` をなくすのはここです。
11. 手順書（英語と日本語）と学習用の画面。
12. 設定と push を保存先に置き、台のあいだで分けます（上の「設定を台のあいだで分ける」）。`internal/maintenance` が、同じ世代で今の値と同じ変更を受けられるようにし、設定の組の `Commit` が失敗でき、組が世代を持てるようにしてからにします。確かめ方は、HSS を 2 台にして設定を変えると加入者 1 人に PPR が 1 通届くこと、push の途中で台を止めても残りの加入者に PPR が届くこと、作り直した台が運用者の操作なしで今の設定になることの試験です。`internal/hss` の試験は、プロセスの中の保存先と、`internal/kvstore/hssstore` の上で両方の保存先（Valkey を含む）を使います。

## 残っている課題

- 保存先があるとき、設定のファイルの 3 つの設定が効くのは、空の保存先で最初に起動した台だけです。ファイルを書き換えて起動し直しても、保存先の値は変わりません。変えるのは保守用の API です。
- ほかの台で変えた設定を取り込むまでの 1 秒ほどのあいだ、その台は前の設定で答えます。その台が SAA で前のプロファイルを渡すと、push のあとでも S-CSCF に前のプロファイルが残り、次の登録で直ります。
- 止まった台が借りていた push は、リース（30 秒）が切れるまで進みません。止める台がリースを返す仕組みはありません。
- 加入 1 件のプロビジョニングで送る PPR と、加入者を消したときの RTR は、要求を受けた台から送ります。その台が S-CSCF の接続を持たなければ送れず、ログに書くだけです。設定を変えたときの push のように、ほかの台に任せる仕組みはありません。
- 収容の対象外で登録していない利用者への着信は、S-CSCF が未成功の SAA に返す 500 で終わります（`internal/scscf/unregistered.go`）。断った理由は、発信側に伝わりません。
- 一括の登録は、OAM が 1 台の HSS に送ります。宛先に組の名前を書けば、DNS が台を選びます。行ごとに台を選び分けることはしません。
- 登録の索引の項目は、加入者が登録の状態に出入りするときと、名前の選ばれ方が変わるときに書きます。この索引を入れる前から動いている保存先には、そのときすでに登録している加入者の項目がありません。その加入者には、次に状態か名前の選ばれ方が変わるまで、設定を変えたときの PPR が届かず、新しいプロファイルは次の登録で届きます。保存先には版の印も移行の仕組みも無く、起動した台が全加入者を読んで索引を埋めることもしません。加入者の数に比例する走査になるためです。
