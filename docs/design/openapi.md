# HTTP の API の OpenAPI

この記録は、このプロジェクトの HTTP の API を OpenAPI で書き、ハンドラーとの食い違いを試験で見つける設計です。3GPP が OpenAPI を定めている API を、独自の API と見分ける方法も決めます。

## 選んだこと

- このプロジェクトが独自に決めた HTTP の API は、API ごとに OpenAPI 3.1 のファイルを 1 つ書き、そのハンドラーのパッケージに `openapi.yaml` として置きます。経路、方法、パラメーター、要求の本文、答えの状態コードと本文、ヘッダを書きます。
- 各 API の試験は、本物のハンドラーを `httptest` で動かし、すべての要求と答えを OpenAPI のファイルと突き合わせます。突き合わせるのは試験だけの部品 `internal/openapitest` です。
- スキーマの検査（JSON Schema 2020-12）には、ライブラリの `github.com/santhosh-tekuri/jsonschema/v6`（Apache-2.0）を使います。OpenAPI の文書の読み取り、経路の照合、状態コードと Content-Type の検査は自分で書きます。
- 3GPP の OpenAPI に従う API は、パッケージのコメントに仕様の番号、版、OpenAPI のファイル名、作った操作と作っていない操作を書きます。型の属性の名前は、その版の OpenAPI のファイルと照らす試験で確かめます。
- 3GPP の OpenAPI のファイルは、リポジトリに入れません。3GPP の著作物だからです。番号と版とファイル名、照らしたタグを書くだけにします。

## スキーマの検査をライブラリに任せる理由

検査に要るのは 2 つです。OpenAPI の文書を読んで、要求がどの操作に当たり、答えにどの状態コードとスキーマが許されるかを引くこと。そして、本文がスキーマに合うかを確かめることです。

前者は小さく、この API が使う範囲（経路の中のパラメーター、クエリのパラメーター、本文、答えのヘッダ）に限れば数百行で書けます。範囲の外のものを見つけたら文書ごと断るように書けば、読み落としもありません。

後者は JSON Schema 2020-12 の意味をそのまま実装することになります。`$ref` の解決、`oneOf` と `additionalProperties` の組み合わせ、`format` の検査などです。自分で書くと、検査の部品そのものに試験が要ります。部品の誤りで試験が素通りしても、気づけません。学習の対象でもないので、[implementation.md](implementation.md) の方針どおり、既存のライブラリを使います。

`santhosh-tekuri/jsonschema` の v6 を選んだのは、次の理由です。

- 2020-12 を含む各版の JSON Schema に対応し、公式の試験の集まり（JSON-Schema-Test-Suite）で確かめられています。
- OpenAPI の文書をそのまま 1 つの資源として登録し、その中の任意の場所（JSON Pointer）のスキーマを取り出して検査できます。スキーマを文書から切り出す処理が要りません。
- 依存は `golang.org/x/text`（BSD-3-Clause）だけです。これを足すと、Go のモジュールの選び方（最小のバージョンの選択）によって、`golang.org/x/sync` が v0.22.0 から v0.23.0 に上がります。
- 読み込むのは試験だけです。どのバイナリにも入りません。

OpenAPI 全体を扱うライブラリは使いません。経路の照合や文書の検証まで任せると、依存が増えます。そのうえ、要るのは上の小さな読み取りだけです。

## 試験が見つけるもの

`internal/openapitest` の `Document.Handler` を通った要求と答えは、すべて次のように確かめます。

| 確かめること | 食い違いの例 |
| --- | --- |
| 文書に操作の無い要求を、404 か 405 で断ること | ハンドラーに経路を足し、文書に書き忘れた |
| 要求の経路とクエリのパラメーター、本文がスキーマに合うこと。合わない要求に 4xx 以外を返さないこと | ハンドラーが文書より緩く要求を受けた。合わない要求で 500 を返した |
| 答えの状態コードが、その操作に書いてあるものであること | 文書に無い状態コードで答えた |
| 本文のある答えに、ハンドラーが Content-Type を付けること。それが書いてあるものであること。JSON の本文がスキーマに合うこと | Content-Type を付け忘れた、フィールドの名前を変えた、文書に無いフィールドを足した |
| 必須と書いたヘッダが答えにあること | `Location` を付け忘れた |

あわせて、次のことも確かめます。

- `Document.CheckRoutes` は、文書の経路ごとに OPTIONS を送ります。返ってきた 405 の `Allow` を、文書の方法と比べます。どの API も OPTIONS を受けないので、`net/http.ServeMux` はその経路の方法を `Allow` に並べて 405 を返します。文書に無い方法をハンドラーが受けていれば、ここで見つかります。
- `Document.CheckCovered` は、どの要求も届かなかった操作を挙げます。試験を書き漏らした操作があれば、そこで落ちます。
- スキーマに使えるキーワードを決めてあり、それ以外を断ります。`minimun` のような書き間違いは、何も確かめないまま通さずに落とします。
- オブジェクトのスキーマには `additionalProperties` を必ず書きます。文書に無いフィールドをハンドラーが足したら、食い違いとして見つけます。
- 試験の要求は、そのまま本物のハンドラーに届きます。要求の本文は、ハンドラーが読むのに合わせて写し取ります。OAM の一括のプロビジョニングのように、読みながら答えるハンドラーもそのまま動きます。

404 と 405 のどちらで断るかは、ハンドラーのほかの経路で決まります。どちらも断ったことに変わりはないので、どちらでも通します。見つけたいのは、文書に無いのに受けてしまう経路です。

## 文書の書き方

検査の部品が読む OpenAPI の機能には、使う文書が 1 つか少ししかないものがあります。どれも、その文書のために足しました。

| 機能 | 使う文書 | 理由 |
| --- | --- | --- |
| ほかの文書のスキーマを指す `$ref` | OAM の文書。各ノードから受け取る本文（`NodeState` など）を、保守の API の文書の `../maintenance/openapi.yaml#/components/schemas/NodeState` から引き、加入の記録の一部を HSS の文書から引きます | 同じ形を 2 か所に書かないので、2 つの文書がずれません |
| `components` の `requestBodies` | OAM の文書（管理の状態、ログのレベル、設定の変更、ロールバック）、メディア中継ノードの文書（ターミネーションの要求）、ラボの文書（転送する本文） | 何度も出てくる要求の本文を 1 回だけ書きます |
| 何も言わない行のスキーマで NDJSON の行を確かめないこと | OAM の文書の一括のプロビジョニング | OAM はどんな行も受け、記録でない行を `rejected` と答えます。行の形を断る文書にはできません |
| `default` の答えと、`*/*` のような範囲の Content-Type | ラボの文書の、別の API へ転送する経路 | 答えは転送先の API のものなので、その状態コードと形は転送先の文書が決めます |
| 文書に無い要求を 404 と 405 のどちらで断ってもよいこと | ラボの文書 | ラボは `GET /` で画面を出すので、API に無い経路への POST に `ServeMux` が 405 を返します |

## 試験が見つけないもの

- 文書にまったく無い経路を、ハンドラーが持っていること。`ServeMux` は登録した経路の一覧を出さないので、試験から問い合わせられません。その経路に要求を送る試験があれば、`Document.Handler` が「文書に無い経路への 404 以外の答え」として見つけます。
- JSON と NDJSON 以外の本文（Server-Sent Events、テキスト、XML）の中身。Content-Type だけを確かめます。NDJSON（`application/x-ndjson`）は、空でない行ごとに、その Content-Type に書いたスキーマと突き合わせます。OpenAPI 3.1 には並びの要素のスキーマを書く場所が無いので、ここの文書は 1 行のスキーマを書くことにしています。
- 文書に書いた状態コードを、ハンドラーが本当に返すかどうか。試験の書いた要求が引き出したものだけを確かめます。
- ラボの経路ごとの方法。`GET /` があるので、ラボのどの経路も GET を受けます。`CheckRoutes` を使わず、要求ごとの検査に任せます。
- メディア中継ノードがコントローラーに送る Notify。文書にはスキーマとして書きますが、その送り先は要求ごとに決まる URL なので、試験はそのやり取りを確かめません。

## 3GPP の OpenAPI に従う API

3GPP が OpenAPI を定めている API（`internal/n5` の Npcf_PolicyAuthorization と、`internal/nhss` の Nhss_ims の各サービス）は、OpenAPI のファイルを自分では書きません。3GPP のファイルが正です。そのかわり、パッケージのコメントに次のことを書きます。

- 仕様の番号と版。例えば TS 29.514 V20.1.0。
- OpenAPI のファイル名。例えば `TS29514_Npcf_PolicyAuthorization.yaml`。
- 作った操作と作っていない操作。

両者が共有する部分（`internal/sbi`）は、TS 29.500 の決まりと TS 29.571 の共通の型に従います。

型の属性の名前は、その版の OpenAPI のファイルと照らします。パッケージごとに 2 つの試験を置きます。

- `TestAttributeNames`（`names_test.go`）。型ごとに、同じ名前のスキーマがファイルで持つ属性の名前の一覧を置き、型の JSON の名前（`openapitest.JSONNames`）と比べます。一覧はファイルから写したものなので、名前を書き間違えた型はここで落ちます。
- 本文の例の往復（`internal/n5/types_test.go` など）。一覧の名前で書いた本文の例を Go の型で読み、書き戻しても同じになることを確かめます。名前の正しさは確かめませんが、型が本文の値を読み落とさず、そのまま書き戻せることを確かめます。

TS 29.571 の ProblemDetails と InvalidParam は、`internal/sbi` の試験だけが確かめます。

照らすファイルは、次のように手に入れます。リポジトリには入れません。

- 正とするのは、3GPP のファイルサーバーにある仕様書の zip に入った OpenAPI のファイルです。仕様書の版と、そのまま合わせられます。
- 3GPP Forge の `forge.3gpp.org/rep/all/5G_APIs` にも置いてあります。ブランチの先頭は、公開された版より先に進んでいることがあります。照らすときは TSG の会合ごとのタグ（`TSG112-Rel20` など）を使います。
- ファイルの `externalDocs` に書かれた版は、当てになりません。TS 29.514 V20.1.0 の zip に入ったファイルは、`externalDocs` に V20.0.0 と書いています。どのタグが仕様書のどの版に当たるかは、zip のファイルと行末を除いて突き合わせて決めます。TS 29.514 と TS 29.562 の V20.1.0 のファイルは、`TSG112-Rel20` のタグのものと同じでした。TS 29.571 V20.1.0 のファイルは、どのタグのものとも違いました。
