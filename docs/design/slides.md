# スライドを図と段階で説明する

スライドの元データの形式と、そこから作る HTML と pptx の作りを決めた記録です。道具を選んだ経緯（自作の生成器にしたこと）は [background/slides.md](../background/slides.md) にあり、書き方と確かめ方は [slides/README.ja.md](../../slides/README.ja.md) にあります。

## 求めること

文字が中心のスライドでは、学習者は「誰が、何を受け取り、何を判断し、その結果どの信号が動くか」を図から追えません。網の全体図で信号を 1 区間ずつ進め、処理するノードに寄り、受け取った値と判断と次の信号の関係を見せ、全体に戻れる教材にします。同時に、次のことを守ります。

- 元データはテキストで、日英の 2 つのファイル。HTML は 1 つのファイルで、ネットワークなしに開ける。pptx の文字、ノード、矢印、表は PowerPoint で編集できる。図を画像にしない。発表者ノートを作らない。
- 今のスライドの内容（概念、根拠、観察点と、実習や設問と答えに含まれる知識）を残す。実習や設問の形は残さなくてよく、著者の説明、結果まで説明する例、手順書の任意の再現の手順に変えてよい。読む人に実行や解答を求めずに、説明が完結するようにする（[book.md](book.md)）。
- リンク、コードの抜き出し、コマンド、アドレスの検査を、新しい形式の文字にも当てる。
- 前に進んでも、戻っても、アドレスで直接開いても、同じ段階は同じ状態になる。動きを減らしても情報を失わない。
- 標準、この実装の動き、説明のための例、実際のキャプチャを区別する。

## 決めたこと

### 元データ

今の Markdown に似た書式を広げます。フロントマターに `format: visual` を書いたデッキは、表紙の前に `ims-model` のブロックを置き、ノードと、デッキのシーンが描くイベントをすべて書きます。本文が `ims-scene` のブロックで始まるスライドがシーンになり、その下の本文がシーンの詳しい説明になります。シーンでないスライドは今までどおりのページで、シーンの無いデッキは今までの形式そのものです。古い形式を別の経路で残すのではなく、今の形式を新しい形式の一部にしました。そのため、22 のデッキを一度に書き換える必要はなく、どのデッキも同じパーサー、同じ検査、同じ書き出しを通ります。

イベントは 3 種類です。1 区間を進む 1 つのメッセージ（`msg`）、1 つのノードの中の処理（`do`）、信号ではない関係（`rel`。パッケージの import など）です。要求と応答は別のイベントにし、同じ REGISTER でも区間ごと、1 回目と 2 回目ごとに別の ID を付けます。地図とシーケンス図と値の表は同じイベントを指すので、同じ区間を図の種類をまたいで追えます。

ブロックは YAML で書きます。仕様の案は JSON でしたが、同じシーン（I-CSCF が S-CSCF を選ぶ 4 段階）を書き比べると、JSON は YAML の 4 倍ほどの行になり、括弧と引用符の誤りが目立ちました。YAML の読み込みには、リポジトリがすでに使っている `go.yaml.in/yaml/v3` を使い、知らないキーと重なったキーを誤りにします。誤りの行番号はデッキの中の行に直して出します。JSON Schema は置きません。形式の正しさはパーサーが決め、試験がそれを確かめます。スキーマを足すと、同じ決まりを 2 か所に持つことになるためです。

段階は前の段階からの差分（`show`、`hide`、`only`）で書けるようにし、パーサーがそれぞれの完全な状態（描くイベント、主役のイベント、強く描くノード、寄る先、値を見せるイベント）に直します。書き出しは完全な状態だけを読みます。作者は差分で短く書けますが、どの段階も前の段階に頼らずに描けます。主役は、既定ではその段階が足した最後のメッセージか処理で、強く描くノードは主役の両端です。この既定で、多くの段階は 3 行で書けます。

日英の 2 つのファイルは、ID、ノードとその位置、イベントの両端と信号の名前、フィールドの数、各段階の完全な状態が同じでなければなりません（`cmd/slides/structure.go`）。今までの「スライドの数とレイアウトが同じ」という検査はそのまま残します。言葉は言語ごとに直せますが、意味の骨組みは同じになります。

### 図

図は 2 種類だけです。ノードを升目に置く地図と、ノードごとに縦の線を引くシーケンス図です。どちらも同じイベントを描きます。コードの依存の図と状態の図は、地図に関係のイベントを描いて表します。図の種類を足す仕組みや、レイアウトのプラグインは作りません。

ノードの位置はモデルに升目の列と行で書きます。どのシーンでも同じノードは同じ位置にいるので、シーンが変わっても見失いません。絶対座標を書かせないのは、出力ごとに大きさが違うためです。メッセージは 2 つのノードの中心を結ぶ線の両側に、向きごとの車線を持ち、要求とその応答が 1 本の線に重なりません。ラベルは線の外側で、ノードとほかのラベルに重ならない最初の場所に置きます。線に沿って位置をずらし、それでも空きが無ければ線の反対側を試します。処理の箱もノードの下、上、右、左の順に空きを探します。どこにも空きが無いときは、重なりのいちばん小さい場所を選び、HTML の検査の表示（`?check`）が重なりを報告します。登録のデッキでは、この検査で 54 件あった重なりが 0 件になりました。

色と線の種類は、プロトコルの系統ごとに決めます。SIP は実線、Diameter は破線、DNS は点線です。ラベルにもプロトコルの名前を書くので、色だけで見分けることはありません。401 の challenge を失敗の赤で描くようなことはしません。

### HTML

HTML は 1280 × 720 の舞台をウインドウに合わせて拡大、縮小します。シーンの舞台には題にした問い、図、今の段階の文と値の表、詳しい説明を開くボタンを置きます。地図が横に長いとき（幅が高さの 2.1 倍より大きいとき）と、シーケンス図の列が 7 つ以上あるときは、図を舞台の幅いっぱいに置き、段階の文をその下に並べます。シーケンス図は行を送って見せるので、全体の高さではなく列の数で決めます。6 列までは、文を右に置いたほうが図が大きく描けます。そうでないときは、文を図の右に置きます。

段階のデータ（完全な状態と、図の見せる範囲）は、ページの中の JSON にあります。スクリプトは段階ごとに、その完全な状態から図の要素の状態を書き換えます。前の段階の DOM に頼らないので、進む、戻る、選ぶ、アドレスで開く、のどれでも同じ状態になります。アドレスは `#シーン/段階` で、文字のページは今までどおり番号（`#12`）です。登録のデッキの 79 の状態すべてで、進んで記録した状態と、戻って記録した状態と、アドレスで開いた状態が同じになることを、ブラウザで確かめました。

動きは 2 つだけです。段階が足したメッセージの上を点が送り手から受け手へ走ることと、寄る先が変わるときに見せる範囲がなめらかに移ることです。どちらも 0.5 秒前後で、連打すると最後の目標の状態に直接向かいます。「動きを減らす」か、システムの設定（prefers-reduced-motion）では、どちらもしません。

詳しい説明は舞台の右から引き出す欄に流れる文章で出します。発表者ノートの代わりではなく、学習者が読む本文です。読み物の表示はすべてのスライドを順に並べ、シーンはチェックポイントごとの図と、そこまでの段階の文と、詳しい説明で書きます。印刷はこの表示を使います。幅が 760 ピクセルより狭い画面と、縦長の小さな画面では、舞台を縮めず、文章を流して図を画面の幅に合わせます。

### pptx

pptx はシーンのチェックポイントごとに 1 枚のページを作ります。HTML の段階の数と pptx のページの数は合わせません。ページにはチェックポイントでの図と、1 つ前のチェックポイントからの各段階の題と文、その段階のメッセージのフィールドの表を置きます。図のメッセージには、それを主役にする段階の番号を付け、文の番号と対応させます。段階を進められない読み手も、何がどの順に起きたかを 1 枚で読めます。図と文が 1 枚に収まらなければ、文字を 80% まで小さくし、それでも収まらなければ誤りにして、作者に前の段階もチェックポイントにするよう求めます。詳しい説明はその次の、「詳しく」の札を付けたページにします。pptx では寄る表現を使わず、図の全体を描き、強く描くノード以外を薄くします。

図はグループ 1 つにまとめた PowerPoint の図形です。ノードは文字の入った角の丸い箱 1 つで、メッセージは矢じりの付いたコネクタ、ラベルはテキストボックスです。図形には `node icscf`、`event uar1` のような名前を付け、選択ウィンドウでノードやイベントを見分けられるようにします。コネクタは箱に接続していません。接続すると、ノードを動かしたときに矢印が付いてきますが、向きごとの車線と、2 つの線に分けた要求と応答の位置を接続点だけでは表せないためです。代わりに、矢印の位置、向き、色、ラベルを 1 つずつ編集できます。

### 大きさの単位

pptx とレイアウトのページは 960 × 540 ポイント（13⅓ × 7½ インチ。1 ポイントは 12700 EMU）です。HTML の舞台は 1280 × 720 の CSS のピクセルで、文字のページはポイントの 4/3 倍で描きます。図は図の単位（地図の 1 マスが 300 × 160）を持ち、出力ごとに置き場所に合わせて拡大、縮小します。今までの HTML は 1 ポイントを 1 ピクセルとして描き、印刷も 10 × 5.625 インチでした。印刷は読み物の表示に変えたので、紙の大きさはブラウザの設定に任せます。

### 検査をつなぐ

今の検査（リンク、コードの抜き出し、コマンド、アドレス）は、スライドの列のブロックを読みます。シーンの文字を新しい型のまま持つと、検査から漏れます。そこで `Deck.Sections` がシーンのリード、各段階の題と文、描くイベントの名前とフィールド、モデルのノードの役目を、段落と表のブロックに直して返し、どの検査もこれを読みます。シーンの段階の文に壊れたリンクを書くと失敗することを、試験で確かめています（`internal/deck/visual_test.go`）。

描いたあとの見た目は、HTML の検査の表示（`?check`）が確かめます。すべてのシーンのすべての段階を描き、収まらない文字、箱より広いノードの名前、ノードかほかのラベルに重なるメッセージのラベルを報告します。`check-html.js` が CI でこれを全デッキに走らせます。デッキを書き直したときに内容が抜けていないかは、`scripts/check_deck_content.py` が、移行の対応表（[book-migration.md](book-migration.md)）の基準のコミットのデッキにあったリンク、行の中のコード、コードの行、表のセルが、いまのデッキか、対応表が書く行き先（Book の章、手順書の節、別のデッキのシーン）に残っているかで確かめます。シーンの YAML は、文を言い換えても誤りにせず、その中の行の中のコードとリンクを比べます。表の見出しの行は比べません。

## 採らなかったもの

- 今の形式を残したまま、新しい形式を別のパーサーで読む作り。2 つの経路の検査と書き出しを保つ手間がかかります。
- Marp、Slidev、reveal.js への切り替え。図を画像にするか、SVG の図形を編集できる pptx にできないかのどちらかで、背景の調査（[background/slides.md](../background/slides.md)）の結論は変わりません。
- 図の自動配置のライブラリ（ELK、dagre など）。HTML の中で動かすと、ビルドのたびに同じ配置になる保証と、pptx と同じ位置を取るための Go の実装が別に要ります。升目の位置を作者が書けば、ノードは 7 つほどなので十分です。
- 画面の参照に使った暗い色や大きな数字などの飾り。舞台は明るい地に濃い文字で、色は意味のある数色だけにしました。
- 動画、音声、字幕。下の「映像にするとき」に論点を残します。

## 映像にするとき

音声の付いた動画は作っていません。その仕組み（動画用のレンダラー、尺や時刻の設定、空のアダプター）も置いていません。作るときに決めることを残します。

| 論点 | 決めること |
| --- | --- |
| 対象と長さ | 1 つの問いに絞るか、1 つのデッキの分にするか。見る前に知っていることと、見たあとに説明できること |
| ナレーション | 説明の順序と言い回し。略語と製品名の読み方。言語ごとの原稿 |
| 音声 | 人の声か音声合成か。声の利用の条件、発音の辞書、間と音量 |
| 字幕 | 校正、1 画面の行数、出す時刻、焼き込むか別のファイルか、日英 |
| 見せ方 | 寄る先、止める間、もう一度見せる場面。見る人が止めない前提での説明 |
| 出力と配信 | 解像度、フレームレート、形式、公開する場所、出典、章立て |
| 保守 | コードが変わったとき、どの画面、音声、字幕を直すか |

今の成果のうち映像にも使えるのは、シーンと段階とイベントの ID、学習の順序、各段階の完全な状態、根拠です。ただし、学習者が止めながら読む HTML の段階と、一定の速さで流れる映像の場面は同じではありません。HTML の段階をそのまま映像の尺にできるとは考えません。

候補の道具（Remotion、Motion Canvas、Manim Community、HyperFrames など）は、作ると決めたときに、登録の 1 つの問いで短い 1 本を作って比べます。比べるのは、音声と字幕を合わせる手間、直しやすさ、利用の条件、見たときの分かりやすさです。ライセンスと版は、そのときの公式の文書で確かめます。映像に合わせるために、HTML と pptx の作りを縛ることはしません。

## 確かめていないこと

- pptx を Microsoft PowerPoint で開くこと。LibreOffice 24.2 で PDF にして見たことと、発行元のスキーマによる検査（`xmllint`）だけです。図形の名前が選択ウィンドウに出ること、ノードを動かして文字を直せることも、PowerPoint では確かめていません。
- Chromium のほかのブラウザで HTML を開くこと。
- スクリーンリーダーで読み上げること。段階が変わったときの短い知らせ（`aria-live`）と、ボタンの名前は付けましたが、実際の読み上げは聞いていません。
- Calibri、Yu Gothic、Consolas が入ったマシンでの見え方。確かめたのは Carlito、Noto Sans CJK JP、DejaVu Sans Mono です。
