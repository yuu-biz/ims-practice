# ラボで IMS を見る

[English](../en/lab.md)

ラボは、IMS を試しながらその動きを観察するための Web の画面です。IMS の登録と通話は、起きるとすぐにラボに表示されます。それぞれをラダー図で描くこともできます。HSS にある加入の一覧も表示します。UE シミュレータ `phone1`、`phone2`、`phone3` の操作もできるので、コマンドを打たずに通話をかけて、その信号を確かめられます。

## 始める前に

- Docker と Docker Compose が動いていること。
- Web ブラウザがあること。

## ラボを開く

リポジトリのルートで次のコマンドを実行します。

```sh
docker compose up -d --build
```

ブラウザで <http://localhost:8080> を開きます。タイトルの横の点が `live` になっていれば、画面はラボのサーバーから更新を受け取っています。

ラボは、ホストのループバックアドレスにだけ公開しています。パスワードを求めず、届いた人は誰でも、HSS が持っているものを読む、UE を操作する、UE をアクセス網から切り離す、障害注入のエージェントが動いていればノードを壊す、といったことができるためです。同じネットワークの別のマシンから開くときは、リポジトリのルートに `compose.override.yaml` を作ります。Compose は `compose.yaml` のあとにこのファイルを自分で読みます。

```yaml
services:
  lab:
    ports: !override
      - "8080:8080"
```

もう一度 `docker compose up -d` を実行し、別のマシンで `http://<ホストのアドレス>:8080` を開きます。要らなくなったら、このファイルを削除します。

## 各パネルの内容

| パネル | 表示する内容 |
| --- | --- |
| UE simulators | UE シミュレータごとのカード。公開ユーザー識別子（IMPU）、登録しているかどうか、今の通話とその通話のセッション、着信の応答方針、送受信したショートメッセージ、付加サービスの設定を表示します。ボタンとフォームで UE を操作します。 |
| Calls | 通話ごとの行。発信者、着信者、状態、最終応答のコード、ダイアログの数を表示します。Call-ID を選ぶと、通話全体のラダー図を描きます。 |
| Ladder diagram | 選んだ通話か登録の、SIP と Cx のメッセージ。ノードごとに縦の線を引きます。矢印を選ぶと、メッセージの全文と、それを定めた仕様の条項を表示します。ショートメッセージを運ぶ MESSAGE では、RP と TP のフィールド、SMS の本文、MESSAGE のボディの 16 進数も表示します。**Copy as text** を押すと、ラダー図の全体を等幅のテキストにして書き出します。 |
| Registrations | 登録を確認できた公開ユーザー識別子ごとの行。Contact、有効期限、S-CSCF を表示します。識別子を選ぶと、最後の REGISTER のラダー図を描きます。 |
| Subscribers (HSS) | HSS にある加入ごとの行。公開ユーザー識別子とそのうち規制されているもの、試験用の利用者の印、受け取るサービスプロファイル、CAT を表示します。このパネルは加入を変えません。加入を作るのは運用者で、OAM から行います。 |
| Access network (EPC) | EPC のスタブに接続した UE ごとの行。スタブが渡したアドレス、EPS bearer、通話の Rx セッションを表示します。ボタンで、網が始める手順を起こせます。bearer の非活性化と、UE の切り離しです。 |
| Faults | 障害注入のエージェントが持つ障害の一覧と、障害を注入するフォーム。このエージェントを起動するまで、パネルは使えません。 |

ラボが知っているのは、ノードから届いた情報だけです。各ノードと UE シミュレータは送受信した SIP と Diameter のメッセージのコピーをすべて HEP でラボへ送ります（[キャプチャの手順書](capture.md) の「ラボに送るコピー（HEP）」を参照）。ラボはこのコピーだけから登録と通話を組み立て、ノードに状態を問い合わせることはしません。例外は 3 つのパネルです。UE シミュレータのカードはその UE が制御用の API で返す状態を、Access network と Faults のパネルは EPC のスタブと障害注入のエージェントがそれぞれの API で返す状態を表示します。どれもコピーから組み立てたものではないので、UE のカードと Registrations パネルの表示が一時的に食い違うことがあります。

## ラダー図の組み立て方

ノードからノードへ送られたメッセージは、送ったノードと受け取ったノードの両方から届きます。ラダー図では送信側のコピーと受信側のコピーのうち、送信元、宛先、中身が同じものを 1 本の矢印にまとめます。1 本の矢印がネットワーク上の 1 つのメッセージにあたります。まったく同じ中身の再送は、別の矢印になります。

Cx のメッセージには、どの SIP のリクエストのために送ったかを示すものがありません。Diameter の Session-Id と SIP の Call-ID は無関係です。そこでラボは手順の決まりを使って両者を結び付けます。Cx のリクエストは、同じノードが 2 秒以内に最後に受け取った SIP のリクエストのうち、同じ利用者を指すものに属するとします。UAR、MAR、SAR では、Authorization のユーザー名が User-Name と同じか、To が Public-Identity と同じ REGISTER です。LIR では、Request-URI が Public-Identity と同じリクエストです。応答は Session-Id でリクエストに結び付きます。この決まりは `internal/lab/causes.go` にあります。

P-CSCF の Rx のセッションも同じように結び付けます（TS 29.214 A.1、A.4）。最初の AAR が UE を示すのはアドレス（Framed-IP-Address）だけです。この AAR は、P-CSCF がそのアドレスから最後に受け取った SDP 付きの SIP のメッセージか、そのアドレスからの REGISTER のうち、あとに来たほうに属するとします。SDP 付きのメッセージは発信側の UE なら INVITE、着信側の UE なら 183 です。セッションのほかのメッセージ（STR、RAR、ASR と、その応答）は Session-Id で結び付きます。ラダー図では PCRF の列を P-CSCF の隣に描きます。メッセージの中身は [VoLTE の呼の流れ](volte.md) にあります。

Cx と Rx の矢印を選ぶと、詳細の **Link to this ladder** の欄に、この結び付きはラボがこの決まりで推定したもので、メッセージには書かれていないことが表示されます。

MMTel AS を通る通話は、1 つのダイアログではありません。AS は routeing B2BUA で（TS 24.229 5.7.5）、S-CSCF から届いた INVITE に自分で答え、自分の Call-ID を付けた新しい INVITE を送ります。そのため UE 1 から UE 2 への通話は、UE 1 とその AS、その AS と UE 2 の AS、UE 2 の AS と UE 2 の 3 つのダイアログになり、転送した通話ではさらに増えます。網の中では、どのダイアログの P-Charging-Vector にも、発信側の P-CSCF が入れてそれぞれの AS が残した、同じ icid-value が入っています（TS 24.229 5.2.6.3.3 step 7、5.7.5.1）。P-CSCF は、UE に送るものからこのヘッダを消します。ラボは、icid-value が同じダイアログを 1 つの通話として表示します。行には発信者のダイアログの Call-ID、状態、応答のコードを出し、Dialogs の列にダイアログの数を出します。ラダー図にはすべてのダイアログを、MMTel AS の列も含めて描きます。矢印を選ぶと、そのメッセージの Call-ID が分かります。転送した通話とほかのサービスは、[MMTel AS の付加サービス](mmtel.md) で説明しています。

ノードが自分自身にメッセージを送ることもあります。S-CSCF が発信側と着信側の両方を受け持つときがそうです。ラダー図では同じ縦の線に戻る矢印になります。このメッセージはコンテナの外に出ないので、Docker のネットワークでのキャプチャには入りません。ラボには表示されて pcap には無いメッセージは、これだけです。

## ラダー図をテキストでコピーする

ラダー図の下の **Copy as text** を押すと、ラダー図を等幅のテキストにして書き出します。1 行目にノードの名前を並べ、その下にメッセージごとの行を 1 行ずつ置いて、送信側の縦の線から受信側の縦の線へ矢印を引いたものです。手順書のラダー図と同じ形式なので、手順書や自分のメモの `text` のブロックにそのまま貼れます。

ラベルは矢印の左端に置き、残りをハイフンで埋めて、矢印の先が受け取ったノードの縦の線に届くようにします。右から左への矢印は `<` で始まります。自分自身に送ったメッセージは `<-+` で自分の縦の線に戻る矢印になり、その右にラベルが付きます。発信側の UE と着信側の UE のように、同じ種類のノードの列が 2 つあるときは、左から順に番号を付けます。

列の幅は、そこを横切るいちばん長いラベルに合わせます。SIP のメッセージのラベルはリクエスト行か応答行の全体なので、通話のラダー図は横に長くなります。貼ったあとで、手順書のラダー図のように、ラベルを短く書き直して手順に番号を付けてください。

コピーにはブラウザのクリップボードを使います。ブラウザは、安全とみなしたページにしかクリップボードを渡しません。<http://localhost:8080> は安全とみなされますが、同じラボを別のマシンから平文の HTTP で開いたときはみなされません。そのときはボタンの下にテキストを表示するので、選んでコピーしてください。

## HSS にある加入を見る

Subscribers パネルは、HSS が今持っている加入の一覧を表示します。加入そのものは変えません。加入を作るのは運用者の仕事で、運用者は OAM から行います（[OAM から網を運用する](registration.md#oam-から網を運用する)）。このパネルは、その変更が何をもたらしたかを見る場所です。

行には、その加入について HSS が持っているものが並びます。

- **Public identities**。規制されている識別子には `(barred)` が付きます。規制された識別子で S-CSCF が通すのは登録だけで、ほかの IMS の通信には使わせません（TS 29.228 B.2.1）。この網で IMS AKA を使う加入は、どれも 1 つ持っています。USIM があり ISIM の無いカードが IMSI から作って登録する、一時的な公開の識別子です。[ISIM の無い端末の識別子](volte.md#isim-の無い端末の識別子) がこの識別子を追っています。
- **Test user**。運用者が機能を試すために取っておく加入に付ける印です。試験用の利用者のサービスプロファイルを選び、網が試験用の利用者だけを収容しているあいだは、そもそも誰が登録できるかも決めます。[試験用の利用者だけを収容する](registration.md#試験用の利用者だけを収容する) にあります。
- **Service profile**。S-CSCF がその利用者について受け取るフィルタ条件、つまり利用者のリクエストがどのアプリケーションサーバーに届くかを決めるプロファイルです。欄に入っているのは、その加入自身が持つ名前です。名前を持たない加入は、種類ごとに HSS の設定が指すプロファイルを受け取り、どれを受け取るかが `from the settings: default` のように出ます。運用者はこの設定を、収容の方針を変えるのと同じ保守用の要求（[試験用の利用者だけを収容する](registration.md#試験用の利用者だけを収容する)）で、HSS を動かしたまま変えられます。
- **Alerting tone (CAT)**。その利用者にかけた相手が、呼び出し中に聞く音です（TS 24.182）。うしろに `(off)` が付いた音は、設定されていて鳴らさない状態なので、かけた相手には自分の呼び出し音が聞こえます。`none` は音を 1 つも持たない加入です。[CAT。着信側の利用者が選ぶ呼び出し音](mrf.md#cat着信側の利用者が選ぶ呼び出し音) が、音を設定して、それを鳴らす通話を追っています。

## 加入の変更が何をもたらすかを見る

HSS が自分から行うことのうち、ここで見るとよいものが 2 つあります。変わった利用者プロファイルを S-CSCF へ送ることと、登録を取り消すことです。どちらも、運用者が加入に加えた変更に続いて起きます。そこで、変更は OAM から行い、その結果をラボで見ます。

OAM のポートはホストのどのアドレスにもありません。BusyBox の `wget` は `GET` と `POST` のほかのメソッドを送れません。そのため以下の要求は、どれも OAM のコンテナの中から、書き下して `nc` に渡します。

ほかの手順書が使う加入者はそのままにしておきたいので、この試しのための加入を 1 つ足します。

```sh
docker compose exec oam sh -c '
body="{\"public_identities\":[\"sip:001010000000005@ims.mnc001.mcc001.3gppnetwork.org\"],\"password\":\"test-password-5\"}"
printf "PUT /oam/v1/subscriptions/001010000000005@ims.mnc001.mcc001.3gppnetwork.org HTTP/1.0\r\nContent-Type: application/json\r\nContent-Length: ${#body}\r\n\r\n%s" "$body" |
  nc -w 5 127.0.0.1 8080'
```

Subscribers パネルにその行が出ます。止めるまで登録したままでいる UE シミュレータで、この加入を登録します。

```sh
docker compose run --no-deps -d --name lab-subscriber-ue ue register \
  --impi 001010000000005@ims.mnc001.mcc001.3gppnetwork.org \
  --impu sip:001010000000005@ims.mnc001.mcc001.3gppnetwork.org \
  --password test-password-5
```

Registrations パネルに `sip:001010000000005@ims.mnc001.mcc001.3gppnetwork.org` の行が出ます。この識別子を選ぶと、その REGISTER のラダー図を描きます。

### 網が変わったプロファイルを送る

同じ加入を、フィルタ条件を 1 つも持たないサービスプロファイル `no-services` を付けて送り直します。

```sh
docker compose exec oam sh -c '
body="{\"public_identities\":[\"sip:001010000000005@ims.mnc001.mcc001.3gppnetwork.org\"],\"password\":\"test-password-5\",\"service_profile\":\"no-services\"}"
printf "PUT /oam/v1/subscriptions/001010000000005@ims.mnc001.mcc001.3gppnetwork.org HTTP/1.0\r\nContent-Type: application/json\r\nContent-Length: ${#body}\r\n\r\n%s" "$body" |
  nc -w 5 127.0.0.1 8080'
```

行の Service profile の欄が `no-services` になります。この利用者は登録中なので、HSS は登録のときに送った条件のままにしておきません。利用者プロファイルの全体を、すぐに S-CSCF へ送ります。Push-Profile-Request（PPR）です。[登録の手順書](registration.md#登録中の利用者のサービスプロファイルを変える) の「登録中の利用者のサービスプロファイルを変える」が、この流れと、そのあと利用者のリクエストがどこへ届くかを追っています。PPR とその答えはキャプチャには現れますが、ラダー図には描かれません。HSS が SIP のリクエストを受けて送るものではないためです。

### 網が登録を取り消す

加入を削除します。

```sh
docker compose exec oam sh -c '
printf "DELETE /oam/v1/subscriptions/001010000000005@ims.mnc001.mcc001.3gppnetwork.org HTTP/1.0\r\n\r\n" |
  nc -w 5 127.0.0.1 8080'
```

その行が Subscribers パネルから消え、登録も Registrations パネルから消えます。HSS が S-CSCF に Registration-Termination-Request（RTR）を送り（TS 29.228 6.1.3）、S-CSCF は RTA で答えて、reg イベントの NOTIFY で UE に知らせるためです。`docker logs lab-subscriber-ue` の最後に、網から登録を解除されたことが出ます。この UE は登録し直しません。流れの全体は [登録の手順書](registration.md#加入を削除するhss-からの登録解除) の「加入を削除する（HSS からの登録解除）」にあります。RTR と RTA はキャプチャには現れますが、ラダー図には描かれません。理由は上の PPR と同じです。HSS は SIP のリクエストを受けて RTR を送るわけではないので、ラボは RTR をどの通話や登録にも結び付けません。

終わったら、UE のコンテナを片付けます。

```sh
docker rm lab-subscriber-ue
```

## UE シミュレータを操作する

3 台の UE シミュレータ `phone1`（加入者 1、`tel:+12025550101`）、`phone2`（加入者 2、`tel:+12025550102`）、`phone3`（加入者 3、`tel:+12025550103`）は、ほかのノードと一緒には起動しません。`phones` プロファイルで起動します。

```sh
docker compose --profile phones up -d --build
```

起動するまで、カードには接続できないと表示されます。起動すると、それぞれが自分で登録します。カードが `not registered` のままなら、**Register** を押してください。

`volte10` と `volte12` のカードはプロファイル `volte` の VoLTE の UE です。どちらも EPC スタブに attach し、IMS-AKA で登録します。`docker compose --profile volte up -d volte10 volte12` で起動し、`volte10` から `tel:+12025550112` に発信します。そうした通話の流れは [VoLTE の呼の流れ](volte.md) で追っています。2 つのプロファイルは加入者もアドレスも別なので、同時に起動できます。

通話は次の手順でかけます。

1. `phone2` のカードで、応答方針を `manual` にします。こうすると、応答するまで鳴り続けます。`auto` では 1 秒後に自動で応答し、`reject` ではすべての着信を 486（Busy Here）で断ります。
2. `phone1` のカードで **Call** を押します。宛先の欄には、HSS の加入から調べたもう一方の UE の tel URI が最初から入っています。
3. `phone2` のカードに、`ringing` の状態の着信が表示されます。**Answer** を押すと、両方のカードで通話が `active` になります。それぞれのカードの **Session** の行には、通話のコーデック、両側の SDP での音声の方向、プリコンディションの表（RFC 3312）、アクセス網がメディアのリソースを確保したかどうかが表示されます。`phone1` と `phone2` は Compose のネットワークから直接 P-CSCF につながります。このネットワークはメディアのリソースを確保する必要がないアクセス網なので、2 つのカードには `no reservation of media resources needed on this access network` と表示されます。
4. `phone1` のカードで **Hold** を押します。UE は音声を `sendonly` にするオファーを入れた re-INVITE を送ります（TS 24.610）。両方のカードの Session の行に、新しい方向が表示されます。**Resume** を押すと、`sendrecv` に戻して通話を再開します。
5. `12#` のような数字を入力して **Send DTMF** を押します。UE はその数字を RTP の telephone event として送ります（RFC 4733）。もう一方のカードの Session の行には、その数字が受け取った数字として表示されます。
6. どちらかのカードで **Hang up** を押します。応答したあとの通話では BYE を送ります。応答の前なら、発信側は CANCEL を送り、着信側は 603（Decline）で断ります。

通話の横の **ladder** を選ぶと、通話中でもラダー図を描けます。それぞれのカードが知っているのは自分のダイアログだけですが、どちらのカードから開いても、ラダー図には通話全体が出ます。UE が受け付けない操作のボタンは押せなくなっています。たとえば、通話中に 2 本目の発信はできません。

ショートメッセージ（SMS over IP、[SMS の手順書](sms.md) を参照）は次の手順で送ります。

1. `phone1` のカードの SMS のフォームに入力します。番号の欄には、もう一方の UE の番号 `+12025550102` が最初から入っています。本文は GSM 7 ビットのアルファベットなら 160 文字まで、日本語などほかの文字なら 70 文字まで書けます。配達の結果を SC に報告してもらうときは、**status report** に印を付けます。
2. **Send SMS** を押します。**SMS sent** にメッセージが `waiting for the submit report` と表示され、すぐに `accepted by the SC` に変わります。
3. `phone2` のカードの **SMS received** に、送信者の番号と本文が表示されます。
4. status report を頼んだときは、`phone1` の行の最後に `status report: delivered (TP-ST 0x00)` と表示されます。

どの加入者も持たない番号（`+12025550198` など）に送ると、`refused by the SC: RP-ERROR, RP-Cause 1, TP-FCS 0xc3` で終わります。加入者 4 の `+12025550104` はここでは登録しないので、SC はメッセージを受け付けますが、status report は `not delivered, the SC has given up (TP-ST 0x62)` になります。

各行の **ladder** を選ぶと、そのショートメッセージを運んだ MESSAGE のラダー図を描きます。submit report、delivery report、status report は別の MESSAGE で、それぞれ別の Call-ID を持ちます。

カードは通話の表示を更新しているのと同じイベントストリームで、ショートメッセージの表示も更新します。各 UE は何かが変わるたびに、ショートメッセージを含めた状態の全体を送ります。

着信転送などの付加サービスは、UE が Ut で XCAP を使って設定します。手順は次のとおりです。

1. `phone2` のカードで **Supplementary services (Ut/XCAP)** を開きます。UE は MMTel AS の XCAP サーバーから自分の文書 `simservs.xml` を読み、カードにすべてのサービスを並べます。着信転送（CFU、CFB、CFNR、CFNRc、CFNL）、規制（BAIC、BIC-Roam、ACR、BAOC、BOIC、BOIC-exHC）、OIR の既定値です。HSS は各サービスを止めた状態で用意するので、最初はどれも `off` です（GSMA IR.92 2.3.2）。
2. サービスを選びます。たとえば **CFU (unconditional)** です。転送先の欄には、もう一方の UE の tel URI が最初から入っています。別の番号にするときは `tel:+12025550103` のように書き換えます。**On** を押すと、一覧に `CFU (unconditional): on to tel:+12025550103` と表示され、その下の ETag が 1 つ増えます。
3. **Off** を押すと、転送を止めます。IR.92 2.3.2 のとおり、転送先は消さずに残ります。

ボタンを押すたびに、UE が自分で XCAP の要求を送ります。最初に文書全体を GET し、次に変える規則 1 つだけを `If-Match` を付けて PUT し、一覧を表示するためにもう一度 GET します。XCAP サーバーは、HSS にある文書を Sh で読み書きします（UDR と PUR、Service-Indication は `MMTEL-Services`）。HTTP も、この Sh の要求も SIP の要求には結び付かないので、ラダー図には出ません。キャプチャには、80 番ポートの HTTP と 3868 番ポートの Diameter としてすべて残ります。最初の GET には 401 が返り、HTTP Digest の challenge が SHA-256、MD5 の順に 2 つ付いています。UE は先頭の SHA-256 で答えます。

利用者に電話をかけた人が聞く呼び出し音（CAT、customized alerting tone、TS 24.182）を鳴らすには、加入者 2 に `cat1` を OAM から設定します。設定の仕方は [CAT。着信側の利用者が選ぶ呼び出し音](mrf.md#cat着信側の利用者が選ぶ呼び出し音) にあります。設定すると、その行の Alerting tone (CAT) の欄が変わります。MMTel AS は、その利用者への着信のたびにこの設定を Sh で読みます。もう一度 `phone1` から `phone2` に発信すると、`phone2` が応答するまで MRFP がその音をアーリーメディアとして `phone1` に流します。`phone1` の Session の行には `rang with early media from the network` と表示されます。音を鳴らさない設定に戻すと、同じ行は `rang with the UE's own ringing tone` になります。

2 つ目の着信を受け、2 つの通話から会議を作るには、次のようにします（TS 24.615、TS 24.147）。

1. `phone1` から `phone2` に発信し、応答させます。
2. `phone3` から `phone1` に発信します。`phone1` のカードの **Other call** に、新しい着信が `waiting` と表示されます。`phone1` は `Alert-Info: <urn:alert:service:call-waiting>` を付けて呼び出しを返しています。
3. `phone1` で **Answer** を押します。`phone2` との通話を保留にしてから、`phone3` に応答します。**Swap** を押すと、もう一方の通話に切り替わります。
4. `phone1` で **Merge** を押します。`phone1` は MMTel AS に会議を作り、相手ごとに REFER を送って、その相手を会議に招くよう頼みます。3 台のカードの **Conference** の行には、会議イベントパッケージが伝える 3 人の利用者が並びます。音声は MRFP が混ぜます。

この呼び出し音、2 つ目の着信、会議をキャプチャで追う手順は、[MRF の手順書](mrf.md) にあります。

同じ設定は、コマンドラインの `ue xcap get`、`ue xcap set cfu on tel:+12025550103`、`ue xcap oir restricted` でもできます。`ue xcap noreply 5` は、CFNR で転送するまでに呼び出す時間を 5 秒から 180 秒の間で設定します。カードでは 20 秒のままです。

この UE シミュレータは加入者 1、2、3 を使います。`ue` プロファイルの `ue`、`ue2`、`ue3` と同じ加入者です。2 つのプロファイルは同時に使わないでください。同じ加入者の UE が 2 台あると、互いの登録を上書きしてしまいます。

## bearer を落とし、UE を切り離す

**Access network (EPC)** のパネルには、EPC のスタブに接続した UE が並びます。`volte` プロファイルの `volte10` と `volte12` です。行には IMSI、スタブが渡したアドレス、アクセスポイント名、UE の EPS bearer、その UE のために P-CSCF が持つ Rx セッションの Session-Id が出ます。

接続した UE には、SIP の信号を運ぶ既定の bearer（EBI 5、QCI 5）があります（IR.92 4.4.1）。通話を組み立てる間は、その隣に音声の専用 bearer（QCI 1）が現れます（4.4.2）。

- 音声の bearer の **Release** を押すと、無線が切れたときと同じように、網がその bearer を非活性化します（TS 24.301 6.4.4.2）。PCRF は通話の Rx セッションを打ち切り、P-CSCF は利用者の代わりに BYE を送って通話を終わらせ、2 台の UE のカードは通話の無い状態に戻ります。この流れをキャプチャで追う手順は、[VoLTE の呼の流れ](volte.md) の「網が bearer を落とす」にあります。
- 既定の bearer に **Release** はありません。PDN 接続と一緒のものなので、スタブは非活性化を断り、代わりに切り離しを求めます。
- **Detach** を押すと、網が UE を切り離します（5.5.2.3）。PDN 接続が終わり、PCRF はその UE の Rx セッションをすべて打ち切り、UE は DETACH ACCEPT で答えます。スタブは再接続を求めないので、UE はアクセス網から離れたままです。`docker compose --profile volte up -d volte10` のように起動し直してください。

この状態を持っているのはスタブで、ラボは写しを持ちません。そのため、パネルは数秒ごとにスタブへ問い合わせます。

## わざとノードを壊す

**Faults** のパネルでは、ノードを止める、凍らせる、プロセスを落とす、パケットを失わせる、遅らせる、ほかのノードから切り離す、といった操作ができます。障害が起きたときの信号を、その場で見るためのものです。これには障害注入のエージェントが要ります。Docker の Engine を操作するため、このエージェントは、起動すると指定したときだけ動きます。その理由、起動の方法、それぞれの障害の内容は [障害注入](../../../deploy/chaos/README.md) にあります。起動するまで、パネルはエージェントが動いていないことを表示し、フォームは使えません。

対象（`pcscf` など）と種類を選びます。フォームに出るのは、その種類が取る項目だけです。続く障害には継続時間、`delay` には遅延とゆらぎ、`loss` には割合、`partition` には切り離す相手、ネットワークの障害には、障害を置く Compose のネットワークです。**Inject** を押すと、ID と状態の付いた行が表に現れ、**Clear** で元に戻せます。継続時間が切れた障害も終わります。既定は 5 分なので、戻し忘れた障害が残り続けることはありません。`crash` と `recreate` は一度きりの障害です。ノードが自分で戻ってくるので `done` で終わり、戻すものはありません。

要求を確かめるのはエージェントで、パネルはその答えをそのまま表示します。すでに障害のある対象にもう 1 つ要求すると `conflict` になり、Docker が実行できなかった障害は `failed` の状態と理由が並びます。

## このプロジェクト独自の API

次の 3 つは、3GPP や IETF の仕様に無いもので、IMS の一部でもありません。

- HEP によるコピー。HEP は信号を集めるための Homer プロジェクトのプロトコルです。キャプチャには、本来のメッセージとは別に、UDP の 9060 番ポートへのコピーのパケットが入ります。
- ラボの HTTP API。`internal/lab/lab.go` のパッケージのコメントに一覧があります。
- UE シミュレータ（`ue serve`）の制御用の API。`internal/ue/phone_http.go` の `Phone.Handler` のコメントに一覧があります。付加サービスの部分は、`internal/ue/xcap.go` の `SupplementaryServices.Handler` のコメントにあります。[通話の手順書](call.md) の「HTTP で UE を操作する」では、この API を直接使います。

一方で、ラダー図に描かれる信号は、仕様で定められたとおりの IMS の信号です。
