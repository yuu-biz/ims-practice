# 音声通話の流れを追う

[English](../en/call.md)

> この手順書は、構成を動かして確かめるための手順です。仕組みと判断の理由を読むだけで分かるように説明した本文は、本の [番号から相手の電話へ](../../book/ja/call.md)、[通話のトランザクション、ダイアログ、メディアの交渉](../../book/ja/call-signaling.md) にあります。

この手順書では UE 1 から UE 2 に電話番号で 1 回発信し、キャプチャに記録されたメッセージを順に読んでいきます。次のことが分かります。

- 電話番号が SIP のアドレスに変わるしくみ。
- 各 CSCF が次の CSCF を見つける方法。
- 2 台の UE がメディアを合意する方法。
- 音声がメディア中継ノードを通って流れる様子。

この手順書は 3GPP の Release 18（TS 24.229 V18.11.0、TS 29.228 V18.0.0）と、各手順で挙げる RFC に沿っています。

## 始める前に

- [UE が IMS に登録する流れを追う](registration.md) を読んでおくこと。通話の前に、2 台の UE がその手順書のとおりに登録します。通話は登録で決まった次のものを使います。
  - Path。
  - Service-Route。
  - P-CSCF の IP の対応付け。
- 略語の説明は [用語集](../../glossary.md) にあります。

## 登場するノード

| ノード | アドレス | 通話での役割 |
| --- | --- | --- |
| UE 1 | 172.28.0.100 | 発信者。`+1-202-555-0101`。 |
| UE 2 | 172.28.0.101 | 着信者。`+1-202-555-0102`。 |
| P-CSCF | 172.28.0.40 | 両方の UE を担当する。1 回の通話は P-CSCF を 2 回通る。1 回目は発信側、2 回目は着信側の通過である。 |
| S-CSCF | 172.28.0.30 | これも両方の UE を担当するので、発信側（originating）と着信側（terminating）の S-CSCF を兼ねる。 |
| I-CSCF | 172.28.0.20 | 着信者のホーム網の入口。着信者がどこにいるかを HSS に問い合わせる。 |
| MMTel AS | 172.28.0.75 | 利用者ごとに 1 回ずつ、合わせて 2 回加わる（手順 3 と 6）。S-CSCF は iFC に従って、すべての INVITE をここへ送る。AS は利用者のサービスの設定を Sh で HSS から読む。既定の設定では何も変えない。ほかの設定での動きは [MMTel AS の付加サービス](mmtel.md) で見る。 |
| HSS | 172.28.0.10 | I-CSCF の所在の問い合わせに Cx で、MMTel AS のサービスの設定の問い合わせに Sh で答える。 |
| DNS | 172.28.0.2 | 電話番号を SIP URI に変える ENUM のレコードを持つ。 |
| メディア中継ノード（IMS-AGW） | 172.28.0.50 | RTP を中継する。P-CSCF が制御する。 |

番号は北米の番号計画で架空用に予約されている 555-0100〜0199 の範囲から選んでいます。

## 発信する

1. 登録の手順書と同じように構成を起動し、Diameter の接続が開くのを待ちます。

   ```sh
   docker compose up -d --build
   ```

2. 1 つ目の端末で、UE 2 を着信の待ち受けにします。UE 2 は 1 秒鳴らしてから応答し、トーンを流し、聞こえた音声を保存します。

   ```sh
   docker compose run --rm ue2 answer \
     -impi 001010000000002@ims.mnc001.mcc001.3gppnetwork.org \
     -impu sip:+12025550102@ims.mnc001.mcc001.3gppnetwork.org \
     -password test-password-2 -wav-out /captures/ue2-heard.wav
   ```

3. 2 つ目の端末で、UE 1 から UE 2 に番号で発信します。UE 1 は 3 秒のトーンを流してから切断します。

   ```sh
   docker compose run --rm ue call -tone 3s tel:+1-202-555-0102
   ```

   `-tone` の代わりに `-wav-in <ファイル>` を付けると、WAV ファイルを流します。ファイルは 16 ビット PCM、モノラル、8000 Hz にしてください。

4. `captures/ue2-heard.wav` に、UE 2 が聞いた音声が入っています。音声プレーヤーで再生できます。

失敗する場合も試せます。

- **話中.** UE 2 を `-reject 486` 付きで起動します。通話は `486 Busy Here` で終わります。
- **未登録.** 登録しない加入者の `tel:+12025550103` に発信します。通話は `480 Temporarily Unavailable` で終わります。
- **存在しない番号.** ENUM のレコードが無い `tel:+12025550198` に発信します。通話は `404 Not Found` で終わります。
- **片方向の音声.** UE 2 を `-tone 0s` 付きで起動し、RTP を送らないようにします。UE 1 はいつもどおり BYE で切断しますが、`ue call` は `no RTP received` のエラーで終わります。UE 2 の SDP のアンサーが `sendrecv` だったので、応答のあとに RTP が届くはずだったからです。UE 2 は UE 1 の音声を受けたので、エラーなしで終わります。通話の終わりに相手の SDP が `sendonly`、`recvonly`、`inactive` のときと、UE 自身が通話を保留にしているときは、RTP が届かなくても失敗にしません。保留にした UE は何も送らないためです（IR.92 2.3.10）。応答の前の早期メディアは、通話の RTP に数えません。

## キャプチャを開く

`captures/` の一番新しいファイルを Wireshark で開き、次の表示フィルタを使います。

```text
sip || diameter.cmd.code == 302 || dns.qry.type == 35 || rtp || rtcp
```

**Telephony > VoIP Calls** に通話が表示されます。選んで次のボタンを押します。

- **Flow Sequence.** シーケンス図を表示します。
- **Play Streams.** 両方向の音声を聞けます。

RTP は SDP でしか知らされないポートを使います。キャプチャに同じ通話の SIP も入っていれば、Wireshark はそのポートを見つけられます。この手順のキャプチャには SIP も入っています。それでもストリームがただの UDP と表示されるときは、**Analyze > Enabled Protocols** で **rtp_udp**（RTP の推定）を有効にします。

## シーケンス

```text
  UE 1      P-CSCF     S-CSCF    MMTel AS      DNS      I-CSCF       HSS      S-CSCF     P-CSCF      UE 2
    |INVITE (1)>          |          |          |          |          |          |          |          |
    |          |INVITE (2)>          |          |          |          |          |          |          |
    |          |          |INVITE (3)>          |          |          |          |          |          |
    |          |          <new INVITE|          |          |          |          |          |          |
    |          |          |ENUM NAPTR (3)------->          |          |          |          |          |
    |          |          <sip: URI-------------|          |          |          |          |          |
    |          |          |INVITE (4)---------------------->          |          |          |          |
    |          |          |          |          |          |LIR------->          |          |          |
    |          |          |          |          |          <LIA-------|          |          |          |
    |          |          |          |          |          |INVITE (5)----------->          |          |
    |          |          |          <INVITE (6)---------------------------------|          |          |
    |          |          |          |new INVITE--------------------------------->          |          |
    |          |          |          |          |          |          |          |INVITE (6)>          |
    |          |          |          |          |          |          |          |          |INVITE (7)>
    <183 with the SDP answer, back through every hop (8)-----------------------------------------------|
    <PRACK, 200 (PRACK) in each of the three dialogs (9)===============================================>
    <180, PRACK, 200 (PRACK) (10)======================================================================>
    <200 OK (INVITE) (10)------------------------------------------------------------------------------|
    |ACK (11)==========================================================================================>
    | RTP and RTCP through the media relay (12) |          |          |          |          |          |
    | BYE, 200 (BYE) (13) |          |          |          |          |          |          |          |
```

I-CSCF はルートセットに入りません。Record-Route を付けないので、PRACK、ACK、BYE は I-CSCF を通りません。

MMTel AS は、利用者ごとに 1 回ずつ、合わせて 2 回加わります（手順 3 と 6）。AS は routeing B2BUA です（TS 24.229 5.7.5）。受けた INVITE に自分で答え、自分の Call-ID で新しい INVITE を送ります。そのため、1 本の通話にダイアログが 3 つできます。UE 1 と発信者の AS、その AS と着信者の AS、その AS と UE 2 のあいだです。ダイアログの中の要求はそのダイアログの相手で終わり、AS が次のダイアログに送り直します。

### 1. UE 1 が INVITE を送る

TS 24.229 5.1.3.1 と 5.1.2A.1.1 の手順です。次の点を見てください。

- **Request-URI.** `tel:+1-202-555-0102` です。UE は番号をダイヤルするだけで、着信者がどこにいるかは知りません。
- **Route.** 2 つあります。P-CSCF と、UE 1 が登録で受け取った Service-Route（`sip:orig@scscf...`）です。UE の要求はすべて、P-CSCF を通って自分の S-CSCF に届きます。
- **Supported: 100rel, timer, 199, precondition.** UE 1 は信頼性のある暫定応答（RFC 3262 4）、セッションタイマー（RFC 4028）、199 の応答（RFC 6228）、プリコンディション（RFC 3312）を受け付けます。プリコンディションは Supported に入れるだけで、Require には入れません（TS 24.229 5.1.3.1）。
- **Session-Expires: 1800.** IR.92 2.2.8 が UE に求めるセッションの間隔です。着信者の 200 で UE 1 がセッションを更新する側に決まり、間隔の半分が過ぎると UE 1 が UPDATE で更新します。
- **P-Early-Media: supported.** UE 1 が網からの早期メディアの許可を受け付けることを示します（TS 24.229 5.1.3.1、RFC 5009）。**P-Preferred-Service** と **Accept-Contact** にはマルチメディア電話（MMTel）の ICSI が入り（TS 24.229 5.1.2A.1.1）、**User-Agent** には UE の名前が入ります（IR.92 2.6）。Contact にも同じ ICSI と `audio` の機能タグが入ります（IR.92 2.2.4）。
- **SDP のオファー**（RFC 3264 5.1）。`c=` と `m=audio` に UE 1 自身のアドレスと RTP のポートがあります。`a=rtpmap:0 PCMU/8000` で G.711 を、`a=rtpmap:101 telephone-event/8000` で DTMF を提示しています（TS 24.229 6.1.1）。`b=AS`、`b=RS`、`b=RR` は RTP と RTCP の帯域です（IR.92 3.2.2.4、3.2.4）。`a=curr` と `a=des` の行がプリコンディションです。UE 1 には資源を確保するアクセス網が無いので、自分の資源はすでにあると示します（TS 24.229 6.1.2）。

`-epc` を付けて起動した UE は先に EPC スタブに接続し、VoLTE の UE として動きます。PCMU より前に AMR-WB と AMR を提示し、網が音声の bearer を作るまでは、資源を確保していないとオファーに書きます。この呼の流れは [VoLTE の呼の流れ](volte.md) で追います。

### 2. P-CSCF が発信者の S-CSCF に送る

一番上の Route に、P-CSCF の Path にある `term` というユーザー部が無いことから、P-CSCF はこれが発信側だと判断します（TS 24.229 5.2.6.2）。そして、TS 24.229 5.2.6.3.3 にある次のことを行います。

- 自分の Route を取り除き、残りが Service-Route と一致することを確かめます。違うものを入れてきた UE には、Service-Route を入れ直します。
- **P-Asserted-Identity** に、UE 1 の既定の公開の識別子を入れます。網はこのヘッダを信用します。UE が From に何を書いていても関係ありません。
- **Record-Route** に自分の URI を入れます。その後の通話の要求が P-CSCF を通って戻ってくるようにするためです。
- メディア中継ノードに**コンテキスト**を作らせます。コンテキストには UE 1 に向いたアクセス側のターミネーションと、網に向いたコア側のターミネーションがあります。アクセス側のターミネーションには、UE 1 が受け取る場所（UE 1 の SDP のアドレス）を教えます。そして **SDP を書き換え**、`c=` と `m=` がコア側のターミネーションを指すようにします。ここから先の網に見えるのは中継ノードで、UE 1 は見えません。

P-CSCF は複数のメディア中継ノードを使えます。一覧は `deploy/compose/pcscf.yaml` の `media_relays` で、この網には 1 つだけあります。呼が中継ノードに分かれるように、P-CSCF は呼ごとに Call-ID の hash で中継ノードを 1 つ選びます。選んだ中継ノードが応答しないときや空いたポートが無いときのように、コンテキストを作れないときは、一覧の次の中継ノードを使います。P-CSCF が記録するダイアログには、コンテキストを持つ中継ノードも入ります。このあとメディアを変えるときも、コンテキストを解放するときも、P-CSCF はその中継ノードに要求を送ります。

要求は、このプロジェクトの小さな HTTP の制御 API で送ります。P-CSCF と中継ノードの間の通信として、キャプチャにも出てきます。この用途の標準のプロトコルは H.248 です。[構成の手引き](README.md#メディア中継ノードを-h248-で制御する)の構成では、P-CSCF は HTTP の API の代わりに H.248 を話します。

### 3. S-CSCF が番号を SIP URI に変える

一番上の Route に `orig` があるので、S-CSCF は発信者を担当する側として動きます（TS 24.229 5.4.3.1）。担当する利用者は P-Asserted-Identity の利用者です。網の中のノードが利用者の代わりに要求を送るときは、P-Served-User の利用者です（TS 24.229 5.4.3.2 の手順 1）。S-CSCF は、その利用者が登録済みであることを確かめます。（アプリケーションサーバーが利用者の代わりや、自分が受け持つ PSI の代わりに要求を送るときは、`orig` を S-CSCF の URI のパラメータとして付けます。会議の URI のように登録の無い利用者なら、S-CSCF は HSS からプロファイルを受け取ります。[フォーカスが相手を招く方法](mrf.md#フォーカスが相手を招く方法) を参照してください。）次に、P-Asserted-Identity の SIP URI の別名である UE 1 の tel URI を、2 つ目の P-Asserted-Identity として加えます（TS 24.229 5.4.3.2 の手順 9）。UE 1 の INVITE には MMTel の ICSI を入れた **P-Preferred-Service** があります。S-CSCF は、その INVITE が音声か映像を含む通話であることを確かめます。このプロジェクトの事業者のデータでは、そうした通話を MMTel とみなします。そのうえで ICSI を **P-Asserted-Service** に入れ、P-Preferred-Service を取り除きます（TS 24.229 5.4.3.2 の手順 4C、RFC 6050）。UE 2 の P-CSCF はあとでこのサービスを PCRF に伝えます。そして Record-Route を付けます。どの加入者にも、INVITE をまず MMTel AS に送る iFC（initial filter criteria）があります（TS 24.229 5.4.3.2 の手順 5）。S-CSCF は `sescase=orig` を付けた **P-Served-User** を加えます。Route の先頭に AS の URI を、その次に元のダイアログの識別子（`odi`）を付けた自分の URI を置きます。AS は発信者のサービスの設定を Sh で HSS から読み、その Route に沿って新しい INVITE を送り返します。`deploy/compose/hss.yaml` の既定の設定では、通話のほかの部分は変えません。INVITE が `odi` を持って戻ってくると、S-CSCF はその iFC の次から処理を続けます。Request-URI が tel URI なので、S-CSCF は DNS に問い合わせます（TS 24.229 5.4.3.2 の手順 10、RFC 6116）。

1. 番号 `+12025550102` を、ドメイン `2.0.1.0.5.5.5.2.0.2.1.e164.arpa` に変えます。数字を逆順にし、1 桁ずつラベルにします。
2. そこにある NAPTR レコードは、サービスが `E2U+sip` です。正規表現で `sip:+12025550102@ims.mnc001.mcc001.3gppnetwork.org` を作ります。
3. これが新しい Request-URI になります。

レコードは `deploy/compose/dns/e164.arpa.zone` にあります。レコードの無い番号には IMS の中からは届きません。実網では BGCF を通して電話網に送ることもできますが、このプロジェクトには BGCF が無いので、S-CSCF は 404 で答えます。TS 24.229 5.4.3.2 の手順 10 は、BGCF に送る代わりに、S-CSCF が発信者に応答を返すことも認めています。

### 4. S-CSCF が着信者のホーム網を見つける

Request-URI のドメインは `ims.mnc001.mcc001.3gppnetwork.org` になりました。S-CSCF は、REGISTER のときの P-CSCF と同じく NAPTR と SRV でこれを引き、そのドメインの入口である I-CSCF に INVITE を送ります。

INVITE は、ノードを通るたびにヘッダが増えて大きくなります。S-CSCF から先では 1300 バイトを超えるので、各 CSCF は UDP ではなく TCP で送ります（RFC 3261 18.1.1）。キャプチャでは、その区間の Via が `SIP/2.0/TCP` になり、応答は同じ TCP の接続で戻ってきます。

### 5. I-CSCF が着信者の所在を HSS に問い合わせる（LIR と LIA）

I-CSCF は着信者の公開の識別子を入れた **Location-Info-Request**（LIR、Cx のコマンド 302）を送ります（TS 24.229 5.3.2.1、TS 29.228 6.1.4）。HSS は DIAMETER_SUCCESS で答え、UE 2 が登録している S-CSCF の **Server-Name** を返します。

I-CSCF はその S-CSCF を Route の一番上に入れて INVITE を転送します。Record-Route は付けません。P-Charging-Vector は届いたまま運びます。信頼のドメインの外にある相手網からの要求のように、P-Charging-Vector の無い要求には、I-CSCF が icid-value を付けます（TS 24.229 5.3.2.1）。

UE 2 が未登録なら、HSS は DIAMETER_ERROR_IDENTITY_NOT_REGISTERED で答え、I-CSCF は 480 を返します。存在しない利用者なら DIAMETER_ERROR_USER_UNKNOWN になり、I-CSCF は 404 を返します。

未登録でも、未登録の状態のサービスを持つ利用者には、HSS は代わりに能力（Server-Capabilities）を付けた DIAMETER_UNREGISTERED_SERVICE（2003）で答えます（TS 29.228 6.1.4.1）。未登録の状態のサービスとは、MMTel AS の着信転送（[MMTel AS の付加サービス](mmtel.md)）のように、session case が TERMINATING_UNREGISTERED の iFC です。I-CSCF は初回の登録と同じように S-CSCF を選び、その S-CSCF が UNREGISTERED_USER の SAR で利用者のプロファイルを取ってきて、そのサービスを動かします（TS 24.229 5.4.3.3）。どのサービスも呼を引き受けなければ、S-CSCF が 480 を返します。`deploy/compose/hss.yaml` の試験用の加入者には、どれもそのようなサービスがあります。TERMINATING_UNREGISTERED の場合に MMTel AS を呼ぶ iFC です。着信転送を設定していなければ、AS は INVITE をそのまま送り返し、S-CSCF が 480 を返します。

### 6. 着信側の S-CSCF が Path に沿って INVITE を送る

一番上の Route に `orig` が無いので、今度は S-CSCF が着信者を担当する側として動きます（TS 24.229 5.4.3.3）。UE 2 の登録を見つけます。発信側の S-CSCF が入れた P-Asserted-Service はそのまま残します。UE 2 が MMTel に加入しているためです（手順 3C）。MMTel AS の iFC が、今度は `sescase=term` を付けて INVITE を AS に送ります（手順 4）。AS は新しい INVITE を送り返します。そのあとで S-CSCF は次のことをします。

- Record-Route を付けます。
- **P-Called-Party-ID** に、発信された宛先を入れます。
- Request-URI を、UE 2 が登録した **Contact** にします。
- UE 2 の REGISTER にあった **Path** を Route に入れます。これで INVITE は、UE 2 が登録に使った P-CSCF に届きます。

ここでは 1 台の S-CSCF が両方の利用者を担当しているので、この 1 台が発信側と着信側の S-CSCF を兼ねます。キャプチャでは、INVITE が S-CSCF から I-CSCF へ出て、また戻ってくる様子が見えます。

### 7. P-CSCF が INVITE を UE 2 に届ける

一番上の Route が P-CSCF の Path の URI（ユーザー部が `term`）なので、今回の通過は着信側です（TS 24.229 5.2.6.4.3）。P-CSCF は次のことをします。

- 自分の Route を取り除き、Record-Route を付けます。
- 通話の着信側のために、**2 つ目の中継のコンテキスト**を作ります。コア側のターミネーションの送り先は、オファーにあるアドレス（1 つ目のコンテキストのコア側のターミネーション）にします。オファーは新しいコンテキストのアクセス側のターミネーションを指すように書き換えます。
- INVITE を、UE 2 の Contact ではなく、UE 2 の REGISTER が来たアドレスに送ります。NAT の内側にいる UE にはそちらでしか届かないためです。

### 8. UE 2 がオファーに答える（信頼性のある 183）

UE 2 は SDP のアンサー（RFC 3264 6.1）を入れた **183 Session Progress** で答えます。アンサーには 1 つのコーデック（PCMU とその telephone-event）と、UE 2 自身のアドレスとポートが入っています。INVITE に `Supported: 100rel` があったので、183 は信頼性のある暫定応答になります（RFC 3262 3）。**Require: 100rel** と **RSeq** が付き、UE 2 は PRACK が届くまで 183 を送り直します。

183 には **Require: precondition** も付きます。INVITE がプリコンディションに対応しているので、UE 2 もこの仕組みを使います（TS 24.229 5.1.4.1）。SDP には両端のプリコンディションの状態の表が入ります。ここではどちらの UE も資源をすでに持っているので、必須のプリコンディションはすべて満たされており、UE 2 は UE 1 に確認を求めません（`a=conf` の行がありません）。

183 で**初期ダイアログ**（early dialog）ができます。183 には To のタグ、Contact、Record-Route の一覧が入っています。

183 が戻る途中で、P-CSCF は 2 回の通過のそれぞれでアンサーを書き換えます。

- 着信側の通過では、アクセス側のターミネーションを UE 2 のアンサーに向け、SDP にはコア側のターミネーションを書きます。
- 発信側の通過では、コア側のターミネーションをそのアンサー（コンテキスト 2 のコア側）に向け、SDP にはアクセス側のターミネーションを書きます。そのため UE 1 に見えるのは、自分のコンテキストのアクセス側のターミネーションです。

その結果、どちらの UE も中継ノードとだけやり取りします。

着信側の通過では、誰が応答したかも P-CSCF が示します。UE 2 が 183、180、200 に入れた P-Asserted-Identity や P-Preferred-Identity を取り除き、手順 6 の P-Called-Party-ID の識別子を **P-Asserted-Identity** に入れます（TS 24.229 5.2.6.4.4 step 1）。UE 1 には、これが応答した相手の識別子として見えます（TIP）。応答に `Privacy: id` があるときは、UE が信頼ドメインの外にあるので、発信側の通過で P-Asserted-Identity を取り除いてから UE 1 に送ります（RFC 3325 7、TS 24.229 4.4.2）。

### 9. UE 1 が 183 を確認する（PRACK）

UE 1 は **RAck**（RSeq と INVITE の CSeq）を付けた **PRACK** を、初期ダイアログの中で送ります（RFC 3262 4）。ダイアログの中の要求なので、Record-Route から作ったルートセットに沿って進みます（RFC 3261 12.2.1.1）。P-CSCF と S-CSCF を通って、ダイアログの相手である発信者の MMTel AS に届きます。それぞれの AS は、UA と同じく、受けた PRACK にすぐ答え、次のダイアログに自分の PRACK を送ります。PRACK はこうしてダイアログごとに UE 2 まで届き、UE 2 が 200 で答えます。プリコンディションを使うときの UPDATE も同じ道を通ります。

### 10. UE 2 が鳴らしてから応答する（180 と 200 OK）

必須のプリコンディションがすべて満たされると、UE 2 は利用者を呼び出し、**180 Ringing** を送ります（RFC 3312 6、TS 24.229 5.1.4.1）。180 も信頼性のある暫定応答なので、180 にも PRACK が返ります。資源がまだ無い着信側は、資源がそろうまで 180 を送りません（IR.92 2.4.1）。

利用者が応答すると、UE 2 は INVITE に **200 OK** を返します（RFC 3261 13.3.1.4）。これでダイアログが確定します。UE 2 は ACK が届くまで、間隔を広げながら 200 を送り直します。

信頼性のある 183 に入れた SDP がアンサーになるので、200 には SDP が入っていません（RFC 3262 5）。UE 1 は最初に受け取ったアンサーを使い、あとから来たものは無視します（RFC 3261 13.2.1）。

### 11. UE 1 が確認する（ACK）

UE 1 は 2xx に対する **ACK** をルートセットに沿って送ります（RFC 3261 13.2.2.4）。この ACK は INVITE のトランザクションの一部ではありません。各プロキシはこれを独立した要求として転送します。

### 12. 音声が中継ノードを通って流れる

各 UE は 20 ms ごとに RTP を送ります。1 パケットには G.711 μ-law が 160 バイト入っています（RFC 3550 5.1、RFC 3551 4.5.14）。送信には受信と同じポートを使います（対称 RTP、RFC 4961）。

UE 1 の音声は次の経路を通ります。

```text
UE 1 -> relay access (context 1) -> relay core (context 1) -> relay core (context 2) -> relay access (context 2) -> UE 2
```

UE 側のターミネーションは**ラッチング**をします。SDP を信用するのではなく、最初に受け取ったパケットの送信元を送り先にします。NAT の内側の UE は SDP には書けないアドレスから送ってきますが、ラッチングならそれでも届きます。

網の側のターミネーションはラッチングをせず、網の側から来た最新の SDP のアドレスへ送ります。網の側には NAT がなく、相手が通話の途中で替わることもあるためです。たとえば呼び出し音（CAT）が終わると、MRFP の SDP に代わって着信者の SDP が届きます（[MRF による音声ガイダンス、呼び出し音、会議](mrf.md)）。MRFP にラッチしたままだと、発信者の声は MRFP へ送られ続けます。

各 UE は数秒ごとに、RTP のポートの 1 つ上のポートから **RTCP** の複合パケットも送ります。中身は送信者レポート（何も送っていないあいだは受信者レポート）と、CNAME を入れた SDES です（RFC 3550 6、IR.92 3.2.4）。通話が続いていることを相手が確かめられるように、少なくとも 5 秒に 1 回は送ります。通話の終わりには RTCP の BYE を送ります。

e2e 試験は、UE 1 が符号化したバイト列と、UE 2 が受け取ったバイト列が完全に一致することを確かめます。G.711 は非可逆の符号化なので、WAV ファイルどうしは比べません。

### 13. UE 1 が切断する（BYE）

UE 1 はダイアログの中で **BYE** を送ります（RFC 3261 15.1.1）。BYE はルートセットに沿って進みます。BYE には通話を終えた理由を示す `Reason: RELEASE_CAUSE;cause=1;text="User ends call"` が入っています（TS 24.229 5.1.5、IR.92 2.2.4）。UE 2 は 200 で答えます（RFC 3261 15.1.2）。そのとき、UE 1 から届いてまだ答えていないダイアログの中の要求（re-INVITE など）があれば、UE 2 はそれに 487（Request Terminated）で答えます。BYE を送る側の UE 1 も、UE 2 から届いてまだ答えていない要求に、同じく 487 で答えます（RFC 3261 15.1.2）。200 が P-CSCF を通るとき、P-CSCF はその通話の中継のコンテキストを削除します。応答を待つのは、BYE が断られることもあるからです。たとえば順序の狂った BYE には 500 が返り（RFC 3261 12.2.2）、ダイアログはそのまま残ります。481 と 408 が返ったときや、応答が無いときも、ダイアログは終わります（RFC 3261 15.1.1）。このときもコンテキストを削除します。

## 通話全体で 1 つの課金の識別子

網の中では、INVITE とそのすべての応答が **P-Charging-Vector** を運びます（RFC 7315 4.6）。その **icid-value** は課金のために通話を識別する値です。UE 1 の P-CSCF が新しい値を INVITE に書き込み（TS 24.229 5.2.6.3.3 の手順 7）、その先のノードはこの値をそのまま運びます。MMTel AS は自分の各ダイアログの INVITE にこの値を入れます（5.7.5.1）。**orig-ioi** は要求を送った網を、**term-ioi** は応答を送った網を示します。

IOI には、各ノードが自分の網を書きます。S-CSCF は MMTel AS とその先へ送る INVITE の orig-ioi に、自分のホームドメインを書きます（TS 24.229 5.4.3.2 の手順 5 d と 7、5.4.3.3 の手順 4 d、7、7A）。送り返す応答には、INVITE が運んできた orig-ioi と、term-ioi として自分のホームドメインを書きます。ここでは網が 1 つだけなので、どの IOI も同じドメインになります。[IMS 網どうしを相互接続する](interconnect.md) では、2 つの網がそれぞれ別の値を書きます。

UE にこのヘッダが届くことはありません。P-CSCF が UE に送るものからも、UE から届いたものからも消すからです（5.2.1）。UE 2 の P-CSCF は UE 2 への INVITE からヘッダを消す前に、icid-value と orig-ioi を保存します（5.2.6.4.3 の 9 番目の項目）。そして、その 2 つを自分の term-ioi と一緒に UE 2 の 183、180、200 に書き込みます（5.2.6.4.4 の 6 番目の項目）。ダイアログの中で UE 2 がその後に送る要求には、INVITE の icid-value を付けます（5.2.6.3.9 の手順 3）。UE 1 の P-CSCF も UE 1 の PRACK、ACK、BYE に同じ icid-value を付けます。

通話をたどるには、P-CSCF が S-CSCF に送る INVITE（手順 2）から icid-value を写し取り、`sip.P-Charging-Vector contains "icid-value=..."` で絞り込みます。すべてのノードで、3 つのダイアログのどれでも、INVITE とその応答が見つかります。

## 自分のマシンから話す

P-CSCF のポート 5060/udp と、中継ノードのポート 40000〜40039/udp は、ホストのループバックアドレス 127.0.0.1 に公開されています。ホスト上のソフトフォン（Linphone など）は、試験用の加入者の SIP Digest の認証情報で登録できます。設定は次のとおりです。

- P-CSCF は `127.0.0.1:5060`。
- ドメインは `ims.mnc001.mcc001.3gppnetwork.org`。

P-CSCF はブリッジのゲートウェイ 172.28.0.1 から来た UE を見分け、その UE には中継ノードのアドレスとして、ポートが公開されている `127.0.0.1` を教えます（`deploy/compose/pcscf.yaml` の `host_access`）。Docker の NAT がソフトフォンに与えるアドレスは、ラッチングで吸収されます。P-CSCF は別のマシンのソフトフォンにも同じ `127.0.0.1` を教えますが、それはそのマシン自身のアドレスです。そのため、ソフトフォンはホストで動かします。

`scripts/e2e-call.sh` の通話の試験は、最後にこの経路での通話を確かめます。コンテナのイメージに入っている UE シミュレータをそのまま実行できるマシンでだけ動かし、ホストのシミュレータから UE 2 を呼びます。コンテナの中の UE 2 は、ホストが中継ノードの公開されたポートに送ったパケットをすべて受け取ります。この経路で試したのはこのシミュレータだけです。Windows 向けにビルドしたものでも試しましたが、ソフトフォンでは試していません。

## HTTP で UE を操作する

`ue serve` は UE を登録したままにして、ほかのプログラムから操作できるようにします。ラボはこの仕組みで発信と応答をします。HTTP の API はこのプロジェクト独自のもので、試験ツールが遠隔操作のために用意する API と同じ種類です。どの仕様にも定めがなく、API のやり取りは IMS には流れません。キャプチャに出るのは、操作の結果として UE が送る SIP だけです。

1. 2 つの端末で UE 2 と UE 1 を起動します。どちらも API のポートをホストに公開します。

   ```sh
   docker compose run --rm -p 127.0.0.1:8091:8090 ue2 serve \
     -impi 001010000000002@ims.mnc001.mcc001.3gppnetwork.org \
     -impu sip:+12025550102@ims.mnc001.mcc001.3gppnetwork.org \
     -password test-password-2
   ```

   ```sh
   docker compose run --rm -p 127.0.0.1:8090:8090 ue serve
   ```

2. UE 2 を応答するまで鳴り続けるようにします。UE 1 から発信し、UE 2 の状態を見ます。

   ```sh
   curl -X PUT -H 'Content-Type: application/json' localhost:8091/answer-policy -d '{"mode": "manual"}'
   curl -X POST -H 'Content-Type: application/json' localhost:8090/call -d '{"target": "tel:+1-202-555-0102"}'
   curl localhost:8091/status
   ```

   UE 2 の状態には、`incoming` の通話が `ringing` の状態で出ます。Call-ID はキャプチャのものと同じです。

3. UE 2 で応答してから、UE 1 で切断します。

   ```sh
   curl -X POST -H 'Content-Type: application/json' localhost:8091/answer
   curl -X POST -H 'Content-Type: application/json' localhost:8090/hangup
   ```

   切断すると、応答の後なら BYE を、鳴っている間なら CANCEL を送ります。着信側で鳴っている間に切断すると、603（Decline）で断ります。要求の本文に `reject_status` を書くと、その応答コードで断ります。

   1 分より長く鳴り続ける通話では、UE が 1 分ごとに 180（Ringing）を送り、プロキシが INVITE を打ち切らないようにします（RFC 3261 13.3.1.1）。鳴っている間に UE を止めると、UE は 480（Temporarily Unavailable）で着信を断ります。

通話中に `curl -X POST -H 'Content-Type: application/json' localhost:8090/hold` を送ると、UE 1 は `a=sendonly` を提示する re-INVITE で通話を保留にします。`/resume` で保留を解き、`curl -X POST -H 'Content-Type: application/json' localhost:8090/dtmf -d '{"digits": "123"}'` で DTMF を telephone-event として送ります。状態の `session` にはコーデック、メディアの方向、プリコンディション、受け取った数字が出ます。`POST` と `PUT` には、本文が無くても `Content-Type: application/json` を付けます。API はそれ以外に 415 を返します。ブラウザで開いたほかのサイトのページに、preflight なしで UE を操作させないためです（[ラボを開く](lab.md#ラボを開く)に説明があります）。

UE 1 はトーンを 1 回流したあと、どちらかが切断するまで通話を続けます。`curl -N localhost:8091/events` を使うと、状態が変わるたびに新しい状態を受け取れます。応答の方針には、2 秒鳴らしてから応答する `{"mode": "auto", "ring_seconds": 2}` と、すべて断る `{"mode": "reject", "reject_status": 486}` もあります。UE の回線は 1 つで、通話を 2 本まで持てます。2 本目を発信するには、先に 1 本目を保留にします（`POST /hold`）。保留にしないうちは、API が 409（Conflict）を返します。通話中に INVITE が届くと、UE はその着信を待たせ、`Alert-Info: <urn:alert:service:call-waiting>` を付けて呼び出すだけで自分からは応答しません。`POST /answer` を送ると、1 本目を保留にしてから待っている着信に応答します（TS 24.615 4.5.5.3）。3 本目の INVITE には 486（Busy Here）で答えます。これらの要求は、シェルから `ue ctl` でも送れます。要求の一覧は `internal/ue/phone_http.go` の `Phone.Handler` のコメントにあります。

## メディア中継ノードを運用から外す

運用する人は、ノードが扱っているものを切らずに、そのノードを運用から外します。新しいものを受けず、始めたものを最後まで扱い、何も残らなくなるまで続けます。これをドレインと呼びます。

メディア中継ノードは運んでいるものを続けなければなりません。コンテキストがあるのは、そのポートを開いたノードの中だけだからです。呼の UDP ソケットを持っているのはこの中継ノードで、P-CSCF が持っているのはこの中継ノードが渡したコンテキストの ID です。呼の RTP はこのプロセスだけを通ります。商用の網は中継ノードを複数台で動かし、P-CSCF は Call-ID の hash で呼ごとに 1 台を選ぶので、ドレイン中の台を避けて新しい呼はほかの台に向かいます。この中継ノードの振る舞いは、IMS-AGW については TS 23.334 6.1.2、MRFP については TS 23.333 6.1.2 が言う graceful の方法です。新しい呼には使えなくなり、持っている接続は、その呼が切れるにつれて解放されます。

このための保守用の API は、中継ノードのノードが 8085 番で出します。`deploy/compose/agw.yaml` の `maintenance` の節が決める待ち受けです。この API はパスワードを求めないので、ポートをホストに公開していません。要求はコンテナの中から送ります。administrative state の値は TS 28.622 5.3.1 のものです。`UNLOCKED` は新しい仕事を受け、`SHUTTINGDOWN` は持っているものだけを扱い、`LOCKED` は新しいものを何も受けません。

1. 中継ノードを shut down します。

   ```sh
   docker compose exec agw sh -c '
   body="{\"administrative_state\":\"SHUTTINGDOWN\",\"operator\":\"learner\"}"
   printf "PUT /maintenance/v1/functions/agw/administrative-state HTTP/1.0\r\nContent-Type: application/json\r\nContent-Length: ${#body}\r\n\r\n%s" "$body" |
     nc -w 5 127.0.0.1 8085'
   ```

   答えの最後に中継ノードの状態が入ります。通っている呼が無ければ、すぐに `LOCKED` になります。

   ```json
   {"role":"agw","administrative_state":"LOCKED","operational_state":"ENABLED","users":0}
   ```

   `users` は、この中継ノードが持っているコンテキストの数です。P-CSCF を通る呼の片側ごとに 1 つ、音声ガイダンス 1 つにつき 1 つ、会議 1 つにつき 1 つで、会議はターミネーションの数によらず 1 つです。前のプロセスが保存先に残し、起動したときに開き直したコンテキストも、この数に入ります。呼が通っているあいだに shut down すると、中継ノードは `SHUTTINGDOWN` のままで、P-CSCF が最後のコンテキストを解放したときに `LOCKED` に移ります。ノードを止めてもメディアを切らないと、運用する人はこれで分かります。`operational_state` は、中継ノードが働けるかどうかを示します（TS 28.622 5.3.3）。ノードが動いているあいだは `ENABLED` です。中継ノードは自分のソケットで答え、状態を報告できるような結び付きを持たないためです。ノード全体の状態は `docker compose exec agw wget -qO- http://127.0.0.1:8085/maintenance/v1/state` で見られます。

2. UE 1 から UE 2 に発信します。

   ```sh
   docker compose run --rm ue call tel:+12025550102
   ```

   呼は `500 Server Internal Error` で失敗します。この網の中継ノードは 1 台で、P-CSCF にはメディアを通す先がほかに無いためです。

```text
 UE 1          P-CSCF         メディア中継ノード
 |   INVITE      |                 |
 |-------------->|                 |  UE 1 の SDP の offer
 |               | POST /contexts  |  Add。UE 側と網側のターミネーションを 1 つずつ
 |               |---------------->|
 |               | 503 Service Unavailable
 |               |<----------------|  運用から外れているので、コンテキストを作らない
 |   500         |                 |  一覧にほかの中継ノードが無く、INVITE は先へ進まない
 |<--------------|                 |
```

- **P-CSCF はコンテキストを求めます。** この呼の片側のために、UE 側と網側のターミネーションを 1 つずつ求めます。INVITE に offer の入った呼では、いつもこうします（TS 29.334 5.17.2.2）。中継ノードは Call-ID の hash で選び、ドレインのことは知りません。
- **中継ノードは 503（Service Unavailable）を返します。** 誤りの符号は `out_of_service` で、ポートは 1 つも確保しません。この答えに `Retry-After` は付きません。P-CSCF は使えない中継ノードを覚えないので、読むものがいないためです。
- **P-CSCF は一覧の次の中継ノードを試し**、1 台も残らなくなってから答えます。ここでは一覧が 1 台なので、呼はそこで終わります。P-CSCF は INVITE に 500 を返し、どこにも転送しません。自分の `Retry-After` は付けません。503 は中継ノードについてのもので、P-CSCF についてのものではないためです。

`UNLOCKED` でないあいだ、中継ノードは運んでいるものを続け、新しく始まるものを断ります。

続けるのは次のものです。

- **持っているコンテキストへの操作すべて。** 着信側が答えたあとや re-INVITE のあとに、制御する側がターミネーションの相手を指す `Modify` と、呼が終わったときにターミネーションやコンテキスト全体を解放する `Subtract` です。これを断ると、ドレイン中の中継ノードはポートを握ったままになります。
- **持っているコンテキストへのターミネーションの `Add`。** この中継ノードに混合がある会議に、参加者が入るときのものです。混合はここにしか無いので、断ると、続いている会議から参加者を締め出します。コンテキストも増えません。中継ノードが数えるのはコンテキストで、shut down のあいだ、その数は減るだけです。
- **制御する側に知らせるイベント**と、コンテキストと音声ガイダンスを読む Audit。どちらもノードが持っているものを伝えるもので、ノードは生きています。

503 を返すのは、新しいコンテキストを作る `Add` です。新しく始まる操作はこれだけです。

3. 同じ要求に `UNLOCKED` を入れて中継ノードを unlock し、もう一度発信します。

   ```sh
   docker compose exec agw sh -c '
   body="{\"administrative_state\":\"UNLOCKED\",\"operator\":\"learner\"}"
   printf "PUT /maintenance/v1/functions/agw/administrative-state HTTP/1.0\r\nContent-Type: application/json\r\nContent-Length: ${#body}\r\n\r\n%s" "$body" |
     nc -w 5 127.0.0.1 8085'
   docker compose run --rm ue call tel:+12025550102
   ```

   呼はまた中継ノードを通ります。MRFP のノードも同じようにドレインします。パスとサービスの名前の `agw` を `mrfp` に替えるだけです。MRFP のドレインが MRFC に何をもたらすかは、[MRFP を運用から外す](mrf.md#mrfp-を運用から外す)にあります。

Wireshark では `http.request.uri == "/contexts" && http.request.method == "POST"` でコンテキストを求める要求が、`http.response.code == 503 && ip.src == 172.28.0.50` でドレイン中の中継ノードの断りが見られます。PUT の要求はコンテナのループバックを通るので、キャプチャには入りません。

administrative state はノードのプロセスの中にあります。起動し直したノードは `UNLOCKED` です。`scripts/e2e-maintenance-sip.sh` は、この手順を実行してキャプチャを確かめます。

## 中継ノードがアンサーを受け取らないとき

P-CSCF は、SDP のアンサーを先へ渡す前に、アンサーを中継ノードに向けます（手順 8 と 10）。まず、答えた側に面したターミネーションに、答えた側がどこで受けるかを `Modify` で伝えます（TS 29.334 5.17.2.3）。そのあとで、もう一方のターミネーションのアドレスを SDP に書きます（TS 24.229 6.7.2.1）。再起動中の中継ノードや、コンテキストを失った中継ノードは、この `Modify` を断るか、時間内に答えません。すると P-CSCF は、先へ渡す自分のアンサーを作れません。届いたアンサーには、向こうの相手のアドレスが書いてあります。これを受け取った UE は、中継ノードを通らずに RTP を送ります。PCRF も、呼が通らない経路のメディアを許可することになります。そのため、P-CSCF は呼を終わらせます。P-CSCF が読めないアンサーでも同じです。解析できない SDP、RFC 3261 20.15 が禁じる `Content-Type` の無い本文、マルチパートの本文の一部に入った SDP です。

TS 24.229 には、メディア中継ノードが働かないときの手順がありません。P-CSCF は、確立の途中のセッションから網が資源を取り上げたときと同じ手順で、呼を終わらせます（TS 24.229 5.2.8.1.1）。違いは 1 つで、500 に `Reason: FAILURE_CAUSE` を付けません。FAILURE_CAUSE は、無線や bearer の資源を失ったことを伝えるものだからです（TS 24.229 7.2A.18.12.2）。CANCEL と BYE には `Reason: SIP;cause=503` を付けます（RFC 3326 2）。TS 24.229 5.2.8.1.1 と 5.2.8.1.2 は、セッションの資源が無くなり、無線や bearer の資源を制御するエンティティが原因を伝えなかったときに、この値を使います。中継ノードはそのエンティティではありません。無線と bearer の資源も残っています。伝える原因が無いので、P-CSCF は同じ 503 を使います。

アンサーが 183 で届いたときは、呼はまだ確立の途中です。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 |               |  SDP のアンサーの入った 183      |
 |               |<---------------------------------|
 |               | PUT .../terminations/core        |  Modify。着信側が受けるアドレス
 |               |--------------->|                 |
 |               | 誤り、または時間内に答えが無い   |
 |               |<---------------|                 |
 |   500         |                |                 |  183 は先へ進まない
 |<--------------|                |                 |
 |               | CANCEL  Reason: SIP;cause=503    |
 |               |--------------------------------->|
 |               |      200 (CANCEL)、487 (INVITE)  |
 |               |<---------------------------------|
 |               | DELETE /contexts/{id}            |  Subtract
 |               |--------------->|                 |
```

- **UE 1 は INVITE への 500 を受け取ります。** 183 は UE 1 に届きません。
- **網へ向けた INVITE を取り消します。** 着信側は INVITE に 487 を返します（RFC 3261 9.2）。
- **P-CSCF は中継ノードのコンテキストを解放します。** 中継ノードが答えないときは、何度か試し直します。中継ノードが受け取らなかったアンサーは、PCRF に渡しません。中継ノードが受け取ったアンサーが前の応答にあったときは、PCRF はそのアンサーを持っています。そこで P-CSCF は、呼の Rx のセッションを終わらせます（TS 29.214 4.4.4）。
- **中継ノードがアンサーを受け取った、信頼性のある 183 の送り直しでは、何も変わりません。** 着信側は、PRACK が届くまで信頼性のある 183 を送り直します（RFC 3262 3）。UE 1 はその 183 をもう持っているので、P-CSCF は最初の 183 と同じものを送り直します。中継ノードを示す SDP が入ったもので、呼は続きます。版の変わらない SDP は同じ SDP でなければならず（RFC 3264 8）、中継ノードにはもう尋ねません。

アンサーが 200 で届いたときは、着信側はもう応答しています。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 |               |  SDP のアンサーの入った 200 (INVITE)
 |               |<---------------------------------|
 |               | PUT .../terminations/core        |  Modify
 |               |--------------->|                 |
 |               | 誤り、または時間内に答えが無い   |
 |               |<---------------|                 |
 |   500         |                |                 |  200 の代わりに 500
 |<--------------|                |                 |
 |               | UE 1 の名前で ACK                |
 |               |--------------------------------->|
 |               | BYE  Reason: SIP;cause=503       |
 |               |--------------------------------->|
 |               |                      200 (BYE)   |
 |               |<---------------------------------|
 |               | DELETE /contexts/{id}            |  Subtract
 |               |--------------->|                 |
```

- **UE 1 は 200 の代わりに 500 を受け取ります。** UE 1 の INVITE にはまだ最終応答が無いので、P-CSCF はそこで呼を終わらせられます。中継ノードを通らない経路を示す SDP の入った 200 は、UE 1 に届きません。
- **着信側のダイアログは確立しています。** そこで P-CSCF は、UE 1 の名前で 200 に ACK を返し（RFC 3261 13.2.2.4）、BYE でセッションを終わらせます（RFC 3261 15）。CANCEL と行き違った 200 と同じ扱いです。着信側は ACK が届くまで 200 を送り直し、P-CSCF は送り直しのたびに ACK を返します。
- **呼が持つものは、183 のときと同じく解放します。** 中継ノードのコンテキストと、前の応答のアンサーで開いた Rx のセッションです。
- **中継ノードがアンサーを受け取った 200 の送り直しは別です。** UE 1 はその 200 をもう持っているので、P-CSCF は最初の 200 と同じものを送り直し、呼は続きます。
- **To タグの違う 200 は、送り直しではありません。** UE 1 が最初のダイアログの 200 を受け取ったあとに届く、フォークした INVITE の別のダイアログの 200 です。この場合の手順は、TS 24.229 にありません。プロキシは INVITE への 200 をすべて先へ送ります（RFC 3261 16.7 step 5）。しかし呼が持つ中継ノードのコンテキストと Rx のセッションは 1 つずつで、どちらも UE 1 が受け取った 200 のダイアログに使っています。別のダイアログのアンサーをそこに通すと、UE 1 の呼のメディアが別のダイアログの相手に移ります。そのまま送れば、UE 1 は中継ノードを通らなくなります。そのため、中継ノードがそのアンサーを受け取るかどうかにかかわらず、P-CSCF はこの 200 を先へ送らず、中継ノードにも問い合わせません。先へ送らない 200 は、着信側が ACK を待つのをやめるまで届き続け、そのあと着信側が自分でダイアログを終わらせます（RFC 3261 13.3.1.4）。そこで P-CSCF はそのダイアログをすぐに終わらせます。UE 1 の名前で 200 に ACK を返し、BYE を送ります。CANCEL と行き違った 200 と同じ扱いです。UE 1 は自分の 200 の呼を続けます。その呼の中継ノードのコンテキスト、Rx のセッション、ダイアログは変わりません。`internal/pcscf` の `TestA2xxOfAnotherForkLeavesTheCallAsItIs` は、どのアンサーも受け取る中継ノードを使って、これを示します。
- **別のダイアログの中の要求は、UE 1 の呼を変えません。** P-CSCF は UE 1 のダイアログを Call-ID と UE 1 のタグで保存していて、別のダイアログの中の要求もこの 2 つを持っています。UE 1 が 200 を受け取ったあとは、P-CSCF は相手のタグで 2 つのダイアログを見分け、別のダイアログの要求では UE 1 の呼を何も変えません。BYE は先へ送ります。その応答が 481 でも、終わるのは別のダイアログだけです（RFC 3261 15.1.1）。そうした要求に SDP が入っていても、その SDP を通せるのは UE 1 の呼の中継ノードのコンテキストだけなので、P-CSCF はその要求に自分で 500 を返します。`TestRequestOfAnotherForkLeavesTheCallAsItIs` は、これらの要求を示します。

UE 2 の P-CSCF では、同じことが逆の向きに起きます。183 や 200 は UE 2 から届き、`Modify` はアクセス側のターミネーションに向けたものになります。500 は網へ、CANCEL、または ACK と BYE は UE 2 へ送ります。

ダイアログの中のアンサーでは、流れが変わります。UPDATE への 200 や、保留のときのような re-INVITE への 200 に入ったアンサーです。この 200 はその要求への最終応答で、答えた側はもうオファーを受け入れています。そのため、P-CSCF は 200 を届いたまま先へ渡します。そのあとでダイアログを解放します。この場合の手順も TS 24.229 にはありません。いちばん近いのは TS 24.229 6.2 です。6.2 は、ローカルポリシーが許さないメディアを SDP のオファーに入れた 200 を扱います。P-CSCF はその 200 を先へ渡し、アンサーの入った ACK が届いたら、BYE でセッションを解放します（TS 24.229 5.2.8.1.2）。この BYE には `Reason: SIP;cause=488`（Not Acceptable Here）を付けます。網が許さないメディアを当事者が求めたためです。ここでは当事者は誤ったものを何も求めていないので、BYE には資源を失ったときと同じ 503 を付けます。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 |               |  SDP のアンサーの入った 200 (UPDATE)
 |               |<---------------------------------|
 |               | PUT .../terminations/core        |  Modify
 |               |--------------->|                 |
 |               | 誤り、または時間内に答えが無い   |
 |               |<---------------|                 |
 |  200 (UPDATE) |                |                 |  届いたまま
 |<--------------|                |                 |
 |               | BYE  Reason: SIP;cause=503       |  UE 1 の名前で
 |               |--------------------------------->|
 |  BYE  Reason: SIP;cause=503    |                 |  相手の名前で
 |<--------------|                |                 |
 |               | DELETE /contexts/{id}            |  Subtract
 |               |--------------->|                 |
```

- **確立したダイアログでは、双方に BYE を送ります**（TS 24.229 5.2.8.1.2）。[網が bearer を落とす](volte.md#網が-bearer-を落とす)ときと同じ 2 つの BYE です。
- **BYE が 200 を追い越すことはありません。** UPDATE のときは、P-CSCF が 200 を先へ渡してから BYE を送ります。re-INVITE への 200 は ACK を待つので、解放も ACK を待ちます。TS 24.229 6.2 と同じです。BYE を送るのは、UE 1 の ACK が P-CSCF を通ったあとです。ACK が来ないときは、64*T1、つまり 32 秒たってから BYE を送ります。着信側も、そこで ACK を待つのをやめます（RFC 3261 13.3.1.4）。アンサーが re-INVITE への 183 で届き、その re-INVITE が失敗したときは、ACK は P-CSCF を通りません。2xx 以外の最終応答への ACK は、1 区間ごとに返るためです（RFC 3261 17.1.1.3）。そのときは、その応答を先へ渡したところで BYE を送ります。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 |               |  SDP のアンサーの入った 200 (INVITE)  re-INVITE への 200
 |               |<---------------------------------|
 |               | PUT .../terminations/core        |  Modify
 |               |--------------->|                 |
 |               | 誤り、または時間内に答えが無い   |
 |               |<---------------|                 |
 |  200 (INVITE) |                |                 |  届いたまま
 |<--------------|                |                 |
 |  ACK          |                |                 |
 |-------------->| ACK                              |
 |               |--------------------------------->|
 |               | BYE  Reason: SIP;cause=503       |  UE 1 の名前で
 |               |--------------------------------->|
 |  BYE  Reason: SIP;cause=503    |                 |  相手の名前で
 |<--------------|                |                 |
```

- **early dialog では、INVITE にまだ最終応答がありません。** VoLTE の UE が資源を確保したことを伝える UPDATE が、この場合に当たります（[プリコンディション](volte.md#プリコンディション)）。UE 1 は INVITE への 500 を受け取り、網へ向けた INVITE は取り消されます。183 のときと同じです。
- **UPDATE が INVITE とは別の P-CSCF のインスタンスを通ったときは、** そのインスタンスは INVITE を終わらせられません。INVITE に答えて取り消せるのは、その INVITE を転送しているインスタンスだけです。UPDATE を通したインスタンスは、ダイアログが持つものを解放し、インスタンスどうしが共有する保存先で、ダイアログに解放の印を付けます。INVITE を転送しているインスタンスは、INVITE への次の応答でその印を見つけ、そこで呼を終わらせます。中継ノードがアンサーを受け取らなかった 183 のときと同じです。その応答が 200 のときは、網には CANCEL の代わりに ACK と BYE を送ります。

```text
 UE 1          P-CSCF a        P-CSCF b         網
 | UPDATE        |                |                 |
 |------------------------------->| UPDATE          |
 |               |                |---------------->|
 |               |                |    200 (UPDATE) |  中継ノードがアンサーを受け取らない
 |               |                |<----------------|
 | 200 (UPDATE)  |                |                 |  b がダイアログに解放の印を付ける
 |<-------------------------------|                 |
 |               |                     180 (INVITE) |  a が印を見つける
 |               |<---------------------------------|
 | 500           |                |                 |  180 は先へ進まない
 |<--------------|                |                 |
 |               | CANCEL  Reason: SIP;cause=503    |
 |               |--------------------------------->|
```

- **PCRF はこのアンサーを受け取りません。** P-CSCF は呼の Rx のセッションを終わらせ（TS 29.214 4.4.4）、中継ノードのコンテキストを解放します。

`internal/pcscf` の試験は、アンサーの `Modify` を断る中継ノードを使って、これらの流れを 1 つのプロセスの中で動かします。`TestRefusedAnswerOfA183EndsTheCall`、`TestRefusedAnswerOfThe200EndsTheCall`、`TestRefusedRetransmissionOfThe200KeepsTheCall`、`TestRefusedRetransmissionOfAReliable183KeepsTheCall`、`TestResponseWhoseSDPTheP_CSCFCannotReadEndsTheCall`、`TestRefusedAnswerWithinTheDialogReleasesTheCall`、`TestRefusedAnswerOfAReINVITEThatFailsIsReleasedAtOnce`、`TestRefusedAnswerOfAnUPDATEInTheEarlyDialogEndsTheCall`、2 つの P-CSCF のインスタンスが 1 つの保存先を共有する `TestRefusedAnswerOfAnUPDATEAtAnotherInstanceEndsTheCall` です。

## 中継ノードがオファーを受け取らないとき

ダイアログの中の新しい SDP も、INVITE のオファーと同じく中継ノードを通ります。UPDATE のオファーや、保留のときの re-INVITE のオファーです。PRACK の SDP もあります。PRACK の SDP は、新しいオファーか、PRACK が確認する信頼性のある応答に入ったオファーへのアンサーです（RFC 3262 5）。P-CSCF は、SDP を送った側に面したターミネーションに、その側がこれからどこで受けるかを `Modify` で伝えます。そのあとで、もう一方のターミネーションのアドレスを SDP に書きます（TS 24.229 6.7.2.1）。この `Modify` が失敗すると、P-CSCF は先へ渡す自分の SDP を作れません。届いた SDP には、送った側のアドレスが書いてあります。相手はそこへ、中継ノードを通らずに RTP を送ることになります。PCRF も、呼が通らない経路のメディアを許可することになります。

そのため、P-CSCF は要求を先へ送らず、自分で答えます。TS 24.229 6.2 も、P-CSCF が通せないオファーの入った要求を、同じように扱います。P-CSCF はその要求に答え、先へは送りません。ローカルポリシーが許さないメディアのオファーには、6.2 は 488（Not Acceptable Here）を返し、ポリシーが許すメディアをそこに入れます。ここではメディアは許されていて、原因は中継ノードにあるので、500（Server Internal Error、RFC 3261 21.5.1）を返します。P-CSCF が SDP をまったく読めないときは、400（Bad Request、RFC 3261 21.4.1）を返します。`Content-Type` の無い本文にも 400 を返します。RFC 3261 20.15 はそのような本文を禁じていて、P-CSCF には SDP かどうか分からないためです。マルチパートの本文の一部に入った SDP には、`Accept: application/sdp` を付けた 415（Unsupported Media Type、RFC 3261 21.4.13）を返します。マルチパートの本文を読まないノードが返す答えです（RFC 5621 4.2）。どの場合も中継ノードには何も頼みません。こうした本文の入った INVITE にも、同じように答えます。こう読むのは、オファーとアンサーを運ぶ要求だけです。INVITE、ACK、UPDATE、PRACK です（RFC 3261 13.2.1）。INFO のようなほかの要求の本文は、届いたまま先へ進みます。

呼がどうなるかは、中継ノードの答えで決まります。

**中継ノードが `Modify` を断り、何も変えなかったとき。** 呼は続きます。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 | 新しい SDP のオファーの入った UPDATE             |
 |-------------->|                |                 |
 |               | PUT .../terminations/access      |  Modify。UE 1 がこれから受けるアドレス
 |               |--------------->|                 |
 |               | 誤り。何も変えていない           |
 |               |<---------------|                 |
 |  500 (UPDATE) |                |                 |  UPDATE は先へ進まない
 |<--------------|                |                 |
```

- **2xx 以外の最終応答を受け取ると、セッションは要求の前のままです。** re-INVITE については RFC 3261 14.1 が、UPDATE については RFC 3311 5.3 がそう定めています。ダイアログが終わるのは、481 か 408 を受け取ったときと、答えが無かったときだけです（RFC 3261 12.2.1.2）。そのため、P-CSCF はどれも返しません。中継ノードは何も変えていないので、メディアは最後のオファーとアンサーのとおりに中継ノードを通り続け、PCRF も許可したものをそのまま持ちます。
- **re-INVITE にも同じ 500 を返します。** 2xx 以外の最終応答なので、UE 1 が返す ACK は P-CSCF で止まります（RFC 3261 17.1.1.3）。呼を保留にしようとした UE は、元のままの呼に残ります。
- **UE 1 は、あとでオファーを送り直せます**（RFC 3261 21.5.1）。
- **網からのオファー**では、コア側のターミネーションに `Modify` を送ります。500 は網へ返り、UE 1 には何も届きません。
- **early dialog では、INVITE は続きます。** VoLTE の UE が資源を確保したことを伝える UPDATE が、この場合に当たります（[プリコンディション](volte.md#プリコンディション)）。着信側は、UE 1 の資源が確保できたことを知らないままです。それを伝える次のオファーを待ちます（RFC 3312 6）。

**中継ノードが時間内に答えないとき、コンテキストを失っているとき、P-CSCF の一覧に無いとき。** P-CSCF は 500 を返し、そのあとで呼を解放します。中継ノードがアンサーを受け取らないときと同じです。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 | 新しい SDP のオファーの入った UPDATE             |
 |-------------->|                |                 |
 |               | PUT .../terminations/access      |  Modify
 |               |--------------->|                 |
 |               | 時間内に答えが無い、またはコンテキストが無い
 |               |<---------------|                 |
 |  500 (UPDATE) |                |                 |
 |<--------------|                |                 |
 |               | BYE  Reason: SIP;cause=503       |  UE 1 の名前で
 |               |--------------------------------->|
 |  BYE  Reason: SIP;cause=503    |                 |  相手の名前で
 |<--------------|                |                 |
 |               | DELETE /contexts/{id}            |  Subtract
 |               |--------------->|                 |
```

- **答えが遅れた中継ノードは、`Modify` を実行したかもしれません。** そのときターミネーションは、UE 1 が 500 を受け取ったオファーのアドレスへ送ります。UE 1 は、もうそこではメディアを受けません。P-CSCF にはどちらか分からないので、呼を終わらせます。
- **コンテキストを失った中継ノード**は、保存先を持たずに起動し直したときのように、もう呼のメディアを運んでいません。このあとのオファーも、同じように断ります。
- **P-CSCF は呼の Rx のセッションを終わらせ**（TS 29.214 4.4.4）、中継ノードのコンテキストを解放します。ほかの解放と同じです。
- **early dialog では、** INVITE にまだ最終応答がありません。UE 1 は INVITE への 500 も受け取り、網へ向けた INVITE は取り消されます。中継ノードがアンサーを受け取らなかった 183 のときと同じです。

**要求が PRACK のとき。** 中継ノードの答えにかかわらず、P-CSCF は 500 を返し、INVITE を終わらせます。UAC は PRACK を送り直しません（RFC 3262 4）。信頼性のある応答は確認されないまま残り、着信側は、応答が PRACK を 64*T1、つまり 32 秒待ったところで、INVITE を 5xx で終わらせます（RFC 3262 3）。P-CSCF はそれを待たずに INVITE を終わらせます。UE 1 は INVITE への 500 を受け取り、網には CANCEL が届きます。PRACK に返すのも 500 で、RFC 3262 3 が信頼性のある応答に合う PRACK に求める 200 ではありません。中継ノードを通る呼の INVITE には必ずオファーが入っていて、着信側がそれに答えたあとは、INVITE へのどの応答にもオファーは入りません（RFC 3261 13.2.1）。そのため PRACK の SDP は新しいオファーです。オファーの入った PRACK への 200 には、アンサーを入れなければなりません（RFC 3262 5）。P-CSCF には入れるアンサーがありません。

TS 24.229 がオファーのためにダイアログを解放するのは、オファーが応答で届いたときだけです（5.2.8.1.2）。6.2 は、そのようなオファーの入った 200 を P-CSCF に先へ渡させ、ACK が届いたらセッションを解放させます。200 は誰も断れないためです。応答に入ったアンサーも断れないので、中継ノードが応答のアンサーを受け取らないときは、P-CSCF は呼を解放します。要求に入ったアンサーは違います。暫定応答に入ったオファーへのアンサーを運ぶ要求には、6.2 は P-CSCF に 488 を返させます。ここではその要求は PRACK なので、上のとおり呼を終わらせます。

`internal/pcscf` の試験は、SDP の `Modify` を失敗させる中継ノードを使って、これらの流れを 1 つのプロセスの中で動かします。`TestRefusedOfferWithinTheDialogIsRejected`、`TestRefusedOfferOfAnUPDATEInTheEarlyDialogKeepsTheCall`、`TestOfferWithinTheDialogEndsTheCallWhenTheRelayMayHaveTakenIt`、`TestMalformedOfferWithinTheDialogGets400`、`TestINVITEWhoseSDPTheP_CSCFCannotReadGoesNoFurther`、`TestUPDATEWhoseSDPTheP_CSCFCannotReadGoesNoFurther`、`TestRefusedSDPOfAPRACKEndsTheCall` です。

## 相手がオファーを断ったとき

中継ノードがダイアログの中の要求のオファーを受け取っても、その先のノードがオファーを断ることがあります。UE 2 は受けられないオファーに 488（Not Acceptable Here）を返し、UE 2 の P-CSCF は、自分の中継ノードが受け取らないオファーに、上のとおり 500 を返します。要求は 2xx 以外の最終応答で終わり、セッションは要求の前のままです（RFC 3261 14.1、RFC 3311 5.3）。UE 1 は最後のオファーとアンサーのアドレスでメディアを受け続けます。ところが P-CSCF はオファーを先へ渡す前に、オファーのアドレスへ送るようアクセス側のターミネーションに伝えています。そこで P-CSCF は応答を UE 1 へ渡す前にもう一度 `Modify` を送り、最後のオファーとアンサーのアドレスへ送るようターミネーションを戻します。

```text
 UE 1          P-CSCF          メディア中継ノード  網
 | 新しい SDP のオファーの入った re-INVITE          |
 |-------------->|                |                 |
 |               | PUT .../terminations/access      |  Modify。UE 1 がこれから受けるはずのアドレス
 |               |--------------->|                 |
 |               | re-INVITE                        |
 |               |--------------------------------->|
 |               |                     488 (INVITE) |  UE 2 がオファーを断る
 |               |<---------------------------------|
 |               | PUT .../terminations/access      |  Modify。UE 1 が前から受けているアドレス
 |               |--------------->|                 |
 |  488 (INVITE) |                |                 |
 |<--------------|                |                 |
```

- **`Modify` は応答より先に送ります。** UE 1 は 488 のすぐあとに新しいオファーを送るかもしれません。そのオファーが届くときには、中継ノードはもう元に戻っています。
- **2xx 以外のどの最終応答でも同じです。** 答えが無かったときも同じで、そのとき UE 1 は 504（Server Time-out）を受け取ります。UPDATE でも、保留のような re-INVITE でも、新しいオファーの入った PRACK でも同じです。
- **網からのオファー**では、コア側のターミネーションを戻します。UE 1 の 488 は網へ返ります。
- **ターミネーションは最後に終わったオファーとアンサーのアドレスへ戻ります。** INVITE のオファーとアンサーか、そのあと 2xx を受け取ったダイアログの中の要求のオファーとアンサーです。P-CSCF はこのアドレスをダイアログと一緒に、各台が共有する保存先に置きます。そのため、要求がそれまでの要求と別の台を通っても戻せます。
- **オファーでメディアのアドレスが変わらないとき**は、ターミネーションは前と同じところへ送っています。ポートを変えない保留がその例です。P-CSCF は 2 回目の `Modify` を送りません。UE 2 の P-CSCF に届くオファーには UE 1 側の中継ノードのアドレスが書いてあり、UE 1 がどんなオファーを送ってもそれは変わりません。そのため、中継ノードを戻すのは UE 1 の P-CSCF だけです。
- **re-INVITE への信頼性のある 183 にアンサーが入っていて**、そのあと re-INVITE が失敗したときは、そのオファーとアンサーはもう終わっています。RFC 6141 3.3 はこのように変更を実行した UAS に、re-INVITE へ 2xx を返すよう求めています。それでも誤りの応答を受け取った UAC は、両者のセッションの見方をそろえるために新しいオファーを送ります（RFC 6141 3.4）。P-CSCF は中継ノードをそのアンサーのままにします。新しいオファーはほかのオファーと同じく中継ノードを通ります。
- **re-INVITE への信頼性のない 183 にだけアンサーが入っていて**、そのあと re-INVITE が失敗したときは、アンサーは来ていません。アンサーは 2xx か信頼性のある暫定応答に入るものです。同じアンサーを、それより前の暫定応答に入れることもできます（RFC 3261 13.2.1）。中継ノードは、その 183 が示す先へ相手に送っていました。そのため re-INVITE が失敗すると、両方の終端が、最後のオファーとアンサーが示す先に戻ります。`TestRejectedOfferAfterAPreviewPutsBothSidesBack` がこれを確かめます。
- **UE 1 が re-INVITE を取り消したとき**も同じです。UE 1 は新しいセッションの資源を確保できず、アンサーを受け取る前に変更をあきらめて、自分の re-INVITE を取り消します（RFC 3261 9.1、TS 24.229 6.1.4.2 の項目 b）。P-CSCF はプロキシなので、CANCEL が届くと、自分が送ったブランチを取り消し、その CANCEL の Reason を写します（RFC 3261 16.10、RFC 3326 2）。セッションを何も変えていない相手は 487（Request Terminated）を返します。これもほかと同じ 2xx 以外の最終応答なので、中継ノードは最後のオファーとアンサーが示す先へ戻ります。`TestCancelledReInvitePutsTheRelayBack` がこれを確かめます。
- **中継ノードが戻す `Modify` を受け取らないとき**は、アクセス側のターミネーションは、UE 1 がもう受けないアドレスへ送り続けます。そのとき P-CSCF は、中継ノードがアンサーを受け取らないときと同じく呼を解放します。488 を渡したあとで、両方に `Reason: SIP;cause=503` の入った BYE を送ります。early dialog では、UE 1 は INVITE への 500 を受け取り、網へ向けた INVITE は取り消されます。

`internal/pcscf` の試験 `TestRejectedOfferPutsTheRelayBack`、`TestRejectedOfferGoesBackToTheLastOfferAndAnswer`、`TestRejectedOfferEndsTheCallWhenTheRelayDoesNotGoBack` が、これらの流れを 1 つのプロセスの中で動かします。
