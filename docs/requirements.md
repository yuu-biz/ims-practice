# 要件定義

この文書は学習用 IMS 実装プロジェクトの目的と、作るものの要件と制約をまとめたものです。何ができていて、何をこれから作るかは [roadmap.md](roadmap.md) に、要件を満たすための作りは [設計の記録](design/README.md) にあります。

各要件の末尾に、次の区分を書きます。

- 「必須」はこのプロジェクトの目的として挙げた要件です。
- 「推奨」は「できると好ましい」として挙げた要件です。
- 「派生」は必須と推奨の要件を満たすために必要になる要件です。数値の目安などはこの区分に入ります。
- 「提案」は目的を達成するために加えることを勧める要件です。採るかどうかはメンテナーが決めます。

## 目的

テレコム技術者が減り、技術継承が課題になっています。このプロジェクトでは、3GPP が規定する標準 IMS を自分たちで実装します。動かしながら次のことを学べるようにします。

- 電話や SMS がつながるまでに、どのノードがどの順番でどんな信号をやり取りするか。
- その信号が 3GPP 仕様のどこに書かれているか。
- 仕様の記述が実際のコードではどう実装されるか。

## 想定する読者と利用者

- IMS やコアネットワークの知識がない初学者。SIP や Diameter という単語を初めて聞く人を含みます。
- 初学者に教える立場のベテラン技術者。シーケンスやパケットを見せながら説明する教材として使います。
- 機能を追加する開発者。HSS や EPC/5GC のスタブを本格的な実装に置き換える人を含みます。

## 作るものと作らないもの

IMS の中核（P-CSCF、I-CSCF、S-CSCF、AS）は自分たちで実装します。信号処理の中身を読めることが学習の目的だからです。既存の OSS（Kamailio など）を設定して使う構成にはしません。

周辺ノード（HSS、EPC/5GC、UE）は、IMS から見て本物と同じインタフェースを持つスタブとして作ります。内部の作り込みは後回しにします。スタブはインタフェースの境界で差し替えられるように作り、本格的な実装や OSS（Open5GS など）に置き換えられるようにします。

開発用のツール（SIP の試験ツール、Wireshark、ソフトフォン）は既存のものを使います。

## 機能要件

### 発着信と音声

- UE を IMS に登録（REGISTER）できる。認証を含む。（必須）
- 登録済みの UE どうしで発信と着信ができる（INVITE から BYE まで）。（必須）
- 通話中に音声（RTP）が双方向に流れ、聞いて確認できる。（必須）
- SMS を送受信できる。SMS over IP（TS 23.204、TS 24.341）の方式で、SIP MESSAGE に SMS を入れて運ぶ。（必須）
- 相手不在、話中、未登録などの異常系の呼を再現できる。（提案）
- iFC（Initial Filter Criteria）で AS を呼び出す流れを確認できる。SMS 用の IP-SM-GW を最初の AS にし、次に MMTel AS を加える。MMTel AS が MRF を使って音声ガイダンス、会議、CAT を提供する流れも確認できる。（提案）
- 認証方式を SIP Digest と IMS-AKA（Milenage）から選べる。（提案）
- 電話番号（tel URI）で発信できる。発信側の S-CSCF が ENUM（RFC 6116）で着信先の SIP URI を調べる。ENUM に無い番号は IMS の外への発信になるが、BGCF への転送は対象外とし、エラー応答を返す。（必須）

### 補足サービスとメディア資源

UE と網の音声の振る舞いは、GSMA IR.92 の必須の要件を満たすことにしています（「UE」の節）。IR.92 2.3 は MMTel の補足サービスを必須にしています。商用のサービスの多くも、これらを基本のサービスとして提供しています。

- MMTel AS を自作し、IR.92 2.3 が網に求める補足サービスを提供する。S-CSCF が iFC で MMTel AS を呼び出す。MMTel AS は `ims` コマンドの役割の 1 つにする。ほかの AS は、HSS の iFC に AS の URI を書けば加えられるようにし、プラグインの仕組みは作らない。（必須）
- 補足サービスの設定データを Sh で HSS に置く。利用者は Ut の XCAP（TS 24.623）で補足サービスを設定できる。範囲は IR.92 2.3.2 が求める最小限にする。MMTel AS が IR.92 のとおりに補足サービスを提供するために要る。（派生）
- MRF（MRFC と MRFP）を作り、音声ガイダンス（TS 24.628）、会議（TS 24.147、TS 24.605）、CAT（TS 24.182）を提供する。MRFC は SIP の役割にし、MRFP はメディア中継ノードの実装をもとにする。180 を受けた UE が自分で呼び出し音を鳴らす場合と、網が early media で音を流す場合を、キャプチャで比べられるようにする。（必須）
- メディアの制御に、H.248（ITU-T H.248.1）で制御する実装を加える。メディアの制御の境界（[media-control.md](design/media-control.md)）の後ろに、独自の API と並ぶ 2 つ目の実装として置き、既定は独自の API のままにする。範囲は 3GPP のプロファイル（Iq の TS 29.334、Ix の TS 29.238、Mp の TS 29.333）が使うものに限る。標準のメディア制御のプロトコルを学べるようにするため。（必須）

### SMS の配達経路

SMS over IP に加えて、IMS を通らない NAS の経路でも SMS を届けます。

- SC を独立した役割にする。SGd で MME、SMSF、IP-SM-GW と、S6c で HSS と通信する（TS 29.338）。（必須）
- SMS を NAS で届けられる。EPC では MME が NAS で SMS を運ぶ方式（SMS in MME、TS 23.272 Annex C）、5GS では AMF と SMSF を使う方式（TS 23.502 4.13.3）を使う。UE シミュレータとアクセス網のスタブの間の NAS（TS 24.301、TS 24.501）は、SMS に要る範囲で作る。CP 層（TS 24.011）は、SMS over IP と同じ RP 層と TP 層の符号化の下に加える。（必須）
- IP-SM-GW が、SMS を IP と NAS のどちらで届けるかを選ぶ（ドメイン選択）。IP で届かなかったときは、NAS で届け直す（TS 23.204 6.4、6.5a）。（必須）

### 信号の観察と解析

- ノード間の信号をキャプチャし、Wireshark でシーケンスを解析できる。（必須）
- キャプチャ経路を用意する。Docker の内部ネットワークはホストの Wireshark から直接見えないため、pcap ファイルの出力またはライブ転送の手段を提供する。（派生）
- 既定の設定では信号を暗号化しない。Wireshark でそのまま読める状態にする。TLS や IPsec は後から有効にできるオプションにする。（派生）
- 各ノードが送受信した信号を収集し、Call-ID ごとのラダー図（シーケンス図）をダッシュボードで表示する。収集には HEP（Homer Encapsulation Protocol）を使う。（提案）
- Wireshark の既定のポート番号（SIP 5060、Diameter 3868 など）を使い、デコード設定なしで解析できるようにする。（提案）

### ドキュメントとダッシュボード

- 初学者が順番に読める手順書を用意する。起動、登録、通話、SMS、障害観察の各シナリオについて、操作手順と期待するシーケンスを載せる。（必須）
- 簡易ダッシュボードで状態を見て操作できる。登録状態、通話状態、加入者情報を表示する。（必須）
- 各手順書に、シーケンスの各メッセージが規定されている 3GPP 仕様や RFC の箇所を載せる。（提案）
- 用語集を用意する。略語（CSCF、HSS、iFC など）の正式名称と一行の説明を載せる。（提案）
- ダッシュボードから加入者の追加と削除ができる（HSS への登録）。（提案）
- コードの中で、仕様の手順に対応する箇所から仕様の条項番号を参照できる。（提案）
- 初学者向けの説明と勉強会に使えるスライドを用意する。実装言語（Go、Rust）の簡単な説明、このリポジトリのパッケージ構成、標準と対応させた IMS の説明、このリポジトリの個別の実装の説明を扱い、1 回の勉強会で扱える分量の複数のデッキに分ける。（提案）
- スライドの元データはテキスト（Markdown など）にして Git で管理する。HTML で表示でき、配布用に pptx も出力できるようにする。（派生）

### 分散構成と障害の観察

- 各論理ノードを別のコンテナとして起動し、ネットワーク越しに連携する分散構成で動く。（必須）
- 1 つのコンテナイメージが、設定によって P-CSCF、I-CSCF、S-CSCF などの役割を持つ。1 コンテナに複数の役割をまとめる構成も選べる。（必須）
- 同じ役割のノードを複数台起動できる（P-CSCF や S-CSCF の冗長構成）。ドレインと障害の観察の前提になる。（派生）
- 通話に影響を出さずにノードを切り離す操作ができる。新規の登録と呼だけを他のノードへ回し、通話中の呼は終わるまで処理を続ける（ドレイン）。（必須）
- 意図的に障害を起こし、その影響と復旧を観察できる。ノード停止、遅延、パケット損失、ネットワーク分断を対象にする。（必須）
- IMS の復旧手順（TS 23.380 IMS Restoration Procedures）を再現できる。S-CSCF や P-CSCF の障害から UE が再登録で復旧する流れを確認する。S-CSCF の障害では、UE が登録し直さずに、別の S-CSCF が HSS から登録の情報を取り戻す流れ（TS 23.380 4.3.3）も確認する。（提案）
- 学習用の画面から障害の注入を操作できる。障害の注入は学習のための試しで、運用の操作ではない。ドレインは運用の操作なので、OAM の側に置く。Docker のソケットを渡すコンテナは、上書きのファイルで明示したときだけ起動する。（提案）
- C-Plane（SIP の処理）と U-Plane（RTP の中継）を、同じコンテナにまとめる構成と、別のコンテナに分ける構成の両方を選べる。（必須）
- RTP は UE 間で直接流さず、メディア中継ノード（IMS-AGW 相当）を経由させる。中継ノードの障害やドレインが通話に与える影響を観察できるようにするため。中継ノードの制御方式は [media-control.md](design/media-control.md) にある。（提案）
- ノードのコンテナが障害で落ち、別のコンテナに置き換わっても、登録と確立済みの呼をできる限り保つ。利用者が障害に気づかずに使い続けられることを目指す。登録の情報（プロファイルを含む）、ダイアログ、メディアの中継が対象になる。方式は標準で決まっていないため、設計の記録に書く（[state-redundancy.md](design/state-redundancy.md)）。外部の保存先を使う方式は呼の処理を遅らせるおそれがあるので、候補を試作して遅延と復旧の様子を測ってから決める。（必須）

### IMS 間の相互接続

- 2 つの IMS 網を IBCF と TrGW でつなぎ、網をまたいで通話と SMS ができる。IBCF は TS 24.229 の IBCF の手順に従う。（必須）
- 相手網として、2 つ目の IMS ドメインを同じイメージと別の設定で起動できる。レルム、番号、加入者は自網と別にする。（派生）
- IBCF は接続先ごとの設定（相互接続プロファイル）を持つ。ヘッダとパラメータの扱い、番号の形式、トランスポート、使えるコーデックを、コードの変更なしに接続先ごとに変えられる。事業者間の SIP の仕様の違いをどこで吸収するかを学べるようにするため。（必須）
- IBCF は網の境界でトポロジーを秘匿できる（THIG）。相手網に届く信号とメディアに、自網の内部のアドレスが現れない。（必須）
- TrGW は網の境界でメディアを中継し、SDP のアドレスを書き換える。メディア中継ノードと同じ実装を使い、IBCF がメディア中継ノードと同じ制御 API で制御する。（必須）
- 自網と相手網のプロファイルを意図的に食い違わせたシナリオを用意する。食い違いで呼が失敗する様子と、プロファイルを調整して通るようになる様子を、キャプチャで比べられる。（提案）
- 国ごとの標準（日本では TTC の標準）に合わせる機能と、接続先の網や国ごとに振る舞いを変える機能を加えられる。3GPP の共通の部分に従って作り、国ごとの違いはその上に加える。（提案）

### 周辺ノード（スタブ）

- HSS のスタブを用意する。I/S-CSCF との間は Diameter Cx（TS 29.228、TS 29.229）で通信する。（必須）
- アクセス網（EPC または 5GC）のスタブを用意する。UE への IP アドレス払い出しと P-CSCF アドレスの通知を模擬する。（必須）
- スタブはインタフェースの境界で本格的な実装に差し替えられる。（必須）
- EPC スタブに PCRF を含め、P-CSCF との間の Diameter Rx（TS 29.214）で、音声用ベアラの確立を模擬する。（提案）
- 5GC 構成では PCF（N5）と HSS（TS 29.562 の Nhss サービス）を HTTP/2 の SBI で模擬する。（必須）
- AS から HSS への Diameter Sh（TS 29.328、TS 29.329）を用意する。（提案）
- 上級者向けに、アクセス網のスタブを Open5GS と UERANSIM に置き換えた構成を用意する。（提案）

### 運用と保守（OAM）

商用の IMS は呼を処理できるだけでは足りません。保守と運用ができて初めて使えます。製品の多くは、標準では決まっていない保守用の API を通して OAM（Operation, Administration and Maintenance）の仕組みから制御され、OAM も IMS の製品と一緒に提供されます。この節の要件は、呼処理だけでなく運用も学べるようにするためのものです。

- 各ノードに保守用の API を持たせる。状態の参照、設定の参照と変更、ドレインの開始と解除、ログの詳しさの変更ができる。API は標準ではなくこのプロジェクト独自のものとし、そのことを手順書に書く。（必須）
- OAM のサーバーを用意し、保守用の API を通して全ノードをまとめて操作できるようにする。学習用の画面とは分ける。学習用の画面は学習の道具で、OAM は保守の装置である。境界で捨てた信号の数などのトラヒックの統計は、OAM から見られるようにする。（必須）
- 加入者データの登録、変更、削除を、OAM から 1 件ずつでも一括でもできる（プロビジョニング）。（必須）
- 加入者データとノードの状態を退避し、障害のあとに戻せる（バックアップとリストア）。戻す手順と、戻したあとに網が正しい状態になったことを確かめる手順を、手順書に書く。（必須）
- ノードの稼働状態、登録や呼の成功率のような指標、警報（アラーム）を OAM で見られる。（必須）
- 試験用の利用者を指定できる。試験用の利用者だけを収容する運用と、特定の機能を試験用の利用者だけに有効にする運用ができる。小さく始めて広げていく導入を学べるようにするため。（必須）
- 設定の変更を記録し、前の設定に戻せる。（提案）
- 指標を Prometheus の形式で公開し、Grafana のような広く使われている道具で見られるようにする。OAM の画面は、簡易なフロントエンドでよい。（提案）
- キャプチャとログを解析する機能を持つ。呼ごとの信号の流れ、失敗した呼の理由ごとの件数などを、Wireshark を開かずに見られる。（提案）

### UE

- UE シミュレータを自作する。CLI とダッシュボードから登録、発信、着信応答、切断、SMS 送信を操作できる。音声は WAV ファイルを送り、受信した音声を保存する。（提案）
- 市販のソフトフォン（Linphone など）からも、SIP Digest 認証で登録と通話ができる。マイクとスピーカーで会話を試せる。（提案）
- UE と網の音声の振る舞いは、GSMA IR.92（VoLTE）と NG.114（VoNR）の必須の要件を満たす。音声コーデックもこれに従う。満たさないと、携帯電話の UE が前提にしている標準から外れるため。推奨の要件は、必要になったときに加える。（必須）

## 非機能要件

- デスクトップの Docker で起動できる。（必須）
- 対象は Windows の Docker Desktop を基準にし、macOS と Linux でも動くようにする。（派生）
- 起動は 1 コマンドで完了する。（派生）
- Kubernetes でも動く。ローカル環境（kind など）での動作を基準にする。（推奨）
- 性能は求めない。ただし、規模を広げられる組み方は、下の「商用網の規模に向けて水平に広げられる組み方」で求める。（必須）
- 性能の目安は、加入者 100 人、同時通話 10 呼とする。この値は仮のもので、メンテナーが変更できる。（派生）
- 段階的に開発する。各段階の終わりに、学習者が動かしてキャプチャできる状態にする。（必須）
- ノードの役割、接続先、加入者データは設定ファイルで与える。コードの変更なしに構成を変えられるようにする。（提案）
- ノードの状態（登録情報、ダイアログ）はノードの外に置けるようにする。冗長構成とドレインの前提になるため、最初の設計から考慮する。（必須）
- ホスト固有のネットワーク設定（`network_mode: host` など）に依存しない。Docker と Kubernetes で同じ構成を使うため。（提案）
- ログは構造化（JSON）し、Call-ID などの相関キーで追えるようにする。（提案）
- CI で、登録、通話、SMS のシナリオを Docker Compose 上で自動試験する。試験時の pcap を CI の成果物として保存し、誰でもダウンロードして Wireshark で開けるようにする。（提案）
- 学習者向けの文書（手順書、用語集、README）は英語と日本語の両方で用意する。言語の使い分けは [CONTRIBUTING.md](../CONTRIBUTING.md) の「言語」に従う。（必須）
- DNS の構成を設定で選べる。プロジェクトの DNS コンテナ（既定）、外付けの DNS サーバー、Docker のネットワークの DNS だけ、Kubernetes のクラスタの DNS のどれでも動く。DNS は設備設計の一部で、構成によって名前解決の流れが変わるのを学べるようにするため。NAPTR と SRV が無い構成では、RFC 3263 の手順どおり A レコードと既定のポートで動く。（提案）
- 商用網の規模に向けて水平に広げられる組み方。商用網の規模（数千から数億の加入者）に向けて、構成を水平に広げられる組み方にする。性能が出るかは問わない。各役割（P-CSCF、I-CSCF、S-CSCF、HSS、メディア中継ノード）を複数台にでき、DNS や Diameter の経路で振り分けられること。1 台のノードやプロセスに利用者を縛る状態、全加入者を走査する処理、全体を止めるロックを設計に入れないこと。これが無ければ、IMS である意味が無く、SIP の PBX で足りてしまうため。（必須）
- 今は作り込まない所も、商用の品質まで作り込める余地を残す。広げる見込みの無い拡張点は作らない。一方で、仕様の値や手順をあちこちに直書きする、1 つの部品に別々の責務を混ぜる、境界（インタフェース、設定、`Store`）を越えて内部の状態を触る、といった、修正や拡張を難しくする作りはしない。（必須）
- デプロイ先に、手元の Docker と Kubernetes のほか、AWS や Azure のようなクラウドを選べる。クラウドの Kubernetes（EKS、AKS など）の上に、Kubernetes 用と同じマニフェストで載せる。SIP と RTP の UDP を通すロードバランサー、公開アドレス、NAT の扱いを、クラウドごとの設定として分ける。（提案）

## 対象外

次のものは作りません。必要になった時点で要件として追加します。

- 商用レベルの性能、可用性、セキュリティ。
- 実際の携帯端末と無線区間（RAN）の接続。SIM のプログラミングと無線機器が必要なため。上級者向けに UERANSIM を使う構成（「周辺ノード」の節）は検討します。
- 課金（Rf、Ro）、法定傍受、緊急呼。
- PSTN や CS 網との接続（BGCF、MGCF）とローミング。ロードマップの拡張の候補として残します。MSC が要る SMS over SGs も、CS 網を使うのでここに入ります。IMS 網どうしの相互接続（IBCF、TrGW）は「IMS 間の相互接続」の節で扱います。

## 未決事項

決まった論点は設計の記録に移しました。実装の言語と自作する範囲は [implementation.md](design/implementation.md)、UE の用意の仕方は [ue-simulator.md](design/ue-simulator.md)、メディア中継ノードの制御は [media-control.md](design/media-control.md)、ホストとコンテナのあいだの通信は [environment-capture.md](design/environment-capture.md)、音声コーデックと AMR の実装の方法は [codecs.md](design/codecs.md)、ダッシュボードの作りは [lab-oam.md](design/lab-oam.md) にあります。

次の論点は決めていません。決まるまでは、それぞれに書いた案で進めます。

- **Diameter のトランスポート。** TCP を使っています。Docker Desktop（Windows、macOS）では SCTP が使えない場合があるためです。実網は SCTP が多いことを手順書に書きます。
- **最初のアクセス網。** EPC（4G）のスタブから始め、5GC はそのあとにします。公開されている解説資料が多く、Diameter で一貫して見られるためです。
- **EVS の実装と、コーデックの特許の扱い。** EVS の実装の方法は、利用条件と特許の扱いを確かめてから、VoNR を作るときに決めます。3GPP の参照コードにはオープンソースのライセンスが付いていないためです。AMR と AMR-WB については、公開されている資料で読み取れたことと読み取れなかったことを [codecs.md](design/codecs.md) に書きました。AMR と AMR-WB は符号化済みのフレームを使うので、製品は AMR と AMR-WB の符号化と復号の実装を含みません。
