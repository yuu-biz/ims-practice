# スライドの道具の調査

この文書は、勉強会で使うスライドの道具を選ぶために、候補を試作して比べた記録と、そこから自作の生成器に決めた経緯、その生成器の作りと確認の仕組みをまとめたものです。スライドは `slides/` にあり、元データは Markdown に近いテキストで、HTML と pptx を作ります。ここに書いたことは、どれも試作の出力を自分で開いて確かめたか、コマンドを実行し直して確かめたものです。仕様の条項は扱いません。

「試した道具」から「最初に選んだ道具」までは、既製の道具（Marp など）を比べた記録です。このプロジェクトは、その後に自作の生成器へ切り替えました。今の作り方は「自作の生成器」に書いてあります。

## 求めること

根拠は [requirements.md](../requirements.md) の、勉強会に使えるスライドを用意し、元データをテキストで Git に置き、HTML と配布用の pptx を出力するという項目と、[roadmap.md](../roadmap.md) のスライドの項目です。

| 求めること | 確かめ方 |
| --- | --- |
| 元データがテキストで、Git で差分を読める | ソースの形式を見る |
| HTML で表示できる | ブラウザで `file://` から開く |
| 配布用の pptx を出力できる | pptx の中の XML を数える。LibreOffice で PDF にして見る |
| 日本語と英語のデッキを作れる（学習者向けの文書は両言語で用意する決まり） | 日本語の文字が日本語の字形で出るかを見る |
| 手順書のラダー図とキャプチャのフィルタが崩れない | 手順書と同じテキストの図と、表示フィルタを置いて見る |
| 発表者ノートを書ける | pptx のノートと HTML の発表者ビューを見る |
| CI（`ubuntu-latest`）で HTML と pptx を作れる | 依存の大きさ、要るプログラム、Node の版を見る |
| ライセンスに問題がない | パッケージの記載を見る |

手順書のラダー図は、Mermaid ではなく、` ```text ` のコードブロックに等幅の文字で描いた図です。`docs/` の中に Mermaid のブロックは 1 つもありません。それでも、図を Mermaid で描き直す場合に備えて、Mermaid の扱いも比べました。

## 試した道具

同じ内容のサンプル（6 枚）を、それぞれの道具の書き方で作りました。表紙、箇条書き（入れ子と手順書へのリンク）、表、表示フィルタと Go のコード（日本語のコメントを含む）、手順書と同じテキストのラダー図、Mermaid のシーケンス図です。表紙と 2 枚目に発表者ノートを付けました。

| 道具 | 版 | ライセンス | 入れ方 | 大きさ |
| --- | --- | --- | --- | --- |
| Marp CLI | 4.5.1 | MIT | npm | `node_modules` が 136 MB、156 パッケージ |
| pandoc（HTML は reveal.js） | 3.1.3、reveal.js 5.1.0 | pandoc は GPL-2+、reveal.js は MIT | pandoc は Ubuntu 24.04 の apt、reveal.js は npm | reveal.js の `node_modules` が 5.9 MB |
| Quarto | 1.11.9 | MIT（pandoc、deno、esbuild、typst などを同梱） | PyPI の `quarto-cli` | パッケージのディレクトリが 420 MB |
| Slidev | 53.1.0 | MIT | npm（PDF と pptx の書き出しに `playwright-chromium` 1.65.1） | `node_modules` が 598 MB、722 パッケージ |
| Mermaid CLI（補助） | 12.2.0 | MIT | npm | `node_modules` が 456 MB |

Marp は Mermaid を描かないので、Marp で Mermaid の図を使うには、前もって SVG にしておく必要があります。その手間を見るために Mermaid CLI も試しました。手順書の登録の図の前半を Mermaid で書き、SVG にできました。

ブラウザは Chromium（Playwright の 1243 番のビルド）を使い、pptx は LibreOffice 24.2.7.2 で PDF にして画像で見ました。

## 見たこと

### pptx

| 道具 | スライドの中身 | 発表者ノート | 気づいたこと |
| --- | --- | --- | --- |
| Marp（既定） | 各スライドが 1 枚の画像。文字は編集できない | 6 枚すべてにある | 見た目は HTML と同じ。日本語、表、テキストのラダー図、コードがそのまま出る |
| Marp（`--pptx-editable`） | 文字が編集できる（文字の連なりが 141、うち日本語を含むものが 32） | 無い | 実験的な機能。LibreOffice が要る。フォントは LibreOffice が選んだ IPAGothic と IPAPGothic になった |
| pandoc | 文字と表が編集できる | ノートを書いた 2 枚にある | テキストのラダー図が大きな文字で折り返され、図として読めない。コードは下に切れる。表の文字が小さい。Mermaid は文字のまま |

勉強会では、スライドの表示フィルタを参加者がそのまま Wireshark に打ち込みます。Slidev の合字はその妨げになります。フォントを変えれば避けられますが、既定のままでは使えません。

テキストのラダー図が崩れないのは、スライドを画像にする道具（Marp、Slidev）だけでした。pandoc と Quarto の pptx は、コードブロックを PowerPoint の文字の枠に入れるので、幅の広い等幅の図が収まりません。

| --- | --- | --- | --- |

### 日本語のフォント

Chromium で、`lang` の付かない HTML に総称の `sans-serif` で日本語を書いて PDF にすると、このマシンでは中国語のフォント（WenQuanYi Zen Hei）が使われました。`lang="ja"` を付けると IPAPGothic になりました。Marp は、フロントマターの `lang: ja` を `<html lang="ja">` にします。デッキではそれに加えて、テーマ（`slides/themes/ims.css`）に日本語のフォントの名前を並べています。`lang` とフォントの名前の 2 つで、漢字が中国語の字形になるのを防ぎます。

スライドを画像にする方式では、ビルドするマシンのフォントがそのまま pptx に入ります。CI では日本語のフォントを入れてからビルドします（下の「CI の案」）。

### Node の版

Marp CLI 4.5.1 は Node 18 以降を求めます。Slidev 53.1.0 は 22.22.0 以降、Mermaid CLI 12.2.0 は 22.13.0 以降です。本番のデッキ 8 つを、Node 22.23.5 と、ダッシュボードの CI と同じ 26.13.1 の両方で、`npm ci` から `npm run build` までビルドできました。


## 最初に選んだ道具（のちに置き換えた）

比べた結果、Marp CLI を使い、pptx は既定の画像の方式で出す案にしました。理由は次のとおりです。

- テキストのラダー図、表示フィルタ、表、日本語が、HTML でも pptx でも崩れずに出たのは Marp だけでした。
- HTML がファイル 1 つで、`file://` で開けます。
- 要るのは Node と Chromium だけです。Chromium は Marp が自分で探します。LibreOffice、pandoc、Python は要りません。依存も Slidev や Quarto より小さく、ライセンスはどれも MIT か、MIT と同じくらい緩いものです（下の「依存のライセンス」）。
- ソースは普通の Markdown で、手順書と同じ書き方で読めます。発表者ノートは HTML のコメントに書き、pptx のノートと HTML の発表者ビューに出ます。

その代わり、pptx の文字は編集できません。配布用なので、見た目が崩れないことを優先しました。編集したい人は Markdown を直してビルドし直します。`--pptx-editable` は、発表者ノートが落ち、LibreOffice が要るので使いません。

Mermaid は使いません。手順書のラダー図がテキストなので、デッキも同じテキストの図を使います。

### 依存のライセンス

`slides/package-lock.json` の 156 パッケージ（直接の依存は `@marp-team/marp-cli` 4.5.1 と `puppeteer-core` 24.43.1）のライセンスは、MIT が 110、Apache-2.0 が 17、ISC が 11、BSD-2-Clause が 6、MIT-0 が 4、BSD-3-Clause が 4、Python-2.0 が 2、PSF-2.0 が 1、0BSD が 1 です。コピーレフトのものはありません。`puppeteer-core` は Marp CLI の依存と同じ版で、はみ出しの確認のスクリプトが直接使うために書いています。新しいパッケージは増えません。


## 自作の生成器

### 切り替えた理由

次の 2 つを求めることにしました。

1. pptx は、PowerPoint で編集できる普通の Office のファイルにする。文字の箱、表、タイトルが編集できること。Marp の既定の pptx は 1 枚 1 枚が画像で、使いにくい。
2. 発表者ノートは付けない。

そのうえで、Marp や pandoc を曲げて使うのではなく、このプロジェクトの生成器を作ることにしました。理由は次のとおりです。

- 書式をそろえられる。HTML と pptx が同じ見た目になる。
- デザインを自由に決められる。
- ソースは Markdown に近いテキストのままにできる。

Marp の `--pptx-editable` と pandoc を実際のデッキで比べる前に方針が変わったので、新しい数字は測っていません。両方の欠点は、上の「見たこと」の表にある試作のとおりです。`--pptx-editable` は LibreOffice が要り、発表者ノートが落ちます。pandoc はテキストのラダー図が崩れます。

### Go にした理由

候補は 2 つでした。(a) 標準ライブラリだけの Go で `slides/` の下に小さなプログラムを置く。(b) `slides/` の Node に pptxgenjs（MIT）を足す。

Go にしました。

- 依存が 1 つも増えません。`go.mod` を変えずに、今のモジュールの中でビルドできます。`archive/zip` と文字列の組み立てで足りました。
- 学習者に npm の道具が要らなくなります。`slides/package-lock.json` の 156 のパッケージが消えました。ビルドに要るのは Go だけで、ブラウザもフォントも要りません。
- 要る OOXML の量は扱える大きさでした。pptx を書く部分（`slides/internal/pptx`）は試験を除いて 711 行です。テーマ、スライドマスター、3 つのスライドレイアウト、スライド、表、コネクタ、グループで済みました。
- CI の `go test ./...` が、そのままデッキの確認にもなります。

最初に 02-registration を機械的に変換して pptx を作り、LibreOffice で PDF にして見たところ、文字、表、日本語がそのまま出ました。これで (a) で進めることにしました。

### 作ったもの

| --- | --- | --- |
| `slides/internal/deck` | ソースを読む。フロントマター、スライド、ブロック、行の中の書式、ラダー図。HTML のコメントを誤りにする。手順書の見出しへのリンクを確かめる | 1086 |
| `slides/internal/layout` | テーマ（色、フォント、大きさ）、文字の幅の測り方、各スライドの箱の位置 | 1055 |

試験は全部で 861 行です。`cmd/slides` の `TestDecks` が、リポジトリのデッキをすべて読んで確かめ、pptx と HTML を書いてみます。

レイアウトは 7 つです。title（表紙）、section（部の始まり）、content（既定。箇条書き、表、コード、ラダー図をこの中に置く）、two-columns、exercise、answers、summary です。スライドの大きさは 960 × 540 ポイント（16:9、PowerPoint のワイド画面と同じ）です。

ソースの書式は次のとおりです。

- フロントマターは `title`、`footer`、`lang` の 3 つだけ。
- `---` でスライドを区切り、スライドは見出しで始める。`#` は表紙と部の始まり、`##` はそのほか。
- 見出しの前の `[layout: 名前]` でレイアウトを選ぶ。`[column]` で 2 列に分ける。
- ブロックは段落、箇条書き（入れ子 1 段）、表、コード、引用、ラダー図（` ```ladder `）。
- HTML のコメントは誤り。

### 文字が収まるかの測り方

pptx は、開くアプリケーションが文字を折り返します。ビルドのときに本物のフォントで測ることはできないので、決まった幅で測ることにしました。

- ラテン文字は Arial の字幅で測ります。pptx が指定する Calibri や、日本語のフォントのラテン文字より広いので、測った行に収まれば、たいていのフォントで収まります。
- 漢字、かな、全角の記号は 1 em、等幅は 0.62 em です。行は箱の幅の 97% までしか埋めません。
- 行の高さは整数のポイントに丸めて、pptx でも HTML でも正確な値で指定します。ブラウザが行の高さを整数のピクセルに丸めるので、小数のままだと HTML のほうが数ピクセル高くなりました。
- 中身が収まらないスライドは、文字を 95%、90%、85%、80% と小さくします。80% でも収まらなければ、ビルドを止めます。

測り方が実物と合っているかは、2 つの方法で確かめました。

1. HTML に `?check` を付けて開くと、ブラウザが箱より大きく描いた文字の箱を一覧にします。Chromium（Playwright の 1243 番のビルド）で 14 のデッキを開き、どれも 0 でした。途中で、小さくした行の中のコードが行を高くすること（ベースラインがずれるため）を見つけ、CSS で直しました。
2. pptx を LibreOffice 24.2.7.2 で PDF にし、全ページを画像にして見ました。ここで 2 か所の崩れを見つけました。LibreOffice は「、」と、空白なしで続くラテン文字の語の間で行を分けません（ブラウザは分けます）。そのため VoLTE のデッキの箇条書きが 1 行増えて下の引用に重なり、表のセル「P-CSCF、UE、S-CSCF」がハイフンで折れて表が高くなりました。測り方を、この組み合わせを 1 つの語として扱うように直し、どちらも収まりました。

### ラダー図

ラダー図はテキストで書き、図形で描きます。参加者の行のあと、`A -> B -> C: ラベル // 注` の形で 1 行に 1 段を書きます。`-->` は応答（破線）、`<->` は Diameter のような要求と応答の組です。pptx では、参加者の箱と生存線、区間ごとの矢印（矢じり付きのコネクタ）、白地のラベルの箱、注記の箱、右の列の注を 1 つのグループにします。HTML では同じ図形を SVG で描きます。

変換した図は 5 つです。登録の全体、通話の INVITE の経路、VoLTE の attach、プリコンディション、bearer の解放です。そのうち VoLTE の 3 つは、もとは「送り手 -> 受け手 メッセージ 説明」の表のような等幅の文字でした。通話の図を変換したとき、P-CSCF から左の S-CSCF へ戻ってから右の UE 2 へ進む段が、2 本の矢印が重なって両向きの 1 本に見えました。1 段の中で向きが変わる行は誤りにし、2 段に分けました。

ネットワークの構成を表す等幅の図（MMTel AS と Ut の図、EPC スタブの図、中継ノードの 2 つのコンテキスト、3 つのダイアログの図）と、SDP、Wireshark の木、16 進のバイト列は、コードのブロックのままです。pptx では等幅の文字の箱なので、文字として編集できます。

### 発表者ノートを付けない方針にしたときの扱い

以前のデッキには、7 つのデッキの 2 つの言語に発表者ノートがあり、1 つの言語で 162 ありました。どれも読んで、次のように分けました。

| 中身 | 行き先 |
| --- | --- |
| 演習と「振り返り」の答え | 演習のすぐあとに answers のスライドを足した（9 枚ずつ、2 つの言語で） |
| 途中で会場に投げる問いと答え | そのスライドに「なぜ〜か。〜だからです」の形で書いた |
| 技術の説明 | 説明するスライドに足した。収まらないものは新しいスライドにした（通話の「2 つのコンテキストとラッチング」、MMTel AS の通話の区間の表、VoLTE の「attach でほかに見るもの」「IMS-AKA の 2 つの部分で見えること」「Rx その 2。AAR を読む」「Wireshark の AMR と比べるフレーム」「網が bearer を落とす。こう見える理由」「作っていないものと、その理由」） |
| 時間の配分、2 回に分ける場所、配る CI の成果物、前提の回 | `slides/README.md` と `README.ja.md` の「勉強会の進め方」 |
| 最初の問いかけ | 「この回で分かること」の最初の行 |

移さずに捨てたものは次のとおりです。

- 発表者への段取りの指示。「手順書のラダー図をここで見せる」「ホワイトボードに書く」「画面でその場で実行して見せる」「2 人 1 組で」の一部（演習の進め方は README に残した）など。
- スライドの文や表を言い直しただけの文。
- 1 回の実行のフレーム番号のうち、スライドがすでに使っているもの以外（例。「#871 から #1429 まで」）。番号は実行ごとに変わるためです。
- 「抜き出しは書いた時点のコード」という書き手向けの注意。README の「デッキを足す」の手順に同じことがあります。

### 確認が見るもの

`slides check` は、リンクとレイアウトを見ます。デッキに書いた事実（コマンド、経路、サービスの名前）が今のコードと合っているかも、次の確認で見ます。

| 確認 | 動かし方 | 見るもの | 見ないもの |
| --- | --- | --- | --- |
| デッキのコマンド | `slides check`、`TestDecks`（`go test ./...`） | `sh` のブロックと行の中のコードにある `docker compose` のサービスとプロファイル、`ue` のサブコマンドとフラグ、ダッシュボードへの `curl` のメソッドとパス、`scripts/` の下のパス | 文で書いた事実（「この構成では動かしていない」など）。`ue ctl` の動作の名前。`<<: *名前` で受け継いだ entrypoint |
| ハイパーリンク | `TestDecks` | pptx のすべての外部の関係の宛先が ASCII の URI で、戻すとソースのリンクになること | PowerPoint がそのリンクを開けること |
| 要素の順番 | `internal/pptx` の `TestPartsFollowTheSchemas` | サンプルとすべてのデッキの部品で、生成器が書く要素の子の順番、なければならない子、なければならない属性 | 表に無い要素。属性の値の型 |
| パッケージの形 | `internal/pptx` の `TestPackageIsComplete` | サンプルに加えて、すべてのデッキで、部品の型と関係の行き先 | |
| 実際のフォントでのはみ出し | `slides/check-html.js`（Node と Playwright） | すべてのデッキの `?check`。はみ出した箱が 1 つでもあれば失敗。デッキが名前を挙げていないフォントが字形の 1% より多くを描いたときも失敗 | pptx を PowerPoint や LibreOffice で開いたときのはみ出し |

決めたことと、その理由です。

- 経路は、`internal/dashboard` のソースを `go/ast` で読みます。ダッシュボードを読み込む（import する）と、スライドの道具がノードのパッケージに依存します。`cmd/ims` を動かすには、ポートと設定が要ります。読み方は 3 つの形だけです。文字列のリテラル、`range` で回す `[]string` の要素、その要素のメソッドとパスのあいだに 1 つのリテラルを挟む形（`method+" /api/ues/{name}"+path`）です。ほかの形の `Handle` や `HandleFunc` があれば誤りにします。読めない経路を黙って見落とさないためです。
- `ue` のフラグは、ソースを読まずに `go run ./cmd/ue register -h` の出力から取ります。学習者が見るのはその出力だからです。そのぶん、`slides check` は Go のビルドを 1 回待ちます。
- `curl` の宛先は、`internal/facts` の `httpHosts` の表にあるアドレス（今は `localhost:8080` だけ）に限ります。ほかの宛先は、表に足すまで失敗にします。
- 1% は、どのフォントにも無い記号のためのゆとりです。このマシンでは VoLTE のデッキの「⊕」だけが Inter で描かれました（35000 の字形のうち 1 つ）。フォントを入れずに動かすと、ラテン文字のほとんどが別のフォントになるので、この割合を大きく超えます。DejaVu だけにした fontconfig で試すと、ja/03-call は 10720 の字形のうち 8560 が DejaVu Sans で、5 つの箱がはみ出しました。

### XSD による検査

要素の順番は、公開されている ECMA-376 の XSD で検査するのが確実です。この環境からは `ecma-international.org` も `www.ecma-international.org` もプロキシに断られ（CONNECT に 403）、XSD を発行元から取れませんでした。ライセンスも読めていないので、リポジトリに入れてよいかは分かりません。そこで、迂回はせずに、上の「要素の順番」の試験を作りました。

表の中身は、この環境にあった変換の道具の付属のスキーマ（ISO/IEC 29500-4:2016 の移行用の `pml.xsd`、`dml-main.xsd` と、ECMA-376 Part 2 の `opc-*.xsd`）から読みました。発行元から取ったものではありません。その写しと `xmllint` 20914 で、14 のデッキの部品を 1 回だけ検査し、`docProps/core.xml` のほかはすべて通りました。`core.xml` は Dublin Core のスキーマをネットワークから読むので、検査できませんでした。試験は、その写しも `xmllint` も使いません。

## デッキの組み立て

- 置き場所は `slides/decks/<言語>/<番号>-<名前>.md` です。日本語と英語で同じスライドを同じ順に並べ、同じコミットで更新します（学習者向けの文書は両言語で用意する決まりです）。
- 1 回の勉強会に 1 つのデッキです。最初に作ったのは次の 4 つで、開発の基盤から SMS までを扱います。ダッシュボードは、登録、通話、SMS の各デッキの中で使います。その後、補足サービスと VoLTE のデッキを足し、全部で 7 つになりました。

| デッキ | 扱う内容 | 目安の時間 | 主に参照する手順書 |
| --- | --- | --- | --- |
| 01-packages | 開発の基盤から SMS までのコードの構成 | 45 分 | README、手順書の各「登場するノード」 |
| 02-registration | 登録（SMS で加わった第三者 REGISTER を含む） | 60 分 | `docs/guide/*/registration.md` |
| 03-call | 音声通話 | 60 分 | `docs/guide/*/call.md` |
| 04-sms | SMS | 75 分 | `docs/guide/*/sms.md` |

- スライドは手順書の説明を繰り返しません。キャプチャで見るものを表にし、手順書の該当する手順へ見出しでリンクします。ラダー図は縮めたものだけを載せ、全体は手順書を開いてもらいます。
- 条項番号は、手順書がその手順に挙げているものだけを、手順書と同じ版で書きます。デッキの中の条項番号は、すべて同じ言語の手順書にあることを確かめました。
- 電話番号は手順書と同じ架空の番号（+1 202 555 0100 から 0199）だけを使います。
- 手順書へのリンクは、デッキからの相対パスです。リポジトリの中で読むときに使えます。ビルドのときに `SLIDES_REPO_URL` を設定すると、HTML の中のリンクがリポジトリのアドレスからの絶対パスになり、CI の成果物を取り出して開いても使えます。

### はみ出しとリンクの確認（Marp の試作での確認）

Marp は幅の広いコードブロックを縮めますが、縦に長いスライドは縮めません。はみ出した行は、HTML でも pptx でも切れて見えなくなります。そこで、ビルドした HTML を Chromium で開き、スライドごとに高さと幅を測るスクリプト（`npm run check:overflow`）を作りました。試作の途中で、Compose のノードの表に 1 行足しただけで 5 px はみ出したのを、このスクリプトで見つけました。

デッキは手順書の 158 か所に見出しでリンクしています。見出しの名前が変わるとリンクが切れるので、リンク先の見出しがあるかを確かめるスクリプト（`npm run check:anchors`）も作りました。ファイルがあるかどうかは、リポジトリの `scripts/check_links.py` が CI で確かめています。

スライドに書いた Wireshark の表示フィルタは、tshark 4.2.2 で空のキャプチャに当て、どれも文法とフィールドの名前が通ることを確かめました。

## CI

自作の生成器にしたので、Node と Chromium を使うジョブは要りません。ジョブは、Go を入れて `go run ./cmd/slides -repo-url ... build` を実行し、`slides/dist/` を成果物 `slides` にするだけです。案は `slides/ci/slides.yml.proposed` にあります。デッキの確認は `go` のジョブの `go test ./...` でも走ります。スライドのジョブは、関係するファイルが変わったときだけ動かす方針です。

Marp を使う案では、次のジョブを考えていました（記録として残します）。

1. Node 26.13.1 を入れる（ダッシュボードのジョブと同じ）。
2. `fonts-noto-cjk` を apt で入れる。
3. `npm ci` と `npm run check:anchors`。
4. `SLIDES_REPO_URL` にコミットのアドレスを設定して `npm run build`。
5. `npm run check:overflow`。
6. `slides/dist/` を成果物 `slides` として保存する。

## 未決の論点

1. pptx が名前で指定するフォント。今はラテン文字が Calibri、日本語が Yu Gothic、コードが Consolas です。Office のあるマシンなら Windows でも macOS でもたいてい入っていますが、日本語を Meiryo や BIZ UDPGothic にしたい、などの好みがあれば変えます。`slides/internal/layout/theme.go` の 3 行です。
2. 表の行の高さ。測り方がわざと広めなので、行が文字に必要な高さより少し高くなることがあります。pptx の行の高さを小さめに書いて、開くアプリケーションに伸ばしてもらう手もありますが、PowerPoint で必ず伸びるかを確かめられないので、今は測った高さを書いています。
3. 構成の図を図形にするか。上の「ラダー図」に書いた等幅の構成の図は、今は文字の箱です。図形にするなら、ラダー図とは別の書式（箱と線の図）が要ります。今は作っていません。
4. デッキの一覧。MRF、相互接続、キャプチャと画面、網の全体の地図のデッキがありません。
5. 登録の前に、網の地図を置くか（ノード、参照点、自網と訪問先、なぜ SIP と Diameter か）。今の 01 はコードの地図で、IMS の地図ではありません。
6. キャプチャと画面の短いデッキを置くか。02 から先は、どれもその技能に頼っています。
7. 03（通話）は、プリコンディション、100rel、MMTel AS の 3 つのダイアログを、05 と 06 が説明する前に使っています。先の説明への一言か、SIP の基礎（トランザクション、ダイアログ、offer と answer、100rel）を通話の前に置くか。
8. MMTel のあとに MRF のデッキを、最後に相互接続のデッキを足すか。VoLTE は MMTel のあとのままにする案です。
9. 要件にある実装言語（Go、Rust）の簡単な説明のデッキを作るか。今のリポジトリのコードは Go だけです。Rust は、呼処理のノードとメディア中継ノードの言語を比べたときにしか使っていません。作るなら Go だけの説明になります。
10. 今後のデッキを、各機能の手順書ができたときに足していくか、区切りごとにまとめて足すか。
11. CI のジョブを、変更を取り込むたびに動かすか、`slides/` か `docs/guide/` が変わったときだけにするか。8 つのデッキのビルドは手元で 40 秒ほどでした。

## 確かめられなかったこと

- pptx を Microsoft PowerPoint と Keynote で開くこと。自作の生成器の pptx も、修復を求められないかは、パッケージの形の試験、python-pptx、LibreOffice で確かめただけです。要素の順番は ECMA-376 の順に合わせましたが、PowerPoint で開いて確かめてはいません。パーセント符号化したリンクを PowerPoint が開けるかも分かりません。LibreOffice 24.2.7.2 は ja/03-call と en/05-mmtel を PDF にでき、ページ数はスライドの数と同じで、PDF のリンクは符号化したまま残り、戻すと日本語のアンカーになりました。
- 発行元の XSD による検査。ホストに断られました。ライセンスも読めていません。
- `check-html.js` を CI で動かすこと。
- 文で書いた事実。確認が見るのはコマンドだけです。「この構成では動かしていない」のような文は、今後も人が読んで確かめます。
- Calibri、Yu Gothic、Consolas が入ったマシンでの見え方。このマシンには無く、LibreOffice は Carlito、Noto Sans CJK JP、DejaVu Sans Mono に置き換えて描きました。
- 自動の段落番号が、入れ子の箇条書きをはさんで続くこと。今のデッキの番号付きの箇条書きには入れ子が無いので、確かめる場面がありませんでした。
- 提案した CI のジョブを GitHub Actions で動かすこと。
- HTML を Chromium のほかのブラウザで開くこと。
- Marp を使う案の分。GitHub Actions の `ubuntu-latest` での実行、ランナーに Chrome があり Marp がそれを自分で見つけること（`CHROME_PATH` には `google-chrome` か `chromium` のパスを渡す案にしました）、`fonts-noto-cjk` を入れたあとのフォントの選ばれ方（手元では IPAPGothic が使われました）、Marp の HTML の発表者ビュー（`p` キー）が別のウインドウで正しく動くこと（ヘッドレスの Chromium では確かめられません）。
- 勉強会の目安の時間が実際に合うか。勉強会はまだ開いていません。
