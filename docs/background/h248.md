# H.248 の調査（符号化と 3GPP のプロファイル）

この文書は、メディア中継ノードを H.248 で制御するときに関わる標準（H.248.1 の符号化、トランザクション、3GPP の 3 つのプロファイル）を調べた記録です。調べた内容を元に、H.248 のメッセージを読み書きするパッケージ `internal/h248` と、MG と MGC の手順の部品 `internal/h248/mediactl` を作りました。仕様の本文は写さず、要点を言い換えて書きます。条項を引くときは版も書きます。

メディア中継ノードと P-CSCF への組み込みは、この記録の範囲に入れていません。MG と MGC の手順の部品は「メディア中継ノードの制御（MG と MGC）」に、Mp の部品は「Mp のプロファイル（MRFC と MRFP）」に、組み込みの分け方は「実装の分け方」に書きます。

## H.248 の考え方

制御する側を MGC（Media Gateway Controller）、制御される側を MG（Media Gateway）と呼びます。Iq では IMS-ALG（P-CSCF）が MGC で、IMS-AGW が MG です。Ix では IBCF と TrGW、Mp では MRFC と MRFP が、同じ関係になります。

- ターミネーションはメディアの出入り口です。コンテキストは、互いにつながるターミネーションの集まりです（RFC 3525 6 章）。この実装の「P-CSCF の 1 回の通過に 1 つのコンテキスト、アクセス側とコア側の 2 つのターミネーション」（[media-control.md](../design/media-control.md)）は、Iq のプロファイルの形（TS 29.334 5.4）と同じです。
- メッセージは、ヘッダ（版と送信者の識別子 mId）と、1 つ以上のトランザクションでできています。トランザクションには、要求（TransactionRequest）、応答（TransactionReply）、処理中の通知（TransactionPending）、応答の受け取りの確認（TransactionResponseAck）があります（RFC 3525 8 章）。
- 要求の中は、コンテキストごとのアクションに分かれ、アクションの中にコマンドが並びます。コマンドは Add、Modify、Subtract、Move、AuditValue、AuditCapabilities、Notify、ServiceChange の 8 つです（RFC 3525 7.2）。
- コマンドの引数はディスクリプタです。メディアの性質は Media ディスクリプタに入れ、その中の Local と Remote に SDP を入れます（RFC 3525 7.1.8）。
- コンテキストの ID には、MG に選ばせる CHOOSE（`$`）、すべてを指す ALL（`*`）、コンテキストの外を指す NULL（`-`）があります。ターミネーションの ID にも `$` と `*` を使えます（RFC 3525 8.1.2、Annex B.1）。
- 機能の語彙はパッケージで足します。プロパティ、イベント、シグナル、統計を、`パッケージ名/項目名` の形で指します（RFC 3525 6.2.3、12 章）。

## 3GPP のプロファイル

3 つの仕様は、どれも 5 章が H.248 のプロファイルで、節の並びも同じです。プロファイルの名前と版は ServiceChange で送ります。

| 項目 | Iq（TS 29.334） | Ix（TS 29.238） | Mp（TS 29.333） |
| --- | --- | --- | --- |
| プロファイルの名前と版（5.1） | `threegIq`、7 | `threegIx`、7 | `MRF`、8 |
| H.248.1 の版（5.3） | 版 2 以上 | 版 2 以上 | 版 2 以上。MRFP でフロア制御を行うときは版 3 |
| ServiceChange に入れる版（5.8.8） | 2 か 3 | 2 か 3 | 2 |
| コンテキストの中のターミネーション（5.4） | 2 つ。アクセスの切り替えの間だけ 3 つ | Iq と同じ | 決めていない。会議では N 個 |
| 符号化（5.9） | テキストと 2 進 | テキストと 2 進 | テキストも 2 進も任意 |
| トークンの長短（5.9） | 受信側は両方を受ける。送信側は選べる | Iq と同じ | 受信側は両方を受ける |
| トランスポート（5.12） | SCTP を推奨。UDP は任意 | Iq と同じ | SCTP は必須。UDP は任意 |
| セキュリティ（5.13） | なし | なし | なし |

3 つとも、参照している H.248.1 は 2002 年 5 月の版 2 と、その Corrigendum 1（2004 年 3 月）です（各仕様の 2 章）。Mp はフロア制御のために版 3（2005 年 9 月）も参照しています。SCTP の運び方として、Mp は H.248.4（2000 年 11 月）とその Corrigendum 1（2004 年 3 月）を参照しています。Iq と Ix は H.Sup7（2008 年 5 月）を参照しています。H.248.8 は版を決めずに、エラーのコードの表の見出しで名前を挙げているだけです。

### 符号化について 3GPP が求めること

- TS 29.334 5.9 と TS 29.238 5.9 は、対応する符号化を「テキストと 2 進」としています。どちらか一方だけを必須にする文はありません。注で、ETSI TISPAN の Ia のプロファイルはテキストだけを使うと述べています。
- TS 29.333 5.9 は、2 進もテキストも任意としています。
- テキストでは、受信側は長いトークン（`Transaction`）と短いトークン（`T`）の両方を受けます。送信側は制御の関連ごとにどちらかを選べます（TS 29.334 5.9 の注 1 と注 2）。
- 2 進の符号化は ASN.1 の BER です（TS 29.334 5.17.1）。
- ターミネーションの ID は、テキスト（TS 29.334 5.6.1.1.1）と 2 進（5.6.1.1.2）の両方の形を決めています。ID の一部だけをワイルドカードにする指定は、テキストでしか使えません（TS 29.334 5.17.3.10 の注 5）。

つまり、3GPP はテキストを禁じておらず、2 進だけを必須にもしていません。テキストだけで作っても、プロファイルから外れません。

### コマンドとディスクリプタ

| コマンド | Iq と Ix（TS 29.334、TS 29.238 の 5.8） | Mp（TS 29.333 5.8） |
| --- | --- | --- |
| Add の要求 | Media（Stream の中に LocalControl、Local、Remote）、Events、Signals | Events、Signals、Media（TerminationState、LocalControl、Local、Remote） |
| Add の応答 | Media（Stream の中の Local）、Error | 要求と同じものと Error |
| Modify の要求 | Add に加えて、Media の中の TerminationState | Add と同じ |
| Modify の応答 | Media（Stream の中の Local）、Error | Add と同じ |
| Subtract の要求 | なし、または空の Audit | なし、または空の Audit |
| Subtract の応答 | なし、または Error | なし。統計を返すことがある（5.7.6） |
| Move | 使わない | 使う。ディスクリプタは Add と同じ |
| AuditValue | ROOT の ServiceState、Packages、空の Audit、ROOT のプロパティ（`root/*`、`ipra/*`） | ROOT の ServiceState、Packages、空の Audit、統計、シグナル、イベント |
| AuditCapabilities | 使わない | 手順はあるが、対象は今後の検討 |
| Notify | 要求は ObservedEvents。応答はなし、または Error | Iq と同じ |
| ServiceChange | 下の表 | 下の表 |

空の Audit を付けた Subtract は、統計を返さなくてよいと MG に伝えるためのものです（TS 29.334 5.8.3 の注）。空の Audit を付けた ROOT への AuditValue は、制御の関連が生きているかを MGC から確かめるために使います（TS 29.334 5.12 の表 5.12.3、5.17.3.10 の注 2）。

応答に入れるディスクリプタは、要求で値を MG に任せた項目だけです（TS 29.334 5.8.1）。たとえば、アドレスとポートを `$` にした Local を送ると、MG が選んだ値の入った Local が返ります。

使わないと書いてあるもの。DigitMap、EventBuffer、多重化のターミネーション（Iq、Ix、Mp）。Iq と Ix では、埋め込みのイベントとシグナル、シグナルのリスト、シグナルの種類と長さの指定、完了の通知、KeepActive、統計、イベントの検出時刻も使いません（TS 29.334 5.7.3 から 5.7.8）。Mp は、シグナルのリスト、種類と長さの指定、完了の通知、KeepActive、統計、イベントの検出時刻を使います（TS 29.333 5.7.2 から 5.7.7）。

コンテキストの属性は、Iq が Topology、優先度、緊急の表示を使います（TS 29.334 5.5、5.8.9）。Topology はアクセスの切り替えのときだけです（5.7.9）。Mp は Topology の向きとして isolate、oneway、bothway のすべてを認めています（TS 29.333 5.7.8）。コンテキストの属性の監査は、Iq と Ix では行いません。

### ServiceChange

MG が MGC に登録し、どちらかが止まるときや戻ったときに知らせる手順です。プロファイルの名前は、登録と再登録で必須です（TS 29.334 5.8.8 の表 5.8.8.7）。

| 手順（TS 29.334 5.17.3） | 送る側 | Method | Reason |
| --- | --- | --- | --- |
| 登録（5.17.3.5） | IMS-AGW | Restart | 901 Cold Boot か 902 Warm Boot。プロファイルと版を付ける |
| 復旧（5.17.3.4） | IMS-AGW | Restart | 900 Service Restored |
| 通信の回復（5.17.3.3） | IMS-AGW | Disconnected | 900 Service Restored |
| サービスの停止（5.17.3.2） | IMS-AGW | Forced か Graceful | 905、908、915 |
| 再登録（5.17.3.6） | IMS-AGW | Handoff | 903 MGC Directed Change |
| 再登録の指示（5.17.3.7） | IMS-ALG | Handoff | 903。別の MGC の mId を付ける |
| IMS-ALG の復旧（5.17.3.8） | IMS-ALG | Restart | 901 か 902 |
| IMS-ALG の停止（5.17.3.9） | IMS-ALG | Forced か Graceful | 905 |

どれも、コンテキストは NULL、ターミネーションは ROOT です。ServiceChangeAddress と ServiceChangeDelay は使いません（表 5.8.8.3、5.8.8.4）。別の MGC を指す ServiceChangeMgcId（テキストでは `MgcIdToTry`）は使います（表 5.8.8.9）。Ix（TS 29.238 5.8.8）も同じ形です。Mp（TS 29.333 5.8.8）は、MRFP が送る Method に Failover が加わります。

版の交渉では、MG が ServiceChange に自分の版を入れ、MGC は低い版しか使えないときに応答でその版を返します（H.248.1 版 2 の 11.3、TS 29.334 5.17.3.5 の注）。この ServiceChange を入れたメッセージは、ヘッダを版 1 にします（「ITU-T の勧告との照合」の「版の交渉」）。

### パッケージ

Iq で必須のパッケージ（TS 29.334 5.14.1）と、このプロジェクトに関わる項目です。

| パッケージ | 名前 | 使う項目 |
| --- | --- | --- |
| Generic | `g` | イベント `g/cause`。ベアラが切れたことを知らせる（5.17.2.7） |
| Base root | `root` | ROOT のプロパティ。AuditValue で読む（5.14.3.2） |
| IP NAPT traversal | `ipnapt` | シグナル `ipnapt/latch`、パラメータ `napt`（5.14.3.12）。ラッチングを指示する |
| Hanging termination detection | `hangterm` | イベント `hangterm/thb`、パラメータ `timerx`（5.14.3.9）。残ったままのターミネーションを見つける |
| Gate management | `gm` | プロパティ `gm/saf`、`gm/spf` など（5.14.3.4）。送信元のアドレスとポートで絞る |
| Traffic management | `tman` | プロパティ `tman/pol`、`tman/sdr`、`tman/mbs` など（5.14.3.5）。帯域を監視する |
| IP domain connection | `ipdc` | プロパティ `ipdc/realm`（5.14.3.7）。アクセス側かコア側かなど、どの網の側かを指す |
| Diffserv | `ds` | プロパティ `ds/dscp`（5.14.3.3） |
| RTCP handling | `rtcph` | プロパティ `rtcph/rsb`（5.14.3.13）。RTCP のポートも確保するかを指す |

任意のパッケージには、UDP を使うときの `it`（イベント `it/ito`。MGC から一定の時間メッセージが来ないことを MG が知る）、`ocp`、`chp`、`ipra`、`adid`（メディアが止まったことの検出）などがあります（5.14.2）。Ix の必須のパッケージ（TS 29.238 5.14.1）は、Iq から `ipnapt` を除いたものです。

Mp で必須のパッケージは `g`、`root`、`nt`、`hangterm` です（TS 29.333 5.14.1）。MRF の機能は任意のパッケージで足します（5.14.2）。アナウンスと会議に関わるものは次のとおりです。

| 機能 | パッケージと項目 | 条項 |
| --- | --- | --- |
| 音声ガイダンスの再生 | シグナル `an/apf`。パラメータは `an`（名前）、`noc`（回数）、`av`、`di` | 5.14.3.18、5.17.2.9 |
| 再生の終わりの通知 | イベント `g/sc`。パラメータは `SigID`、`Meth` など | 5.14.3.1、5.17.2.11 |
| トーン | シグナル `cg/*` など | 5.14.3.7、5.17.2.6 |
| DTMF の検出 | イベント `dd/d0` から `dd/d9`、`dd/ds`、`dd/do`、`dd/da` から `dd/dd` | 5.14.3.6、5.17.2.18、5.17.2.19 |
| 会議 | コンテキストに N 個のターミネーションを入れる。専用のパッケージは要らない | 5.17.2.30 |
| 統計 | `nt/dur`、`nt/os`、`nt/or`、`rtp/ps`、`rtp/pr` など | 5.14.3.4、5.14.3.5 |

パッケージの定義そのものは ITU-T の勧告にあります。H.248.1 の Annex E にある基本のパッケージのうち、読んだのは `root`（E.2）だけです。ほかの枝番の勧告（H.248.37、H.248.43 など）は読んでいません。名前、ID、パラメータは、プロファイルの表に書いてある範囲で確かめました。テキストの符号化では名前で指すので、数値の ID は使いません。TS 29.334 の表 5.14.1.1 は `root` の ID を 0x0051 と書いていますが、5.14.3.2 と TS 29.333 5.14.1 は 0x0002 としています。

### 通話の手順と、今の API との対応

今の独自の API（`internal/agw`）の操作は、Iq の手順に次のように写せます。

| 独自の API | Iq の手順 | H.248 のメッセージ |
| --- | --- | --- |
| `POST /contexts` | Reserve AGW Connection Point（TS 29.334 5.17.2.2）を 2 回 | コンテキストを `$` にした 1 つのトランザクションに、Add を 2 つ入れる。ターミネーションの ID は `$`。Local の SDP は、アドレスとポートを `$` にする。応答で、コンテキストの ID、ターミネーションの ID、MG が選んだアドレスとポートが返る |
| `PUT /contexts/{id}/terminations/{side}` | Configure AGW Connection Point（5.17.2.3） | Modify に Remote の SDP を入れる |
| `DELETE /contexts/{id}` | Release AGW Termination（5.17.2.5） | コンテキストを指定し、ターミネーションを `*` にした Subtract。応答をまとめる指定（`W-`）を付けられる（5.10 の表 5.10.5） |
| `GET /contexts` | Audit Value（5.17.3.10） | AuditValue |
| ラッチング（今は常に行う） | Reserve の中の Latching | Signals に `ipnapt/latch` |
| なし | Termination Heartbeat Indication（5.17.2.6）、IP Bearer Released（5.17.2.7） | MG からの Notify |
| なし | IMS-AGW Register（5.17.3.5） | MG からの ServiceChange |

ターミネーションの ID は `ip/<group>/<interface>/<id>` の形です（TS 29.334 5.6.1.1.1）。Add では MGC が必ず `$` を使い、そうでなければ MG は 501 で断ります（同じ表の注 4）。ストリームが 1 つだけなら、Stream ディスクリプタを省けます。MG はストリームの ID を 1 とみなします（5.7.2.0 の注 1）。

Local と Remote の SDP で必須の行は `v=`、`c=`、`m=`、`b=` です（TS 29.334 5.15）。`o=` と `s=` は、MGC が送らなくても MG が受けられればよいとされています。

向きが独自の API と逆になる点に注意が要ります。独自の API では P-CSCF がクライアントで、メディア中継ノードがサーバーです。H.248 では、MG が MGC に ServiceChange で登録してから、MGC がコマンドを送ります。

## トランスポート

- 既定のポートは、テキストが 2944、2 進が 2945 です（H.248.1 版 2 の 9 章、Annex D.1）。IANA の登録簿では、2944 が `megaco-h248`、2945 が `h248-binary` で、どちらも TCP、UDP、SCTP に登録されています。
- SCTP の PPID は 7（H.248）です（IANA の登録簿、H.248.4 の 1 章）。
- UDP では、応答が失われたときのために、トランザクションの層が再送と重複の排除を受け持ちます。応答を受けた側は TransactionResponseAck で確認を返し、処理に時間がかかる側は TransactionPending を返します（RFC 3525 Annex D.1）。
- TCP では、メッセージの区切りに TPKT（RFC 1006）を使います（H.248.1 版 2 の Annex D.2）。H.248.1 の 9 章は、IP の上では MGC が TCP と UDP の両方を、MG がどちらか一方を備えるとしています。ただし、3GPP のプロファイルのトランスポートの表に TCP はありません。プロファイルの表が挙げるのは SCTP と UDP だけです。
- UDP を使うとき、制御の関連の監視は、MG の側は `it` のパッケージ、MGC の側は ROOT への空の AuditValue で行います（TS 29.334 5.12 の表 5.12.3）。SCTP では、SCTP 自身の仕組みに任せます。
- 分割（セグメンテーション）は、UDP では行いません（TS 29.334 5.12 の表 5.12.2）。

## トランザクションと UDP の運び方

`internal/h248` の `Endpoint` が、UDP の上でトランザクションを運びます。RFC 3525 の 8 章と Annex D.1 に従って作り、あとで H.248.1 版 2 と Corrigendum 1 の本文と照らし合わせました。MGC も MG も要求を送るので（MGC は Add など、MG は Notify と ServiceChange）、1 つの `Endpoint` が、要求を送る側と受ける側の両方を受け持ちます。メディア中継ノードと P-CSCF へのつなぎ込みは作っていません。

前提は次のとおりです。符号化はテキストだけ、トランスポートは UDP で、ヘッダの版は `MEGACO/2` にします。ただし、版を交渉する ServiceChange のトランザクションだけは `MEGACO/1` にします。H.248.1 の 11.3 がそう決めているためです（「ITU-T の勧告との照合」の「版の交渉」）。

### 要求を送る側の決まり

- 応答が来なければ要求を繰り返します。再送のたびに AAD（平均の応答の遅れ）を倍にし、次のタイマーを 0.5 AAD から AAD の間の乱数にします（Annex D.1.3）。乱数は、同じきっかけで始まった要求がそろって再送されるのを防ぎます。タイマーの上限は 4 秒が勧められています。
- Annex D.1.5 の例は、最初のタイマーを 200 ms にしています。再送が多すぎるとき（目安は 7 回から 11 回）か、最初の送信から T-MAX を過ぎたときに、相手が止まったとみなします。MG は、そのあと 11.5 の手順で MGC を探し直します。
- TransactionPending を受けたら、別のタイマーに切り替えます（Annex D.1.4）。Pending が来るたびにタイマーをやり直し、切れたら要求を再送します（8 章の冒頭）。応答のあとに届いた Pending は無視します。
- Pending のあとに最終の応答を受けたら、すぐに確認を返します（Annex D.1.4）。

### 要求を受ける側の決まり

- 最近送った応答の一覧と、実行中のトランザクションの一覧を持ちます。同じ送信者（MId）から同じ ID の要求が来たら、実行せずに、持っている応答をもう一度送ります。実行中なら、実行せずに Pending を返します（Annex D.1.1、D.1.4）。
- 応答の写しは、送ってから LONG-TIMER（30 秒を推奨）がたつか、TransactionResponseAck で確認されたら消してよいとされています。確認のあとも ID は LONG-TIMER まで残し、遅れて届いた要求の写しを黙って捨てます（Annex D.1.1、D.1.2.2）。
- 実行に時間がかかるときは Pending を送ります。ROOT の ProvisionalResponseTimerValue は、要求を受けてから Pending を送るまでの最長の時間です（Annex D.1.4、E.2.1）。Pending を送った側は、最終の応答に ImmAckRequired を付けなければなりません。
- 版 2 では、1 つの要求に送れる Pending の数に上限があります。超えるときは処理をやめ、エラー 506 で応答します（H.248.1 版 2 の 8.2.3、E.2.1）。エラーは、時間のかかったコマンドか、誤りを起こしたコマンドへの応答に入れます。
- 応答は、要求が来たアドレスとポートに返します（9 章、Annex D.1）。
- 1 つのメッセージに応答と要求の両方があるときは、応答を先に処理します（Corrigendum 1 で 8 章に加わった文）。
- 応答がトランスポートの上限より長くなるときは、上限を超えさせるコマンドを誤りとみなし、エラー 533 を返します。その前のコマンドの応答は残し、残りのコマンドは実行しません（H.248.8 の 4.2.66）。
- メッセージに入れてよいトランザクションの数を超えたときは、エラー 413 を返します。メッセージの単位で返すと、メッセージのどれも実行していないという意味になります（H.248.8 の 4.2.9）。

### 3GPP のプロファイルが決めていること

- トランザクションのタイマー（normalMGExecutionTime、normalMGCExecutionTime、MGOriginatedPendingLimit、MGCOriginatedPendingLimit、MGProvisionalResponseTimerValue、MGCProvisionalResponseTimerValue）は、どれも Provisioned です（TS 29.334 と TS 29.238 の表 5.10.7、TS 29.333 の表 5.10.6）。値は書いてありません。
- 1 つのメッセージに入れるトランザクションは 10 個までです（表 5.10.1）。Iq と Ix の注によると、Ia のプロファイルの上限は 1 個で、普通は 1 個になる見込みです。
- UDP では分割をしません（TS 29.334 と TS 29.238 の表 5.12.2、TS 29.333 の表 5.10.2 と表 5.12.2）。TS 29.333 の表 5.10.2 の注は、H.248.1 版 3 の Annex E.14 にある分割のパッケージは、UDP でも SCTP でも要らないとしています。
- エラー 506（Pending の数の超過）と 533（応答がトランスポートの PDU の上限を超える）は、両側が送るエラーの一覧にあります（TS 29.334 と TS 29.238 の 5.7.10、TS 29.333 の 5.7.9）。

### 作ったもの

タイマーと上限は、どれも設定で変えられます。0 のままにすると、次の既定値になります。

| 設定 | 仕様の名前 | 既定値 | 既定値の根拠 |
| --- | --- | --- | --- |
| `InitialRetransmissionTimer` | なし | 200 ms | Annex D.1.5 の例 |
| `MaxRetransmissionTimer` | なし | 4 s | Annex D.1.3 の推奨 |
| `MaxRetransmissions` | 切断のしきい値（D.1.5） | 10 | D.1.5 の目安の 7 から 11 の中から選びました |
| `TMax` | T-MAX | 25 s | H.248.1 に値はありません。D.1.5 は、合わせて 30 秒待つのはおそらく許されると書いています。LONG-TIMER の 30 s から、伝搬の遅れの見込みとして 5 s を引きました |
| `LongTimer` | LONG-TIMER | 30 s | Annex D.1.1 の推奨 |
| `ProvisionalResponseTimerValue` | MGProvisionalResponseTimerValue（MG）、MGCProvisionalResponseTimerValue（MGC） | 100 ms | H.248.1 に値はありません。2013 年の版の E.2.1 は既定値を Provisioned とし、最初は通常の実行時間にネットワークの遅れを足した値で、下げてもよいとしています。最初の再送より前に Pending が届くよう、200 ms の半分にしました |
| `PeerProvisionalResponseTimerValue` | 相手の同じ値 | 100 ms | 同上 |
| `PendingLimit` | MGOriginatedPendingLimit（MG）、MGCOriginatedPendingLimit（MGC） | 20 | H.248.1 に値はありません。2013 年の版の E.2.1 は既定値を Provisioned としています。既定のタイマーで、約 2 秒まで処理を続けられます |
| `PeerPendingLimit` | 相手の同じ値 | 20 | 同上 |
| `MaxMessageSize` | なし | 1452 オクテット | 1500 オクテットの Ethernet のフレームに、IPv6 と UDP のヘッダと一緒に入る大きさです |
| `MaxTransactions` | なし | 10000 | 送った要求と受けた要求の、それぞれの上限です |

作りの要点です。

- 受けた要求は、送信者の MId とトランザクションの ID の組で引きます。Annex D.1.1 が MId ごとに比べるとしているためです。MId の大文字と小文字は区別しません（Annex B.2）。
- 送った要求は ID で引きます。ID は `Endpoint` の中で一意です。最初の ID は乱数にします。再起動のあと、相手がまだ覚えている ID と重ならないようにするためです。
- 受けた要求の状態は、実行中、応答ずみ、確認ずみの 3 つです。確認ずみになると応答の写しを捨て、ID だけを LONG-TIMER まで残します。
- Pending を受けたあとは、相手の ProvisionalResponseTimerValue に `InitialRetransmissionTimer` を足した時間だけ待ちます。足した分は、ネットワークの遅れの見込みです。
- Handler は、要求ごとに別の goroutine で動きます。実行中は `ProvisionalResponseTimerValue` ごとに Pending を送ります。時間がかかると分かっている Handler は、`IncomingRequest.Pending` ですぐに送れます。
- 長すぎる要求は送らずに `ErrMessageTooLong` を返します。長すぎる応答は、収まらなくなるコマンドの応答のところで切り、そのアクションの最後にエラー 533 を入れます（H.248.8 の 4.2.66）。最初のコマンドの応答も収まらないときだけ、トランザクション全体のエラーにします。
- トランザクションが 10 個を超えるメッセージには、メッセージの単位のエラー 413 で答え、どのトランザクションも処理しません（H.248.8 の 4.2.9、TS 29.334 の表 5.10.1）。Pending は数えません。表の見出しが挙げているのは、要求、応答、確認、分割の応答だけだからです。Mp（TS 29.333 5.7.9）のエラーの一覧には 413 がありません。上限は同じなので、同じエラーを使います。
- 1 つのメッセージの中では、応答を先に処理してから、要求、Pending、確認を並びの順に処理します（Corrigendum 1 の 8 章）。
- ServiceChangeVersion を入れた ServiceChange のトランザクションは、要求、Pending、応答、確認のどのメッセージもヘッダを `MEGACO/1` にします。ほかのメッセージは設定の版（既定は 2）です（H.248.1 の 11.3、H.Sup7 の 8 章）。
- 状態は `MaxTransactions` で上限を決め、LONG-TIMER で消えます。上限を超えた要求は、応答せずに捨てます。相手が再送するので、二度実行されることはありません。
- `Endpoint` 全体を止めるロックはありません。トランザクションの表は `sync.Map` で、1 つのトランザクションの中だけを個別のロックで守ります。データグラムを書く間と Handler を呼ぶ間は、どのロックも持ちません。各役割を複数台に広げられるようにするためです。
- 時計は `Clock` のインタフェースで差し替えられます。試験は、言われたときだけ進む偽の時計を使い、実際には待ちません。

ImmAckRequired の応答に確認が来ないとき、受ける側が応答を自分から再送する手順はありません。RFC 3525 にも、H.248.1 の版 2（2002 年 5 月）と今の版（2013 年 3 月）の Annex D.1 にも見当たりませんでした。そこで、応答を送り直すのは要求が繰り返されたときだけにしています。Pending を受けた側は相手のタイマーで待ち、切れたら要求を再送するので、応答が失われても回復します。

### 簡略化したところ

コードには `SIMPLIFIED:` のコメントを付けています。

| 箇所 | 省いたこと | 理由 |
| --- | --- | --- |
| `endpoint.go` の `Endpoint` | SCTP（プロファイルの推奨。Mp では必須）。SCTP の上では H.248.4 が Annex D.1 の一部に代わります（PPID 7、TransactionResponseAck を使わない、three-way handshake を使わない） | Go の標準ライブラリに SCTP がありません。UDP はどのプロファイルでも任意として認められています |
| `endpoint.go` の `Timers` | MGC が ROOT のプロパティを Modify で変えたときに、タイマーを変えること（H.248.1 版 2 の Annex E.2.1） | 値は作るときの設定で決めます。変えるときは `Endpoint` を作り直します |

### tshark で確かめたこと

`Endpoint` が実際に書いたバイト列を、試験の中の偽のネットワークから取り出しました。時刻は偽の時計の値です。text2pcap で pcap にし、tshark 4.2.2 で読みました。

```sh
text2pcap -q -D -t "%H:%M:%S.%f" -4 192.0.2.2,192.0.2.1 -u 2944,2944 exchange.txt exchange.pcap
tshark -r exchange.pcap
tshark -r exchange.pcap -V | grep -ci 'malformed\|unknown\|expert info'
```

1 つめは、最初の要求が失われ、200 ms 後の再送が届き、MG が 150 ms 後に Pending を送ってから応答した場合です。

| 番号 | 時刻 | 向き | tshark の表示 |
| --- | --- | --- | --- |
| 1 | 0.000 | MGC から MG | `1 Request \|=Choose one Add=ip/1/access/$`（ネットワークで失われたもの） |
| 2 | 0.200 | MGC から MG | `1 Request \|=Choose one Add=ip/1/access/$`（再送） |
| 3 | 0.350 | MG から MGC | `1 Pending` |
| 4 | 0.350 | MG から MGC | `1 Reply \|=7 Add=ip/1/access/11`（本文に `ImmAckRequired`） |
| 5 | 0.350 | MGC から MG | `1 TransactionResponseAck` |

2 つめは、`PendingLimit` を 2 にして、Handler が終わらない場合です。0.1 秒と 0.2 秒に Pending が出て、0.3 秒に `Context = $ { Error = 506 }` の応答が出ます。tshark は「Number of Transaction Pendings Exceeded (506)」と表示します。そのあと MGC が TransactionResponseAck を返します。

どちらも、すべてのフレームが MEGACO としてデコードされ、Malformed、Unknown、Expert Info の表示は出ませんでした。Pending は、Info の欄では「Pending」と出ますが、詳細では「Transaction: Reply」と出ます。上の「Wireshark での見え方」と同じ制約です。`ImmAckRequired` には専用のフィールドがなく、RAW の本文で読めます。

次の 2 つは、手で書いたメッセージを同じ方法で pcap にして確かめました。

- `TransactionResponseAck { 1-2, 3 }` のような範囲も、エラーなく表示されます。
- `Reply = 1 { ImmAckRequired, Error = 506 { ... } }` のように、ImmAckRequired のあとにトランザクション全体のエラーを置くと、文法では正しいのに「Parse error: Missing "="」の Malformed になります。ImmAckRequired の無い同じ形や、エラーをアクションの応答に入れた形は正しく表示されます。エラー 506 を最初のアクションの応答に入れたのは、このためでもあります。エラー 533 は H.248.8 に合わせてアクションの応答に入れるようにしたので、Pending のあとでも正しく表示されます（すぐ下の表）。トランザクション全体のエラーで残っているのは、応答を書けなかったときのエラー 500 と、最初のコマンドの応答も収まらないときのエラー 533 だけです。

ITU-T の勧告と照らし合わせたあとにも、`Endpoint` が書いたバイト列を同じ方法で pcap にして確かめました。

| メッセージ | tshark の表示 |
| --- | --- |
| 登録の ServiceChange（`MEGACO/1`、`Version = 2` 入り）とその応答 | `5001 Request \|=NULL ServiceChange=ROOT` と `5001 Reply \|=NULL ServiceChange=ROOT`。詳細では、ヘッダの版が 1 と出ます |
| 2 つめのアクションの 2 つめのコマンドで溢れた応答（ImmAckRequired の有無の両方） | `1 Reply \|=7 Add=ip/1/access/11 Add=ip/1/core/12 \|=8 Add=ip/1/access/11`。最後にエラー 533 が「Response exceeds maximum transport PDU size (533)」と出ます |
| 最初のコマンドで溢れ、ImmAckRequired の付いた応答（`Context = 7 { Error = 533 }`） | `2 Reply \|=7` とエラー 533 |
| メッセージの単位のエラー 413 | `Error` と出て、エラーのコードは「Unknown (413)」です。tshark 4.2.2 の表に 413 の名前がないためで、メッセージは正しく読めています |
| 波括弧の無い `Signals`（手で書いたもの） | 読めますが、「Empty Signal Descriptor」の注意が付きます。`Signals { }` には付きません |

どれも Malformed の表示は出ませんでした。413 の「Unknown」は、エラーのコードの名前の欄に出るものです。

## メディア中継ノードの制御（MG と MGC）

### パッケージの分け方

プロファイルの手順は、`internal/h248` の下の `internal/h248/mediactl` に分けました。

- `internal/h248` は、メッセージの読み書きとトランザクションの運び方を受け持ちます。Iq、Ix、Mp のどれにも使う土台で、すでに 30 ほどのファイルがあります。
- `mediactl` は、Iq の手順と、このプロジェクトのプロファイルの決めごとだけを持ちます。学習者は、符号化の層と手順の層を別々に読めます。`internal/sip` と、その上で手順を実装する役割の関係と同じです。
- 試験で使う偽の時計と偽のネットワークは、`internal/h248` の試験のものを写しました。試験のファイルは、別のパッケージから import できないためです。
- SDP の形式は `internal/sdp` の `Codec` で受け渡します。P-CSCF が SDP から読んだ形式を、そのまま渡せるようにするためです。Local と Remote の SDP は、`$` を書く必要があるので、このパッケージの中で書いて読みます。

### 操作の集まり

`mediactl.Relay` は、P-CSCF がメディア中継ノードに頼む操作の集まりです。今の HTTP の制御 API と、P-CSCF の `Relay` と同じ 3 つの操作を、Iq の手順の名前で並べました。

| 操作 | Iq の手順 | 今の HTTP の API（`internal/agw`） | 今の P-CSCF の `Relay` |
| --- | --- | --- | --- |
| `Reserve(ctx, media)` | Reserve AGW Connection Point（5.17.2.2）を、アクセス側とコア側に 1 回ずつ | `POST /contexts` | `Add(ctx)` |
| `Configure(ctx, id, side, remote)` | Configure AGW Connection Point（5.17.2.3） | `PUT /contexts/{id}/terminations/{side}` | `Modify(ctx, id, side, remote)` |
| `Release(ctx, id)` | Release AGW Termination（5.17.2.5）を、両方のターミネーションに | `DELETE /contexts/{id}` | `Subtract(ctx, id)` |

今の API との違いは次のとおりです。

- `Media` には、アドレスとポートのほかに、m= 行の形式（`sdp.Codec` の並び）と b=AS の値を入れます。Iq の表は、音声の Local と Remote にコーデックの一覧と帯域を入れるとしているためです（5.17.2.2、5.17.2.3）。中継ノードはペイロードを変えずに運ぶので、この値は使いません。キャプチャで見えるようにするためのものです。形式を渡さないときは、m= 行の形式を `-` にします（5.15 の表 5.15.1）。
- `Release` は、何も返しません。Iq は Subtract の応答で統計を返さないためです（TS 29.334 の表 5.7.7.2）。
- `GET /contexts` に当たる操作は入れていません。P-CSCF が使わないためです。
- エラーは `ErrNoContext`（コンテキストが無い）、`ErrInsufficientResources`（ポートが足りないなど）、`ErrUnavailable`（使える MG が無い）の 3 つです。MG のエラーのコードは `CommandRejected` に入り、`errors.Is` でこの 3 つに当てはめられます。

### 操作とコマンドの対応

| 操作 | H.248 のコマンド | ディスクリプタと中身 | 条項 |
| --- | --- | --- | --- |
| `Reserve` | `Context = $` の 1 つのアクションに、`Add = ip/1/access/$` と `Add = ip/1/core/$` | Media（LocalControl の `Mode = SendReceive`、アドレスとポートを `$` にした Local）、`Events = 1 { hangterm/thb { timerx = 1800 }, g/cause }`、`Signals { ipnapt/latch { napt = LATCH } }`。応答の Local に、MG が選んだアドレスとポートが入る | TS 29.334 5.17.2.2、5.6.1.1.1、5.15、H.248.1 7.1.7、7.1.8 |
| `Configure` | `Modify = ip/1/<side>/<context>` | Media（`Mode = SendReceive`、相手の SDP を入れた Remote）、Reserve と同じ Events | TS 29.334 5.17.2.3、H.248.1 7.1.9 |
| `Release` | `Subtract = *`（Audit なし） | 応答はターミネーションごとの Subtract で、ディスクリプタは付かない（統計を返さない） | TS 29.334 5.17.2.5、5.7.7 の表 5.7.7.2、5.8.3 の表 5.8.3.2、H.248.1 7.2.3 |
| MG の登録 | `ServiceChange = ROOT`（Restart、901 Cold Boot、Profile、`Version = 2`、TimeStamp）。メッセージは `MEGACO/1` | 応答に TimeStamp | TS 29.334 5.17.3.5、H.248.1 7.2.8、11.3 |
| 関連の回復 | `ServiceChange = ROOT`（Disconnected、900 Service Restored） | | TS 29.334 5.17.3.3、H.248.1 11.5 |
| 監視の開始 | `Modify = ROOT` | `Events = 2 { it/ito { mit = 2750 } }` | TS 29.334 5.17.3.15、H.248.14 6.6.2 |
| MGC からの生存の確認 | `AuditValue = ROOT` | 空の Audit | TS 29.334 5.12 の表 5.12.3、5.17.3.10 |
| MG からの生存の確認 | `Notify = ROOT` | `ObservedEvents = 2 { it/ito }` | TS 29.334 5.17.3.16、H.248.14 6.6.4 |
| 残ったターミネーションの検出 | `Notify = ip/1/<side>/<context>` | `ObservedEvents = 1 { hangterm/thb }` | TS 29.334 5.17.2.6、H.248.36 5.6 |

決めたことと、その理由です。

- LocalControl の Mode は必ず書きます。書かないと Inactive になり、メディアが流れないためです（H.248.1 7.1.7）。MG は SendReceive だけを受けます。
- Events ディスクリプタは前のものを置き換えます（H.248.1 7.1.9）。そのため Modify にも、Reserve と同じ 2 つのイベントを入れます。Iq の Configure の表も、ターミネーションの生存の通知を必ず入れる形です。
- 1 つのトランザクションに入れるのは、1 つのアクションです。Reserve の 2 つの Add は、同じアクションに入れます。
- RequestID は、ターミネーションのイベントが 1、ROOT の it/ito が 2 です。Notify の RequestID で、どの要求への報告かを見分けます。

### プロファイルの名前

ServiceChange で名乗るプロファイルは `imsPracticeIq/1` にしました。独自の名前にして、3GPP のプロファイルの名前と区別しています。

- `threegIq/7` を名乗ると、Iq の必須のパッケージ（TS 29.334 5.14.1 の `gm`、`tman`、`ds`、`ipdc`、`rtcph` など）にも対応していることになります。この MG は対応していません。
- 対応するパッケージは、`g`（版 1）、`root`（版 2）、`it`（版 1）、`hangterm`（版 1）、`ipnapt`（版 1）です。ROOT への AuditValue で Packages を問われたときに、この一覧を返します。
- 手順は、対応するパッケージについて Iq に従います。Subtract の応答は、Iq の表 5.7.7.2 のとおり統計を返しません。Mp は MSRP の統計だけを返します（TS 29.333 の表 5.7.6.2）。
- MGC は、別のプロファイルを名乗る MG を受け入れません。応答に自分のプロファイルを入れて返します（H.248.1 7.2.8）。MG は、応答に別のプロファイルが入っていたら、受け入れられなかったとみなします。
- プロファイルの名前を IANA に登録する手順は H.248.1 14.4 にあります。この名前は登録していません。このプロジェクトの中だけで使います。

### コンテキストとターミネーションの ID

- コンテキストの ID は、MG が選びます。最初の値を乱数にして、1 つずつ増やします。再起動のあとに、MGC がまだ持っている ID と重ならないようにするためです。トランザクションの ID と同じ考え方です。中継ノードのコンテキストの ID（今は `c1` など）とは別の値で、MG が対応を覚えます。
- ターミネーションの ID は `ip/<group>/<side>/<コンテキストの ID>` です。`<side>` は `access` か `core` です。`<group>` は MGC が指定した値で、MGC は 1 を使います。Iq では `<id>` はインタフェースごとに一意であればよいので、両方のターミネーションにコンテキストの ID を使います（TS 29.334 5.6.1.1.1 の表の注 3）。ID を見ただけで、どのコンテキストのターミネーションかが分かります。
- MGC が P-CSCF に返す ID は `<コンテキストの ID>@<MG の MId>` です。たとえば `3735928559@agw1.ims.example.net` です。MGC はコンテキストの一覧を持たず、この ID から送り先の MG を決めます。

### 制御の関連

UDP のときの監視は、MG の側の `it` のパッケージと、MGC の側の空の AuditValue の 2 つです（TS 29.334 の表 5.12.3）。Iq は、UDP を使う MG に `it` の手順を必須にしています（表 5.17.3.1.1 の注 4）。

- MG は、起動すると 0 から MWD（既定は 5 秒）の間の乱数だけ待ってから登録します（H.248.1 9.2）。多くの MG が同時に起動しても、登録が一度に集まらないようにするためです。登録が受け入れられなかったときも、同じように待ってからやり直します（11.2）。
- 登録は Restart と 901 Cold Boot です。中継ノードは起動したときにコンテキストを持たないためです（H.248.8 5.2.2）。
- MG は、登録の応答を受けるまで、MGC からの要求に 505 で答えます（H.248.1 11.2、H.248.8 4.2.46）。
- MGC は、MG の MId ごとに関連を 1 つ記録します。宛先は、ServiceChange が届いたアドレスです。同じ MG がもう一度登録すると、前の関連を終わらせ、その上で待っている要求を失敗させます。
- MGC は、登録から 1 秒後に、MG の it/ito に mit（既定は 27.5 秒）を設定します。すぐに送ると、登録の応答を追い越して 505 になることがあるためです。断られたときも 1 秒後にやり直します。
- MGC は、MG に何も送らないまま 10 秒たつと、空の AuditValue を ROOT に送ります（H.248.14 6.6.2）。これに答えがなければ、MG が止まったとみなします。
- MG は、MGC からのメッセージが mit の間なければ、ROOT の Notify で it/ito を知らせます（H.248.14 6.6.4）。答えがなければ、MGC が止まったとみなします。
- MGC は、MG が止まったとみなすと、その MG を新しいコンテキストに使わなくなります。待っている要求も、その MG のコンテキストへの操作も、`ErrUnavailable` で失敗させます。
- MG は、MGC が止まったとみなすと、同じアドレスに Disconnected と 900 Service Restored を送ります（TS 29.334 5.17.3.3、H.248.1 11.5）。コンテキストは残っているので、MGC が受け入れれば、P-CSCF が持っている ID がそのまま使えます。届かなければ、乱数だけ待ってから送り直します。
- MG が再起動したときは、Restart の登録になります。前のコンテキストは無くなっています（H.248.8 5.2.2）。P-CSCF が前の ID で操作すると、MG は 411 で答え、`ErrNoContext` になります。
- MGC が再起動したときは、MGC は MG を知りません。MG の it/ito の Notify に 507 で答えます。MG はこれを関連が切れたとみなし、Disconnected を送ります。MGC は、知らない MG からの Disconnected を、新しい関連として受け入れます。
- MG が Forced で止まると知らせたら、MGC はそのコンテキストがすべて失われたとみなします（H.248.1 7.2.8）。Graceful なら、新しいコンテキストに使わないだけで、今のコンテキストへの操作は続けます。
- 残ったターミネーションの検出（hangterm/thb）は、ターミネーションごとに timer X（既定は 30 分）で動きます。MG が Notify を送ると、MGC は `TerminationHeartbeat` で P-CSCF に、そのコンテキストをまだ使っているかを尋ねます。使っていなければ、411 で答えてから、そのコンテキストを Release します（H.248.36 5.6.2）。Reserve の応答が失われて P-CSCF が知らないコンテキストも、これで片付きます。

既定値と、その根拠です。

| 設定 | 既定値 | 根拠 |
| --- | --- | --- |
| `GatewayConfig.MaxWaitingDelay` | 5 秒 | H.248.1 9.2 は、家庭用の MG に 600 秒を勧め、ターミネーションの多い MG ではずっと短くするとしています。Compose での起動を待たせないように、短くしました |
| `ControllerConfig.KeepAliveInterval` | 10 秒 | 値の決まりはありません。mit より十分に短くしました |
| `ControllerConfig.InactivityTimer`（mit） | 27.5 秒 | H.248.14 6.6.5.1 は T-MAX の 110% を例に挙げています。`Endpoint` の T-MAX の既定は 25 秒です |
| `TimerX`（timer X） | 30 分 | H.248.36 5.2.1.1.1 は、呼の保留時間の何倍かにするよう勧めています。H.248.1 9.2 が見込む平均の通話の 3 分の 10 倍にしました |
| 監視の開始までの待ち | 1 秒 | 登録の応答を追い越さないための値です |

### 複数台にしたとき

- MGC が持つのは、登録した MG との関連だけです。コンテキストの一覧は持ちません。コンテキストの ID に MG の MId が入っているので、どの MGC の台でも、その MG と関連があれば操作できます。
- 新しいコンテキストは、使える MG に順番に割り当てます。MG の一覧は、登録と障害のときだけ作り直します。Reserve のたびにロックを取りません。
- MG は、1 つの MGC にだけ登録します。コンテキストは MG のプロセスの中にあります。中継ノード自身もコンテキストをプロセスの中に持つので、状態の置き場所は変わりません。
- P-CSCF を複数台にしたときに、どの MG がどの MGC に登録するかは決めていません（「未決の論点」の 1）。

### tshark で確かめたこと

試験の中の偽のネットワークから、`Gateway` と `Controller` が実際に書いたバイト列を取り出しました。時刻は偽の時計の値です。text2pcap で pcap にし、tshark 4.2.2 で読みました。手順は「トランザクションと UDP の運び方」の「tshark で確かめたこと」と同じです。

流したのは、登録、監視の開始、Reserve（AMR-WB と PCMU）、2 つの Configure、空の AuditValue による生存の確認、hangterm/thb の Notify、Release、解放したあとのコンテキストへの Configure（411）、MGC の再起動による 507 と Disconnected の再登録です。28 のフレームのすべてが MEGACO としてデコードされ、Malformed と Expert Info の表示は出ませんでした。

- Local と Remote の SDP は、すべて SDP として展開されます。`c=IN IP4 $` と `m=audio $ RTP/AVP 96 0` では、アドレスとポートが `$` と表示されます。`a=rtpmap` と `a=fmtp` も展開されます。
- 形式を渡さない `m=audio $ RTP/AVP -` も読めます。形式は `-` と表示されます。
- ServiceChange の Profile は `imsPracticeIq/1`、TimeStamp は `20261120T09000010` のように表示されます。
- 507 は「Unknown (507)」と表示されます。tshark 4.2.2 の表に 507 の名前が無いためで、413 と同じです。
- Add の要求の Info の欄に「(Signal:{)」と出ます。詳細の表示では `ipnapt/latch` と `napt = LATCH` が正しく展開されるので、Info の欄の表示だけの問題です。

### 中継ノードと P-CSCF につなぐときに要ること

`internal/agw` と `internal/pcscf` は、このインタフェースにつないでいません。つなぐときの、今の作りとの差は次のとおりです。

- P-CSCF の `Relay` の 3 つのメソッドを、`mediactl.Relay` に合わせます。`Reserve` と `Configure` に渡す形式と帯域は、P-CSCF が SDP から読めます（`sdp.Media.Codecs` と `Bandwidth("AS")`）。
- 中継ノードは、ターミネーションごとに送った RTP のパケットの数と、送受信したオクテットの数を数えます。今は受け取ったパケットの数だけを数えています。
- 中継ノードは、知らないコンテキストに `mediactl.ErrNoContext` を、ポートが足りないときに `mediactl.ErrInsufficientResources` を返します。
- P-CSCF の Subtract の再試行は、`ErrNoContext` で止めます。MG が再起動したあとのコンテキストは、もう無いためです。
- `TerminationHeartbeat` を使うなら、P-CSCF が中継のコンテキストの ID からダイアログを引けるようにします。今の保存先には、その索引がありません。全件の走査はできないので（商用網の規模に向けて広げられる作りにするためです）、索引が要ります。
- 設定（役割の切り替え、MGC の名前とポート、MId）と Compose のポート 2944 も要ります。

## Mp のプロファイル（MRFC と MRFP）

メディア中継ノード（`internal/agw`）は MRFP を兼ねます。コンテキストに 3 つ以上のターミネーションを持て、ターミネーションの追加と 1 つだけの削除、ターミネーションごとのモード、アナウンスの再生、再生の終わりの通知ができます。Mp を H.248 に載せられるように、`internal/h248/mediactl` をこの操作の組に合わせました。`internal/agw` と `internal/mrfc` へのつなぎ込みは作っていません（「Mp を中継ノードと MRFC につなぐときに要ること」）。

### 操作の集まりを Iq と分けたこと

Mp の操作は、`Relay` とは別のインタフェース `mediactl.Processor` にしました。`Relay` は変えていません。Iq を使う側（P-CSCF のつなぎ込み）は影響を受けません。

- Iq の `Relay` は、アクセス側とコア側の 2 つのターミネーションを持つコンテキストの操作です。Mp は、ターミネーションの数が決まらず、シグナルとイベントがあります。1 つのインタフェースにまとめると、Iq の実装にも Mp のメソッドが要り、P-CSCF が使わない操作を中継ノードが実装することになります。
- 型は `internal/agw` の HTTP の API に合わせました（`TerminationRequest`、`Mode`、`Signals`、`Play`、`Events`、`SignalCompleted`）。中継ノードと MRFC を、どちらの API にもつなぎやすくするためです。`internal/agw` は import していません。中継ノードの API が変わっても、このパッケージは壊れません。
- `Controller` と `Gateway` は、Iq と同じ型を使います。登録、関連の監視、ターミネーションの生存の確認は、Mp でも同じ手順だからです。`ControllerConfig.Profile` に `MpProfile` を入れると、`Controller` は Mp を話し、`Processor` を実装します。`GatewayConfig` に `Relay` の代わりに `Processor` を入れると、`Gateway` は Mp を話します。1 つの `Controller` は 1 つのプロファイルだけを話し、そのプロファイルを名乗る MG だけを受け入れます。

| 操作 | Mp の手順（TS 29.333） | HTTP の API（`internal/agw`） |
| --- | --- | --- |
| `Add(ctx, terminations...)` | Reserve IMS Resources（5.17.2.2）。相手のアドレスがあれば Reserve and Configure IMS Resources（5.17.2.4）、シグナルがあれば Start Announcement（5.17.2.9）も同じ Add で行う（5.17.2.1 の表の注） | `POST /contexts` |
| `AddTermination(ctx, contextID, t)` | Reserve IMS Resources を、あるコンテキストに対して行う。会議に人が加わるとき（5.17.2.30） | `POST /contexts/{id}/terminations` |
| `Modify(ctx, contextID, id, change)` | Configure IMS Resources（5.17.2.3）。シグナルがあれば Start Announcement、空のシグナルなら Stop Announcement（5.17.2.10） | `PUT /contexts/{id}/terminations/{tid}` |

決めたことと、その理由です。

- Start Announcement のシグナルは `an/apf` です。TS 29.333 の表 5.17.1.1 が、Announcement Cycles を H.248.7 の `noc` と決めているためです。`an/apf` には再生の間の無音を指すパラメータがありません。RFC 4240 の `delay` を運べないので、無音を入れるときだけ `aasb/play` を使います。プロファイルには両方のパッケージがあります（5.14.3.14、5.14.3.18）。`aasb/play` の `an` は `bannsyx` の書き方なので、MG は `bannsyx` も名乗ります（H.248.9 8）。
- `an/apf` の種類の既定は TimeOut です。長さを書かないと、長さの上限は MG の設定で決まります。`Duration = 0` なら上限がなくなり、`noc` の回数だけ鳴ります（H.248.7 4.5 の表 1）。設定に任せないように、上限がないときも `Duration = 0` を書きます。
- `aasb/play` の種類の既定は Brief で、長さを無視します。長さの上限があるときだけ、種類を TimeOut にして長さを書きます（H.248.9 8.5）。
- 長さは 16 ビットの 10 ms 単位なので、655.35 秒までです（H.248.1 Annex B.2 の `sigDuration`）。MRFC の上限の 10 分は収まります。それより長い `Duration` は、`Controller` が送る前に断ります。
- 終わりの通知は、`NotifyCompletion = { TimeOut }` と、Events の `g/sc` の両方がそろったときだけ来ます（H.248.1 7.1.11）。`Controller` はシグナルに必ず `NotifyCompletion` を書きます。`g/sc` が無ければ、何も起きません。
- ターミネーションの生存の確認（`hangterm/thb`）には KeepActive を付けます。イベントを検出すると、鳴っているシグナルは止まるのが既定だからです（H.248.1 7.1.9）。Mp は KeepActive を使うとしています（表 5.7.2.3）。
- Events ディスクリプタは前のものを置き換えます。そのため、`Add` では必ず書き、`Modify` では呼び出し側が `Events` を渡したときだけ書きます。書かなければ、前のイベントがそのまま残ります。RequestID は呼び出し側が選びます。0 は 1 にします。RequestID が 0 の Notify は、H.248.1 7.2.7 で今後の検討とされているためです。

### ターミネーションの ID

- TS 29.333 5.6.1.1 は、ID の形を設定で決めるとし、IP のターミネーションでは数の識別子にすぎないとしています。テキストの符号化では、ID は文字で始まる名前です（H.248.1 Annex B.2 の `pathNAME`）。そこで `ip/<コンテキストの ID>/<n>` にしました。`<n>` はコンテキストの中で 1 から数えます。キャプチャで、どのコンテキストのターミネーションかが分かります。
- `Add` では、MRFC は必ず `$` を送ります（TS 29.333 の表 5.17.2.2.1）。名前を指定した `Add` は 501 で断ります。
- `Gateway` は、H.248 の ID と、`Processor` が付けた ID（中継ノードでは `t1` など）の対応を、コンテキストごとに覚えます。
- MRFC に返すコンテキストの ID は、Iq と同じ `<コンテキストの ID>@<MG の MId>` です。`Controller` はコンテキストの一覧を持ちません。

### モードを必ず書くこと

H.248 の Mode の既定は Inactive です。一方、中継ノードの API は Add で sendrecv になります。H.248.1 7.1.7 で確かめました。

- `Controller` は、Mp の `Add` と `Modify` のすべてに LocalControl の Mode を書きます。`TerminationRequest.Mode` が空なら、送る前にエラーを返します。`Modify` で Mode を省くと H.248 では前のモードが残りますが、呼び出し側の思い込みとずれないように、毎回書かせます。
- `Gateway` は、Mode の無い Add を受けると、Inactive を `Processor` に渡します。`Processor` に空の Mode が渡るのは、Mode の無い Modify のときだけで、前のモードを残す意味です。中継ノードの API と同じ意味です。
- Iq の `Controller` も調べました。Reserve の 2 つの Add と Configure の Modify は、どれも `Mode = SendReceive` を書いていました。直すところはありませんでした。この先も落とさないように、送ったメッセージの文字列を調べる試験（`TestIqWritesTheModeOnEveryAddAndModify`）を足しました。

### 再生の終わりの通知の道筋

1. 中継ノードは、アナウンスが最後まで鳴ったら、`Gateway.SignalCompleted(<自分のコンテキストの ID>, <自分のターミネーションの ID>)` を呼びます。`Gateway` は、中継ノードの ID から自分のコンテキストを引きます。この索引は MG ごと、コンテキストごとで、全体を走査しません。
2. `Gateway` は、そのターミネーションでシグナルが鳴っていて、`g/sc` と `NotifyCompletion = { TimeOut }` の両方が求められていたときだけ、Notify を送ります。止めたあとに遅れて届いた報告や、求められていない報告は送りません。
3. Notify は、MG が登録した MGC に届きます（H.248.1 7.2.7、11.2）。`Controller` は、`ControllerConfig.Notify` に `Notification` を渡してから、応答を返します。
4. MRFC を複数台にしても、グローバルな状態はありません。Notify は、MRFP が登録した MRFC の台にだけ届きます。その台の `Controller` しか、その MRFP にコマンドを送れないので、Events を設定したのもその台です。MRFC は、今の `waiting` の表と同じように、RequestID で待っているダイアログを探せます。MRFP が別の台に登録し直したあとに届いた Notify は、待っている台がありません。今の HTTP の API で、知らない RequestID の Notify を記録して捨てているのと同じ扱いになります。

### 統計（オクテットの数は要るか）

オクテットの数は、Mp には要りません。

- Mp で Subtract の応答に入れる統計は、表 5.7.6.2 では MSRP の統計だけです。RTP の `rtp/ps` と `rtp/pr` は、任意の統計で、Subtract の応答にも入れられます（表 5.14.3.5.1）。
- `nt/os` と `nt/or`（オクテットの数）は、必須のパッケージ `nt` の必須の統計ですが、使うコマンドは AuditValue だけです（表 5.14.3.4.1）。
- この MG は、Subtract の応答に `rtp/ps` と `rtp/pr` だけを入れます。中継ノードが数えているパケットの数です。ターミネーションの統計の AuditValue には対応していないので（「Mp で簡略化したところ」）、オクテットの数を使う所がありません。
- ターミネーションの AuditValue に対応するなら、`nt/os` と `nt/or` が要ります。中継ノードの側にも、この 2 つを数える処理が要ります。
- Iq の MG（`imsPracticeIq/1`）は、Subtract の応答に統計を入れません（TS 29.334 の表 5.7.7.2）。

### Mp を tshark で確かめたこと

試験の中の偽のネットワークから、`Gateway` と `Controller` が書いたバイト列を取り出しました。MGC から MG と MG から MGC の 2 つのファイルに分け、それぞれを text2pcap で pcap にして、mergecap で時刻の順にまとめました。時刻は偽の時計の値で、同じ時刻のメッセージには送った順に 1 ms ずつ足しました。

```sh
text2pcap -q -t "%Y-%m-%dT%H:%M:%S.%f" -4 192.0.2.1,192.0.2.2 -u 2944,2944 mgc.txt mgc.pcap
text2pcap -q -t "%Y-%m-%dT%H:%M:%S.%f" -4 192.0.2.2,192.0.2.1 -u 2944,2944 mg.txt mg.pcap
mergecap -w mp.pcap mgc.pcap mg.pcap
tshark -r mp.pcap -V
tshark -r mp.pcap -Y '_ws.malformed || _ws.expert'
```

アナウンスの流れ（20 フレーム）と、会議の流れ（24 フレーム）を流しました。どれも MEGACO としてデコードされ、Malformed と Expert Info の表示は出ませんでした。

- アナウンスの流れ。登録、監視の開始、`Add = $`（SendOnly、Local と Remote の SDP）、`an/apf` を鳴らす Modify、`g/sc` の Notify と応答、`aasb/play` を鳴らす Add、`Signals { }` で止める Modify、2 つの Subtract、引いたあとのコンテキストへの Modify（411）。
- 会議の流れ。2 つの `Add = $` を 1 つのトランザクションに入れたもの、3 つめの `Add = $`（ReceiveOnly）、その Modify（SendReceive と Remote）、1 人の Subtract、引いたターミネーションへの Modify（430）、`cg/rt`（440）と `an/apv`（452）、残りの 2 つの Subtract、消えたコンテキストへの Add（411）。
- LocalControl の Mode は、すべての Add と Modify で `Mode: SendOnly` などと表示されます。Info の欄にも `(Mode:SendOnly)` と出ます。
- Events は `pkgdName: hangterm/thb` と `KeepActive, timerx = 1800`、`pkgdName: g/sc` のように、項目ごとに表示されます。
- Signals は `pkgdName: an/apf` と `Duration = 0, NotifyCompletion = { TimeOut }, an = notice, noc = 3`、`pkgdName: aasb/play` と `SignalType = TimeOut, Duration = 12000, NotifyCompletion = { TimeOut }, an = "sid=<file://welcome>", it = 0, iv = 50` のように表示されます。パラメータは 1 行のまま表示され、1 つずつには分かれません。tshark のテキストのデコードの細かさです。`Signals { }` は、中身の無い Signal Descriptor として表示されます。
- ObservedEvents は `RequestID: 7` と、`20261120T09000610: g/sc` に続けて `SigID = "an/apf"` と `Meth = TO` が表示されます。検出時刻が pkgdName の欄にも一緒に出ます。これも表示だけの問題です。
- Subtract の応答の Statistics は `rtp/ps = 250` と `rtp/pr = 250` が 1 つずつ表示されます。
- エラーは `ERROR Code: Unknown TerminationID (430)` のように、名前付きで表示されます。411、440、452 も同じです。
- Iq と同じく、Signals のある要求の Info の欄に「(Signal:{)」と出ます。詳細の表示は正しく展開されます。

### Mp を中継ノードと MRFC につなぐときに要ること

`internal/agw` と `internal/mrfc` は、このインタフェースにつないでいません。つなぐときの、今の作りとの差は次のとおりです。

`internal/agw`（MRFP の側）。

- 中継ノードに `mediactl.Processor` を実装します。今の `Relay` のメソッドに引数の `ctx` を足し、型を移し替える薄い層で足ります。`Play` の `Delay` と `Duration` は `time.Duration` なので、`DelayMS` と `DurationMS` に直します。
- `Add` は、作ったターミネーションを要求の順に返します。今の `agw.Context` はターミネーションを ID の map で返すので、順番が分かりません。層の側で ID を名付けて渡すか、`agw.Relay.Add` が順番を返す形にします。
- 再生の終わりを、HTTP の POST の代わりに `Gateway.SignalCompleted(<中継ノードのコンテキストの ID>, <ターミネーションの ID>)` で知らせる道が要ります。たとえば `agw.Events` に、JSON に出ない関数の欄を足す形です。`SignalCompleted` はすぐに戻るので、中継ノードの時計のゴルーチンから呼べます。
- エラーを当てはめます。`agw.ErrNoContext` は `mediactl.ErrNoContext`、`agw.ErrNoTermination` は `mediactl.ErrNoTermination`、`agw.ErrNoPort` は `mediactl.ErrInsufficientResources`、`agw.ErrUnknownAnnouncement` は `mediactl.ErrUnknownAnnouncement` にします。
- `SubtractTermination` は、`Packets` を `PacketsReceived` に、`PacketsSent` を `PacketsSent` に入れて返します。オクテットの数は要りません。
- 役割 `mrfp` で、`mediactl.GatewayConfig{Processor: ...}` の `Gateway` を動かす設定が要ります。MId（たとえば `mrfp1.ims.example.net`）、MRFC の名前とポート 2944 です。設定と Compose も要ります。

`internal/mrfc`（MRFC の側）。

- `mrfc.MRFP` を `mediactl.Controller` で満たします。型を移し替える層を作るか、`mrfc.MRFP` を `mediactl` の型にします。`Controller` は `ControllerConfig{Profile: mediactl.MpProfile, Notify: ...}` で作ります。
- Modify のたびに Mode を渡します。今の `announce` の Modify は、Signals と Events だけを渡しています。`leg` が今の向きを覚えて、毎回渡す形にします。
- `ControllerConfig.Notify` で、今の `waiting` の表に RequestID で渡します。`Config.NotifyURL` と `NotifyHandler` は、H.248 では要りません。RequestID に 0 は使わないでください。0 は 1 として送られ、届く Notify の RequestID と合わなくなります。
- `SubtractTermination` は、コンテキストが消えたかを返しません。H.248 の Subtract の応答に、その情報が無いためです。会議の終わりは、Store で参加者を数えて決めるか、次の `AddTermination` の `ErrNoContext` で気づく今の道（`attach`）に任せます。後者だけだと、最後の人が抜けたあとの Store の記録が、次に誰かが来るまで残ります。
- `Announcement`（アナウンスがあるかを先に確かめる操作）に当たる手順は Mp にありません。AuditCapabilities は今後の検討とされています（5.8.6）。MRFC の設定にアナウンスの名前と長さを持たせるか、確かめずに Start Announcement を送り、449 を「アナウンスが見つからない」とみなすかを決めてください。後者では、200 OK を返したあとに失敗が分かります。
- MRFC を複数台にしたとき、各台の `Controller` が知っているのは、自分に登録した MRFP だけです。今の `choose` は、どの台でも同じ MRFP を選び、会議の Store は MRFP の名前で記録します。登録していない台は、その MRFP にコマンドを送れません。Iq の「未決の論点」の 1 と同じ問題です（「未決の論点」の 3）。
- `TerminationHeartbeat` を使うなら、MRFC がコンテキストの ID から、使っているかを答えられるようにします。会議は Store に、アナウンスは各台のダイアログにあります。

## テキストの符号化の要点

文法は RFC 3525 の Annex B.2 にあります。版 2 での違いは、草案の Appendix II の一覧で確かめました。

- ヘッダは `MEGACO/<版>`、区切り、mId の順です。mId は `[192.0.2.10]:2944`（アドレス）、`<agw1.example.net>`（ドメイン名）、デバイス名、MTP のアドレスのどれかです。プロファイルはドメイン名を勧めています（TS 29.334 5.11）。
- 予約語にあたるトークンは、大文字と小文字を区別しません。ターミネーションの ID も区別しません。SDP だけは区別します。
- 空白、改行、`;` で始まるコメントは、`{`、`}`、`,`、`=` の前後に自由に入れられます。
- Local と Remote の中身は、`}` までがそのまま SDP です。SDP の中の `}` は `\}` と書きます。
- 値には、引用符で囲む形と、囲まない形があります。文字列の型は必ず囲み、数、列挙、真偽値は囲みません。
- プロパティの値には、1 つの値のほかに、すべてを表す並び（`[a,b]`）、どれか 1 つを表す並び（`{a,b}`）、範囲（`[a:b]`）、不等号があります。
- 版 2 で文法に加わったもの。項目を 1 つずつ指す監査（`Audit{Media{TerminationState{ServiceStates}}}` のような形）、ストリームごとの Topology、ServiceChange に入れる監査の項目、多重化の種類 `Nx64`、DigitMap のタイマー。版 1 から変わっていない部分が大半です。
- 版 2 の本文（11.3）は、登録の ServiceChange を入れたメッセージを版 1 の形で符号化すると書いています。ITU-T の版 2、Corrigendum 1、2013 年の版のどれにもこの決まりがあります。
- Corrigendum 1 は、Signals ディスクリプタの波括弧を省けるようにしました。ほかに、監査の応答に入れられるトークンだけの項目の絞り込みと、コンテキストの属性 EmergencyOff が加わりました（「ITU-T の勧告との照合」）。

## ITU-T の勧告との照合

符号化とトランザクションの層は、最初は RFC 3525 と版 2 の Internet-Draft で作りました。そのあと ITU-T の勧告を取れるようになったので、本文と照らし合わせました。読んだ版は「読んだ資料」の表のとおりです。プロファイルが参照しているのは H.248.1 の 2002 年 5 月の版と Corrigendum 1 なので、まずこの 2 つと比べ、今の版（2013 年 3 月）との違いも書きます。

### 文法（Annex B.2）

- 草案の ABNF と、ITU-T の版 2（2002 年 5 月）の ABNF を規則ごとに比べました。改行の位置を除いて同じです。
- Corrigendum 1 は Annex B.2 を全部載せ直しています。版 2 から変わったのは次の 6 か所で、プロファイルが使う範囲に関わるのは 1 と 2 です。
  1. Signals ディスクリプタの波括弧を省けるようになりました（signalsDescriptor）。`Signals` だけで、シグナルの無いディスクリプタになります。`Parse` はこれを構文の誤りとして断っていたので、直しました。
  2. 監査の応答に入れられるトークンだけの項目が、auditReturnItem（Mux、Modem、Media、DigitMap、Statistics、ObservedEvents、Packages）に絞られました。`internal/h248` は応答の中のトークンだけの項目を読み書きしないので、変えるところはありません。
  3. コンテキストの属性に EmergencyOff が加わりました。注によると、版 1 と版 2 では MG から MGC への向きだけで使います。MGC が送るのは Emergency だけなので、作っていません。トークンの綴りは、Corrigendum 1 では `EmergencyOffToken`、2013 年の版では `EmergencyOff` です（短い形はどちらも `EGO`）。
  4. ContextID の `-` が NULL のコンテキストだという注が加わりました。今の作りと同じです。
  5. 不等号の `#` が「等しくない」だという注が加わりました。不等号は読み書きしません。
  6. ServiceChange のパラメータは 1 回ずつという注に、監査の項目を除く、と加わりました。ServiceChange の中の監査の項目は読み書きしません。
- 2013 年の版（版 3）の文法には、分割（`Segment`）、ターミネーションの ID の並び（`[a, b]`）、シグナルの向き（`SPADirection`）と RequestID（`SPARequestID`）、通知の動作（`ImmediateNotify` など）、ContextAttr、IEPS などが加わっています。2005 年 9 月の版 3 にも、シグナルの向きと RequestID があります。Mp が使うシグナルの RequestID（TS 29.333 の表 5.7.4.6）と、Iq と Ix が使わないシグナルの向き（TS 29.334 と TS 29.238 の表 5.7.5.4）は、この版 3 の項目です。
- 版 3 の文法では、シグナルの無い Signals ディスクリプタは `Signals` とだけ書き、`Signals { }` は書けません。`internal/h248` は版 2 のメッセージとして `Signals { }` を書きます。版 1 から版 2 の Corrigendum 1 まで、どれもこの形を認めています。読むときは両方を受けます。
- 引用符で囲む文字列に改行と 0x80 以上の文字を入れられるのは、2013 年の版からです。`Parse` は前から受けています。

### トランザクション（8 章）

- 版 2 の 8 章、8.1.1、8.2.2、8.2.3、8.3 は、RFC 3525 と草案で読んだ内容と同じでした。
- Corrigendum 1 は 8 章に、1 つのメッセージに応答と要求の両方があるときは応答を先に処理する、という文を加えています。`Endpoint` は並びの順に処理していたので、直しました。
- 8.2.3 は、Pending の数の上限を超えたときのエラー 506 を、時間のかかったコマンドか誤りを起こしたコマンドへの応答に入れるとしています。そのコマンドの応答に入れるように直しました（「エラーと簡略化の見直し」）。

### UDP の上の運び方（Annex D.1）

- 版 2 の D.1.1 から D.1.5 は、RFC 3525 と同じでした。2013 年の版も、言い回しを除いて同じです。違うのは、D.1.4 から ROOT の ProvisionalResponseTimerValue を説明する一文が消えたことだけです。このプロパティの説明は Annex E.2.1 にあります。
- ImmAckRequired の応答に確認が来ないとき、受ける側が応答を自分から再送する手順は、どの版にもありません。
- D.1.3 は、再送のタイマーの値をわざと決めていないと書いています。タイマーの上限 4 秒、LONG-TIMER 30 秒の勧め、最初のタイマーを 200 ms とした D.1.5 の例、切断のしきい値の目安の 7 回から 11 回は、RFC 3525 と同じです。T-MAX の値はありません。D.1.5 は、合わせて 30 秒待つのはおそらく許されると書き、LONG-TIMER を T-MAX に伝搬の遅れの最大を足した値としています。
- 9 章は、IP の上では MGC が TCP と UDP の両方を備え、MG がどちらか一方を備えるとしています。3GPP のプロファイルは、トランスポートを SCTP と UDP に絞っています（各仕様の 5.12）。

### ROOT のプロパティ（Annex E.2.1）

- 版 2 は、8 つのプロパティの型と意味だけを書き、既定値を書いていません。2013 年の版は、8 つとも既定値を Provisioned としています。
- MGProvisionalResponseTimerValue と MGCProvisionalResponseTimerValue は、最初は通常の実行時間（normalMGExecutionTime か normalMGCExecutionTime）にネットワークの遅れを足した値で、下げてもよいとされています。
- MGOriginatedPendingLimit と MGCOriginatedPendingLimit は、相手から受け取れる Pending の数です。この数を超えるときは、Pending を送っていた側がエラー 506 で応答します。
- H.Sup7 にもタイマーの値はありません。自分で選んだ既定値（T-MAX、ProvisionalResponseTimerValue、PendingLimit）を置き換える ITU-T の値はないので、既定値は変えていません。
- base root のパッケージの版は 2 です。2013 年の版は、このパッケージの版 2 にはプロトコルの版 2 以上が要ると書いています。

### 版の交渉（11.3）

- 版 2 の 11.3 は、MG が登録に使う ServiceChange に自分の版を入れ、そのメッセージは ServiceChangeVersion の値にかかわらず版 1 のメッセージとして符号化する、としています。Corrigendum 1 はこの節を書き直しましたが、この決まりは残っています。
- 2013 年の版は、応答も版 1 で符号化するとしています。
- H.Sup7 の 8 章の例では、ServiceChangeVersion を入れた要求（Restart、Handoff、Failover）とその応答が版 1 です。Disconnected、Forced、Graceful と、MGC からの Handoff は版 2 です。
- `Endpoint` はすべてを設定の版で送っていたので、直しました。ServiceChangeVersion を入れた ServiceChange のトランザクションは、要求、Pending、応答、確認のどれも `MEGACO/1` で送ります。

- 413 は、TS 29.334 と TS 29.238 の 5.7.10 の一覧にあり、TS 29.333 の 5.7.9 の一覧にはありません。`Endpoint` は、トランザクションが 10 個を超えるメッセージにメッセージの単位の 413 で答えるようにしました。
- 533 は、トランザクション全体のエラーにしていました。H.248.8 に合わせて、収まらなくなるコマンドのところに入れるように直しました。

### SCTP の上の運び方（H.248.4）

- PPID は 7、既定のポートは UDP と同じ 2944 と 2945 です（1 章）。
- Annex D.1.1 の At-Most-Once に従うことを勧めます。ただし TransactionResponseAck は使わず、three-way handshake（D.1.2.2）も使いません（2000 年の版の 3 章と 4.2）。
- 応答の写しを消す時期は版で違います。2000 年の版は LONG-TIMER を使わないとし、Corrigendum 1 は SCTP の DATA の確認か応答で消すとしています。2009 年の版は SCTP の DATA の確認で消す方法を勧めないとして、LONG-TIMER を使わないという例外を外しています。
- `Endpoint` は SCTP を作っていません。SCTP の上で変わる点は、`endpoint.go` の `SIMPLIFIED:` の注に書きました。

### 分割のパッケージ

- 分割のパッケージは、2005 年の版 3 の Annex E.14 にあります（`seg`）。分割をしないトランスポートの上で H.248 の分割を行うためのもので、root を拡張し、分割のタイマーと PDU の最大の大きさのプロパティを持ちます。
- プロファイルは UDP で分割をしないとしています（TS 29.334 の表 5.12.2 など）。TS 29.333 の表 5.10.2 の注も、このパッケージは要らないとしています。作りません。

### 読めないメッセージへの答え方

8.2.2 と H.248.8 を合わせると、受けた側は次のように答えます。`Endpoint` はこのとおりに作りました。

- ヘッダ（版と mId）を読めないときと、トランザクションを 1 つも読めないときは、メッセージの単位の 400 です（4.2.1）。
- ヘッダの版に対応していないときは、メッセージの単位の 406 で、中身は無視します（4.2.5）。
- トランザクションの ID を読めないときは、TransactionID が 0 の応答に 403 を入れます。8.2.2 は「NULL の TransactionID」と書き、8.1.1 は ID の無い要求への応答に 0 を使うとしています。この 2 つをつなぐ根拠は、下の「NULL の TransactionID」に書きました。
- ID を読めた要求では、読めた分を実行し、残りに答えます。トランザクションの終わりが分からないときは 403、最初のアクションの ContextID を読めないときは 422 を単独で返します。アクションの終わりが分からないときは 422、ターミネーションの ID かコマンドの終わりが分からないときは 442 を、そのアクションの応答の最後に入れます。ContextID を読めない場合を 422 とするのは、2013 年の版の言い方です。2002 年の版は「ContextID の処理で誤り」と書いています。
- 読めた分の処理が失敗で止まったときは、構文の誤りを足しません。8.2.2 は、失敗のあとのコマンドには応答を出さないとしています。
- 壊れた応答、Pending、TransactionResponseAck、エラーには答えません。8.2.2 は要求への答え方だけを決めています。応答に誤りの応答を返すと、相手は自分の要求への応答と読んでしまいます。エラーに答えないのは、互いに読めない 2 つのノードが答え合いを続けないためです。

受けた側が知らない mId に、メッセージの単位で返すエラーは、H.248.1 にも H.248.8 にもありません。410 は、mId などの長さや文字の誤りに使うコードです。ヘッダの誤りには、まとめて 400 を返しています。

### NULL の TransactionID

ID を読めない要求に 0 で答えることは、はじめは H.248.1 の 2002 年の版の 8.1.1 から推した解釈でした。その後、2013 年 3 月の版（`www.itu.int` から取りました）の本文で確かめました。

- 8.2.2 は、正しいトランザクションを見分けられないときに、NULL の TransactionID と 403 だけを入れた応答を返すとしています。NULL がどの値かは、8.2.2 にも 8.1.1 にも書いてありません。
- 8.1.1 は、要求に TransactionID が無いことを伝えるエラーの応答では、TransactionID を 0 にするとしています。RFC 3525 の 8.1.1 も同じ内容で、2002 年の版の 8 章は RFC 3525 と同じです（上の「トランザクション（8 章）」）。
- Annex B.2 の ABNF では、TransactionID は UINT32（10 桁までの数字）だけです。ContextID には NULL を表す `-` がありますが、TransactionID にはそのような記号がありません。Annex A の ASN.1 でも、TransactionId は 0 から 4294967295 の整数です。ContextID には「NULL は 0」という注がありますが、TransactionId にはありません。
- このため、ID を読めない要求に答えるときに書けるのは数字だけで、その場合の値として本文が決めているのは 8.1.1 の 0 だけです。

`internal/h248/unread.go` の `receiveUnread`（198 行のコメント）が TransactionID 0 と 403 を返すのは、`Transaction` の記号のあとの ID を読めないときと、トランザクションの記号そのものを読めないときだけです。どちらも ID の無い要求で、8.1.1 がそのまま当てはまります。コードは本文と合っているので、変えていません。相手の実装がこの応答をどう扱うかは、ほかの実装とつないで見てはいません。

### tshark で確かめたこと

直したところで書き出すメッセージを、試験の中で取り出して text2pcap で pcap にし（UDP の 2944）、tshark 4.2.2 の `-V` で確かめました。400、406、403（TransactionID 0 を含む）、422、442 の応答、コマンドの応答の中の 533 と 506、g/sc の `Meth = EV`、MgcIdToTry の入った ServiceChange の応答、ターミネーションの停止のあとの Subtract、合わせて 58 フレームです。どれも MEGACO としてデコードされ、Malformed の表示は出ませんでした。エラーのコードは名前付きで表示されます。「Unknown」と出るのは、試験の要求にある `Audit { Packages }` の「Audit Item: Unknown-token」だけで、上の「Wireshark での見え方」に書いた tshark の側の制約です。エラーの文字列の無い `Error = 506 { }` では、「ERROR String」の欄にメッセージ全体が出ました。これも表示の癖で、`Endpoint` と `mediactl` が送るエラーには文字列が付いています。

### 残ったこと

- ラッチは、本物の網の振る舞いと違うままです。`Relay` にモードを伝える口を足すかは決めていません。
- ターミネーションの停止とベアラの解放を P-CSCF に伝える口も決めていません。回線の上の手順は、どちらも条項のとおりになりました。
- ベアラの解放を受けた IMS-ALG がセッションをどう扱うかは、TS 29.334 にはありません。TS 23.334 などは読んでいません。

テキストのデコードで分かったこと。

- Local と Remote の中身は SDP として展開されます。アドレスやポートが `$` でも展開されます。
- LocalControl の中のプロパティのうち、`ds/dscp`、`gm/saf`、`gm/sam`、`gm/spf`、`gm/spr`、`gm/esas`、`tman/pol`、`tman/sdr`、`tman/mbs`、`tman/pdr`、`tman/dvt`、`ipdc/realm` には名前が付きます。たとえば `ipdc/realm` は「IP Realm Identifier」と表示されます。ほかのプロパティ、イベント、シグナルは、`hangterm/thb` のように書いたままの形で表示されます。
- エラーのコードには説明が付きます（510 なら「Insufficient resources」）。ServiceChange の Reason にも付きます。
- 長いトークンでも短いトークンでもデコードされます。短いトークンでは、`MO=IN` のように値が略されたまま表示されます。

テキストのデコードの弱いところ。Wireshark の側の制約で、メッセージは正しい形です。

- TransactionPending が「Reply」と表示されます。
- 項目を 1 つずつ指す監査（版 2）は「Audit Item: Unknown-token」になります。`Audit { Media, Packages }` のようなトークンだけの監査は正しく表示されます。
- ContextAudit があると、そのメッセージのデコードが途中で止まります（「MEGACO truncated」）。
- コンテキストの属性（Priority、Emergency、Topology）は、コマンドのように表示されます。
- ターミネーションの ID の並びを返す形の AuditValue の応答（`AuditValue = Context { ... }`）は、「No Descriptor detectable」の警告になります。
- Local や Remote の SDP のあと、`}` の前に空白だけの行があると、「Invalid SDP line」の注意が出ます。SDP の最後の改行のすぐあとに `}` を置けば出ません。
- ObservedEvents の時刻は、イベントの名前と同じ行にまとめて表示されます。
- エラーのコード 413 には説明が付かず、「Unknown (413)」と表示されます。

`internal/h248` の往復の試験にある 43 個のメッセージも、`Marshal` で書き出し、同じ方法（UDP の 2944）で確かめました。どれも MEGACO としてデコードされ、Malformed や truncated の表示は出ません。「Unknown-token」と出るのは、項目を 1 つずつ指す監査を入れた 1 件だけです。これは上に書いた Wireshark の側の制約によるものです。

2 進のデコードは ASN.1 から生成されていて、構造はすべて展開されます。パッケージの名前は、Wireshark が持っている表（Generic、Hanging Termination、IP NAPT Traversal、Gate Management、Traffic Management、RTCP Handling など）で付きます。これは、登録されているフィールドの一覧（`tshark -G fields`）とライブラリの中の文字列で確かめたもので、パッケージを入れた 2 進のメッセージを作って試してはいません。

## 設計の選択

| 決めること | 採った案 | ほかの案 |
| --- | --- | --- |
| 符号化 | テキスト。長いトークンで書き、長短の両方を読む | 2 進（ASN.1 の BER）。両方 |
| 書くときの形 | 入れ子ごとに改行して字下げする。SDP は行の頭から書き、最後の改行のすぐあとに `}` を置く | 空白を入れずに 1 行で書く |
| 範囲 | 3 つのプロファイルが使うコマンドとディスクリプタ。下の「パッケージの範囲」のとおり | RFC 3525 の文法をすべて |
| SDP の扱い | Local と Remote の中身を、そのままの文字列で受け渡す。`internal/sdp` を import しない | このパッケージの中で SDP を解釈する |
| パッケージの項目 | 名前と値の組として汎用に扱う。パッケージごとの型は作らない | パッケージごとに型と検査を持つ |
| トランスポート | UDP の 2944。再送と重複の排除を RFC 3525 Annex D.1 のとおりに作る | TCP と TPKT。SCTP |
| mId | ドメイン名（`<agw1.ims.example.net>`） | アドレスとポート |

### 符号化をテキストにする理由

- 3 つのプロファイルは、どれもテキストを認めています。2 進だけを必須にする文はありません。
- 学習者が、Wireshark の下の欄や `tcpdump -A` でメッセージをそのまま読めます。SIP と SDP を読んできた学習者には、同じ読み方が通じます。独自の HTTP の API と並べて比べるのにも向いています。
- ターミネーションの ID を `ip/1/access/$` のように名前で書けます。一部だけのワイルドカードはテキストでしか使えません。
- パッケージの項目を名前で書けます。2 進では数値の ID になり、パッケージの定義（ITU-T の勧告）が手元に要ります。
- 標準ライブラリだけで作れます。2 進には BER の符号化が要ります。Go の `encoding/asn1` は DER 向けで、H.248 の ASN.1 が多く使う CHOICE や自動のタグ付けをそのままは扱えません。自作すると、符号化の層だけで大きな作業になります。
- 弱みは、Wireshark のテキストのデコードが 2 進ほど細かくないことです。上に挙げた制約のうち、通話の手順（Add、Modify、Subtract、Notify、ServiceChange、トークンだけの AuditValue）に当たるものはありません。

2 進は作りません。あとで要るようになったら、同じ型（`Message` など）から書き出す関数を足せます。

### パッケージの範囲

`internal/h248` が読み書きするもの。

- ヘッダ（`MEGACO/<版>`、mId はアドレス、ドメイン名、デバイス名）、メッセージ全体のエラー。
- TransactionRequest、TransactionReply（ImmAckRequired とエラーを含む）、TransactionPending、TransactionResponseAck。
- コンテキストの ID（数、`$`、`*`、`-`）、コンテキストの属性（Topology、Priority、Emergency）。
- コマンド。Add、Move、Modify、Subtract、AuditValue、AuditCapability、Notify、ServiceChange と、その応答。要求の `O-`（失敗しても続ける）と `W-`（応答をまとめる）。
- ディスクリプタ。Media（TerminationState、Stream、LocalControl、Local、Remote）、Events、Signals（シグナルのリストを含む）、ObservedEvents、Audit、ServiceChange、Statistics、Packages、Error。

読み書きしないもの。プロファイルが使わないか、任意の機能にしか要らないものです。読んだときはエラーを返します。

- Modem、Mux、DigitMap、EventBuffer の各ディスクリプタと、イベントに埋め込むイベントとシグナル。
- 認証ヘッダ、MTP のアドレスの mId。
- プロパティの値のうち、どれか 1 つを表す並び、範囲、不等号。
- ServiceChange の Delay、Address、拡張のパラメータ。
- ContextAudit と、ターミネーションの ID の並びを返す AuditValue の応答。tshark 4.2.2 がデコードできない形でもあります。
- 項目を 1 つずつ指す監査のうち、TerminationState の中の項目を指すもの以外。
- 版 3 で加わった文法（分割、通知の動作の指定など）。版 3 のシグナルの RequestID（`SPARequestID`）と向き（`SPADirection`）は、名前と値の組のパラメータとして読み書きします。
- コンテキストの属性の EmergencyOff（Corrigendum 1 で加わった、MG から MGC への向きだけのもの）と、応答の中のコンテキストの属性。Iq と Ix はコンテキストの属性を監査しません（TS 29.334 5.8.9）。
- 監査の応答の中のトークンだけの項目（Corrigendum 1 の auditReturnItem。`Media` や `Packages` だけを書く形）。

読むだけのものもあります。Signals ディスクリプタの波括弧を省いた形（Corrigendum 1）は読みます。書くときは、どの版でも読める `Signals { }` を書きます。

## 実装の分け方

H.248 によるメディア制御を、並べて進められる単位に分けます。

| 単位 | 内容 | 前提 | 触る場所 |
| --- | --- | --- | --- |
| 1. 符号化 | メッセージを読み書きする。作りました | なし | `internal/h248` |
| 2. トランザクションの層 | UDP の 2944 で送受信する。要求の再送、重複した要求への同じ応答、TransactionResponseAck、TransactionPending、タイムアウト（RFC 3525 Annex D.1）。作りました（「トランザクションと UDP の運び方」） | 1 | `internal/h248` |
| 3. MG の側 | メディア中継ノードが MGC に ServiceChange で登録する。Add、Modify、Subtract、AuditValue を受けて、今の `Relay` の操作に写す。ターミネーションの ID を割り当てる。手順は `internal/h248/mediactl` の `Gateway` で作りました。残りは、中継ノードが `mediactl.Relay` を実装し、`Gateway` を動かすつなぎ込みです | 1、2 | `internal/h248/mediactl`、`internal/agw` |
| 4. MGC の側 | メディア中継ノードの制御の境界（[media-control.md](../design/media-control.md)）の後ろに、H.248 で制御する実装を置く。登録を受け、Add、Modify、Subtract を送る。設定で独自の API と切り替える。手順は `mediactl.Controller` で作りました。残りは、P-CSCF の `Relay` を `mediactl.Relay` に合わせ、設定で切り替えるつなぎ込みです | 1、2 | `internal/h248/mediactl`、P-CSCF、`internal/config` |
| 5. 障害の観察 | ServiceChange（Forced、Graceful、Disconnected）、空の AuditValue による監視、`it/ito`、`hangterm/thb` を、障害を起こす操作と組み合わせる。手順そのものは `mediactl` にあります | 3、4、冗長構成 | 3 と 4 の続き |
| 6. MRFP | Mp のシグナル（`an/apf`、`aasb/play`）、イベント（`g/sc`）、N 個のターミネーション、ターミネーションごとの Subtract を写す。手順は `mediactl.Processor` と、`MpProfile` の `Controller` と `Gateway` で作りました（「Mp のプロファイル（MRFC と MRFP）」）。残りは、中継ノードが `Processor` を実装し、MRFC が `Controller` を使うつなぎ込みです。DTMF（`dd/*`）と Topology は作っていません | 3、4、MRF | `internal/h248/mediactl`、MRFC、MRFP |
| 7. 試験と手順書 | e2e のスクリプト、CI での pcap の確認、手順書「H.248 でメディアを制御する」（英語と日本語） | 3、4 | `scripts`、`docs/guide` |

2 が決まれば、3 と 4 は並べて進められます。3 と 4 の間の約束は、ターミネーションの ID の形、Local と Remote に入れる SDP の行、使うパッケージの項目です。先にこの 3 つを決めておくと、互いを待たずに済みます。5 と 6 は、それぞれ冗長構成と MRF のあとになります。

## この実装で採った選択と、未決の論点

### この実装で採った選択

1. 符号化はテキストだけにしました。3 つのプロファイルがどれもテキストを認めているためです（「符号化をテキストにする理由」）。
2. トランスポートは UDP にしました。プロファイルは SCTP を推奨（Mp は必須）としていますが、Go の標準ライブラリに SCTP はなく、UDP はプロファイルで任意とされています。SCTP を使わないことは `SIMPLIFIED:` に書きます。
3. ServiceChange で名乗るプロファイルの名前は、独自の `imsPracticeIq/1` にしました（「プロファイルの名前」）。
4. 動かすパッケージの項目は、最小の組（`ipnapt/latch`、`hangterm/thb`、`g/cause`）に、制御の関連の監視に要る `it/ito` を加えたものです。`g/cause` は受け取るだけで、中継ノードに知らせる出来事がないので、知らせることはありません。
5. ターミネーションの ID は `ip/<group>/<side>/<コンテキストの ID>` にしました。`<side>` は `access` と `core` です。
6. メッセージのヘッダの版は、プロファイルが求める版 2 以上のうち、すべて `MEGACO/2` で送ります。ただし H.248.1 の 11.3 が版 1 で送ると決めているので、ServiceChangeVersion を入れたトランザクションだけは `MEGACO/1` で送ります。
7. Subtract の応答で統計を返しません。Iq の表 5.7.7.2 が、返さないと定めているためです。中継ノードが運んだ量は、Subtract の応答では返りません。MGC は、空の Audit を付けても付けなくても Subtract を送れます（TS 29.334 の表 5.8.3.1）。
8. `mediactl.Relay` の `Media` に、m= 行の形式と帯域を入れます。Iq の表に従い、キャプチャで見えるためです。ほかの案は、アドレスだけを渡し、m= 行の形式を `-` にすることで、P-CSCF の変更は少なくなります。
9. MGC は、知らない MG からの Notify に 507 で答えます。ほかの案は、MGC が起動したときに、設定にある MG に ServiceChange の Restart（IMS-ALG Restoration、TS 29.334 5.17.3.8）を送ることです。こちらは Iq の手順ですが、MGC が MG の一覧を設定で持つことになります。
10. 制御の関連と hangterm/thb の既定値（「制御の関連」の表）は、どれも仕様に値がないので、根拠を書いて選びました。
11. Mp の ServiceChange で名乗るプロファイルの名前は、Iq と同じ考えで `imsPracticeMp/1` にしました。`MRF/8` を名乗ると、Mp の必須のパッケージと手順のすべてに対応していることになります。
12. 再生の間に無音を入れるときは `aasb/play` を使います。RFC 4240 の `delay` を Mp でも運べるためです。ほかの案は、`an/apf` だけにして、無音を `SIMPLIFIED:` にすることです。MG が名乗るパッケージは減りますが、MRFC の `delay` が効かなくなります。
13. Mp の Subtract の応答に入れる統計は、`rtp/ps` と `rtp/pr` だけにしました（表 5.14.3.5.1）。`nt/dur`、`nt/os`、`nt/or` は、Mp では AuditValue で使うとしているので入れません（表 5.14.3.4.1）。

### 未決の論点

1. MGC と MG の関連の張り方。H.248 では、1 つの MG が 1 つの MGC に登録します。P-CSCF もメディア中継ノードも複数台にするとき、どの台がどの台に登録するかを決める必要があります。1 つの案は、MG が設定にある MGC の名前へ登録し、DNS で複数台に分かれる形です。`Gateway` は、Restart で登録するたびに `LocateController` で MGC を探すので、この形に合います。ただし、この形では MG は P-CSCF の 1 台にだけ登録します。ダイアログを別の P-CSCF の台が引き継ぐと、その台の MGC は MG を知らず、コンテキストを操作できません。どの台でも続きを処理できるようにするなら、中継ノードの中で P-CSCF の台ごとに `Gateway` を 1 つずつ動かし、仮想の MG（H.248.1 11.1）としてすべての MGC に登録する案になります。MId は台ごとに変えます。もう 1 つの案は、P-CSCF の台ごとにメディア中継ノードの組を分けることです。
2. MRFP が返すエラーのコード。今は Iq の MG と同じコード（444、446、451、452、457 を含む）を使っています。TS 29.333 の表 5.7.9.2 にそろえるなら、これらを 501 か 449 に替えます（「MRFP が返すエラー」）。
3. MRFC を複数台にしたときの、MRFP の登録先。1 と同じ問題です。MRFP は 1 台の MRFC にしか登録しないので、会議の Store がほかの台の名前で MRFP を記録していると、その台はコマンドを送れません。案は 1 と同じく、MRFP の中で MRFC の台ごとに `Gateway` を 1 つずつ動かす形（仮想の MG、H.248.1 11.1）か、会議を作った台にその会議の SIP のダイアログを寄せる形です。

## 確かめられなかったこと

- パッケージを定める枝番の勧告の本文のうち、H.248.41、H.248.43、H.248.52、H.248.53、H.248.57 などです。H.248.7（2004 年 3 月）と H.248.9（2009 年 12 月）は、Mp のために読みました（「Mp のプロファイル（MRFC と MRFP）」）。H.248.1 の Annex E は、`root`（E.2）、`g`（E.1）、`nt`（E.11）、`rtp`（E.12）のほかは読んでいません。これらのパッケージの項目は、3GPP のプロファイルの表で確かめた範囲です。H.248.1、H.248.8、H.248.4、H.Sup7 は `www.itu.int` から取って読みました（「ITU-T の勧告との照合」）。H.248.14、H.248.36、H.248.37 も同じく読みました（「メディア中継ノードの制御（MG と MGC）」）。
- H.248.8 の古い版（2002 年 3 月、2005 年 9 月、2007 年 8 月）。プロファイルは H.248.8 の版を決めていないので、今の版（2013 年 3 月）だけを読みました。
- H.248.1 版 3（2005 年 9 月）の本文の大部分。読んだのは、分割のパッケージと、シグナルの向きと RequestID の文法だけです。Mp がフロア制御で使う部分は読んでいません。
- ETSI TS 183 018（TISPAN の Ia のプロファイル）。3GPP のプロファイルの元になった文書ですが、読んでいません。
- TS 23.334、TS 23.333（Stage 2）。手順の名前の元ですが、読んでいません。
- 国内標準（TTC）。`www.ttc.or.jp` が 503 を返すため、H.248 に当たる標準があるかを確かめていません。
- 2 進の符号化で、Wireshark がパッケージの項目にどこまで名前を付けるか。パッケージを入れた 2 進のメッセージは作っていません。
- tshark 4.2.2 以外の版での見え方。
- 実機や商用の製品がテキストと 2 進のどちらを使うか。公開の資料からは決められません。
- 商用の製品が、ImmAckRequired の応答に確認が来ないときに応答を自分から再送するか。H.248.1 には手順がありません。
- 登録の ServiceChange を版 1 で送ったとき、実機の MGC が版 1 の文法で読むか、版 2 として読むか。どちらで読んでも、登録のメッセージの中身は同じ形です。
- 実機の MG が、m= 行の形式の `-` や、知らない MG への Notify の応答の 507 をどう扱うか。公開の資料からは分かりません。
- `an` のパッケージの版。TS 29.333 の表 5.14.2 は版 2 としています。ところが、TS 29.333 が 2 章で参照している H.248.7（2004 年 3 月）は、版 1 を定めています。`www.itu.int` の一覧には、2000 年 11 月と 2004 年 3 月の版しかありませんでした。版 2 の定義を確かめられなかったので、MG は版 1 を名乗ります。
- `aasb` のパッケージの版。TS 29.333 は、2 章で参照している H.248.9 の Amendment 1（2007 年 3 月の草案）に従って版 2 としています。この草案は読んでいません。2 章が `bannsyx` のために参照している H.248.9 の 2002 年 3 月の版も読んでいません。読んだ 2009 年 12 月の版は `aasb` の版 3 を定めているので、MG は版 3 を名乗ります。使う項目（`play` の `an`、`it`、`iv`、`di`）は、TS 29.333 の表 5.14.3.14.1 と同じです。
- `g/sc` の RequestID のパラメータ（`RID`）。TS 29.333 の表 5.14.3.1.1 は任意として挙げていますが、H.248.1（2002 年 5 月）の E.1.2 にはありません。版 3 の本文で確かめていないので、送っていません。
- 実機の MRFP が、`an/apf` の `Duration = 0` を上限なしとして扱うか。H.248.7 4.5 はそう読めますが、実機は確かめられません。
- 実機の MRFC と MRFP が、ターミネーションの ID にどんな形を使うか。TS 29.333 5.6.1.1 は設定で決めるとしています。
