# IMS の仕組みを本文と図と段階で説明する

最初に読むもの。リポジトリの [AGENTS.md](../../../AGENTS.md) の「Book とスライド」、[slides/README.ja.md](../../../slides/README.ja.md) の「シーン」「Book」「確かめる」、[docs/design/slides.md](../../../docs/design/slides.md) と [docs/design/book.md](../../../docs/design/book.md)、移行の対応表 [docs/design/book-migration.md](../../../docs/design/book-migration.md)。手本は、本文が `docs/book/ja/registration-*.md` の 3 つの章、スライドが `slides/decks/ja/04-registration.md` と、それぞれの英語版です。パスは実際の配置で確かめ、無い文書を推測で指さないでください。

読者は、構成を動かさず、問いに答えず、コードも書かずに、本文と図だけで理解します。著者の仕事は、問いを立て、その場か続く説明で答え、その答えの根拠を自分で確かめることです。読者に課していた実習や設問を、著者の説明に移します。

## 1. 学習上の問いと、元の内容の行き先を決める

- 移すデッキの元の版（移行の対応表の基準のコミット）を読み、スライドごとに「読んだあとで一文で言える答え」を書き出します。答えは、本文の節の最初の文と、シーンの `lead` になります。
- 元のスライドの表、フィルタ、コマンド、リンク、条項、設問と答えの行き先を決めます。本文で説明するもの、段階の文で言うもの、フィールドに書くもの、シーンの下の詳しい説明に残すもの、手順書の任意の再現の手順に任せるもの、に分けます。削らず、発表者ノートにも移しません。
- 振り返りと答え、演習と解答は、問いとその答えを本文の説明にまとめます。答えだけを別のページに隠しません。「探してください」「試してください」で終わる文は、著者が関数、条件、結果を示す文に書き直します。設計を考えさせる課題は、著者が選べる方法を並べ、それぞれで何が起き、この実装がどれを選び、どんな条件で別の方法が合うかを説明します。
- 構成の起動、キャプチャの開き方、後片付けのコマンドは、手順書にあれば手順書へ案内し、無ければ手順書に足します。本文とデッキには、結果と、その読み方を残します。
- 行き先を移行の対応表に書きます。見出しが消えるスライドと、中身を別のファイルへ移したスライドに、行き先のファイルと節、扱い、行き先に残る語を書きます。

## 2. 根拠を確かめる

- 信号の向き、区間、値は、対応する手順書（`docs/guide/ja/*.md`）とコードで確かめます。デッキの元の文と手順書が食い違えば、手順書とコードに合わせ、食い違いを報告に書きます。プロトコルの動作を直す必要があるものは、教材では直さず、別の Issue にします。
- 要求と応答は別のイベントにします。同じ REGISTER でも区間ごと、1 回目と 2 回目ごとに別の ID にします（`reg1-ue-p`、`reg2-p-i` など）。実装が順序を保証しない後続の処理を、確かな一列の順序に見せないでください。
- 条項番号は、手順書がその手順に挙げているものを入口にし、新しく書く主張は公開の原典（3GPP、IETF の文書）で版と条項を確かめます。確かめられない番号は書かず、`docs/unverified-clauses.md` に記録します。図の `basis` は、手順書から描いたこの実装の動きなら `repository`、仕様の手順なら `standard`、説明のための例なら `illustration` にします。例の値を実測のように書きません。
- 本文で言う動作は、コードを読み、関係する試験を実際に流して確かめます。試験が確かめている範囲だけを、その試験の結果として書きます。試験の相手役が返す応答を、一般の応答として書きません。確かめた単位は `docs/book/units.yaml` に、章、シーン、コードと試験の名前、条項、確かめたコードのコミットとして書きます。

## 3. 図と段階を組む

- 経路と判断は地図（`view: map`）、誰がどの順に話すかはシーケンス図（`view: ladder`）、依存は地図の上の関係（`rel`）で見せます。関係とメッセージを 1 つのシーンで混ぜません。三列のカードのような同じ構図を、すべての主題に当てはめないでください。
- ノードの升目（`at`）はモデルで一度だけ決め、どのシーンでも同じ位置に置きます。別の経路を通る信号が同じ直線に重ならないように置きます。たとえば登録のデッキでは、I-CSCF を P-CSCF と S-CSCF を結ぶ線の上の段に置き、Service-Route の要求が I-CSCF を通らないことが見えるようにしました。
- 1 つの段階で新しく分かることは 1 つにします。ノードの判断は、そのノードの `do` のイベントにし、入力と結果をフィールドに書きます。
- 地図にイベントがたまって読みにくくなったら、段階を `only` で始めて描き直します。
- 寄る（`zoom`）のは、ノードの中の判断や 2 つのノードのやりとりを見せる段階です。HTML だけが寄り、pptx は全体に薄さの差を付けて描きます。
- チェックポイントは、1 つ前のチェックポイントからのできごとを止まったページで説明できる段階に付けます。文とフィールドが多すぎて収まらないと、確かめる段階で誤りになるので、前の段階にもチェックポイントを付けます。シーケンス図で全体の形を見せるだけのシーンは、`detail: []` でフィールドを出さないようにします。

## 4. 本文を書く

- 章は、問いへの答えを最初の数文で言い切ってから、条件、判断する関数、状態、結果を順に説明します。章ごとに同じ見出しの型を当てはめず、問いに合う順にします。
- コードは、1 つの判断が読める範囲を、ファイルへのリンクだけの段落のすぐ下に、そのファイルの行のまま置きます。抜き出しの前後で、入力、見る条件、変えるもの、次に起きることを説明します。ファイルの一覧だけで済ませません。
- 図は `![図が示すことの文](figures/<デッキ>.<シーン>.<段階>.svg)` と書き、`go run ./cmd/slides figures` で描きます。図に要るものが段階に無ければ、デッキのシーンに段階やフィールドを足します。値を見せる段階には `detail` を付け、本の図の下にもフィールドの表が出るようにします。
- 標準が求めること、この実装の選択、簡略化、説明のための例、試験で確かめたことを、文の上で分けます。説明のために値を短くしたときは、そう書きます。
- 上級の章は、標準の制約、守る性質、選べる方法、この実装の判断と限界、方法が合う条件を説明し切ります。標準に反する案を、同じ重さの選択肢として比べません。
- 自分で動かしたい人への案内は、章の終わりに手順書の節へのリンクとして置き、それを読まなくても章が分かるようにします。

## 5. スライドを書く

- YAML のキーは README の表のとおりです。バッククォートで始まる値と、`:`、`#`、`{` などを含む値は引用符で囲みます。`"` を含む値は単一引用符で囲みます。流れの形（`{...}`）の中では、値にコンマを書けません。
- スライドの見出しと段階の題は、扱うものを 1 つの句で言います。見出しの中を「。」で区切らず、手順の番号は末尾の括弧に入れます（「最初の REGISTER と DNS（1、2）」）。信号の順を縦に並べた図は、日本語では「シーケンス図」と呼びます。
- メッセージの名前（`msg`）は信号の名前で、日英で同じにします。役目、処理、ノート、フィールドの名前のうち説明の言葉は訳します。ヘッダや AVP の名前は訳しません。
- 英語版と日本語版は、ID、ノードの位置、イベントの両端、フィールドの数、各段階の状態を同じにします。日本語版を先に書き、英語版はその構造をそのまま写して言葉だけを訳すと、食い違いが出にくいです。
- 日本語の文は、書いたあとで yomiyasu スキルで推敲します。長い説明（README、手順書、設計の記録）を新しく書くときは、tsuzuri スキルで要件と設計を決めてから書くことも考えます。tsuzuri の記録はリポジトリの外に置き、`.gitignore` を書き換えさせないでください。推敲のあとで英語版と読み比べ、意味が同じことを確かめます。

## 6. 確かめる

`slides/` で次を実行します。

```sh
GOTOOLCHAIN=auto go run ./cmd/slides figures
GOTOOLCHAIN=auto go run ./cmd/slides check
GOTOOLCHAIN=auto go run ./cmd/slides build
node check-html.js
```

`check` が「読み直す」と挙げた学習単位は、コードか試験が確かめたときから変わっています。章を読み直し、まだ正しければ `docs/book/units.yaml` の `verified` を進めます。

リポジトリのルートで次を実行します。

```sh
GOTOOLCHAIN=auto go test -timeout 500s ./slides/...
python3 scripts/check_deck_content.py docs/design/book-migration.md
python3 scripts/check_links.py
python3 scripts/check_glossary.py
python3 scripts/check_learner_text.py
```

`check_deck_content.py` が「なくなった」と言うものは、1 つずつ行き先を確かめます。本文や手順書に移したなら、移行の対応表に行き先を書きます。言い換えたなら構いませんが、黙って落としたものは戻します。表を書いても、行き先にその知識が本当にあるかは、自分で読んで確かめます。

そのうえで、描いた結果を見ます。

- HTML を 1440 × 900 と 390 × 844 で開き、すべてのシーンのすべての段階を見ます。現在地が分かるか、本文の動詞に対応する変化が図にあるか、ラベルが線やノードと読み違えないか、主役のイベントが分かるか、を見ます。全段階の画面を並べた一覧を作ると、見落としが減ります。
- `?check` の一覧が空であることを確かめます（ラベルとノードの重なりも出ます）。
- Book の図を、幅 720 ピクセル前後と 390 ピクセル前後で開いて読みます。本文に出てくる値とメッセージが図にあるか、HTML の途中の段階にしか出ない信号を落としていないか、を見ます。
- Zenn の下書きを書き出し（README の「Book」）、ローカルのプレビューで章、図、コード、表を開きます。画像は遅れて読み込まれるので、スクロールしてから見ます。
- pptx を LibreOffice で PDF にし（`soffice --headless --convert-to pdf`）、チェックポイントのページを、段階を見ていない読み手のつもりで読みます。図の番号と文の番号が合っているか、表が重なっていないか、を見ます。
- 確かめられなかったこと（PowerPoint の実機、ほかのブラウザ、スクリーンリーダーなど）は、報告にそう書きます。構造の検査、ブラウザでの描画、CI、Office の実機を分けて書きます。

## 7. 直すとき

- 図の配置、ラベルの置き場所、pptx のページの組み方は `slides/internal/layout/`、舞台の見た目と動きは `slides/internal/html/` にあります。見た目の不具合を 1 つのデッキの書き方でごまかさず、同じことがほかのデッキでも起きないかを考えて、生成器で直します。直したら、すべてのデッキで上の確認をやり直します。
- 検査や技術的な内容を弱めて見た目を整えることはしません。
- 音声、字幕、動画は、頼まれたときだけ扱います。映像にするときの論点は [docs/design/slides.md](../../../docs/design/slides.md) の「映像にするとき」にあります。
