## なぜ Go なのか

- 呼処理のノード（CSCF、HSS のスタブ、UE シミュレータなど）は Go で書いています。
- コードを書く前に、同じ処理（SIP の解析、Diameter の接続の手順、Cx の要求）を Go と Rust で試作して比べました。決め手は Diameter のライブラリです。Cx と Sh は IMS の中心なので、ライブラリをフォークして保守し続ける負担を避けました。
  - Rust のライブラリでは、アプリケーションとコマンドが閉じた enum でした。Cx を足すにはフォークが要り、サーバーから要求を送ることもできませんでした。
- 学習者が読むときの負担も比べました。Go には、Rust の非同期（async）と所有権にあたる概念がありません。その代わり、要求と応答の区別は型ではなく約束で守ります。
- 速さは決め手になりませんでした。このプロジェクトの規模では、2 つの言語に差が出ないからです。
- メディア中継ノードも Go です。1 つのツールチェーンで、すべてをビルド、検査、試験できるようにするためです。コードは全部 Go です。

## 試験を動かす

| 何をするか | コマンド |
| --- | --- |
| 全部の試験 | `go test ./...` |
| パッケージ 1 つ | `go test ./internal/sms` |
| 試験 1 つ | `go test -run TestRPMessages ./internal/sms` |
| 表の 1 行だけ | `go test -run 'TestRPMessages/RP-ACK_without' -v ./internal/sms` |
| 前の結果を使わない | `go test -count=1 ./internal/sms` |
| データの競合を探す | `CGO_ENABLED=1 go test -race ./...` |
| 静的検査と整形 | `go vet ./...` と `gofmt -l .` |
| 説明を読む | `go doc ./internal/sms ParseRP` |

- 2 回目の `go test` は、コードが変わっていなければ `(cached)` と出ます。`-v` を付けると、試験ごとに PASS か FAIL が出ます。
- `-run` の値は正規表現です。「/」の後ろは `t.Run` で付けた名前で、名前の空白は「_」になります。
- `gofmt -l` は、整形が要るファイルの名前だけを出します。何も出なければ合格です。

## コンテナの Go とホストの Go

Go はコンテナで動かせます。ホストに要るのは Docker だけです。

```sh
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD:/src" -v ims-practice-gomod:/go/pkg/mod \
  -w /src golang:1.27.4-alpine go test ./...
```

Docker が使えない環境では、ホストの Go を使います。

```sh
GOTOOLCHAIN=auto go test ./...
```

- 版は [go.mod](../../../go.mod) の `go 1.27.4` の行で決まります。ホストの Go が古ければ、`GOTOOLCHAIN=auto` でその版を取ってきます。
- `-race` には C のコンパイラが要ります。コンテナでは `sh -c 'apk add -q gcc musl-dev && CGO_ENABLED=1 go test -race ./...'` です。CI は `-race` 付きで試験するので、push の前に 1 回は実行します。
- ボリューム `ims-practice-gomod` は、ダウンロードしたモジュールを次の実行まで残します。`docker volume rm ims-practice-gomod` で消せます。

## ディレクトリ 1 つがパッケージ 1 つ

- 1 つのディレクトリの `.go` のファイルは、どれも同じ `package` の行で始まります。
- import のパスは、go.mod の `module` の後ろにディレクトリをつないだものです。たとえば `github.com/yuu-biz/ims-practice/internal/sms` です。
- `internal/` の下のパッケージは、このモジュールの外から import できません。試すと `use of internal package ... not allowed` で止まります。
- `cmd/ims` と `cmd/ue` は `package main` で、`main` 関数が入口です。`cmd/ims/main.go` の `run` 関数が、設定の roles を見て、役割ごとの部品を作ります。
- 1 つの役割のパッケージは、手順ごとにファイルが分かれています。これは Go の決まりではなく、このリポジトリの約束です。

```go
// file, so the same binary and image serve as HSS, I-CSCF,
// S-CSCF, P-CSCF, or several of them at once.

```

## context.Context で待つのをやめる

[internal/diameter/peer.go](../../../internal/diameter/peer.go)

```go
func (p *Peer) Request(ctx context.Context, request *diam.Message) (*diam.Message, error) {
	ctx, cancel := context.WithTimeout(ctx, p.node.timers.Answer)
	defer cancel()
	out := &outgoing{message: request, answer: make(chan answerResult, 1)}
	select {
	case p.outbox <- out:
	case <-p.done:
		return nil, ErrPeerUnavailable
	case <-ctx.Done():
		return nil, ctx.Err()
	}
```

- 待つ関数は最初の引数に `ctx` を取ります。取り消しか期限で `ctx.Done()` が閉じます。ここでは Diameter の応答を待つ時間に上限を付け、`defer cancel()` で後始末をします。
- `select` は、先に準備ができた channel を 1 つ選びます。ここでは「送れた」「ピアが終わった」「時間切れ」の 3 つです。
- context は取り消しと期限にだけ使い、値の受け渡しには使いません。`cmd/ims/main.go` は `signal.NotifyContext` で、SIGTERM を受けたらノード全体の context を取り消します。

## ロックは利用者ごと。役割全体のロックは無い

[internal/scscf/scscf.go](../../../internal/scscf/scscf.go)

```go
	// users serializes what happens to one user's registration and the
	// subscriptions to it, so that the NOTIFYs of a user go out in the
	// order of the events. Each user has a lock of its own, so that a
	// Cx round trip of one user never holds up another.
	users ims.UserLocks
```

```go
	defer s.users.Lock(privateID)()
```

- `Lock` はロックを取り、ロックを放す関数を返します。`defer` がそれを関数の終わりに呼びます。
- 役割全体を止めるロックも、全加入者を走査する処理もありません。どちらがあっても、役割を何台にも、何人もの利用者にも広げられなくなります。ロックの表は [internal/ims/locks.go](../../../internal/ims/locks.go) の `UserLocks` です。
- `MemoryStore` の `sync.Mutex` は、map を読み書きする間だけ持ちます。Cx の往復の間は持ちません。

## バイト列を組み立てる

[internal/rtp/rtp.go](../../../internal/rtp/rtp.go)

```go
func (p Packet) Marshal() []byte {
	b := make([]byte, headerLen+len(p.Payload))
	b[0] = version << 6
	b[1] = p.PayloadType & 0x7f
	if p.Marker {
		b[1] |= 0x80
	}
	binary.BigEndian.PutUint16(b[2:], p.SequenceNumber)
	binary.BigEndian.PutUint32(b[4:], p.Timestamp)
	binary.BigEndian.PutUint32(b[8:], p.SSRC)
	copy(b[headerLen:], p.Payload)
	return b
```

- `b[2:]` は同じ配列の 3 バイト目からを指す窓です。写しは作りません。
- `binary.BigEndian` は上位バイトを先に書きます。網で使う順です。0 から 11 バイト目が、RFC 3550 5.1 のヘッダの図の順に埋まります。
- 読む側の `Unmarshal` は、長さを確かめてから同じ位置を読みます。`internal/sms` は `append` でバイト列を伸ばし、読む側は `decoder` という小さな型で最初のエラーを覚えておき、最後に 1 回だけ確かめます。

1. `internal/scscf/scscf.go` の `challenge` にある `s.respond(st, 401, ...)` です。IMS AKA の 401 は `internal/scscf/aka.go` にあります。`grep -rn "401" internal/scscf` で両方が見つかります。
2. `{name: "RP-SMMA 9", rp: RPSMMA{MessageReference: 9}, hex: "06 09"}` を足し、`go test -run 'TestRPMessages/RP-SMMA_9' -v ./internal/sms` で実行します。
3. `internal/agw/api.go` の `*agw.Client` です。`Add`、`Modify`、`Subtract` を持っています。
4. `Lock` をその場で呼び、`Lock` が返したロックを放す関数を、関数の終わりに呼ぶよう予約します。
5. `TestRoundTrip` が `first bytes ... want V=2 and M set` で失敗します。`git checkout internal/rtp/rtp.go` で戻します。
