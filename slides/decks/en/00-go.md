## Why Go

- The call-processing nodes (the CSCFs, the HSS stub, the UE simulator and others) are written in Go.
- Before the code was written, the same work (parsing SIP, the Diameter handshake, a Cx request) was tried in Go and in Rust. The Diameter library decided it: Cx and Sh are at the heart of the IMS, so the project avoided forking a library and maintaining the fork.
  - In the Rust library the applications and the commands were a closed enum, so adding Cx needed a fork, and a server could not send requests.
- The load on a learner who reads the code was compared too. Go has nothing like Rust's async and ownership; in exchange, requests and answers are told apart by convention, not by type.
- Speed decided nothing: at the size this project runs at, the two make no difference.
- The media relay is in Go as well, so that one toolchain builds, checks and tests everything. All of the code is Go.

## One directory, one package

- Every `.go` file in a directory starts with the same `package` line.
- An import path is the `module` of go.mod followed by the directory, such as `github.com/yuu-biz/ims-practice/internal/sms`.
- A package under `internal/` cannot be imported from outside this module. Trying stops with `use of internal package ... not allowed`.
- `cmd/ims` and `cmd/ue` are `package main`, and the function `main` is the entry point. The function `run` of `cmd/ims/main.go` reads the roles from the configuration and makes the parts of each.
- Inside a role's package there is a file per procedure. That is a convention of this repository, not a rule of Go.

[cmd/ims/main.go](../../../cmd/ims/main.go)

```go
// Command ims is one IMS node. Its roles come from the configuration
// file, so the same binary and image serve as HSS, I-CSCF,
// S-CSCF, P-CSCF, or several of them at once.
package main
```

## The first letter of a name, and doc comments

- A name that starts with an upper-case letter can be used from outside the package. One that starts with a lower-case letter is for inside the package only.
  - In `internal/sms`, `ParseRP` and `RPAck` are for outside; `decoder` and `maxTPDU` are inside only.
- The comment right before a declaration documents the name (a doc comment). The comment right before the `package` line documents the package.
- `go doc ./internal/sms ParseRP` prints the comment below. `go doc ./internal/scscf` prints the package comment, which names the procedures the S-CSCF follows.
- The comments cite the specifications. They are in English, so that the readers of both language editions of the guides read the same code.

## context.Context: when to stop waiting

[internal/diameter/peer.go](../../../internal/diameter/peer.go)

```go
func (p *Peer) Request(ctx context.Context, request *diam.Message) (*diam.Message, error) {
	ctx, cancel := context.WithTimeout(ctx, answerTimeout(ctx, p.node.timers))
	defer cancel()
	out := &outgoing{message: request, answer: make(chan answerResult, 1)}
	select {
	case p.outbox <- out:
	case <-p.done:
		return nil, ErrPeerUnavailable
	case <-ctx.Done():
		// The loop never took the request, so it is still here and nothing
		// of it went out on the connection.
		return nil, fmt.Errorf("diameter: the peer did not take the %s, so %w: %w", commandName(request), errNotSent, ctx.Err())
	}
```

- A function that waits takes `ctx` first. Cancelling or a deadline closes `ctx.Done()`. Here it bounds the wait for a Diameter answer, and `defer cancel()` cleans up.
- `select` takes the first channel that is ready: sent, the peer has ended, or time is up. `answerTimeout` takes the Answer timer of the node, unless the caller put another timeout in `ctx`.
- The context is used only for cancelling and deadlines here, never to carry values. `cmd/ims/main.go` cancels the context of the whole node on SIGTERM with `signal.NotifyContext`.

[internal/scscf/scscf.go](../../../internal/scscf/scscf.go)

```go
	// users serializes what happens to one user's registration and the
	// subscriptions to it, so that the NOTIFYs of a user go out in the
	// order of the events. Each user has a lock of its own, so that a
	// Cx round trip of one user never holds up another.
	users ims.UserLocker
```

```go
	unlock, err := s.users.Lock(ctx, privateID)
	if err != nil {
		s.lockFailed(st, err, log)
		return
	}
	defer unlock()
```

- `Lock` waits for the lock and returns the function that releases it, which `defer` calls at the end. It returns an error when `ctx` ends while it waits. On an error nothing is held, and `lockFailed` answers the request with a 500.
- `UserLocker` has two types: `UserLocks` in [internal/ims/locks.go](../../../internal/ims/locks.go), in one process, and the lock in the shared store of `internal/kvstore/kvlock`, which fails when the store does.
- No lock holds up a whole role, and no code walks over all subscribers: either would keep a role from growing to many instances and many users.
- The `sync.Mutex` of the `MemoryStore` is held only while it reads or writes its maps, never during a Cx round trip.

## Building bytes

[internal/rtp/rtp.go](../../../internal/rtp/rtp.go)

```go
func (p Packet) Marshal() []byte {
	b := make([]byte, headerLen+len(p.Payload))
	b[0] = version << 6
	b[1] = p.PayloadType & 0x7f
	if p.Marker {
		b[1] |= 0x80
	}
	binary.BigEndian.PutUint16(b[2:], p.SequenceNumber)
	binary.BigEndian.PutUint32(b[4:], p.Timestamp)
	binary.BigEndian.PutUint32(b[8:], p.SSRC)
	copy(b[headerLen:], p.Payload)
	return b
```

- `b[2:]` is a window onto the same array from the third byte on. It copies nothing.
- `binary.BigEndian` writes the most significant byte first, the network order. Bytes 0 to 11 fill in the order of the header figure of RFC 3550 5.1.
- Broken to `version << 5`, it makes `TestRoundTrip` fail twice: `first bytes 0x40 0x80, want V=2 and M set`, and `rtp: version 1, want 2`. The top two bits of the first byte are the version, and the version of RFC 3550 is 2.
- `Unmarshal`, the reading side, checks the length and reads the same positions. `internal/sms` grows its bytes with `append`, and reads them with a small type, `decoder`, that keeps the first error for one check at the end.

| Read the documentation | `go doc ./internal/sms ParseRP` |

- A second `go test` prints `(cached)` when the code has not changed. `-v` prints PASS or FAIL for each test.
- `-run` takes a regular expression. After the `/` comes the name given to `t.Run`, with each space turned into `_`.
- `gofmt -l` prints the files that need formatting: nothing printed means it passes.

## Running it yourself: Go in a container, Go on the host

Go can run in a container, with nothing but Docker on the host.

```sh
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD:/src" -v ims-practice-gomod:/go/pkg/mod \
  -w /src golang:1.27.4-alpine go test ./...
```

Where Docker cannot be used, the host's Go does.

```sh
GOTOOLCHAIN=auto go test ./...
```

- The line `go 1.27.4` of [go.mod](../../../go.mod) sets the version. With `GOTOOLCHAIN=auto`, an older Go on the host fetches that version.
- `-race` needs a C compiler. In the container: `sh -c 'apk add -q gcc musl-dev && CGO_ENABLED=1 go test -race ./...'`. The CI runs the tests with `-race`.
- The volume `ims-practice-gomod` keeps the downloaded modules between runs; `docker volume rm ims-practice-gomod` removes it.
