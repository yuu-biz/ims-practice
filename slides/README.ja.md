# スライド

[English](README.md)

IMS の仕組みを図と段階で見せるスライドです。説明の本文は Book（[docs/book/ja/](../docs/book/ja/README.md)）にあり、スライドは同じ問いを、網の地図とシーケンス図の上で 1 段階ずつ見せます。デッキごとに、Markdown に似た小さな書式のテキストファイルが 1 つあります。このリポジトリの生成器 [cmd/slides](cmd/slides/main.go) が各スライドを割り付け、2 つのファイルを書きます。PowerPoint で編集できる pptx と、1 人で読み進められる HTML です。同じ生成器が、Book の図もデッキのシーンから描きます。

スライドは 2 種類あります。文字、表、コードを並べたページと、シーンです。シーンは網やコードの図で、読む人が段階を 1 つずつ進めます。信号を 1 区間ずつ追い、それを受けたノードに寄って、受け取った値と判断を見せ、その結果として次に出る信号を描きます。HTML ではシーンを段階ごとに進めます。pptx には動かなくても説明できる状態を残し、図の横に各段階の文を書き出します。

デッキは、読むだけで分かるように書きます。問いを立てたら、同じスライドか続くスライドで答えます。構成を動かす手順は手順書（[docs/guide/](../docs/guide/)）にあり、デッキは、自分で動かしたい人のためにその節へ案内します。シーケンス図の全体と、キャプチャで見るヘッダの説明も手順書にあります。

## 読む順と、本文との関係

番号は勧める順です。Book の目次（[docs/book/ja/README.md](../docs/book/ja/README.md)）にも、入門、中級、上級の読む順があり、各章が対応するデッキのシーンを挙げています。章を読んでからシーンを進めても、シーンを見てから章で理由を読んでも構いません。

- 網の地図と、キャプチャとラボのデッキは、登録の前に読みます。これより先のデッキは、どれもこの地図の一部をキャプチャで読むためです。
- 登録と通話のデッキは、SMS、付加サービス、MRF、VoLTE、網間接続のデッキより先に読みます。Path、Service-Route、LIR、INVITE、PRACK、ACK、iFC の読み方は、あとのデッキで説明し直しません。
- MRF のデッキは付加サービスのあと、VoLTE のデッキはそのあとです。MRFC を動かすのは MMTel AS で、VoLTE の通話もすべて MMTel AS を通るためです。
- 2 つの網のデッキは最後です。それまでの通話、SMS、会議の流れを、そのまま境界の向こうまで延ばします。
- 0 の Go のデッキは任意です。Go を読んだことがない人が、デッキと Book に出てくるコードの抜き出しを読むための補足です。

条項番号は、手順書が挙げている版のものです。ほかの版を開くと、番号が違うことがあります。

自分で動かしたい人は、デッキが案内する手順書の節で構成を起動し、キャプチャを開けます。動かさなくても、CI の成果物に各シナリオのキャプチャがあります。`registration-capture`、`sms-capture`、`mmtel-capture`、`mrf-capture`、`volte-capture`（AMR の録音と UE のログも）、`interconnect-capture`（両方の網と網のあいだ）です。

## ビルドする

要るのは Go だけです。版は [go.mod](../go.mod) にあり、`GOTOOLCHAIN=auto` を付ければ古い Go がその版を取ってきます。Node、ブラウザ、フォント、LibreOffice は要りません。このディレクトリで実行します。

```sh
GOTOOLCHAIN=auto go run ./cmd/slides check   # すべてのデッキを確かめる
GOTOOLCHAIN=auto go run ./cmd/slides build   # 確かめてから dist/ に書く
```

ホストに Go が無ければ、リポジトリのほかの部分と同じコンテナで、リポジトリのルートから実行します。

```sh
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD:/src" -v ims-practice-gomod:/go/pkg/mod \
  -w /src/slides golang:1.27.4-alpine go run ./cmd/slides build
```

`build` は `dist/ja/` と `dist/en/` に、デッキごとに `.pptx` と `.html` を 1 つずつ書きます。確かめる段階で問題が見つかれば、何も書きません。`dist/` は Git の対象外です。出力はソースだけで決まるので、2 回ビルドしても同じファイルになります。

手順書へのリンクは相対パスなので、チェックアウトした中の `dist/` から開いたファイルで使えます。CI の成果物のように、ファイルをほかの場所へ持ち出すときは、リポジトリのツリーのアドレスを渡します。リンクが絶対パスになります。

```sh
go run ./cmd/slides -repo-url https://github.com/<owner>/<repository>/blob/<commit> build
```

## Book

Book の本文は [docs/book/](../docs/book/ja/README.md) の普通の Markdown で、リポジトリのホストでそのまま読めます。生成器は本文の 3 つの形を読みます。

- `figures/<デッキ>.<シーン>.<段階>.svg` を指す画像は、図です。同じ言語のデッキのそのシーンの段階を、全体の図として描きます。地図は全体を、シーケンス図は最初の段からその段階の最後の段までを描き、段階が `detail` で見せるフィールドの表を図の下に、線の種類の凡例と図の根拠（この実装の動き、仕様の手順、説明のための例）をその下に置きます。SVG は CSS もスクリプトも使わないので、画像として単独で開けます。
- ファイルへのリンクだけの段落のすぐ下のコードブロックは、そのファイルの抜き出しです。デッキと同じく、ファイルの連続した行と同じでなければなりません。
- 同じディレクトリの章のファイルへのリンクは、章へのリンクです。

章の順は [docs/book/book.yaml](../docs/book/book.yaml) にあり、各言語の `README.md` が目次です。[docs/book/units.yaml](../docs/book/units.yaml) には、学習単位ごとに、問い、構成、章、シーン、説明が引くコードと試験の名前、条項、確かめたコードのコミットを書きます。

```sh
GOTOOLCHAIN=auto go run ./cmd/slides figures   # 本文の図をデッキから描き直す。どの章も使わない図は消す
GOTOOLCHAIN=auto go run ./cmd/slides check     # デッキと一緒に本文も確かめる
```

`check` は、本文について次のものを報告します。存在しないファイルと見出しへのリンク、もうファイルに無い抜き出し、いまのデッキから描いたものと 1 バイトでも違う図、どの章も使わない図のファイル、シーンや段階が無い図、目次がリンクしていない章、`book.yaml` に無い章のファイル、日本語と英語で図か抜き出しが違う章、学習単位が名前を挙げるのにもう無い関数、型、試験、シーン。さらに、学習単位のコードか試験が `verified` のコミットから変わっていれば、「to read again」としてその単位を挙げます。挙げるだけで失敗にはしません。章を読み直し、まだ正しければ `verified` を進めます。

### Zenn の下書きを作る

Zenn の Book の形に書き出し、ローカルでプレビューします。書き出すのは未公開の下書きで（`published: false`）、どこにも送りません。

```sh
GOTOOLCHAIN=auto go run ./cmd/slides -repo-url https://github.com/yuu-biz/ims-practice/blob/$(git rev-parse HEAD) zenn
node book-images.js dist/zenn
cd dist/zenn && npx zenn-cli@0.5.14 preview
```

`zenn` は `dist/zenn/books/ims-practice-book/` に `config.yaml` と章のファイルを、`dist/zenn/images/ims-practice-book/` に図の SVG を書きます。章の題はフロントマターに移ります。章へのリンクは Book の中の章へ、ほかのファイルへのリンクは `-repo-url` のコミットの GitHub のアドレスへ直します。抜き出しは、そのコミットのファイルとも照らし合わせ、違えば何も書きません。`-lang en` を付けると、英語の本文を `books/ims-practice-book-en/` に書きます。Zenn は SVG の画像を受け付けないので、`book-images.js` が Chromium で図を 2 倍の大きさの PNG にし、表紙の `cover.png`（500 × 700）も描きます。Playwright と、その Chromium が要ります。プレビューの画像は遅れて読み込まれるので、スクロールしてから見ます。

## pptx の中身

pptx は普通の PowerPoint のファイルです。スライドの上のものは、どれも編集できる PowerPoint の部品です。

| スライドの上 | pptx の中 |
| --- | --- |
| タイトル、副題、フッター、スライド番号 | スライドのレイアウト「Title Slide」「Section Header」「Title Only」のプレースホルダー。タイトルは PowerPoint のアウトラインに出ます。 |
| 段落、箇条書き、引用 | テキストボックス。箇条書きの記号は段落の箇条書き、番号は自動の段落番号です。 |
| 表 | 表（`a:tbl`）。見出しの行があります。 |
| コードのブロック | 灰色の地に等幅のフォントで書いたテキストボックス。 |
| シーケンス図 | 図形のグループ 1 つ。参加者ごとの箱と線、メッセージごとの矢印（矢じりの付いたコネクタ）とテキストボックス、注記ごとの箱です。一部を直すときはグループを解除します。 |
| シーンの図 | 図形のグループ 1 つ。図形には、表すものの名前が付きます。ノードごとに文字の入った角の丸い箱（`node icscf`）、メッセージごとに矢じりの付いたコネクタ（`event uar1`）とラベルのテキストボックス（`label uar1`）、ノードの中の処理ごとに箱です。名前は PowerPoint の選択ウィンドウに出ます。 |
| 手順書へのリンク | ハイパーリンク。パッケージはアドレスを URI として持つので、日本語のアンカーはパーセント符号化します（`%E7%99%BB...`）。 |

画像は 1 枚もありません。発表者ノートもありません。

シーンはチェックポイントごとに 1 枚のページになります。チェックポイントはソースで残すと決めた段階で、シーンの最後の段階は必ずチェックポイントです。そのページにはその段階での図を描き、メッセージにはそれを主役にする段階の番号を付けます。図の横か下には 1 つ前のチェックポイントからの各段階の題と文を書き出し、その段階のメッセージのフィールドを表にします。段階を進められない pptx の読み手も、HTML が 1 段階ずつ見せることを、このページで読めます。その文と同じページに収まらないほど大きな地図は、図だけのページにし、文を次のページに置きます。シーンの詳しい説明はそのあとの「詳しく」の札を付けたページにします。矢印は箱にくっついていません。PowerPoint でノードを動かしても、矢印はそのまま残ります。

分かっている制約。

- pptx はフォントの名前を書いています。ラテン文字は Calibri、日本語は Yu Gothic、コードは Consolas です。どれかが無いマシンでは別のフォントに置き換わり、文字の幅が少し変わります。
- 生成器は文字の幅を Arial の幅で測ります。Arial は Calibri や多くの日本語のフォントのラテン文字より広いので、普通の幅のフォントなら行は収まります。その代わり、表の行が文字に必要な高さより少し高くなることがあります。
- 収めるために文字を小さくしたスライド（「確かめる」を参照）は、pptx でもその大きさのままです。PowerPoint で箱に文字を足しても、下の箱は動きません。

## HTML

デッキごとにファイル 1 つで、ディスクから開けます。ネットワークからは何も読みません。スライドを 1 枚ずつ、ウインドウの大きさに合わせて出します。文字のページは pptx と同じ箱で描きます。シーンは舞台のような画面です。題にシーンの問いを置き、図と、今の段階の文とメッセージのフィールドを並べます。シーンの詳しい説明はボタンで開きます。

| キー | 動き |
| --- | --- |
| →、↓、Page Down、Space、Enter | 次の段階。スライドの最後の段階からは、次のスライド |
| ←、↑、Page Up、Backspace | 前の段階。スライドの最初の段階からは、前のスライドの最後の段階 |
| Home、End | 最初のスライド、最後のスライドの最後の段階 |
| `d` | シーンの詳しい説明（「詳しく読む」）を開く、閉じる。Esc でも閉じる |
| `m` | 動きを減らす。どの変化もすぐに出る |
| `r` | 読み物の表示。Esc で戻る |
| `f` | 全画面 |

舞台の下の帯にも同じボタンと、スライドの一覧と、今のシーンの段階ごとのボタンがあります。ボタンの上で Space と Enter を押すと、そのボタンが押され、段階は進みません。

アドレスはスライドと段階を指します。`#select/uaa` はシーン `select` の段階 `uaa`、`#12` は文字のページなら 12 枚目です。リンクや再読み込みで同じ状態が開きます。段階は前の段階からの差分ではなく、それぞれの完全な状態から描きます。そのため、進んで着いても、戻って着いても、アドレスで開いても、同じ図になります。どのスライドも指していないアドレスでは、最初のスライドが開きます。もう一方の言語のデッキへのリンクはアドレスを引き継ぐので、同じ段階が開きます。

メッセージを足す段階では、送り手から受け手へ点が線の上を走ります。段階がノードに寄るときは、図がなめらかに動きます。「動きを減らす」か、動きを減らすシステムの設定があると、どちらもしません。それで欠ける情報はありません。スマートフォンのような狭い画面では、スライドを縮めません。文字を流し込み、図を画面の幅に合わせ、段階の文を図の下に続けます。

読み物の表示はすべてのスライドを順に並べます。文字のページは流れる文章にし、シーンは pptx と同じくチェックポイントごとに描いて、詳しい説明を続けます。印刷すると読み物の表示が出ます。印刷の画面の「PDF に保存」で PDF になります。

アドレスの最後に `?check` を付けると（`04-registration.html?check`）、すべてのスライドを並べ、すべてのシーンのすべての段階を描きます。そのうえで、ページの下に次のものを一覧で出します。ブラウザが箱より大きく描いた文字のある箱、文字が収まらないシーンの欄、名前が箱より広いノード、ノードかほかのラベルに重なるメッセージのラベルです。ビルドの測り方が本物のブラウザのフォントでも合っているかを確かめられます。

[check-html.js](check-html.js) は、これをすべてのデッキについて、画面なしの Chromium で行います。`build` のあとに、このディレクトリで実行します。

```sh
node check-html.js   # dist/ を読む
```

デッキごとに、問題の数と、文字を描いたフォントを出します。問題が 1 つでもあるときと、デッキの字形の 1% より多くを、デッキが名前を挙げていないフォントが描いたときに失敗します。デッキのフォントが無いマシンではそうなり、そこで測っても何も分からないためです。「⊕」のように、どのフォントにも無い記号は、どのマシンでも別のフォントで描かれますが、この割合には届きません。Node と Playwright、その Chromium と、フォントが要ります。Ubuntu では、パッケージ `fonts-crosextra-carlito`（`Calibri` と同じ幅の `Carlito`）、`fonts-noto-cjk`（`Noto Sans CJK JP`）、`fonts-dejavu-core`（`DejaVu Sans Mono`）です。

### 大きさ

出力によって単位が違います。同じ数でも、同じ長さとは限りません。

| どこ | 単位 | 大きさ |
| --- | --- | --- |
| レイアウトのページと pptx | ポイント。1 ポイントは 12700 EMU | 960 × 540 ポイント。13⅓ × 7½ インチ |
| HTML の舞台 | CSS のピクセル | 1280 × 720。ウインドウに合わせて拡大、縮小します。文字のページは、ポイントの 4/3 倍で描き、舞台いっぱいにします。 |
| 図 | 図の単位 | 地図ではノード 1 つに 300 × 160 の升目、シーケンス図では列が 168、段が 42。出力ごとに、置き場所に合わせて拡大、縮小します。 |
| 読み物の表示と印刷 | CSS のピクセル | ウインドウか紙の幅 |

## 確かめる

`go run ./cmd/slides check` は、次のものを報告します。

- ソースの誤りと、その行。知らないブロック、セルの数が合わない表の行、HTML のコメントなどです。
- 文字を 80% まで小さくしても中身が収まらないスライド。黙って切ったり、さらに縮めたりはしません。スライドを分けるか、短くします。
- 存在しないファイルへのリンクと、手順書のもう無い見出しへのリンク。デッキは手順書の各手順に見出しでリンクしているので、見出しの名前を変えるとリンクが切れます。
- もうファイルに無いコードの抜き出し。抜き出しとは、ファイルへのリンクだけの段落のすぐ下にあるコードのブロックと、それに続く同じ言語のブロック（2 つ目の `go` のブロックなど）です。コードを動かす `sh` のように、ほかの言語のブロックが来ると、そこで終わります。どの抜き出しも、ファイルの中の連続した行と、タブまで同じでなければなりません。そのため、デッキが追いついていないコードの変更は、この確認で失敗します。
- 片方の言語にしか無いデッキと、2 つの言語でスライドの数かレイアウトが違うデッキ。モデルかシーンが違うデッキも報告します。比べるのは、ID、ノードとその位置、イベントの送り手と受け手、信号の名前、フィールドの数、各段階の完全な状態です。
- シーンの誤りと、その行。知らないキー、使われている ID、段階が 2 回出すイベントや出していないのに消すイベント、シーンが描かないノード、図と文が 1 枚のページに収まらないチェックポイントです。
- リポジトリが受け付けないコマンド。`sh` のブロックと行の中のコードを読みます。`docker compose` は `compose.yaml`（`-f` があればそのファイル）のサービスとプロファイルと照らします。`ue` は、`docker compose run` の中のものも含めて、`ue register -h` が出すサブコマンドと、サブコマンドごとに `ue サブコマンド -h` が出すフラグと照らします。ラボへの `curl` は、メソッドとパスを `internal/lab` が登録する経路と照らします。経路はそのソースから読みます。`scripts/` の下のパスは、ファイルがあるかを確かめます。ほかのアドレスへの `curl` は、そのアドレスとパッケージを [internal/facts/routes.go](internal/facts/routes.go) の `httpHosts` に足すまで失敗します。
- そのアドレスではもう動いていないノード。デッキのすべての表を読み、セルごとに、Compose のネットワークのアドレスとサブネットを探します。セルは 2 つ目から最後の数字だけを並べることがあるので、`172.28.0.100、101、103` は 3 つのアドレスです。どれも、`compose.yaml` か、2 つ目の網とそのあいだのリンクを足す `deploy/interconnect/compose.yaml` にある、サービスのアドレスかネットワークのサブネットでなければなりません。表の最初の 2 列がノードとそのアドレスなら、ノードの列がコードで書いたサービス（`` `mrfp` ``）も、その行のアドレスのサービスでなければなりません。どの Compose のネットワークの範囲にも入らない 4 つの数字は、アドレスではなく仕様の条項です。読むのは表だけです。図や文には、網の境界が要求を捨てる相手網でないホストのように、どのノードのものでもないアドレスをわざと書くことがあるためです。

名前か役目が地図のノードの箱かシーケンス図の頭より広いときと、生成器が空いた場所を探したあとも、メッセージのラベルがノードかほかのラベルに重なるときと、ラベルがシーケンス図の幅より広く、画面で切れてしまうときも、デッキの確認で誤りになります。日本語のデッキで、スライドか段階の見出しの中に「。」があるときも誤りになります（例「CAT。着信側が選ぶ呼び出し音」）。見出しは、スライドが見せるものを 1 つの句で言い、補足は括弧に入れます。

シーンの文字もスライドの文字と同じ確認を通ります。リード、各段階の題と文、描くイベントのフィールドの名前と値です。段階の文のリンクや、フィールドのアドレスとコマンドは、段落や表に書いたときと同じように確かめます。

デッキごとに、収めるために文字を小さくしたスライドと、その割合も出します。`ue` のフラグを読むために、リポジトリのルートで `./cmd/ue` をビルドして実行します。そのため、Go がビルドするぶん確認に時間がかかります。

リポジトリのルートで `go test ./...` を実行すると、同じ確認がデッキと Book に対して走ります（`cmd/slides` の試験 `TestDecks` と `TestBook`）。だから CI でも同じ確認で失敗します。`internal/pptx` の試験も、すべてのデッキを組み立てて、パッケージの部品を 1 つずつ確かめます。確かめるのは 2 つです。1 つは、どの部品にもコンテンツの型があり、どの関係にも行き先の部品があることです。もう 1 つは、生成器が書く要素ごとに、子の順番と、なければならない子と属性が、ECMA-376 のスキーマがその型に定めるとおりになっていることです。そのうえで、すべての部品を `xmllint` に渡し、スキーマそのもので検査します。[internal/pptx/testdata/ecma376](internal/pptx/testdata/ecma376/README.md) に、Ecma International が ECMA-376 とともに公開している移行用（Transitional）のスキーマがあります。生成器が書く名前空間のスキーマで、どれをどこから取ってきたかもそこに書いてあります。スキーマは、順番の確認では見つからず、ファイルを読む側なら断るものを捕まえます。たとえば、その型が許す値の集合に無い属性の値です。`xmllint`（パッケージ `libxml2-utils`）が無いマシンでは、この試験だけを飛ばしてほかを走らせます。環境変数 `PPTX_XMLLINT=xmllint` があるときは、飛ばさずに失敗にします。CI はこちらで動かします。リポジトリのルートの `python3 scripts/check_links.py` は、デッキを含むリポジトリのすべての Markdown のリンクを確かめます。

## デッキを書く

デッキは、リポジトリの中では Markdown のように読めるテキストファイルです。書式はわざと小さくしてあります。ブロックの種類はいくつかだけで、既定のレイアウトが合わないときにレイアウトの行を書きます。

````markdown
---
title: UE が IMS に登録する流れ
footer: ims-practice 4. 登録
lang: ja
---

# UE が IMS に登録する流れ

SIP Digest での登録

---

## 全体の形

```ladder
UE, P-CSCF, I-CSCF, S-CSCF, HSS
UE -> P-CSCF -> I-CSCF: REGISTER // 1 - 2
I-CSCF <-> HSS: UAR, UAA // 3
UE <-- P-CSCF <-- I-CSCF <-- S-CSCF: 401 // 6
```

- 1 回目は「誰か」を伝え、2 回目で「本人であること」を証明します。

---

## REGISTER が 2 回ある理由

1 回目の REGISTER への答えとして、網が認証の問い（nonce）を出します。2 回目の REGISTER で、UE がその問いに答えます。
````

- **フロントマター。** ファイルは 2 つの `---` の行で挟んだ `title`（デッキの名前）、`footer`（各スライドの下に出す文字）、`lang`（`en` か `ja`。ディレクトリと同じ）で始めます。ほかのキーは書けません。
- **スライド。** `---` の行でスライドが終わります。スライドは見出しで始めます。`#` は最初のスライド（表紙）と、デッキの部の始まりのスライドに使い、ほかのスライドは `##` にします。表紙と部の始まりのスライドには段落だけを書き、それが副題になります。
- **レイアウト。** 見出しの前の `[layout: 名前]` の行で、`content` 以外のレイアウトを選びます。`two-columns` のスライドでは、2 つの列の間に `[column]` の行を 1 つ置きます。
- **コメントは書かない。** HTML のコメント `<!-- ... -->` は誤りになります。デッキに発表者ノートはありません。読む人への問いは、その答えと一緒に同じスライドか、すぐ続くスライドに書きます。

### ブロック

| ブロック | 書き方 | スライドでは |
| --- | --- | --- |
| 段落 | 文字の行。ソースの改行がスライドでも改行になります。 | 文字 |
| 箇条書き | 記号は `- `、番号は `1. `。入れ子は 2 つの空白で字下げし、1 段までです。記号の無い字下げの行は、すぐ上の項目の続きです。 | 箇条書きの記号か、自動の番号 |
| 表 | `\| a \| b \|` の行と、見出しの行のあとの区切りの行 `\| --- \| ---: \|`。セルの中の `\|` は `\\|` と書きます。 | 幅いっぱいの表 |
| コード | ` ``` ` で囲むブロック。`sh` や `go` のような語を付けます。タブは空白 4 つになります。 | 折り返さない等幅の文字。幅の広いブロックは文字を小さくします |
| シーケンス図 | ` ```ladder ` で囲むブロック。下を見てください。 | 図形 |
| 引用 | `> ` で始まる行。デッキでは手順書を指すのに使います。 | 左に線の付いた小さな灰色の文字 |

行の中では、`**太字**`、`` `コード` ``、`[文字](https://example.org/)`、`<https://example.org/>` を使えます。記号の前にバックスラッシュを置くと、ただの文字になります。

### シーケンス図

最初の行に、参加者を左から順にコンマで区切って書きます。ほかの行は 1 行が 1 段です。

| 段 | 描き方 |
| --- | --- |
| `A -> B: ラベル` | A から B への要求。実線の矢印で、上にラベルを置きます |
| `A --> B: ラベル` | 応答。破線の矢印です |
| `B <- A: ラベル`、`B <-- A: ラベル` | 同じものを右から左へ書いたもの |
| `A -> B -> C: ラベル` | B を通る 1 つのメッセージ。区間ごとに矢印を描きます。1 段の参加者は、左から右か右から左の順に並べます |
| `A <-> B: ラベル` | Diameter の組のような要求と応答。両端に矢じりのある矢印 1 本です |
| `note A, C: 文字` | A から C までの参加者にまたがる箱（1 人なら `note A: 文字`） |
| `... // 注` | 注は右の列に出ます。手順書の手順の番号などに使います |

ラベルはただの文字です。ラベルが図より広い段や、名前が列より広い参加者は、確かめる段階で誤りになります。

### レイアウト

| レイアウト | 選び方 | 中身 |
| --- | --- | --- |
| `title` | 最初のスライドの `#` | デッキの題、短い線、副題。左にアクセントの色の帯があります。 |
| `section` | 2 枚目以降の `#` | デッキの部の始まり。アクセントの色の地に白い文字です。 |
| `content` | `##`。既定 | 下に線の付いたタイトルと、上から順に並べたブロック。表、コード、シーケンス図は幅いっぱいに広げます。 |
| `two-columns` | `[layout: two-columns]` | content と同じで、ブロックを同じ幅の 2 つの列に並べます。 |
| `exercise` | `[layout: exercise]` | 黄土色の content のスライドで、「演習」の札が付きます。演習と「振り返り」に使います。 |
| `answers` | `[layout: answers]` | 緑の content のスライドで、「解答」の札が付きます。演習のすぐあとに置きます。 |
| `summary` | `[layout: summary]` | ブロックを薄い色の板の上に並べます。「このデッキで分かること」に使います。 |

どのスライドも左下にデッキのフッターがあり、最初のスライドのほかは右下に番号があります。中身が高すぎるスライドは文字を 80% まで小さくし、それでも収まらなければ確かめる段階で誤りになります。

### シーン

シーンのあるデッキはフロントマターに `format: visual` を書きます。フロントマターと表紙のあいだには `ims-model` のブロックを置き、ノードと、デッキのシーンが描くすべてのイベントを書きます。本文が `ims-scene` のブロックで始まるスライドが、シーンになります。どちらのブロックも YAML です。キーはすべて決まっていて、書き間違えたキーはその行とともに確かめる段階で誤りになります。

````markdown
---
title: UE が IMS に登録する流れ
footer: ims-practice 4. 登録
lang: ja
format: visual
---

```ims-model
nodes:
  - {id: icscf, label: I-CSCF, role: ホーム網の入口, at: [2, 0]}
  - {id: hss, label: HSS, role: 加入者のデータ, at: [3, 0]}
  - {id: scscf, label: S-CSCF, role: 認証と登録, at: [3, 1]}
events:
  - id: uar1
    msg: UAR
    from: icscf
    to: hss
    proto: Cx
    note: (1 回目)
    fields:
      - User-Authorization-Type: REGISTRATION (0)
  - id: uaa1
    msg: UAA
    from: hss
    to: icscf
    proto: Cx
    note: (1 回目)
    fields:
      - Experimental-Result: DIAMETER_FIRST_REGISTRATION (2001)
  - id: icscf-select
    do: S-CSCF を選ぶ
    at: icscf
```

---

# UE が IMS に登録する流れ

---

## I-CSCF が UAR で HSS に尋ねる（3、4）

```ims-scene
id: select
lead: 最初の UAA が返すのは、S-CSCF の名前ではなく、必要な能力です。
steps:
  - id: uar
    title: HSS に尋ねる（UAR）
    show: [uar1]
    text: Cx のコマンド 300 です。
  - id: uaa
    title: HSS が必要な能力を返す（UAA）
    show: [uaa1]
    checkpoint: true
    text: まだどの S-CSCF も割り当てられていません。
  - id: choose
    title: I-CSCF が S-CSCF を選ぶ
    show: [icscf-select]
    focus: [icscf]
    zoom: [icscf, hss, scscf]
    text: 設定の一覧から選びます。
```

| 見るもの | 見どころ |
| --- | --- |
| UAA の結果 | DIAMETER_FIRST_REGISTRATION（2001）。Experimental-Result の中にある。 |
````

シーンのブロックの下に書いた文は、そのシーンの詳しい説明です。ほかのスライドと同じブロックを書けます。HTML は「詳しく読む」の奥に、pptx は別のページに出します。段階では書ききれない、学習者に要るものを残す場所です。キャプチャで見るものの表、フィルタ、コマンド、手順書へのリンクと条項を書きます。

**モデル。**

| キー | 中身 |
| --- | --- |
| `nodes` | ノードごとに、`id`、`label`（名前。どの言語でも同じ）、`role`（役目を短く。デッキの言語で。地図でも、シーケンス図の頭でも、名前の下に出ます）、`at: [列, 行]`（地図の升目の位置）を書きます。ノードはデッキのどのシーンでも同じ位置にいます。 |
| `groups` | 一緒に囲むノード。2 つの網などに使います。`{id, label, nodes: [...]}` と書きます。 |
| `events` | イベントごとに `id` を書き、3 種類のどれかにします。`from`、`to`、`proto` と一緒に書く `msg: 名前` は、1 区間を進む 1 つのメッセージです。要求とその応答は 2 つのイベントで、1 つの REGISTER の区間もそれぞれ別のイベントです。`at` と一緒に書く `do: 文` は、1 つのノードが受け取ったもので行う処理です。`from` と `to` と一緒に書く `rel: 文` は、信号ではない関係です。パッケージの import などに使い、矢じりの付いた破線で描きます。`proto` を付けた関係は参照点です。たとえば `rel: Cx` と `proto: Diameter` で、2 つのノードのあいだのインタフェースを、そのプロトコルの線で、矢じりを付けずに描きます。 |
| `note` | イベントの名前の下に添える短い言葉。`(2 回目)` など。 |
| `fields` | 段階が見せるヘッダ、AVP、値。1 つにつき `- 名前: 値` と書きます。値は 1 行の Markdown です。バッククォートで始まる値は引用符で囲みます。 |

メッセージの名前は信号の名前（`REGISTER`、`UAA`、`200 OK`）で、2 つの言語で同じです。メッセージの線はプロトコルで決まります。SIP は実線、Diameter（`Cx`、`Sh`、`Rx` など）は破線、DNS は点線で、HTTP とメディアは別の色です。線のラベルにもプロトコルの名前を書くので、色や線の種類だけで見分けることはありません。

**シーン。**

| キー | 中身 |
| --- | --- |
| `id` | アドレスでのシーンの名前。`#select/uaa` の `select` です。デッキの中で 1 つだけで、2 つの言語で同じです。 |
| `view` | `map`（既定）は、ノードを升目に置き、メッセージを 2 つのノードのあいだに描きます。`ladder` は、ノードごとに縦の線を引き、イベントを段階が出す順に 1 段ずつ描きます。 |
| `nodes` | シーンが描くノード。既定では、地図はモデルのすべてのノードを、シーケンス図はイベントがつなぐノードを描きます。 |
| `lead` | 題の下の 1 行。シーンの問いへの答えを書きます。 |
| `basis` | 図が何をもとに描いたものか。`repository`（既定。手順書が説明する、この実装の動き）、`standard`（仕様の手順）、`illustration`（考え方を説明するための例）です。図の下に 1 行で書くので、図がキャプチャそのものに見えることはありません。 |
| `steps` | 段階を順に並べます。 |

**段階。**

| キー | 中身 |
| --- | --- |
| `id`、`title`、`text` | アドレスでの段階の名前、題（番号ではなく、起きることの名前）、図が今見せていることを言う 1、2 行の文。 |
| `show`、`hide`、`only` | 段階が描くイベント。前の段階のイベントから `hide` を除き、`show` を足します。`only` は、その一覧から描き直します。 |
| `active` | 段階の主役のイベント。いちばん強く描きます。既定では、段階が足した最後のメッセージか処理です。`active: ''` で主役を無しにします。 |
| `focus` | いちばん強く描くノード。既定では主役のイベントの両端です。描くイベントのどれにもつながらないほかのノードは、薄く描きます。 |
| `zoom` | HTML が寄って見せるノード。そのあいだのイベントも入ります。書かなければ図の全体を見せます。 |
| `detail` | フィールドを見せるイベント。既定では、フィールドがあれば主役のイベントです。1 回目と 2 回目の UAA のように 2 つ並べると、見比べられます。 |
| `checkpoint` | `true` で、その状態を pptx と読み物の表示に残します。最後の段階は必ずチェックポイントです。 |

パーサーは段階をそれぞれの完全な状態に直します。そのため段階の意味は進んで着いたときもアドレスで開いたときも同じです。片方の言語のシーンはもう片方と同じ ID、ノード、イベント、状態を持ちます。違うのは言葉だけです。

シーンの選び方と分け方。

- シーンごとに、学習者が図から答えられる問いを 1 つ決め、答えを `lead` に書きます。1 つの段階では新しく分かることを 1 つだけ足します。1 区間、1 つの判断、変わる 1 つの値です。
- 地図は、信号がどこを通り、誰が判断するかを見せます。シーケンス図は、誰が誰とどの順に話すかを見せます。関係は、パッケージのように何が何に依存するかを見せます。関係は信号ではないので、1 つのシーンでメッセージと混ぜません。
- ノードが何を判断するかを見せる段階には、そのノードの `do` のイベントを置き、入力と結果をフィールドに書きます。
- 地図にイベントが増えてきたら、段階を `only` で始め、もう要らないものを消します。
- 1 つ前のチェックポイントからのできごとを、止まったページで説明できる段階を、チェックポイントにします。文とフィールドが 1 枚に収まらないチェックポイントは、確かめる段階で誤りになります。その前の段階もチェックポイントにします。
- 元のスライドにあったことのうち、段階で言わないものは、詳しい説明か Book の本文に残します。別のファイルへ移したものは、移行の対応表に行き先を書きます。読む人に要るものを省かず、発表者ノートにも移しません。

### デッキを足す

1. 2 つの言語のデッキを同じコミットで書きます。`decks/ja/NN-name.md` と `decks/en/NN-name.md` に、同じスライドを同じレイアウトで同じ順に並べ、モデルとシーンも同じにします。今あるデッキのフロントマターを写して、`title` と `footer` を変えます。
2. 手順書へは、デッキからの相対パスでリンクします。たとえば `../../../docs/guide/ja/call.md#3-s-cscf-が番号を-sip-uri-に変える` です。手順書のシーケンス図を丸ごと写さないでください。全体がどこにあるかを書いたうえでなら、縮めた図は構いません。
3. 条項番号は、手順書がその手順に挙げているものだけを、手順書と同じ版で書きます。電話番号は手順書と同じ架空の番号（+1 202 555 01xx）を使います。
4. コードの抜き出しは、リポジトリのコードから数行をそのまま写し、ブロックのすぐ上にファイルへのリンクを置きます。ファイルにその行がその順で無くなると、確認が失敗します。そのため、コードを変えると、一緒に直すスライドが分かります。
5. `go run ./cmd/slides build`、`node check-html.js`、`python3 scripts/check_links.py` を実行します。HTML を開き、どのシーンも進む向きと戻る向きの両方で、広いウインドウと狭いウインドウで段階を追います。pptx を開き、チェックポイントのページを、段階を見ていない学習者のつもりで読みます。

### 見た目を変える、レイアウトを足す

見た目は [internal/layout/theme.go](internal/layout/theme.go) にあります。色、フォント、文字の大きさ、content のスライドの枠です。2 つの出力も pptx のテーマも、ここから値を取ります。

レイアウトを足すときは、次の 4 か所を変えます。

1. [internal/deck/deck.go](internal/deck/deck.go) の `Layouts` に名前を足す。
2. [internal/layout/layout.go](internal/layout/layout.go) の `Slide` に箱の置き方を書き、`layout_test.go` に試験を足す。
3. [internal/pptx/slide.go](internal/pptx/slide.go) の `layoutOf` で、使う pptx のスライドのレイアウトを決める（表紙、部の始まり、そのほかのスライドに 1 つずつあります）。
4. 上のレイアウトの表に、2 つの言語で行を足す。

HTML は変えなくて済みます。レイアウトが置いた箱を、そのまま描くからです。

シーンの図は、[internal/layout/diagram.go](internal/layout/diagram.go) が置き、[internal/layout/scene.go](internal/layout/scene.go) が pptx のページに描き、[internal/html/svg.go](internal/html/svg.go) が舞台に描きます。舞台の見た目は [internal/html/style.go](internal/html/style.go) に、段階の進め方は [internal/html/script.go](internal/html/script.go) にあります。
